# AndroidCtl 第七轮评审：候选 `f401deb`

评审对象：产品 `f401deb`（在第六轮候选 `fb75afc` 之上追加 5 个提交，版本仍是 0.4.0）、独立 docs 仓库 `dfe5e45`。两个仓库都按实施方给的历史包还原过，树哈希与包内声明一致。

按第六轮第 6 条，这一轮评审的是"这一批改完、实测做完、还没整理提交"的头部，要回答的核心问题是：**这个候选能不能合入主分支；合入前还必须改什么；整体方向有没有走偏。**

**做法**：主评审先核包、还原源码、在 Linux 上跑主机全量测试、读实施方的交付稿和成本页；再由 16 名核查员各做一个专题（裁决逐条落实、四条行为链、原因码、成本重算、两组真实任务轨迹、指引、规模与维护、实施方证据审计、整体方向、Kotlin 和 Python 差量的逐行评审），每份都回到源码或原件；主评审复核了其中会影响结论的条目。工作记录是 `sub-reports/88` 到 `103`，清单见附录二。

**限制**：没有 Android 设备、模拟器和 Android 构建环境。Kotlin 一侧的结论来自读源码和实施方的设备原件；主机一侧的结论有很多是在本机实际运行得到的。每条结论都标了依据的性质。

**说法**

- **基线**是主分支 `7d5be70`；**上一轮候选**是 `fb75afc`；**候选**是 `f401deb`；**调用者**是使用这个命令行工具的 LLM agent。
- **常驻进程**是设备上以 shell 身份运行、真正执行界面操作的那个进程；**后台屏**是产品创建的虚拟显示屏。
- **观察**是一次命令返回的界面内容；**正文**是观察里逐行列出节点的部分；**首行**是命令输出的第一行；**回执**是一条动作命令的输出；**引用**是观察里打印的节点编号（如 `e15`）。
- **回合**是执行任务的模型发出一次请求；**总输入**是一次任务各回合读入的 token 之和（含缓存）；**固定前缀**是每个回合都要重复发送的系统提示、工具定义和题面，本轮约 1.7 万 token。
- **四道固定任务**：网页题（Chrome 里读 GitHub）、长列表题（Feeder 阅读器）、路线题（Google Maps 步行路线）、后台屏题（后台屏上的 Contacts）。
- **原因码**是回执里机器可读的拒绝或失败原因；**未发出**是回执里的 `not sent`；**结果未知**是 `UNKNOWN`。
- "第 N 条"指第六轮决定文件（`androidctl-r6-decisions.md`）里用户的第 N 条裁决；A1 到 A4、B1 到 B6 指第六轮评审报告里的编号。
- 本报告的新发现编号：**挡-1** 是建议挡合入的；**下-1** 到 **下-22** 是建议进下一轮的。

## 1. 第一页

### 1.1 结论

**整体设计成立，候选可以合入主分支。合入前必须改的只有一处，而且只改测试、不改产品。25 条裁决都落实了，没有发现会造成误操作、数据或资源损失、或让调用者重复执行已完成动作的缺陷。这一轮之后，建议不再做同样形式的下一轮（§6 第 3 题）。**

1. **裁决落实**：25 条裁决、A1／A2／A4、B2／B3／B6、附录一逐行、成本页三句话、内部 docs 的两份文档，在候选上都有对应的实现；十处风险提示都照顾到了；先后依赖都遵守了；正式实测用的构建确实出自最终头部。有三项是"做了，但没有达到裁决的目的"（B2、`open` 带界面树、第 10 条的改名诊断），见 §1.4 的下-1、下-4、下-5；它们不造成误操作，只多花调用。
2. **正确性**：核查员逐行读了本轮全部 Kotlin 和 Python 主源码差量，没有找到挡合入的错误。"已执行的动作被报成失败或未发出""没执行的被报成完成"这两类路径，在设备端、主机端、`open`、借用粘贴里都没有找到。
3. **真实任务**：四道题各 5 次，20 次全部成功（上一轮也是 20 次全部成功）。322 条命令里非零退出 8 条，都在一到两条命令内恢复，没有出现结果未知。
4. **成本**：网页题比上一轮候选再降约三成；长列表题、后台屏题持平；**路线题比上一轮候选贵了约 22%，实施方的成本页没有写这一点**。查下来没有找到产品变差的证据，原因见 §4。
5. **这一轮的收益集中在很少的几条上**。看得见效果的是默认输出变瘦（A1 和第 15 条）和按引用读屏外节点（B3）。其余大多数改动在 322 条真实命令里一次也没有被用到。同时这一轮净增了约 430 行源码、约 1,850 行测试，出过一个回归（已修），留下一个 Linux 上的测试失败。
6. **评审方自己的错误**：第 10 条的改名诊断在它要解决的场景里按构造不可能触发，根源是我第六轮给的一条风险提示；B2 的判定规则我写错了网页场景；我建议的首页示例改动给路线题带来了副作用。完整清单在 §5。

## 2. 整体判断

### 2.1 设计是否成立

成立。产品的骨架没有变：带引用的紧凑界面树；动作前的现场身份检查；如实区分"未发出"和"结果未知"、结果未知不重发；不依赖 ADB 的通道；后台屏；网页内容可读。这套骨架和 Playwright 面向 agent 的那套循环是同一个形状（快照带引用、动作后带观察、命名会话），在"远程操作用户自己的手机"这件事上比能查到的同类工具（mobile-mcp、agent-device、DroidRun 等，只读了公开文档）做得深，而且深的地方有理由：网页上点错可以重来，手机上发消息、付款、删除不能重来。

没有哪个大方向需要替代方案。核查员专门从"今天从头设计会怎样"的角度看过（记录 101 第 5 节），结论是会少做几样东西，但不会换骨架。

### 2.2 哪些能力应当保留

下面这些在真实任务里频繁出现，或者一旦出错就会造成误操作，属于"保证不出错所必须的精确"：

- 四个主结果词和"结果未知不重发"；动作前的身份检查和旧引用拒绝。
- 采样不完整的标记（本轮 11 次运行、38 处）和"不完整不能证明不存在"；动作后"可能还在变化"的提示（79 处）；节点被遮挡的事实（路线题每次运行都有）。
- 这一轮统一后的可见性定义。它只有一处实现，6 个读点共用；后台屏长网页上"平台报可见但其实在屏外"的节点从上一轮的四千多个降到 0（核查员从原始树独立重算）。本轮 20 次运行里没有一次拒绝是这条新规则带来的。
- `find` 搜屏外内容、`scroll-until`、按引用读屏外节点、网页可读、后台屏的建立和关闭前的任务归属确认。
- 常驻进程意外退出后的自动重连、自动化登记被占时不再把自己锁死。这两条在任务里没有触发，但源码核查和设备检查都支持，是真实的远程可用性问题。

### 2.3 哪些责任可以减少

下面这些只改变"失败被描述得多准"，不改变调用者下一步会不会做错。它们每加一条，都要在设备端、契约样本、主机端、首行、测试、指引六处同步。本轮 322 条真实命令里，它们出现的次数都是 0：

- 主结果与退出码不一致的各种组合（完成加退出码 1 或 3）；按件保存失败。
- 150 个原因码里的绝大多数。模型在 20 次运行里一共只见到 6 个码，每次的下一步都跟着回执里那句话走，没有一次依赖码本身；第六轮并掉的 6 个码在两轮 57 份运行里从未出现。
- 借用粘贴及其恢复规则、截断时的唯一性例外、引用修复、后台屏外来任务的拦截、改名诊断。

这不是说它们应当现在删。它们已经写完测完，对调用者是"用到才付费"，拆掉要改契约和两端测试，本身就是一轮新工作。合理的规则是：**不再给这几块加规则；哪一块以后出了缺陷或挡住别的改动，优先删除或降级成只报告，不再修补**。上一轮我把这叫"冻结"，你没有采纳（第 7 条）。本轮这几块又各被改了一遍，在任务上都看不出效果，所以这里再提一次，但只作为合入之后工作方式的一部分（§6 第 3 题），不单独要你表态。

维护成本真正高的不是这些能力块，而是两样横切的东西：首行呈现和测试对输出文字的耦合（下-20）。这一轮唯一的回归就出在那里。

### 3.1 挡合入

**挡-1：一个主机测试在 Linux 上必然失败**

- **依据**：主机端本地复现。我在 Linux 上对 `f401deb` 跑主机全量测试，结果是 1,958 个通过、21 个跳过、1 个失败；单独重跑这个测试 3 次都失败。另一名核查员独立发现了同一个问题。

- **为什么实施方没发现**：它的完整质量检查只在 Windows 上跑。`AGENTS.md` 里 `task ci` 对 Linux 和 macOS 只做类型检查，不跑测试。

- **修正**：只改这个测试，让"管道被关闭"在各平台上都必然发生（例如缩小管道缓冲区，或让读端在写端开始写正文之前关闭）。不改产品代码，不改默认输出。
- **复核**：改完后我在 Linux 上重跑主机全量测试即可，不需要设备，也不需要重跑任何一道固定任务。

### 3.2 进下一轮：已经在真实任务里多花调用的

**下-1：页面跳转后的回执标"已变化"，树却是旧页面**

- **现象**（实测，记录 96 第 2.2 节、90 第 4 节）：网页题里点开一个 issue 链接，5 次里 5 次回执首行是 `change=changed at content,eNNN:focused,actions`，而回执里的页面标题还是列表页。模型每次都接着发一次 `snapshot`。上一轮是 5 次里 4 次。
- **原因**（源码，`UiPostAction.kt:244-284`）：B2 新加的规则是"导航类动作之后，如果只有边界变化，就不标已变化"。网页上点链接之后，被点节点的焦点和可用动作也变了，不属于"只有边界变化"，规则碰不到。这条规则是我第六轮写的，我把网页场景判断错了。
- **路线题上的改善靠的是写死的文案**：同一处新增了一张"加载中"文字表，内容是 `loading`、`正在加载`、`正在查找最佳路线`、`finding the best route`、`finding best route`（`UiPostAction.kt:284`，我核过）。后三个是 Google Maps 专用的，换一种语言或换一个版本就不命中。这是对固定任务过拟合的直接痕迹。另外它和已有的进度条判定（`UiSemantics.loading`）是两套"加载中"的定义。
- **B2 的另一半做对了**：滚动查找成功时"页面可能还在变化"的提示，上一轮 13 次里 12 次，本轮 15 次里 0 次。
- **实施方的记录要更正**：计划表把 B2 记成"已闭"，与网页题的实测不符。
- **修正方向**：见 §6 第 5 题。代价不大，但涉及动作后采样等多久，需要你定方向。

**下-2：`back` 等系统按键的回执不可靠**

- **现象**（实测，记录 96 第 2.3 节）：`back`、`key`、`home`、`recents`、`open` 取动作后观察时不传入动作前的样本（`SystemActions.kt:56`），连续两次采样相同就算稳定。结果是 16 条 `back` 回执全部标"可能还在变化"；长列表题 5 次里有 3 次，第二个 `back` 的回执里仍是返回之前的阅读页，模型只能补 `snapshot`。
- **修正方向**：用会话里最近一份完整样本作比较基准，与基准相同不算稳定。代价中等：要防止"原地不动的 `back`"白白等满时限。

**下-3：输出上限没有省下成本**

- **现象**（实测，记录 91 第 1 节、95 第 2.4 节、96 第 2.4 节，我核过原件）：20 次运行里上限触发 2 次，都是网页题的整页 `snapshot --all`。两次模型都立刻把保存的全文文件读了回来（168 KB 和 259 KB，被执行框架截到约 2 万 token）。读文件分别占那两次运行总输入的约 21% 和 26%，这两次正是网页题 5 次里最贵的两次。上一轮同样的命令直接打印时，模型收到的内容量是同一量级，本轮还多了一回合。
- **产品自己把调用者引到了这条路上**，有四处：
  1. `find` 命中 0 条时，输出里有一行 `omission reason="find" nodes=654 read="snapshot --cached --all"`（`ui_view.py:896-898`）。两次触发里有一次正是模型照抄它执行的。
  2. 超限摘要固定写 `Narrow the current sample: androidctl snapshot --cached --depth 2`（`ui_client.py:888`），与刚才用的命令无关；对 Chrome 这样的页面，深度 2 只能看到外层包装节点。两次都没人用。
  3. 首页 `SKILL.md:87` 写"Read/search that file after host-tool truncation"，模型照做了"读"。
  4. `--all` 下，无名的平台标准动作（`action-40` 之类）仍然全部打印。两份保存的 `--all` 文件里这类字段占 32% 到 50%。去掉之后那份维基长页的正文能从 843 KB 降到 406 KB。默认输出里这类字段确实清零了（322 条命令里 0 处），所以 A1 在默认模式下修好了；`--all` 下没有。
- **判断**：上限作为防失控的保险是对的，应当保留；它"省成本"的目的没有达到。前三处是改字符串，第四处涉及 `--all` 到底表示什么，见 §6 第 6 题。

**下-4：`open` 和跨 App 点击的回执经常不带界面树**

- **现象**（实测，记录 92 第二节、96 第 2.7 节、97 第 4 节）：本轮能找到的 11 次真实 `open`（网页题准备阶段在主屏打开 Chrome 5 次、后台屏题 5 次、另一次设备检查），9 次结果是完成、落地已确认，但附带的树不可用。主屏上的 5 次，回执还建议 `snapshot --window 17; snapshot --window 10`，那两个窗口是导航栏和状态栏。后台屏题 5 次里 3 次没有树，模型下一条命令都是 `snapshot`。长列表题里点击"在 Web view 中打开"跳到另一个 App，5 次里 4 次同样没有树。
- **原因**（源码推断）：确认落地看的是系统的任务表，它比无障碍窗口列表早；动作后观察只在 1.5 秒窗口里等，对"一个应用窗口都还没有"的情形不会多等。
- **与裁决的关系**：第 15 条要求"落地之后带上界面树"。实施方把观察挪到了落地确认之后，方向对，但真实结果几乎没有改善，上一轮后台屏题是 5 次里 4 次没有树。计划表记成"已闭"，应更正。
- **修正方向**：只对这类情形，在还没有任何应用窗口时，在请求时限内继续采样到第一个应用窗口出现；可选窗口的列表里去掉系统窗口。十来行。

**下-5：第 10 条的改名诊断按构造不会触发**

- **现象**（实测加源码，记录 89 第四节、97 第 3.1 节，我核过源码）：路线题第 1 次，步行标签页从 `"Walking mode: "` 变成 `"Walking mode: 18 minutes"`，旧引用被拒。这正是第 10 条要解决的场景，前两轮出现过 7 次。诊断没有触发，模型补了一次 `snapshot`。
- **原因**：裁决要求窗口、来源节点编号、角色、行标签、行列位置都相同、只有名字不同。实现照做了（`UiRefRepair.kt:49-69`）。但行标签的取法是（`UiSemantics.kt:181-237`）：目标自己就是列表项时，行标签取自它自己子树里的文字或它自己的名字。所以这类目标的名字一变，行标签必然跟着变，"行标签相同"永远不成立。列表行和标签页恰恰是最常见的目标。测试没有发现，是因为测试里的行标签是手写的固定值 `"Row"`。
- **这是谁的错**：我的。第六轮决定文件第四节第 7 处写了"行标签是区分'同位置已经换了内容'的字段，判定时不能省"，你据此选了严格判定，实施方照做了。实施方为这次没触发写了一份 8 KB 的诊断文档，结论是"原因从保存的正文确定不了"；核查员从前后两份观察就推出了原因，不需要它说没有归档的字段。
- **行标签在这里其实没有安全价值**：这一行只陈述"同一位置现在是 eNNN 'Y'"，从不自动派发。
- **另外更正一个数**：实施方写路线题有 4 次旧引用被拒，实际是 2 次，另外 2 次是滚动方向不可用。2 次里另一次（第 4 次）原目标已经整片消失，拒绝是对的，也不该附这行诊断。
- **修正方向**：见 §6 第 4 题。

**下-6：平台拒绝动作时首行不写原因**

- **现象**（实测加主机端本地复现，记录 90 第 3.2 节、97 第 3.4 节，我看过原件）：路线题第 5 次有一条 `scroll` 退出码 1，首行是 `scroll: failed; change=unsettled …; dispatchStarted=true; Estimated next sample exceeds the observation deadline`。命令只跑了 1.8 秒。按源码，这是无障碍动作被应用拒绝（平台返回 false），设备端生成这个结果时不带原因（`UiActions.kt:900`），主机端又把一句采样说明印在了首行。实施方的成本页把它读成了"观察超时"。
- 同一次运行里另一条 `scroll-until` 失败：外层容器滚了 2 步后到底，第 3 步没发出。回执准确写了"已滚 2 步"，但措辞是"目标未就绪……可以用 `scroll … backward`"，对一次查找来说，"往回滚"是错的建议；首行里同一段原因文字出现了三遍。
- **影响**：两次模型都只多花 1 条命令。不会造成误操作：平台返回 false 通常意味着动作没有执行。
- **修正方向**：设备端在这种失败里写一句原因；主机端只在观察侧确实有问题时才印那句采样说明；滚动查找在"这个方向不再有路线"时单独写"已到末端，没有匹配"。合计约 20 行。

**下-7：`reveal` 的可用性看不出来**

- **现象**（实测，记录 89 第二节、96 第 2.6 节、103 的 F1）：首页写"Use `reveal REF` when advertised"。默认输出把 `show-on-screen` 这个动作归在默认省略里，调用者看不出哪个节点公布了它。长列表题第 4 次 `reveal` 因目标没有公布该动作被拒，之后改走滚动、截图、看图、再点击。网页题第 1 次点击屏外目标被拒为"目标不可见"，回执给了 `reveal` 的建议，照做后成功，这一次是按裁决应有的代价（上一轮同一页面也出现过）。
- 另外，`reveal` 完成但目标仍在屏外时，默认文本没有任何直接信号（`f401deb` 有意把对应的测试改成了相反的断言）。
- **修正方向**：只在屏外节点上打印一个 `+reveal` 标记，或者把首页那句改成"带 `offscreen` 的目标先 `reveal`；不支持时会被安全拒绝，改为滚动它的容器"。`reveal` 不可用时，回执里点名最近的可滚动容器。都是几行。

**下-8：常驻进程附着窗口期里的报错让调用者去找用户**

- **现象**（实测加源码，记录 93 的 F1、100 的 F2）：激活之后的第一条 `status`，在实施方 21 次正常的设备准备里有 6 次报 `workerUnavailable`，文字是"Worker is unavailable; check the device App"。这时产品知道进程正在绑定。码表对这个码写的下一步是请用户点刷新。实施方把它记成"准备阶段的事件"，没有改产品。自动重连期间到来的命令得到同样的回执，这削弱了第 19 条"免人工"的效果。
- **修正方向**：附着进行中且没有超时的时候，回执改成"正在附着，几秒后重试"；码表这一行补一句。不新增原因码。约 5 到 10 行。

**下-9：专题指引在两道题里占了不小的成本**

- **现象**（实测加估算，记录 98 第 3 节、95 第 4 节）：后台屏题 5 次都按首页的要求读了显示专题，4 次连带读了参考专题，两篇合计约 13.8 KB，估计占这道题总输入的 16%，是这道题里产品能控制的最大单项。长列表题 5 次里 4 次读了动作专题，读完做的只是首页已有的"再滚一次容器"。路线题和网页题 10 次都只读首页就完成了。
- **修正方向**：见 §6 第 7 题。

### 3.3 进下一轮：只有源码依据的缺陷和风险

**下-10：方向词映射可能误滚**（源码，`UiScroll.kt:40-71`，我核过）

- 附录一要求"只公布前后方向的竖向容器接受 `down`、`up`"。实现判断"竖向"的条件之一是"高大于宽"。竖屏上整屏高的横向翻页列表（不是标准的 ViewPager 类、只公布前进和后退）会被当成竖向，`scroll 引用 down` 会横向翻一页，回执报完成。回执里的 `Selected` 一行会写出实际执行的是 `scroll-forward`，所以调用者能看出来；后果是翻错了方向，不是破坏性的。
- 这条映射在路线题里起了正面作用：上一轮 2 次因方向词被拒，本轮没有再出现。
- **修正方向**：`collectionInfo` 显示"一行多列"时不走形状判据。一行。
- 这是最接近"误操作"门槛的一条。我把它放在进下一轮，理由是：没有真实样本；遵守指引（"按节点公布的滚动方向选"）的调用者不会走到这条映射；后果是一次可见的翻页。你如果认为"报完成但做的不是所请求的方向"应当挡合入，可以把它挪过去，那样要重新构建并跑 Android 测试。

**下-11：`open` 的第二次落地确认**（源码推断，记录 92 的 F3）

**下-12：很大的页面上的等待和 `find`**（源码推断加一次设备实测，记录 90 的 F1 到 F3、100 的 F4）

- 第 17 条和我给的风险提示都默认"截断"是节点数或字节上限。实测的长网页每次采样截在 3 秒的采集时间上限上，提前失败和超时说明都不认这种截断。结果是等待消失、等待空闲、滚动查找的第一步、按选择器执行的动作，在这类页面上会等满时限，回执不说原因。
- `find` 命中 0 条时的自动新采（第 11 条）在 20 次运行和设备检查里一次都没有触发过。按长网页的实测耗时（读缓存约 1.2 秒，新采 4 到 4.6 秒）和 5 秒的默认时限，它在大页面上估计常以时限失败告终。回执报的是失败并写明"缓存 0 条，新采失败"，不会被读成"页面上没有"。设备检查里那次 `find` 超时不是这条路径，而是上一条 `back` 未稳定引起的重采，它命中了 1 条、引用可用，却因为窗口目录没在时限内交付而整条报失败。

**下-15：重连和自动化登记的三处边角**（源码，记录 93 的 F2、F4、F5，88 第三节，102）

## 4. 成本数字怎么读

### 4.1 对基线的比值

- **网页题 0.33**：不能读成"效率是基线的三倍"。基线读不到网页内容，只能靠截图和坐标。
- **长列表题 0.96**：沿用的基线跑在旧版执行框架上，首回合输入多约 1,200 token；起始列表的状态也略有不同。两轮候选之间这道题没有变化。
- **路线题 0.92**：基线 5 次里成功 4 次，是两天前和上一轮候选交替跑的。不能读成"路线题在持续改善"。

### 4.2 对上一轮候选

两轮的模型、推理档位、执行框架版本号、设备实例都相同，所以这个对比比对旧基线的对比更干净。它也有局限：两批不是同日交替跑的，5 对 5 的检验力很低。

- **网页题便宜了约三成**（中位数比 0.70，但在 5 对 5 的样本里不显著）。每条命令的输出平均少了 39%，其中大约五分之四来自"不再打印无名动作"。输出上限的净贡献约为零（下-3）。
- **长列表题、后台屏题持平**。后台屏题每条命令的输出减了约 45%，总输入只降了 6%，因为固定前缀占了七成。
- **路线题贵了约 22%**，回合从 22 到 26，五次的回合数（24 到 30）全部高于上一轮的五次（15 到 23）。

### 4.3 路线题为什么变贵

两名核查员分别按阶段拆了两轮的 10 次运行，结论一致：

- 建立步行路线这一段，本轮反而少了约 2 个回合；读前三段路线持平。
- 多出来的回合全在最后一段"核对两端地址并回到博物馆页面"：上一轮 4 到 10 个回合，本轮 13 到 20 个。
- 每个回合新增的输入本轮少了约 21%。如果回合数和上一轮一样，本轮的总输入会略低于上一轮。所以成本是回合数决定的，不是输出变大。
- 逐一检验过的解释：可见性改动、引用过期判定变严、瘦身删掉了有用信息，都没有证据。滚动方向映射略有帮助。
- 查到的系统性原因有两条：
  1. **首页示例改成了 `fill … --submit`**。上一轮 5 次都是先 `fill` 再点建议列表里的一项，那一项旁边就写着"Trafalgar Square, London, UK"，起点地址是顺手得到的。本轮 5 次都直接提交（我核过两轮的命令序列），Maps 不再显示建议列表，起点地址要另找。这个示例改动是我在第六轮附录一里建议的，依据只来自网页题。它让建立路线少了一步，净效果略亏。
  2. **模型找博物馆完整地址时走得更远**：多滚动、多截图（7 次对 2 次）、翻到别的标签页。题目没有写读到什么程度算完成。
- 两批的日期和时段不同，博物馆页面一批显示"营业中"，一批显示"已闭馆"，页面下半部分的内容顺序也可能不同。这一项分离不出来。

**结论**：没有找到产品在任何一步上变差的证据，但不能排除。它不构成合入的障碍。成本页应当把这件事写出来。

- `session close` 成功时默认文本打印完整的任务处置 JSON，状态只是"清空"。
- 到期任务记录在默认文本里是双重转义的 JSON，每个任务约 800 字节。
- "New worker: previous refs are invalid"这句从基线就有的提示，在后台屏题 5 次里次次出现，纯属噪声。
- 首行里的保存路径很长（文件名里有时间戳、包名和标题）。
- Feeder 每一行重复 8 个相同的动作标签，占长列表题输出约 19%。
- `snapshot`、`find` 保存失败时首行把同一段错误原文打了两遍。

**条件、滚动、选择**（90、102）

- `wait --text` 未命中时报的 `complete` 没扣除读不到的文字字段，`scroll-until --contains` 扣了。
- 多条件等待未命中时，各条件的候选引用混在一起。
- `covered` 一个码有三种意思。
- 坐标取点用整个节点边界的中心，不用它与窗口交集的中心。
- 目标不可见时 `notReady` 等满整个时限（约 5 秒）才返回。
- 树里没有"部分可见"这项事实，长列表题 5 次都靠截图确认整张卡片可见。

**会话和生命周期**（93）

- 不写 `--display` 而新开在主屏时，首行看不出这是默认选的。
- 到期后 `status` 只报 `callerState=none`。
- 替换、接管的首行不显示被替换的会话名。
- 重连本身失败、之后由别的途径恢复时，提示丢失。

**指引可以删减的**（98）

- 全部指引估计可以从 72 KB 删到约 49 KB。但 20 次运行里只有动作、显示、参考三个专题被读过（共 13 次），删专题的收益有限，应排在首页改动之后。
- `--raw` 的组合、`wait` 的截断、到期记录、重连阈值几段可以各删一半。
- 首页里解释 `find` 何时重采的三行是内部缓存规则，调用者不需要知道。

**帮助和报错**（98）

- 直接敲 `session`、`clipboard` 会把整页帮助压成一行（约 930 字节）打出来。
- `--print` 的帮助没提超过 64 KiB 只打摘要。
- `--raw` 与形状选项冲突时给的写法一律是 `snapshot --cached --raw`，对 `find` 不贴切，也把"新采"的意图改成了读缓存。
- 写错形状的引用（`ref15`、`E15`）要到设备端才被拒。

**测试**（103、94）

- `test_ui_reading_delivery.py:167` 的 `"fresh" in stdout` 在失败场景里自动成立，没有真正检验标记。
- 新采结果为未知、新采后树交付失败、异常树、显式 `--out` 配合超限正文，这几种情形没有测试。
- 原因码登记测试会静默漏掉 `Fault(code="x")`、`protocol.Fault("x")`、`Fault` 的子类和 Kotlin 的 `put("code", "x")` 这几种写法。

**合入后减法的排序**（99 第 5 节）

1. 测试里的输出解析收拢到一个辅助函数（净减 150 到 300 行；以后改输出时测试改动从约 400 行降到几十行）。

3. 内部 docs：`reference/ui.md` 删到"为什么这样设计"的十几条，案例清单裁成发布清单（减 80 到 90 KB）。
4. 两套"加载中"判定合并，删掉 Maps 专用字符串。
5. 退出码覆盖统一走一个助手（现在散在 18 处）。

明确不值得做的：单独裁剪契约样本；继续收拢参数校验；回退本轮的到期记录、重连、默认主屏。
