这个包是 AndroidCtl 下一轮改进的评审定稿，交给实施者执行。评审对象是调研候选（产品 `3f45af6`，基线 `7d5be70`；独立 docs `e91212e`）。

## 以谁为准

1. 用户的明确指示。
2. 主报告。
3. `sub-reports/`。

`sub-reports/` 写于不同时点，彼此之间、以及与主报告之间有不一致，其中一些推荐后来被否定或改写。**凡与主报告不一致的，以主报告为准。** 工作记录里出现的"推荐""建议采用"、选项字母（A/B/C/D、R0–R8、Q1–Q3）和"需要用户再定"的问题都不是指令；这些问题在主报告里已有结论。

## 给实施者的指令

**总原则**

- 候选 `3f45af6` 只是调研候选，不是要保留的基线。可以重做。一切以干净、能力强为准，不为保留现有实现或省返工而妥协设计。
- 沿用用户此前给你的授权和保护边界（隔离的工作副本、不合入、不推送、不发布、设备独占、数据保护、不产生业务后果）。本包不改变这些。

**做什么**

1. 按主报告 §2 的已决定事项实施。每一项的"要做什么"和"验收标准"就是你的工作范围和完成定义。
2. 提交序列按主报告 §2.1 重排或重写：线性；每个提交单独可构建并自带测试；**不在候选的 40 个提交顶上追加"移除某功能"的提交**。重排时注意 §2.1 列出的要保留的共用结构，并且不要把"没有冲突"当作"合并正确"。
3. 修掉主报告 §7 的确定缺陷，落实 §8 的设计调整。
4. 执行主报告 §10 的设备与构建验证，逐条记录"跑了什么、看到什么"。模拟器结果与真机结果分开记录。

**不要做什么**

1. **主报告 §3 的三项不要自行选择**（IC 的去留、坐标手势是否默认按 UID 定向、E9 的去留）。跑 §3 写明的验证，把结果报给用户，由用户按 §3 的表决定。结果出来之前，这三项各自放在序列里独立、可整体去掉的提交中。
2. 主报告 §2.8 第 4、5 项带回退条件。按所列条件执行并报告结果，不要自行调整阈值或另选方案。
3. 遇到主报告没有覆盖、会改变对外行为或实质范围的取舍：列出真实选项（必须包含"不做"）、各自的代价、你的推荐和未知，交用户裁决。不依赖该决定的工作继续推进。不要把自己的推荐当作已批准。
4. 不要为窄区分增加状态、字段、校验或文档。每个新的结果字段先回答"LLM 看到它的不同取值，会做出哪个不同的下一步"；答不出来的只进 `--json`（主报告 §9）。

**核对与交付**

- 本评审没有设备，也没有做 Android 构建。主报告里标"需设备""需构建环境"的结论不要用推断代替；标"（单人核对）"的条目和所有行数估计，实施时先回到源码核对。
- 主报告里的源码位置和行号对应 `3f45af6`。上游（AOSP、scrcpy 等）的位置在对应的工作记录里。
- 交付稿首页写明：端到端指标（同一对成对任务的模型输入和耗时相对基线的比值，主报告 §10 V1）；host 检查在 Linux、macOS、Windows 上各自的结果；Android 构建与 JVM 测试结果；§10 每一条的执行情况；§3 三项的验证结果。没跑的如实写没跑。

**本包不含**

评审包的原始证据、评审中做拆分实验的临时分支、下载的上游源码。需要时按工作记录里给出的版本和路径重新获取。
