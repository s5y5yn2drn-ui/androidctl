## 1. 结论摘要

1. **一致性**：十条主线拼起来基本是一个产品。目标屏、任务事实、节点事实各只有一个权威来源，没有发现两条主线对同一情形给出相互矛盾的硬规则。但有 6 处接缝含糊，调用者会看到同一个 DONE 或同一个退出码却该走不同的下一步，见 §2.1。其中最要紧的两处：退出码 3 同时表示"动作结果不确定"和"动作完成但清理失败"；同一个 open 动词有三种 DONE 含义。
2. **规模（离线重算加设计投影）**：照 r3 推荐全部落地，CLI 叶命令 71→69，长选项 68→65（如果通知身份参数不被选择串取代，则是 70），隐藏接口成员 57→72（Q7 选 A 时为 70），生命周期对象约 19→约 20，输入通道 10→10，规范句数无法离线计算，按新增契约推断不会下降。相对候选基本持平，命令略减、内部接口明显增加；相对基线仍是全面增加（命令 +22，选项 +27，隐藏成员 +38，状态对象约翻倍）。"能力都留"完全兑现；"合并入口"兑现很少，净减 2 个命令；"减少状态"没有兑现，删 3 个、加约 4 个。
3. **13 道题问得对不对**：真正需要用户裁决的只有 4 组：Q10（Result 与退出码）、Q12 和 Q13 合并成一题（身份与公开名字是否改用不受可见性影响的原始语义）、Q7（是否为通知落点放宽"只允许一处内部接口"）、Q6（监听器的权限窗口）。Q3 应改问成"合并入口还是删"。Q1、Q2、Q4、Q9、Q11 是实施者自己该定的细节，Q8 的题本身来自可以不加的机制，Q5 可以作为默认值请用户点头。另有 7 处改变用户此前偏好或对外行为的地方没有列成题，见 §2.3。

5. **16 个提交**：真实依赖是"会话 → 稀疏表示 → 身份 → 目标/名字 → 阅读/交付"一条主链，加上若干条独立支线。可以先做一个不依赖 13 题的先行批次，含文件早关、F25、F1、F9/F10/F11、F14/F15、F19、F20、F21、F23、通知注销不封锁、紧凑正文、find 全已采、打印不依赖保存。这一批价值最高，证据最硬。r3 的提交表漏了 F15 和定稿 §2.13.2（变化只给一个结论）的归属，也没有说明最终历史是"40+16 先加后删"还是重切，见 §2.5。
6. **文档**：主稿面向实现者和内部 reviewer 写成，用户不可读。要用户据此做 13 个决定不现实，应改成一页决定单，见 §2.6。

## 2. 逐题分析

### 2.1 组合后是不是一个一致的产品（连续流程走查）

我把十条主线沿一条完整流程逐站走了一遍：开会话 → 选显示目标 → 观察 → 找元素 → 点击或输入 → 等待 → 读结果 → 保存或对比 → 通知 → 关闭清理。每站检查三件事：同一事实是否只有一个权威来源；失败时调用者看到什么；下一步能做什么。

**权威来源方面，主体成立【推断，依据 r3 L11–20、底表 §1 L15–27】：**

| 事实 | 唯一来源 | 判断 |

| 现在操作哪块屏 | 设备 lease（删 host `display.json`、每请求种类、batch 冻结） | 成立。候选里这件事有 4 个来源（`app.py:774-863` 的 display select/create，`workspace.save_display`，每请求 expectedDisplayKind，batch 冻结）【源码 3f45af6】，r3 收成 1 个 |

**接缝处的矛盾或含糊（按严重程度排序）：**

**J1. 退出码 3 有两种含义，下一步相反【源码加推断】。** 候选 `skills/androidctl/reference.md:60-68` 里，UNKNOWN 的常规退出码是 3，"清理失败、不确定或信号失败"也覆盖成 3。r3 Q10 推荐 A（L226）又明确："普通资源清理失败给 exit3，包括动作本身 DONE"。Q11 推荐 A 则新增了"可确认阶段显式 retry"。于是调用者拿到 exit 3 时，可能是两种情形：

- 动作结果不确定。下一步应该观察，不要重发。
- 动作已经 DONE、清理失败。下一步应该执行 retry 或在本机 Stop，同样不能重发。

两条出路不同，主稿却没有规定调用者凭哪个字段区分；只说"调用者须同时看 Result、分项事实和 exit"（L218）。这不是新矛盾，但 r3 加了 retry 入口以后，区分变成了必需。建议（实施细节，不必问用户）：清理失败时回执首行固定写出"清理未完成"和具体的出路命令，退出码保持 3。

**J2. 同一个 open 动词有三种 DONE 含义【推断，依据 r3 L12、L19、L189】。**

- typed launch（主屏和 VD 一样）：DONE 表示目标包或 UID 的可见 leaf 存在；未确认就是 UNKNOWN 并停 batch。
- 通知 open，VD 上的 Activity：Q7 选 B 时，DONE 表示有唯一可解释候选，并且当次可见匹配。
- 通知 open，主屏：DONE 只表示 send 成功。L19 写"main…仍原准入"，L189 写"main 及非 Activity 仍原准入/回执"。

U27 用户的要求按转述是"主屏与 reply/dismiss/非 Activity 保持原**准入**"（decisions.md L38）。"准入"不等于"回执语义"，r3 把它扩成了"回执也不变"。结果是：主屏上 `open X` 的 DONE 证明可见，`notifications open` 的 DONE 只证明发出；batch 会在前者未确认时停下，在后者未确认时继续。这算含糊处，应当在 skill 里按命令写明 DONE 的含义；更好的做法是让主屏的通知 Activity open 也报告落点事实（只报告，不改主结果）。

另外，VD 上的通知 open 遇到创建者在别屏有任务时会预先拒绝（r3 L19），但 PendingIntent 没有 `--multiple-task` 这条出路。定稿 §2.7.4 写"按 §2.3 的规则…拒绝并提示"，提示什么，r3 和底表都没写。拒绝时调用者的下一步不明确，大概只能改在主屏操作。

**J3. 交付失败：单动作和 batch 的规则不同【推断，依据 r3 L224 和 L227】。** 单动作时，附属观察交付失败"不因任意 deliveryError…统一加 exit1"，退出码仍为 0；同一步放进 batch，"该步已请求的附件交付失败…都停止"，外层 exit 为 1。这是有意的不对称（batch 必须拿到请求的观察才能继续），本身合理。但用户此前的方向是"结果与退出码一一对应"（定稿 §2.14.1），这一不对称就是 Q10 A 放弃一一对应的具体表现。r3 只在 Q10 里列出，没有在流程层面说明。

**J4. 零派发、动作后观察与图像资格【源码加推断】。** r3 L16 写"零派发是否跳后观察只按确知派发事实决定，不能因此保留本已失效的图像资格"；定稿 §6 说明坐标手势在发出第一个事件之前就记为"派发已开始"并使当前图失效（`VisualInput.kt:276-290`，评审方 sub-report 24 已核）。两者叠加的效果是：首个按下被平台以 UID 不符明确拒绝（确知未发）时，跳过动作后观察，但图像资格已经作废，调用者带 `--expect` 重试前必须先重新截图，而此时屏幕并没有因为这次操作改变。r3 L47 的 Bili 206→207→208→209（206 零派发且附图因预算耗尽、207 首步 staleImage 停批、208 重截、209 才成功）说明这种多步恢复的成本真实存在。不过按 `exploration-20261119/mumu/README.md:105` 的原件描述，206 是选择器无匹配的 notReady，不是坐标 UID 不符，所以这组样本不能直接证明坐标路径的问题。

这里还有一处没写清：预测器在派发前就拒绝（无样本、命中自身）时，图像资格是否保留？我的建议（实施细节）是：失效动作放在"确知已发出首个事件"之后；确知零派发的情形保留原图资格。这条只需要源码上的推理，不需要设备。

**J5. 区域裁图与坐标帧【推断，依据 r3 L18、L211】。** Q9 A 用"当前完整图的 metadata"解释区域坐标，同时规定"新观察发现变化仍可使旧输入资格失效"。按 REF 裁图需要当前观察签名，可能触发一次新采样。于是"截图 → 按 REF 细看 → 按原图坐标点击"这条常见流程里，细看这一步可能让下一步点击的坐标资格失效。主稿没有写明按 REF 裁图是否会刷新或作废坐标帧。

**J6. 两种选区共存时偏移域不同【原件转述加源码】。** Q3 B 保留 IC 选区（用当前 editor 的原生文本偏移），同时新增 AX 选区（按 REF，偏移以 AX 文本为准）。实施方自己的证据是：Contacts 的 AX 文本多一个", 姓名"后缀（底表 §5 G1 引 E13），regex101 上 AX 是 51 字、原生是 49 字（r3 L55）。调用者从快照里读到的是 AX 文本；如果拿这里的偏移去调 `editor select`，就会选错位置。r3 只写了"不能直接互换"（L61），没有规定公开文档里两种偏移各以哪份文本为准。保留两个入口，这个学习陷阱就是必须付的代价，应写进 Q3 的代价栏。

**两处只算轻微含糊：**
- wake 在清理封锁门存在时是否放行，r3 没有写。
- "带 REF 的 editor 输入必须已是当前焦点，AX select 可以先 focus"（L15）在一条流程里给出两种聚焦规则。这是有意设计，文档写清即可。

**没有发现问题的接缝：** 两次窗口缺席判 gone → 后续 REF 各自重新准入 → batch 继续（r3 L16，底表 L20 引 [WRV] 的真实 Contacts 原件，我没有亲核原件）；同名调用者共同跟随加监听器跟随 lease 结束；身份规则变更与 View 文件 schema 的关系（schema 不匹配时输出全文和原因）。

## 4. 值得删除或简化的机制（r3 基础上的更干净方案）

以下各项能力都不减少。

1. **`select [REF] START END --via ax|editor` 一个入口**：同时删掉 `editor select` 和 `editor commit`，`editor` 命令组整体消失。叶命令再减 1，投影为 68。需要的证据：无，属于纯入口设计。
2. **把清理 retry 并入 `session close`**：同一 owner 在有待完成清理时再次执行 close，就重试可确认阶段，不新增命令，叶命令再减 1，投影为 67【重算，`project_r3.json` 中 alt.leaf】。需要的核对：清理失败之后 lease 是否仍可由原 owner 寻址；如果 lease 已经结束，需要 close 接受"仅清理"语义。这是源码层面的问题。
3. **Q12 与 Q13 合并成一题**，Q8 删题，Q1、Q2、Q4、Q9、Q11 转为默认值。用户题从 13 减到 4 组。
4. **确知零派发时保留图像资格**（J4）：把图像失效放到确知已发出首个事件之后。这样可以省掉"零派发 → staleImage → 重截"这种多余循环。需要的证据：源码推理，确认首个按下的 targetMismatch 是在平台注入前被拒的。
5. **通知身份参数统一换成选择串**：`--post-time --creator --creator-uid --title --title-null` 合并为一个值，选项减 5。r3 有这个方向但没有写明，应当写明。
6. **（可选，须用户同意）`notifications` 无子命令时展开通知栏**（候选 `ui_commands.py:491-495`）：一个命令组名同时又是动作，容易混淆，可以考虑改名。这一项影响小，我只是记一笔。

按这个方案，相对候选的命令为 71→67，选项为 68→65，隐藏成员仍为 70 或 72（取决于 Q7），状态对象约为 20。也就是说，"合并入口"可以做得更彻底；"减少状态"在保住全部能力的前提下，能做到的就是持平。这一点应当如实告诉用户。
