## 1. 总评

初稿的总判断大体站得住：候选的正确性和符合性确实做到了；默认输出偏重、长页面上的严格规则把成本转给调用者、整轮从未与主分支基线做过真实任务对照，这三点都有源码和原件支撑，我复核后同意。但"方向偏了"这个总判断写得比证据更满，几处事实有错，几条"回调严格规则"的建议没有评估最坏情形。最需要改的是这几处：

1. **A4 的"截断时选择器立即失败"不能原样用在 `wait` 上。** 导航刚开始时，`wait` 的第一份样本往往还是旧页面。如果旧页面是一张被截断的长页，`wait` 会立刻失败，而新页面一秒后其实会变成完整树。快速失败应只用于 `click/locate` 这类作用在当前页面的命令，或者只在"同一页面连续截断"时触发（§2.1）。
2. **A3 的"平台返回成功就报完成"会削弱 batch 和后台屏的保护。** batch 里 `open` 之后紧跟一个按名字的动作，目标 App 还没起来时，这个动作会作用在前一个 App 上；后台屏上冷启动时目标暂时哪里都看不见，"只有出现在别屏才报未知"根本判断不了。子报告 35 自己给过的"在剩余预算内轮询任务列表"能修掉实测的两次误报，又保住原来的保护，初稿没有提到这个选项（§2.2）。
3. **"96 份 review 只带来 3 项产品修正"是错数，而且没有说明这些 review 是用户明令要求的。** 仅 `02-results/review.md` 一份就有 2 项产品代码修正，合计至少 5 项。用户授权原话要求"每个完整改进继续由……专门子 agent 独立 review"（§2.5）。
4. **"本轮授权的主旨是删除、合并、简化"与用户原话、第三轮评审都不符。** 第三轮自己写的是"能力全部保留"，并预测落地后"状态最多持平"。另外"通知是本轮增长最多的子系统"与初稿自己的表格矛盾，输入 +553 行比通知 +416 行多（§2.6）。
5. **"仍然空缺的只有 macOS 原生运行"是错的。** 最终树没有重新构建 APK 和 R8，设备运行用的是各阶段的构建，实施方和子报告 43 都写了（§2.7）。
6. **精简输出的数字和"缺失为 0"都要加边界。** 第 0 阶段 GitHub new 一臂不含 `find` 也只降到 31%，不在 16%–24% 之内；`find` 输出是 23%–50%。初稿 §8 的验收线"不超过 30%"连它自己的原型都过不了。子报告 40 的检查脚本比报告写的弱：只在整份输出里查子串，状态标志只计数、不比对，省略行被排除在外，而精简版恰好把省略行的续读指引丢了；八臂里也没有一份不完整的树。我按节点逐个重查，引用、名字、状态和"能否点击"确实都保住了，所以结论可以保留，但要写清检查范围（§2.8）。
7. **A5、A7 和第一题的选项 E 都需要补条件。** A5 只修得了两次实测失败中的一次；A7 会让保存的屏幕内容（通知、聊天）静默落进别人可读的目录；E 说"唯一能排除搬屏"说过头了，经中转页的 `open` 也是同一种机制（§2.3、§2.4、§2.11）。
8. **按"使用次数"论证能力去留的地方要降级。** 八臂是第三轮评审指定的两类只读任务，任务本身就用不到通知、后台屏和剪贴板，所以"从未被自然用到"几乎是定义使然。实施方的委托明确写了"不按……少量任务中的使用次数衡量"。初稿的"核心层"里也有 `open`、shell、文件传输，它们在 84 次自然调用里同样是 0 次（§2.12）。

## 2. 逐条反驳

按重要性排序。每条标出类别：**事实错误**、**证据不足或说过头**、**判断有争议**。

### 2.1 A4 与 §7 第 3 项：截断时选择器立即失败，用在 `wait` 上会造成新的误拒（判断有争议，风险未评估）

- **初稿原话**（§4 A4）："树因节点上限或字节上限被截断时，选择器类命令（`click --name …`、`locate`、`wait` 选择器、`wait --gone`、`wait --idle`）反复重采到预算耗尽才失败……这类截断下次采样会原样重现：第一次采样后就失败，并附上候选引用。"§7 第 3 项把它列为"回调严格规则"之一。
- **反驳**：
  - "下次采样会原样重现"只在同一页面上成立。`wait` 的主要用途正是导航后等新页面出现，首页指引也这样教。导航刚发出时，`wait` 的第一份样本往往还是旧页面。
    - 初稿 §3.4 承认，长页面上动作后观察必然 `unsettled`。
    - 实施方的 GitHub new 臂就是"click 返回 unsettled 后接 wait"（子报告 40 §3.3 第 2 条）。
    - 如果旧页面恰好被截断，按初稿的规则，`wait` 看到第一份样本就失败。可新页面可能一秒后就是一棵完整的小树，按现行规则本可以等到。
  - 【源码】`UiCondition.kt:134-160`：不完整的样本只让条件"暂不满足"并继续采样。`UiSelector.kt:21-24, 43`：完整性取整棵树。按初稿的修法，"暂不满足"会变成"立即失败"，失败条件里也没有"页面没变"这一项。
  - 子报告 36 原本的修法比初稿窄：只在截断原因是 `nodeLimit` 或 `treeByteLimit` 时停止重试，`collectionLimit` 仍然重采；它也没有专门讨论 `wait`。初稿合并时把 `wait`、`wait --gone`、`wait --idle` 都放进了快速失败名单。
  - `wait --gone` 和 `wait --idle` 在一直截断的长页面上本来就不可能成功，对它们快速失败没有损失。问题只出在"等出现"的选择器 `wait` 上。
- **证据**：【源码】上述位置；【原件】子报告 40 §3.3 引用的 `ST/16-delivery/efficiency/github-new` 第 5 次调用（click unsettled 后接 wait）；"旧页面截断导致 wait 立即失败"是【推断】，八臂里的 GitHub 页面都是完整树（我用 `W/drops.py` 扫过，八臂所有采样的 scope 状态都是 `full`），没有直接实例。
- **建议怎么改**：A4 拆成两半。
  1. `click/long-click/... --name`、`locate`、`wait --gone`、`wait --idle`：照初稿，第一次截断采样后就失败并给候选。
  2. 选择器 `wait`：只有连续两份样本属于同一页面（窗口和根节点身份不变）而且都因节点或字节上限截断时，才快速失败；页面一变就继续等。

  验收标准加一条："从一张截断的长页导航到短页后，`wait --name` 能成功。"

### 2.2 A3 与 §6 第 2 条：启动确认改为"平台返回成功即完成"，丢掉了 batch 和后台屏的保护（判断有争议，漏了更好的选项）

- **初稿原话**：A3 的修正方向是"平台返回成功就报完成，落点作为附带事实；只有目标出现在别的屏上才报未知"；§6 第 2 条说更早定稿 §2.2 的规则"应当撤回"。
- **反驳**：
  1. **漏掉了一个保留语义、又能修掉实测误报的选项。** 子报告 35 §2.1 给了两种修法，第 1 种是在剩余请求预算内每 100–200 毫秒轮询一次任务列表；§6.2 把它列为 C，并说"B 和 C 都优于 A"。`open` 默认预算 5 秒、观察窗 1.5 秒，余量足够。两次实测误报（VLC 冷启动、WPS 打开 PDF）事后几秒内都证实已经启动，轮询很可能就能确认。初稿只写了 B，没有比较 B 和 C。
  2. **B 削弱了 batch 的安全性。** batch 遇到非 0 退出码就停（【源码】`ui_batch.py` 停止规则，子报告 39 §3.6）。现在冷启动报未知，batch 停下。改成 B 以后，`open X; click --name Y` 这样的计划会在 X 还没出现时执行第二步。如果前一个 App 上恰好也有名为 Y 的可见目标，就会点错 App【推断】。更早定稿 §2.2 第 3 条要求"未确认就停止 batch"，防的就是这个。
  3. **B 在后台屏上判断不了"别屏"。** 冷启动的典型情形是：观察结束时目标在任何屏上都还不可见（VLC 093 原件 `matchingTaskCount=0`）。"只有出现在别屏才报未知"在这一刻无从判断，结果只能报完成；之后如果它落到了主屏，也没有人知道。更早定稿 §2.2 和 §2.3 的验收里有"主屏任务是否不变"，B 等于放弃了后台屏启动的这项核对。
  4. 初稿 §3.5 说"基线和旧候选在主屏上都按平台返回码报完成"，这是事实（【源码】`git show 7d5be70:…/SystemActions.kt:190-195`；`git show 3f45af6:…/ActivityLaunch.kt:247-253`）。但它没提旧候选在后台屏上把落点挂起、`exit 1`。更早定稿当时要求改严，依据是 VLC 实测和"未确认表达成失败会诱发重发"（`androidctl-candidate-route-review-3f45af6.md` §2.2 依据、缺陷 F16）。
- **证据**：【源码】`ActivityLaunch.kt:295-312`（只读一次 `liveTasks()`）；【原件】子报告 35 引用的 `ST/12-sessions/03-authority/preflight-fix/runtime/api34/commands/093-…/stdout.bin`，我只核了子报告的引述，没有重开原件；【推断】batch 误点。
- **建议怎么改**：A3 的推荐改为"观察结束后在剩余预算内轮询任务列表，确认才报完成，预算耗尽仍是未知"。B 作为次选，只用于主屏、而且不在 batch 里时。§6 第 2 条从"应当撤回"改为"实现应改为预算内轮询；'主屏也确认'这一规则可以保留"。

### 2.3 A5：等"出现"不要求唯一，只修得了两次实测失败中的一次（证据不足，修法要补条件）

- **初稿原话**：§3.5 表格把"一次目标在屏幕外，一次有三个同名节点"都归因于"要求恰好一个可见目标"；A5 的修法是"有一个及以上可见匹配就算满足"。
- **反驳**：
  - 屏幕外那一次失败，按初稿的修法照样失败。【源码】`UiSelector.kt:47`：`matches()` 遇到不可见节点直接返回 false，根本不算匹配；子报告 40 D3 引的失败原因是 "No visible target matches the selector"。"一个及以上可见"修不了它。
  - 唯一性不只是严格。`wait` 成功时返回 `data.predicate.ref`（【源码】`UiCondition.kt:151-153`；`observations.md` "Success returns `data.predicate.ref`, windowId and the current sequence"）。允许多个匹配之后，这个引用指哪一个，必须先定义清楚，否则调用者可能拿着它去点三个同名节点中的任意一个。
  - 关于"假就绪"：唯一性本身不防旧页面。旧页面上如果恰好只有一个同名节点，现行规则也会提前成功。所以放宽唯一性带来的新增假就绪风险有限。真正的风险在页面过渡期：新旧两页的节点同时在树里，这时常见多个匹配；放宽后会更早成功，但成功时新页面的节点至少已经出现【推断】。
- **建议怎么改**：
  - §3.5 表格只把"三个同名节点"归入唯一性问题；屏幕外那次另列，修法是让指引推荐 `wait --contains`，或者对"出现"条件改为"已采到即可"（这另需用户定）。
  - A5 的修法补一句："多个匹配时满足条件，但不返回单个 ref，改为返回候选列表；动作仍要求唯一。"

### 2.4 A7 与 §6 第 3 条：已存在的工作区目录不查权限，保存的屏幕内容会静默落进他人可读的目录（判断有争议，风险未写）

- **初稿原话**（A7）："工作区缓存只在新建时设为私有，已存在的目录不再检查权限；凭据目录维持现状。"
- **反驳**：
  - 工作区缓存保存的是界面正文和截图，里面可能有通知内容、聊天、验证码。【源码】`history.py:67-80` 对三个缓存目录调用 `private_directory`；`private_files.py:221-236` 对已存在的目录做检查。
  - 实施方在 Windows 上撞到的失败，原因是"用普通 mkdir 建的目录继承了父目录的 DACL"（子报告 39 D2）。Windows 上某些位置继承下来的 ACL 会给其他本地用户读权限【推断，未在本机验证】。初稿的修法在这种情况下会静默写入，用户毫无察觉。
  - 这项检查在基线就有（子报告 39 已核）。本轮的问题是第三轮把"保存失败"升级成了读命令失败，放大了后果。修的对象应该是后果，而不是保护本身。
  - A7 把 `screenshot` 和 `snapshot`、`find` 并列。但截图的交付物就是图片文件，保存失败就是没交付，不能算"正文已打印"。§6 第 3 条已经限定在"默认文本模式下"，A7 的表格行没有限定。
- **建议怎么改**：
  - 目录属于当前用户而权限过宽时，先收紧（chmod 700，或重设 DACL）。
  - 收紧失败（例如 WSL 的 drvfs）而正文已经打印时，结果维持完成，附一条明确警告，不再升级为失败。这也是子报告 39 §3.3 原本的建议。
  - 截图和 `--json`、`--no-print`、`--out` 这些"文件是唯一交付渠道"的情形，保存失败仍算失败。
  - 两种做法都能修掉实测的误伤。

### 2.10 §7 第 4 项：16 次基线实测的判读规则落在噪声里（方法问题）

- 【重算 `W/power.py`】：
  - 按子报告 41 估的单次对数成本标准差 0.5 来模拟"4 个任务、每臂每任务 2 次、取中位数比"：
    - 两版其实一样贵时，初稿规则判"不构成障碍"的概率只有约 61%；
    - 候选其实贵 1.5 倍时，判"倒退"的概率约 30%；
    - 贵 2 倍时约 68%。
  - 标准差取 0.3 时，三个数分别是约 78%、32%、86%。

  也就是说，1.25 倍和 1.5 倍这两条线都在噪声里；这个设计对"是否贵一倍以上"有中等把握，对 1.25 倍没有。

- **成本估计**：每次 0.4M–2.3M 输入、16 次合计 1,500 万–2,000 万，与八臂实测一致，可以接受。
- **建议**：
  - 判读改为只回答一个问题："候选是否仍比基线贵一倍以上"，并写明比值落在 1.25–2 倍之间时结论不定；
  - 每项任务先确认基线能完成，基线完不成的任务单列成功率，不算成本比；
  - 先做的零模型同屏对照应作为主证据，它没有路径噪声。

### 2.11 §5.1 第一题的选项 E：方向可取，但"唯一能排除搬屏"说过头，"伤害被掩盖"要降级（说过头）

- **类型判断是可靠的。** 【源码】`NotificationOperations.kt:244-249` 用公开的 `PendingIntent.isActivity/isBroadcast/isForegroundService/isService` 判断类型，最低 API 34 上都可用；`NotificationActions.kt:193` 据此只给界面型发送加目标屏选项。所以 E 在发送前可以区分界面型和广播、服务型。
- **E 排除不了同一类伤害的其它入口**【推断】：
  1. 老目标版本 App 的广播型通知按钮，可以在接收器里再启动界面（通知跳板限制只针对目标 Android 12 及以上的 App）。这样的界面不会进后台屏，但会出现在用户的主屏上。
  2. 后台屏会话里 `open` 一个中转页（深链交给代理 App，代理再启动浏览器），机制与 Feeder 完全相同。【源码】`ActivityLaunch.kt` 的预检只看解析出的处理者包，不看它后继打开谁。

  所以 E 是"在通知这条路径上排除"，不是"唯一能排除搬屏的做法"。
- **实施方并没有轻描淡写搬屏。**
  - 【原件】`ST/15-notifications/receiver-options.md`"任何方案都须正视：这次主屏浏览器 Activity 进入 VD，结束后没有自动回主屏"，并写明"若用户要求恢复或不影响主屏，这会改变需求及候选范围"。交付稿也写了"同一 Chrome task 确从 main 搬到 VD，结束后没有自动回 main"。
  - 初稿"比交付稿写得更重"成立的部分只在于：被搬的是主屏上可见的顶部任务，界面在会话结束时进入销毁（子报告 38 核过 073/078）。
  - 还要说明：这是测试布置下的 `about:blank` 页，不是用户真实在用的页面。
- **"按 D……伤害反而被掩盖"**：在 D 下回执仍列出目标屏上可见的 Chrome；现行的 A 也不报告"任务是从主屏搬来的"。D 只是把结果字从未知改成了完成，提示更不显眼，但并没有隐藏比 A 更多的事实。应改为"D 下这类搬屏更不显眼"。
- **建议**：推荐 E 可以保留，表述改为"在通知路径上排除搬屏"；补一句"后台屏 `open` 经中转页仍可能搬任务，属同一机制，另行评估"。F（D 加搬屏检测）不只是"你确实需要时"的次选：它对 `open` 也适用，可以作为整块后台屏的通用补救。

### 2.14 §6 第 7 条：手写采集器"保留但冻结"的裁断基本站得住，但"出错再换"等于临阵换路（判断有争议）

- **支持初稿的理由**（我核过子报告 36 的依据）：
  - 节点相关的隐藏成员比基线少（16 个降到 10 个，因为最低 API 提到了 34）；
  - 回调接口在 AOSP 14 到 main 之间没变（子报告 43 核了 21 个签名）；
  - 采集耗时被采集后的处理和 CLI 固有开销盖过。

- **不足**：
  - 手写 Binder 和 Parcel 是对厂商 ROM 最敏感的部分，而四轮下来没有一次真机运行。如果某个 ROM 改了回调布局，现在的快速失败会让每次采集都立即失败，产品整体不可用；这时才"改走公开路线"，换上的是一条从未运行过的路线。
  - 快速失败本身也只在本地回环里验证过（子报告 36 §4）。
  - "本轮又长了约 370 行"是第三轮 N4、N5 要求的快速失败诊断带来的（§2.6），不能算作保留的代价。
- **建议**：结论维持"保留"。§7 第 4 项的真机检查里，顺带做子报告 36 §3.1 设计的同页对照（长网页、原生长列表各连续 5 次，比较两条路线的采集时间和完整率）。设备时间已经花了，额外成本小；结果出来就把"出错再换"变成"有数据支撑的备选路线"。
