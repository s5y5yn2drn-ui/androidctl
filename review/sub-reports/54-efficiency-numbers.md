## 1. 结论摘要

**整体状态**：70 次运行的原始用量数字可以完全复现，记账诚实，没有发现漏报或挑选样本。但"候选比基线便宜"这个总结论站不住。它几乎全部来自一个特殊任务：网页内容能否进入界面树。在两道原生 App 任务上，候选总是比基线贵 3% 到 86%。

最重要的发现：

1. **数字成立**【重算】
   - 66 行结果表的 396 个数（总输入、缓存、未缓存加输出、轮数、CLI 次数、耗时）与我从逐响应 usage 独立重算的结果完全一致，墙钟误差为 0。另外 4 次图像题运行见各自的结果页，数字也一致。
   - 包内 70 个 `agent_path` 恰好对应 70 个目录，没有被藏起来的正式尝试。
   - 失败的 CLI 调用、补查和帮助读取都计入了成本。

2. **GitHub issue 题的 0.39 倍是真实的，但测的是一项能力差别，不是"整体变便宜"**【原件】
   - 基线的 `7d5be70` 没有让 Chromium 交出网页内容的无障碍服务（`BrowserAccessibilityService`）。基线的界面树里网页只剩一个空的 "Web View" 节点，见 `E/c2-baseline-01/evidence/cli/1795303268708783700-…/child.stdout`。
   - 所以基线只能靠"截图、看图、按坐标点、滑动"推进，每一步要多一轮去看图。31 轮主要由此而来。
   - 候选臂由操作者事先启用了这项服务（`ST/real-tasks.md:97`），界面树里有完整网页。
   - 这是候选的真实收益，但只适用于 Chromium 网页。

3. **原生 App 任务上候选更贵**【重算】
   - Feeder 长列表题：总输入 1.26 倍（精确秩和检验 p=0.056）。新内容 token 1.44 倍（p=0.008）。
   - Maps 路线题：Play 镜像组 3 对 1.035 倍；冷启动组 1 对 1.49 倍；旧内存快照组 1 对 2 次 1.86 倍。
   - Feeder 题上，多出的约 10.8 万总输入里，约 9.1 万来自候选每次都会读的 30 KB 专题 `actions.md`。这份文档读进来之后每轮都要重发。
   - 其余多出的部分来自候选在 5 次里全部误用 `scroll-until`：`--timeout` 不带单位，以及用纯标题去精确匹配"标题加摘要"合并而成的名称。

4. **"未缓存输入加输出"这个量主要是缓存未命中的噪声，不能用来判产品**【重算】
   - 同一臂内，它的变异系数达 18% 到 35%。
   - 单次运行因服务端缓存未命中多计的量可达 3.1 万到 5.3 万 token。
   - 用"每轮新增内容"重算后，GitHub issue 题两臂几乎一样（0.96 倍），Feeder 消融两臂也一样（0.94 倍）。实施方原表里的 1.22 倍和 1.54 倍都是噪声。

5. **合入底线的状态**
   - 按第 18 项的字面，"完整成本门未齐"如实：Maps 路线题没有凑满两边各 5 次。
   - 但即使 Maps 路线题取已观察到的最坏比值 1.86，三题几何平均也只有 0.97，离 2 很远。按几何平均这一条，三题几何平均要超过 2，Maps 路线题的比值得超过 16.2；单题 3 倍上限这一条也要求它超过 3。
   - 因此继续为凑满 Maps 五次而反复恢复环境，对合入判定几乎没有信息价值。

6. **两组消融的结论成立，但量的是"强制使用"**
   - batch 一组：用 batch 时轮数多 27%（p=0.024），耗时多 28%（p=0.008）。
   - `scroll-until` 一组：差别都在噪声内。
   - 两组都是在提示里规定"必须用"或"不许用"，量的是"被要求使用时的代价"，不是"模型自然选用时的收益"。

**对待决题的看法**：本专题不直接涉及两道待决题（搬屏归因 A/B、M6 坐标 A/B/C/D）。与本专题有关的待定事项见第 6 节的 A/B/C/D。

## 2. 确定缺陷（证据层面）

### D1【中，必须修正口径】版本组的总结论把一项网页能力的收益当作整体成本结论

- **触发条件**
  - `core-results.md` 和工作稿 `T/deliverables/r4-candidate.md:8,50` 用 GitHub issue 题和 Feeder 题的几何平均 0.70237 概括成本底线。
  - 两题的性质完全不同。GitHub issue 题的差距来自基线读不到网页：基线 5 次各有 8 到 13 个图像块，候选 0 个；基线每步要单独调一次 `view_image`。
  - Feeder 题是原生列表，候选更贵。
- **原件**
  - `E/c2-baseline-04/native.rollout.jsonl.review.jsonl` 的工具调用序列是"截图、看图、点坐标、截图、看图、滑动"这样循环。
  - `E/c2-candidate-02/cli-index.json` 只有 8 次 CLI，界面树正文约 8.5 KB，含全部 GitHub 链接。
- **实际影响**：读者会以为本轮整体让调用变便宜了。原生 App 上的数据方向相反（第 4 节）。
- **最小修正**
  - 结果页把"网页内容可读"单列为一项能力收益。
  - 原生 App 任务的比值单独报告。
  - 不要把两类任务放进同一个几何平均后只报一个数。
- **确定性**：高。原件和重算都支持。

### D2【中，必须修正口径】"未缓存输入加输出"被当作稳健的第二指标

- **原件**：逐响应的 `cached_input_tokens` 常常跌回 17,024（只命中系统前缀），例如 `E/c2-baseline-03` 的第 3、6、10、14 次响应。这是服务端缓存没有命中，与产品无关。
- **重算**（`misses.out`），"超额"指实际未缓存量减去"每轮新增内容"：
  - GitHub issue 题基线 5 次的超额为 1,358、945、31,413、550、43,055 token。
  - 候选 5 次的超额为 12,933、449、31,472、25,369、18,931 token。
- **影响**
  - GitHub issue 题"52,539 升到 64,054（1.22 倍）"不显著（p=0.69）；改用新增内容为 0.96 倍。
  - Feeder 消融"with 比 without 高 54%"同样是噪声，新增内容为 0.94 倍。
- **最小修正**：把这一项换成"新增内容 token"。算法是首轮输入减去系统前缀，加上各轮输入增量之和。或者报"最终上下文长度"。两者都不受服务端缓存是否命中影响。
- **确定性**：高。

### D3【低，可选】结果表每项指标的中位数来自不同的运行

- 例如 GitHub issue 题基线的总输入中位数取自第 3 次（1,334,238），未缓存加输出的中位数取自第 1 次（52,539）。
- 这在统计上没有错，但读者容易把"1,334,238 对 521,085"和"52,539 对 64,054"当成同一对运行来比较。
- 建议附上每臂五个原值（见第 4.2 节）。

### D4【低，可选】成本结构里没有拆出"指引文档读入"这一项，错过了最直接的改进点

- 重算（`guidance.out`）：候选在 Feeder 题、Maps 路线题、后台屏 Contacts 题中，几乎每次都读 30 KB 的 `actions.md`。指引读入占总输入的 16% 到 26%。
- 基线在 GitHub issue 题有 4 次读了 65 KB 的 `reference.md`，那 4 次占比约 31%。
- 候选在原生任务上的劣势大部分来自这一项。实施方的 b2 后续分析（`E/b2-followup-analysis.md`）和结果页都没有指出这一点。

没有发现数字造假、漏计失败或选择性汇报。

## 3. 设计与简化

### 3.1 第 18 项的判据（总输入中位数）现在怎么看

【推断，基于重算】

- **总输入的组成**
  - 总输入约等于轮数乘平均上下文长度。
  - 其中执行框架固定前缀（系统提示、工具定义和任务提示，第一次响应约 18.4k token）乘轮数，占 39% 到 68%。
  - 指引读入占 1% 到 31%，图像占 0% 到 21%。CLI 输出和模型自己的历史合计只占 14% 到 38%。
- **缓存命中率**：84% 到 97%。按典型计价（缓存读入是正常输入的十分之一，输出是输入的 8 倍）折算时，总输入的差距会被缩小。
  - GitHub issue 题：总输入 0.39 倍，折算成本 0.555 倍。
  - Feeder 题：两者都约 1.23 倍。
- **方向是否一致**：对每道任务，总输入、折算成本、轮数、耗时、新增内容这五个视角的方向一致。唯一不一致的是"未缓存输入加输出"，原因是 D2 的噪声。
- **这个指标不合适的地方**
  - 它主要反映框架前缀乘轮数，而框架前缀与产品无关，会把产品差异压向 1 附近。
  - 两倍上限对 alpha 产品太宽：原生任务上 1.3 到 1.9 倍的退步都能"过线"。
  - 几何平均允许一项网页能力的大收益掩盖原生任务的退步。
  - 每臂 5 次只能分辨约 25% 以上的差别。例如 Feeder 题总输入比值的 95% 自助法区间是 0.99 到 2.02。
- **更合适的做法**：逐任务报告"轮数中位数"和"按缓存计价折算的成本中位数"，再加最终上下文长度。合入看"原生任务上没有超过 1.25 倍的退步，或者能解释并接受"，不再用全局几何平均。见第 6 节 A 项。

### 3.2 消融的设计

- 两组消融都在提示里强制"本次必须使用"或"本次不使用"。batch 一臂因此要读 `batch.md`，还要写 JSON 计划文件。
- 测出来的是"把能力塞进一个并不需要它的任务里要付多少钱"，回答不了"这项能力在需要它的任务上省不省"。
- 第 6 项为 batch 和 `scroll-until` 设的"中位轮数至少少三成"，在这两道题上不可能达到：Feeder 列表只隔两个视口，基线用两次普通 `scroll` 就到了（`E/s1-core-baseline-04/cli-index.json`）。
- 这是任务选择问题，不是能力的结论。实施方按规则没有据此降级能力，处理正确。
- 第四轮评审方建议的"三成"门槛和"与不用对比"的验收方式，现在看会导致两种结果：要么永远过不了，要么为了凑出能过的题而去造题。见第 6 节 B 项。

### 3.3 候选可以直接做的改进（实施细节，不需要用户裁决）

- 把 `actions.md` 拆小，或者把首页里最常用的几条写全，让常见任务不必读 30 KB 的专题。【推断】
  - 按 Feeder 题的数据，这一项约占候选多出成本的八成。
- `scroll-until` 的 `--text` 和 `--name` 匹配的是"标题加换行加摘要"合并后的整段名称。
  - Feeder 题 5 次自由策略的候选运行中，第 3 次和第 4 次以 `observationIncomplete`（观察不完整）停止，其余 3 次都在派发 3 步后，因原目标此时只声明 `backward, up` 两个方向而以 `routeUnavailable` 停止。
  - 指引应写清"名称是合并字段，建议用包含匹配"，或者由命令自己支持部分匹配。
  - `--timeout` 缺单位的问题已在 `7693794` 修正（只改指引示例），但修正后没有复测。

## 5. 与第四轮数字的衔接

第四轮的 1.80 倍和 2.35 倍来自第三轮包 `S/pkg6/root/…/final-verification/paired-runtime/{contacts-1,contacts-2,chrome-2,chrome-1c}`【原件】。条件与本轮有四处不同：

1. **推理档位**：当时是 `xhigh`，本轮是 `medium`。
2. **任务不同**：当时的 Chrome 题是在网页里用"页内查找"找 Addis Ababa，本轮是 GitHub issue 搜索；当时的 Contacts 题是主屏新建联系人。
3. **候选的输出体积**
   - 当时旧候选一次 `snapshot` 约 40 KB，单次运行交付的工具文本达 360 KB，共 29 轮。
   - 本轮候选一次 `snapshot` 约 8.5 KB，交付文本 121 KB 到 284 KB，共 12 到 15 轮。
4. **基线的表现**：当时的 Chrome 基线也靠截图和坐标，27 轮 104 万。本轮 31 轮 133 万。两者档位和任务都不同，但量级接近。

所以，从 2.35 倍到 0.39 倍的变化主要在候选一侧：轮数从 29 降到 13，每轮的上下文也变小。这与本轮紧凑输出的方向一致。但因为任务和档位都换了，不能把这个降幅全部归因于产品【推断】。

原生 App 一侧，第四轮 Contacts 题是 1.80 倍，本轮 Feeder 题 1.26 倍、Maps Play 组 1.035 倍、Maps 冷启动组 1.49 倍（各 1 次）、Maps 旧快照组 1.86 倍（1 对 2）。从这些数字看，原生任务上的差距可能缩小了，但候选仍然更贵。

**基线在 GitHub issue 题上 31 轮、22 次 CLI 的原因**【原件，读了基线第 1、3、4 次的轨迹和 CLI 回执】：

- 主因是能力缺失。`7d5be70` 没有网页无障碍服务，Chrome 的界面树里网页只是一个空节点。基线的模型只能截图、调 `view_image` 看图、按坐标 `tap` 或 `swipe`。CLI 把图片保存成文件，看图必须另用一轮，所以每推进一步至少要两轮。
- 次因是指引。基线 5 次里有 4 次读了 65 KB 的 `reference.md`（约 1.2 万 token），之后每轮重发，约占总输入 31%。
- 与基线默认输出格式的关系不大。基线的 `--print` 输出每次只有 1.5 到 3 KB。
- 也不是模型策略不同：两臂是同一个模型、同一档位、同一提示。

## 6. 需要用户裁决的新取舍

### A. 第 18 项第 3 条成本底线的量法

- **A1（维持现状）**：总输入中位数，几何平均不超过 2，单题不超过 3。
  - 网页收益会掩盖原生任务退步；两倍对 alpha 产品太宽。现在的数据下它几乎必然通过，起不到约束作用。
- **A2（推荐）**：逐任务判定，不做全局几何平均，而且网页任务和原生任务分开看。
  - 判据用"轮数中位数"和"按缓存计价折算的成本中位数"。原生任务上任一项超过 1.25 倍，要给出原因并由用户接受。
  - 同时报告新增内容 token，替换掉"未缓存加输出"。
  - 代价是要多写一页说明，不需要多跑。
- **A3**：在 A2 的基础上再要求每臂 8 到 10 次，以分辨 15% 左右的差别。
  - 成本是每道题多 6 到 10 次运行，加上环境恢复。我不推荐。
- **A4**：取消成本底线，只报趋势。
  - 最省事，但用户会失去"调用便宜"这个目标的硬约束。
- **剩余未知**：真实计价的折扣比例；本报告用的是十分之一的缓存价和 8 倍的输出价。

### B. 能力对照（batch、`scroll-until`）是否继续用"强制使用的消融加少三成"

- **B1（维持现状）**：只会继续得到"未通过"，而且容易引出为了凑出能通过的题而造题。

  - 指引修正后用同一题复测 5 次即可。
- **B3**：只为确实需要该能力的长距离任务（例如目标在 10 个视口以外）各做一次对照。
- **B4**：把这两项能力降为实验，不再投入。
  - 按第 6 项的规则，要连续两次全量不过才能降级。现在只有一次。
- **剩余未知**：修正指引之后，`scroll-until` 的失败率是否会下降。

- **C3**：从固定任务集里换掉 Maps 路线题，改用另一个不依赖实时网络的原生 App 任务。

### D. 固定任务集是否算已经确定
