# 第五轮子评审 52：主机端的结果、退出码、观察交付、batch 与工作区权限

评审对象：产品 `cab84b8` 的主机端（`androidctl/src/androidctl/`）和公开指引；独立 docs `31bae00`。
本报告的工作文件都在 `S/agents8/52/`（`S` 为评审 scratchpad 根目录）。

## 1. 结论摘要

整体状态：主机端这一块按第四轮决定基本做到了，结果五态与退出码的主干是一致、可预期的；真实任务里 950 次模型发出的 CLI 调用没有一次未处理异常，退出码 1 和 2 都是"已知结果"。剩下的问题不在主干，而在三处"按字面执行决定"造成的规则分叉，以及 batch 这项能力本身的价值。

最重要的发现：

1. **自动保存失败的退出码取决于失败原因，而不是交付方式**（可选修，但建议修）。只有"权限收紧失败"走了第 14 项的规则；其它保存失败（目录被占、配额、写入错误）规则正好相反：`--json`／`--no-print` 下的动作照样退出 0，打印模式下的 `snapshot` 反而报 failed。我在 Linux 上用真实目录复现了全部 15 种组合。【实跑】
2. **batch 停止时，结果字和退出码对不上，也与 `fill` 这类复合动作的规则不一致**：前面的步骤已执行、后一步未发出时，batch 报 `failed`、退出 2（退出 2 在总表里的意思是"没有发出"）；停止步是结果未知时报 `failed`、退出 3。`fill` 在同样的情形下报 failed、退出 1。【实跑】【源码】
3. **batch 在真实任务里没有省成本，而且省成本的那条路调用方本来就有**。在 GitHub 上用 batch 做同一任务的两臂对照里，用 batch 的一臂中位轮数是 14，不用的是 11；不用 batch 的那臂，模型本来就在一次工具调用里串联多条命令（5 次运行里有 14 次工具调用含两条以上命令，抽查确认其中有 CLI 串联）。batch 有 334 行源码、1,658 行测试、85 行专题指引，另外有十多处跨专题的停止规则。【原件】【重算】
4. **33 次退出码 2 里，有 23 次可以由产品侧低成本消除**：按键名区分大小写（2 次，整批被拒）、时长不带单位（10 次）、`reveal` 在节点不提供该动作时给出错误的说法（8 次）、`@e…` 被报成过期引用（1 次）、`open --package` 的报错要求"指定 --package"（2 次）。16 次退出码 1 全部是如实的业务失败；其中 12 次 `scroll-until` 失败的根因是它只能做精确匹配，而列表项的文字是标题加摘要合并成的。【原件】
5. 第 4、9、11、14 项和 U30 的组合契约第 5、7 条：保存的文件与打印的正文逐字节相同（实跑比对），0755 目录能收紧到 0700 并正常成功（实跑；实施方在 Windows 上把这几条用例跳过了），动作命令和 `wait` 的输出形状选项都已删除，`wait` 成功只打印匹配节点及其祖先，加载指示只在检测到时报告。**这些我判为成立。**【实跑】【源码】
6. 单条命令在拿到设备结果之后被 Ctrl‑C 中断，或主机本地出现未预期异常时，整条结果会被替换成 `androidctl: UNKNOWN`，已知的 done 和全部事实都丢掉，命令名也变成 `androidctl`。提交 `8731032` 的"保留执行事实"只在 batch 里做到了。处理方向是保守的，不会诱发重复操作，属于低严重度。【实跑】

对待决题的看法：这一块不涉及两道待决题。新的需要用户定的点见第 6 节：batch 的去留（我建议删除，或至少现在就降为实验）。

## 2. 确定缺陷

### 2.1 自动保存失败的退出码随失败原因分叉（可选修，建议本轮修；有原件，确定）

- 触发条件：工作区 `.androidctl` 的自动保存失败。
- 源码：`ui_client.py:1366-1371` 只在错误码等于 `privatePermissionsRepair` 时置 `permissions_failed`；`finish_delivery_result`（`ui_client.py:1386-1469`）只对这一种失败做"打印模式记警告、非打印模式退出 1"。其它失败只写进 `historyError`／`snapshotError`。
- 实跑：脚本 `S/agents8/52/delivery_probe.py` 直接调用 `cab84b8` 的 `deliver` 和 `print_delivery`，用三种真实目录状态：0755 可收紧、0755 但属主是别的用户（root 能改模式，改不了属主，于是收紧失败）、`snapshots` 是个普通文件。结果：

| 情形 | 0755 可收紧 | 收紧失败（属主不同） | `snapshots` 是文件（非权限错误） |
| --- | --- | --- | --- |
| `click` 文本模式 | done／0，模式变 0700，文件与打印相同 | done／0，带警告 | done／0 |
| `click --no-print` | done／0 | **done／1** | **done／0** |
| `--json click` | done／0 | **done／1** | **done／0** |
| `snapshot` 文本模式 | done／0 | **done／0，带警告** | **failed／1** |
| `--json snapshot` | done／0 | failed／1 | failed／1 |

- 实际影响：规则本身不难懂，难懂的是它的条件。U30 的原话是"文件为唯一或显式要求的交付时仍按失败处理"，依据是交付方式；实现的依据却是失败原因。结果有两处反常：非打印模式下文件同样是唯一交付，配额满或目录被占时动作却退出 0；打印模式下正文已经交到调用方，`snapshot` 却因为非权限的保存失败报 failed，而权限失败时报 done。指引不得不专门写一条"打印文本的权限警告例外"（`observations.md:36-43`，`reference.md:67`，`images.md:153`）。实施方的内部 review 明确写了"没有据此扩展其它历史错误的容忍范围"（`ST/permissions-review.md`），也就是有意只按字面做。
- 测试：`test_observation_files.py:873-917` 通过替换 `history.save` 抛出那个特定错误码来验证分类，只覆盖权限这一种；没有测试覆盖非权限失败在非打印模式下的退出码。
- 最小修正方向：改成只看交付方式的一条规则。打印模式下，任何自动保存失败都是警告、退出 0（`snapshot`／`find` 也一样）；`--json`／`--no-print` 下，任何自动保存失败都退出 1；`--out`、`--image-out`、截图要的图，失败都退出 1。这样 `finish_delivery_result` 里关于权限的特例和指引里的例外条款都可以删掉，大约少 20 行代码、6 行指引。

### 2.2 batch 停止时，结果字与退出码不一致，也与复合动作的规则不一致（可选修；实跑，确定）

- 源码：`ui_batch.py:180-201` 的 `aggregate`：只要停止步的退出码不是 0，结果就是 `"failed"`，`exit` 继承停止步的退出码。
- 实跑：脚本 `S/agents8/52/local_fail_probe.py` 替换掉设备调用，跑 `cab84b8` 的 `app.main()`：
  - 第 1 步未发出：`batch: failed; Step 1 stopped: not sent (exit 2)`，退出 2。实际什么都没执行，结果字却是 failed。
  - 第 1 步完成、第 2 步未发出：`batch: failed`，退出 2。退出 2 在总表里是"请求的输入没有发出"，可第 1 步已经执行了。
  - 第 2 步结果未知：`batch: failed; Step 2 stopped: UNKNOWN (exit 3)`，退出 3。而 Ctrl‑C 中断时，同一个 batch 报的是 `batch: UNKNOWN`。
  - 真实原件里也有这种情况：`ST/runtime/api34/commands/2066-regex-one-nonnewline-selection-paste` 的 JSON 是 `"result":"failed"` 加 `"exit":3`。
- 对照：`fill` 的规则是"任何一步已派发，整体就是 failed／1；一步都没派发才是 not sent／2"（`actions.md:315-316`）；`scroll-until` 在第 4 步未发出时也报 failed／1（S1 原件）。batch 是唯一一种"已执行却退出 2"的复合形式。
- 实际影响：只看退出码的包装脚本会把"已执行一部分"误读成"什么都没做"。指引里写了"保留之前 batch 的效果"（`SKILL.md:69`），所以模型按指引走不会出错，但规则本身多出了一个例外。
- 最小修正方向：按 `fill` 的规则汇总。一步都没派发是 not sent／2；停止步是结果未知时报 UNKNOWN／3；其余情形是 failed／1；步骤自身的结果仍然原样保留在 `data.steps` 里。如果第 6 节决定删掉 batch，这一条就不用做了。

### 2.3 单条命令遇到本地中断或异常时，丢掉已知结果（低；实跑，确定）

- 源码：`app.py:903-918` 把任何 `Exception` 或 `KeyboardInterrupt` 都变成 `Result(command="androidctl", result="UNKNOWN")`，`data` 为空。`ui_batch.py:280-300` 则会保留已经返回的步骤，并给当前步附上 `deliveryError`。
- 实跑：设备已返回 done 之后，在保存阶段注入 Ctrl‑C，得到 `androidctl: UNKNOWN; Command interrupted; execution outcome is unknown`，退出 3，JSON 是 `{"command":"androidctl","result":"UNKNOWN",...,"data":{}}`；在渲染阶段注入 `RuntimeError`，输出同样形状的结果。
- 实际影响：处理方向是保守的，不会让调用方重复操作；但 `reference.md` 的"字段指南"写着顶层 `command` 是固定的公开命令路径，失败时也一样，这里与之不符；已经确定的 done 也被降成了"结果未知"。反过来，连接之前就按下 Ctrl‑C 也会报 UNKNOWN，实际上什么都没发出。
- 最小修正方向：单命令路径学 batch 的做法：`UiCommand.invoke_command` 持有已返回的 Result，本地异常只附 `deliveryError`；还没返回才报 UNKNOWN，并保留命令名。大约 20 行。

### 2.5 `scroll-until` 只能精确匹配（可选修，影响显著；有原件）

- S1 的 12 次 `scroll-until` 失败全都用了标题文字，而列表项的文字是标题加摘要合并成的，所以 `matches=0`：一直滚到列表尽头（第 4 步 `routeUnavailable`），或者遇到观察不完整才停。模型随后改用完整的合并文字重试，以 `found` 结束（例：`ST/efficiency/s1-with-01/cli-index.json` 的第 2 到第 4 条）。B2 第一次运行那两次 `maxSteps` 失败，用的也是片段文字（`--text "May 12, 2023"`）。
- `wait --contains` 和 `find` 都支持子串匹配，`scroll-until` 只接受精确的 `--text`／`--name`（`ui_commands.py:1238-1290`）。
- 修正方向：给 `scroll-until` 加 `--contains`，复用 `wait` 的子串匹配；或者失败时附上"包含所给文字的节点"作为提示。属于动作专题，这里只记下它在退出码统计里的分量：16 次退出码 1 里占了 12 次。

### 2.6 `open` 解析不到处理者时报 failed（低；源码）

`ActivityLaunch.kt:214-220`：找不到任何处理者时报 FAILED（退出 1），有歧义时报 NOT_SENT（退出 2）。两种都发生在派发之前，回执都带 `dispatchStarted=false`（原件 `ST/runtime/api34/commands/311-richclip-real-mdn-source-open`）。这和总表"没有发出就是 not sent"不一致，虽然 `actions.md:371` 写明了这个例外。建议统一成 not sent。

## 3. 设计与简化

### 3.1 结果五态与退出码的主干是对的

`protocol.py:45-69`：done 0、failed 1、not sent 2、UNKNOWN 3、still running 4。显式的 `exit` 优先；`deliveryError` 只会把 0 改成 1。这套简单、可预期，`reference.md:64-70` 的总表与实现一致（逐行核对过）。"结果字说主动作，退出码汇总整条命令"会带来"done 加退出 1"和"done 加退出 3"两种组合，它们有用：可以告诉调用方"不要重做这个动作"。可以改进的一点是，文本模式的首行不显示被覆盖后的退出码（JSON 里有 `exit` 字段）。建议首行在 `exit` 与默认映射不同时补一个 `exit=1`，代价是一行代码。

### 3.2 观察交付：已经是"一份正文、打印和保存共用"

`deliver` → `render_observation` → `save_delivery` → `finish_delivery_result`（`ui_client.py:1131-1469`）用同一个 `body` 打印和保存，没有第二份格式。`5a817f1` 删了 1,629 行，旧的专用格式、解码器和 `--diff-from` 都没有残留（grep 过），只剩 `history.py:34` 为回收旧文件仍认 `.xml`／`.source` 后缀。这一行可以留一个版本，之后删掉。

能简化的是交付判定。`finish_delivery_result` 里 `observation_requested`、`observation_delivered`、`permission_warning`、`tree_satisfied` 等五六个布尔量拼成一个 12 行的条件，2.1 的分叉就藏在里面。改成"交付方式（打印、JSON 或不打印、显式文件）乘以产物（正文、图）"的一张小表，大约能少 40 行，指引里的例外也一起去掉。

### 3.3 batch：建议删除（见 6.1）

- 形态：一个 JSON 文件，每一步是一组 argv；整个计划先完整走一遍真实的参数解析，然后用同一个连接按顺序执行，遇到第一个非零退出码就停；中间的普通动作不下载附件，最后一步和停止步才交付（`ui_batch.py:212-278`）。**"预校验不过就整批不执行"本身是合理的**：静态计划半途因为参数错误停下，比开头就拒绝更难收拾。真正的问题是 2.4 里那条没必要的大小写限制。
- 步骤之间没有任何观察复用，设备端的采样、稳定等待和核验都照常做。batch 省掉的只是进程启动、本地连接和中间附件的下载。
- 真实使用（B2 用 batch 的一臂，5 次，版本 `7693794`）：计划都是 2 到 3 步，有"填写后按回车""先 reveal 再点击""返回、返回、等待"三种；第 1、2 次运行的首个计划因为 `ENTER`／`Enter` 被整批拒绝；第 4 次运行写了 3 份计划。成功率两臂都是 5/5；中位轮数用 batch 时 14、不用时 11，总输入是不用时的 1.32 倍（`ST/efficiency/core-results.md:227-275`，我核对了表中数字所引的各条原件）。
- 关键反证【原件，重算 `S/agents8/52/chain.py`】：模型所用的执行环境允许一次工具调用里执行多条命令。不用 batch 的 5 次运行里，有 14 次工具调用含两条以上命令（这个计数也包括读文件之类的非 CLI 命令）；抽查 `b2-without-01` 的轨迹，确认其中有"snapshot 之后紧接 find"、"返回之后紧接 snapshot"这样的 CLI 串联。S1 不用 `scroll-until` 那臂的 5 次运行里，同口径有 16 次。shell 的 `a && b` 本来就有"遇到非零就停"的效果。所以 batch 主打的"少几轮"，调用方不借助任何产品能力就能做到。它独有的价值只剩：整批预先校验，加上一次连接。
- 维护代价：`ui_batch.py` 334 行，`test_ui_batch.py` 1,658 行，`batch.md` 85 行，`reference.md`、`images.md`、`input.md`、`displays.md`、`actions.md`、`observations.md` 里还有十多处"会让 batch 停下"之类的规则；docs 的 `reference/ui.md:316-335` 另有一节。2.2 那种汇总上的例外也是它带来的。

### 3.5 第四轮的决定和评审建议，现在怎么看

- 第 14 项（权限）：方向对，但它的写法是"收紧失败怎么处理"，把规则绑在了原因上；实施方又严格按字面执行，于是出现 2.1 的分叉。U30 的更正已经给出了按交付方式表述的原则，这里只需要把那条原则落实。不用推翻原决定。
- 第 6 项（batch 作为正式能力继续打磨）：现在看代价过高。"不用它就做不成"的任务不存在，对比门第一轮也没过；更要紧的是，反证说明它要量的那个收益，在调用方的执行环境里本来就有。按第 6 项的规则，要连续两次全量实测不过才能降级，这一条会让实施方再花一整轮在 batch 的打磨和验收上。这是本块最明显的"在低价值处投入"。
- 第 4、8、9、11 项（一份正文、默认精简、动作不再有形状选项、`wait` 只打印匹配）：效果好，实现干净，应当保留。

### 3.6 其它

- 输出量：`snapshot --all` 在 GitHub 页面上一次打出约 257 KB（6 次调用，B2 和 C2 的原件），执行环境把它截断成约 2 万 token 的提示，模型还得再去读文件。这符合"保存的文件等于打印的正文，截断后去读文件"的约定，但每次都要付出这么多。可选的做法：正文超过某个上限（比如 64 KB）时只打印首行和路径，文件照常保存完整正文。这与"保存等于打印"的约定冲突，如果要做，需要用户点头，这里只记一笔，不列成待决题。
- `locate` 还保留着 `--all/--boxes/--depth/--interactive/--max-chars/--print`。它是只读命令，不在第 9 项范围内，不算违约；以后如果再精简选项，可以一起考虑。
- 跨专题的发现：`open --multiple-task` 仍然存在（`ui_commands.py:1093`），第四节的决定是删除，`EVIDENCE_GUIDE.md` 也写明尚未做，归显示屏专题。

## 6. 需要用户裁决的新取舍

### 6.1 batch 的去留

- A. 按第 6 项继续作为正式能力，下一轮全量实测再判一次门。得：保留整批预校验和单连接的执行方式。失：再花一轮打磨和验收；就现有证据看，门过不了的原因是结构性的（执行环境本来就能串联命令），再测一轮大概率还是不过。
- B. 现在就降为实验：首页和专题里不再推荐，代码留着，不再投入，也不做验收。得：立刻止损，可以随时恢复。失：代码、测试和十多处停止规则仍然要跟着别的改动一起维护。
- C. 删除 batch。得：少约 2,100 行代码和测试、一个专题、十多处跨专题的规则，2.2 也不用修了。失：失去"整批预校验"（这类错误一般一次重试就能纠正）和单连接执行（每步省一次本地连接，几十毫秒级）。
- D. 留着，但大幅精简：只做"按顺序执行、遇到非零就停、汇总规则与 `fill` 一致"，去掉中间附件的特殊交付逻辑，也不再要求计划是文件。得：维护成本降一半左右。失：仍然要维护；而它的收益，调用方的执行环境本来就提供。

推荐 **C**。理由：没有"非它不可"的任务；B2 实测更贵；不借助 batch 的串联在真实轨迹里已经在用。如果用户想保守一点，就选 B，并在下一轮全量实测时直接删掉。剩余的未知：使用不允许一次调用里串联多条命令的执行环境的调用方会受影响。本包所有运行用的都是同一种执行环境，没有反例可查。

### 6.2 关于自动保存失败的规则（实施细节，原则上用户已经定了）

2.1 的修正方向（只看交付方式）是把 U30 已写明的原则落实下去，不需要新的决定。只有一种情况要问用户：如果用户反过来想要更宽松的 C 规则，即"自动保存永远不改变退出码，只有显式文件和截图的图像会"，那就得推翻第 14 项"JSON 或不打印时按失败处理"这一条。我不推荐这样做。
