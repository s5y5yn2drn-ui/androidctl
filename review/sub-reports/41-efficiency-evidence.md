## 1. 结论摘要

**整体状态。** 交付稿里的效率数字可以复现：我重算了 54 个数，53 个完全相同，墙钟只差 0.4 秒。八臂业务答案全部正确，失败、截断和非零退出都如实保留。问题在于这组实验在设计上回答不了用户真正要决定的事：**整轮 68 个提交相对主分支基线 `7d5be70`，在真实任务上是更省还是更贵，从来没有测过。**唯一一次基线对照在上一轮，结论是旧候选比基线贵 1.8 到 2.35 倍。

最重要的发现：

1. **数字属实。** 两张效率表的 token、CLI、RPC、墙钟、动作后补读、CHANGED 但 Loading 次数、正文与 actions 字节，我都从原生 rollout 和 CLI 原流逐项重算过，全部吻合。【重算】
2. **new 与 old 的对照测不出总成本差别。** 同一臂在两个阶段之间成本差到 0.6 到 4.0 倍，比两臂之间的差别还大：Maps 是 new 先便宜、后贵 2 倍；GitHub 是 new 先贵 2.4 倍、后便宜 2.7 倍。因此"净成本因果未知"这句话本身准确。但交付稿漏写了两件事：一是这个设计根本没有检出能力；二是根本没有与基线比较。【重算】
3. **有一个一致、实施方却没写出来的正向信号。** 在 4 对里，new 每次 CLI 输出新增进上下文的 token 都少 23% 到 37%；new 在 4 次中有 3 次没有读主题文档，old 4 次都读了，指引累计计费约少 64%。前提是页面状态不同、样本小。【重算】
4. **绝对成本的大头不在产品输出。** 执行框架固定的约 1.8 万 token 前缀（系统提示、工具定义、全局 AGENTS 文件）每轮重发，占总输入的 19% 到 60%。其次是 CLI 输出累计（30% 到 69%），再次是指引（3% 到 25%）。总输入近似等于"轮数乘平均上下文"，所以**轮数**是第一杠杆。墙钟有 93% 到 96% 花在模型侧，每轮约 16 到 27 秒。【重算】
5. **CHANGED 但 Loading 几乎每次导航都会发生。** 八臂中 9 次，每次都要多读一轮，单次约占全任务输入的 5% 到 8%。产品的稳定判断只表示"界面变了"，不表示"业务就绪"。这是真实、反复出现的成本。【原件】【重算】
6. **过程成本与产出不相称。** 28 个产品提交配了 96 份文件名含 review 的文档、161 个绑定 JSON、2.1 MB 说明文字。内部源码 review 发现并修掉的实质产品缺陷是 3 个，其中 2 个出自同一份 review。最实质的一个缺陷（虚拟屏会话预检的调用包与 UID 不符）是设备实跑发现的，不是 review 发现的。【原件】

**对相关待决题的看法。**
- 第 2 题（动作后仍见旧页）：推荐 A 可以接受。但应补上两点事实：这类多读每次约值 5% 到 8% 的任务成本；现有 batch 组合在 84 次自然调用里一次也没用过。
- 第 3 题（页级动作字典）：推荐 A 可以接受，因为残余 actions 的绝对占比已经不是最大成本项。
- 另外建议新增一个用户裁决：合入前要不要做一次最小的"最终候选对基线"真实任务对照（见 §6）。

## 3. 设计与简化

### 3.1 效率实验本身的形态

实施方在八次 n=1 的运行上投入的取证工程包括：记录器、分析器补丁 3 个、分类更正、配置纠正、准备 review 4 份。材料占 61 MB（`ST/efficiency` 32 MB、`ST/16-delivery/efficiency` 29 MB）。这套工程能准确回答"这一次发生了什么"，却回答不了"哪个更省"。

更简单、也更有判别力的做法分两层：

1. **零模型成本的同页对照。** 在同一屏、同一份 raw 上分别用两种渲染各输出一次，计 token。上一轮评审 `sub-reports/10-offline-rerender` 已经这样做过。
2. **少量任务的多次复跑。** 每次从模拟器快照恢复起点，交替顺序，只记 usage、成功与否、轮数这三项，不再为每臂建绑定、冻结和多层 review。

### 3.2 从成本结构看产品该优化什么

- **轮数是第一杠杆。** 总输入约等于"轮数乘平均上下文"。框架前缀 1.8 万 token 在每轮重发；本例中它与产品无关，但轮数由产品决定。
- **单轮输出是第二杠杆。** 默认输出减半，在路径不变的前提下约省 15% 到 32% 的输入（§4.3）。
- **首页长度不是杠杆。** 首页减半只省 1% 到 3.6%。
- 因此"动作后自动等到业务就绪"或"一次命令同时动作并等待"，即待决第 2 题的 B 方案，值得做一次实测。本轮实施方推荐 A 的理由是"没有净收益原件"，这个理由成立，但它是因为没测，不是测了没用。

### 3.3 评审方前几轮建议的回看

- 第三轮工作记录 `review/sub-reports/31-real-flows.md` 第 9 条把"输出瘦身"列为第一优先，并要求"按第一轮方法实测 token"。实施方做了瘦身，per-call token 下降有信号支持（§4.2），但没有按第一轮的方法（基线对候选）实测。评审方当时的要求措辞含糊，没有写明要与基线比，这是评审方的疏漏。
- 评审方第三轮要求的第 0 阶段四臂（新旧阅读同后端对照），从设计上就测不出总成本差别。它带来的主要可用产出只有 per-call 字节与 token 事实。按"一个人维护的 alpha"立场看，这一项实验的投入与产出不相称。评审方当时应该直接要求对基线做多次复跑。

**外层 20000 token 上限对两臂并不对称。** 上限只会截断大输出。
- 第 0 阶段只在内层设了上限，old 被外层截断 3 次。模型随后改用 `--json --no-print` 自己删掉 actions 字段再读（第 0 阶段 GitHub old 第 3、4、6 次调用）。
- 最终阶段两层都设了上限：old 在 15 次非帮助调用里有 10 次主动加 `--max-chars`，没有被截断；new 唯一的大输出 `find --all` 被截断，随后 3 次读文件花掉该臂 15.9% 的输入。

所以"输出体量"与"模型应对截断的策略"混在一起了。【原件】【重算】

**能支持的结论**：

1. 两套呈现与指引都能让新上下文模型完成这两项只读任务。8/8 完成，答案都有原件支撑（§4.5）。
2. new 每次 CLI 调用平均新增进上下文的 token 更少，4 对方向一致。【重算】按响应间 input 增量扣除上一响应输出计算：

   | 阶段 | Maps old | Maps new | 降幅 | GitHub old | GitHub new | 降幅 |
   | --- | ---: | ---: | ---: | ---: | ---: | ---: |
   | 第 0 阶段 | 4,475 | 2,812 | 37% | 7,267（已自行删 actions） | 5,622 | 23% |
   | 最终 | 4,275 | 2,852 | 33% | 8,441 | 6,464 | 23% |

   页面状态不同，所以这是方向一致的观察，不是等内容压缩率。
3. 自包含首页让 new 少读主题文档：new 4 次里只有 1 次读了 1 份主题文档（最终 Maps new 读了 `images.md`）；old 4 次都读了，最终 GitHub old 读了 4 次。指引的累计计费：new 合计 201k，old 合计 558k。【重算】
4. 导航或提交后的"CHANGED 但 Loading"是常态：9 次，每臂 1 到 2 次。
5. 产品零派发拒绝是正确的：两次 `scroll down` 被拒（exit2，`dispatchStarted=false`）。

**不能支持的结论**：

1. new 比 old 总体更省或更贵：符号在两个阶段之间翻转，噪声大于效应。
2. 任何相对基线 `7d5be70` 或相对旧候选 `3f45af6` 的结论：两臂都不是它们。
3. 推广到其它 App 或任务：只有 2 个只读任务，同一模拟器上已重复做过至少 3 轮，而且任务参与了指引调优。
4. find 默认范围的效果：没有默认 find 样本。
5. 成功率差异：n=1，全部成功。

**"净成本因果未知"是恰当的谨慎，还是掩盖？** 我的判断：作为一句话它准确，没有掩盖任何测得的负面结果。实施方保留了失败、截断，也保留了"Maps new 本次更贵"。但效率章节的组织方式让读者容易误以为"只差因果归属"，实际缺的是两样：

- **检出能力**：这个设计连 2 倍差别都分不出来；
- **对照对象**：从未与基线比较。

同时它也**低估**了自己唯一可靠的正向信号，即上面第 2、第 3 条的 per-call token 和指引读取。它只报了字节比例，没有报原生 token 增量，而后者本来就能从 rollout 里精确取出。

## 6. 需要用户裁决的新取舍

### 1. 合入前，是否做一次"最终候选对基线"的最小真实任务对照

**候选 A：做。**

- **实验设计**：
  - 两臂：基线 `7d5be70`（含它自己的 APK、主机和指引）对最终 `4235af9`。
  - 环境：同一模拟器快照，每次运行前从快照恢复，消除历史建议与顺序影响。同模型、同 effort、同外层上限。
  - 任务 4 项：Maps 路线（原生阅读）、GitHub issue 评论（长网页，记成功率）、Contacts 表单填写后放弃（输入）、再加一项文件或通知任务（覆盖本轮的正确性改动）。
  - 每臂每任务 2 次，按 ABBA 顺序，共 16 次。
  - 记录：成功与否（独立核验）、未缓存输入加输出、轮数、墙钟、非零退出。
- **判读**：
  - 4 项中有 3 项新旧中位数比值不超过 1.25 倍，且成功率不降，就视为"效率不构成合入障碍"；
  - 有 3 项达到 1.5 倍或以上，就视为倒退属实，应在合入前或紧接合入后处理。
  - 这个设计只能检出约 1.5 到 2 倍的差别。
- **成本**：
  - 按本轮实测，每次约 0.4M 到 2.3M 输入 token，其中约九成命中缓存；每次 4.5 到 11 分钟，另加准备与恢复。
  - 16 次合计约 1,500 万到 2,000 万输入 token、约 4 到 6 小时的设备串行时间。
- **先做的零模型步骤**：同一组约 10 个屏幕，分别用两版各取一次默认输出，比较 token。这一步几分钟就能做完。

**候选 B：不做，只按正确性改动合入，效率之后再看。** 省时间，但合入时对"调用便宜"这个目标没有任何依据。

**候选 C：只做零模型的同屏对照。** 便宜，但测不到轮数，而轮数是最大的杠杆。

**我的推荐：A。** 剩余未知：模拟器快照能否把 Chrome 和 Maps 的动态内容稳定恢复到同一起点；以及两版主机在同一快照上安装、切换的准备成本。

### 2. 是否停止为 n=1 的实验建立"冻结、绑定、多层 review"
