## 1. 结论摘要（按重要性）

1. **B 和 A 都把“效率”和“给得更少”放在最前面，这一项候选反而做反了。** 【实测】交付方自己的最终成对真实任务里（`UG/reviews/final-paired-runtime.md:53-56,123-126`）：
   - CLI stdout：Contacts 34,879B → 149,803B（×4.3），Chrome 36,131B → 184,116B（×5.1）；
   - 模型 input：Contacts 0.81M → 1.46M，Chrome 1.04M → 2.45M；
   - wall time 两对都更长。

   我用一次性 `python3 -I` 只读脚本对候选 stdout 做了逐行重算（方法见 §3.1）：每个目标节点打印的完整 `"actions":[{id,name,label}…]` 数组占 51–56%，近期事件行另占 9–13%。上次外评已经点名这两项（效率-1、效率-2），交付方却把它们降为“未批准的可选改进”（`candidate-final.md:76-111`），交付稿只写一句“不能称普遍提速”。**这是本专题最重要的一条发现。**

2. **报告的“行格式”没有按原意落地。** 【实测+源码】B §4.3 的样例是 `[e7] button "Allow"`。候选实际是“角色 + 一整段 JSON 对象”，每行都带动作对象数组，连无 ref 意义的文本容器行也带（`androidctl/src/androidctl/ui_view.py:117-118`）。结果行首行常超过 1KB（§7 有原文）。用户选“行格式、删 XML”时依据的是研究期测得的“比 XML 省 11.5% token”，这个收益没有传到产品里。

3. **两份报告都要求虚拟屏“先探针、再决定投入”，候选跳过了这道门。**
   - B §0.2 的第 3 件事、§3.8 的 P0 门槛是 14/15/16 的 Pixel 加两家国产 ROM；A §10.1 的阶段 0 写的是“若目标 App 普遍因 task/IME 限制不可用，应调整范围”。
   - 候选做了全量 VD（#38，1,130 行，是最大的单项提交），再加上 B 和 A 都没有提出的“协议必填 kind + 主机级持久偏好”。
   - 正例只来自 AOSP 模拟器；唯一装有真实 App 的 MuMu 因缺权限不可用。

4. **文本输入取了两份报告的并集，而不是二选一。**
   - A 主张用窄 AccessibilityService 走 IC，并明确说不要同时维护 IC 和 clipboard 等多套通道，也不要悄悄改全局剪贴板（A §8.4）。
   - B 主张走 paste + keys，并论证 IC 在 UiAutomation 下不可行（B §7.4）。
   - 候选同时做了 IC（#29）、借用剪贴板粘贴（#36）、keys/type（#27），连同 fill 一共五条文本通道。合计约 1,840 行。
   - 这里有一层是用户选择造成的（IC C），但交付方给出选项时没有把“二者择一”列成选项。

5. **B 排在第 3 位、成本“小到中”的“结果直接给下一步”几乎没有落地。** 【源码】
   - `next:` 和 `unknownCheck` 在源码里出现 0 次；
   - staleRef 不给候选，只提示 run snapshot；
   - B 想删掉的“X 不证明 Y”句式在新 skill 里依然密集（§7）；
   - skill 目录从 81.5KB 涨到 147.7KB（+81%）。
   
   B 自己强调“长度不是首要问题，句式才是”，这一点被交付方整体跳过。

6. **通知 D、借贴、原生图源 zoom、剪贴板“当次准入”这几处，都把报告里的低优先级或按需项做成了重型实现。**
   - B 把通知动作和回复放在“按需再议”；
   - zoom 自述“完整 JPEG 本来可读，不宣称新细字收益”；
   - 剪贴板 null 的 AppOps 准入采样，防的是一个从未实际发生的拒读/可写组合。
   
   这些都应重新裁决（§6）。

7. **上次外评的总体判断成立。** 本轮成对实测还进一步证实了它的预测：输出没变小，效率没有证据。但它有两点要指出。
   - 它的作者就是报告 B 的作者，外评 §0.1 已披露利益关系。
   - 它也推动了两处增加状态的改动：主机级偏好（裁决-2a）和基线年龄字段（裁决-6）。
   
   整合时，交付方接受了 U25 中增加状态的几项，却以“各有实际职责”“未批准”为由拒绝或延后了几乎全部“删减/合并/默认精简”类建议（§5）。

8. **用户在关键节点上一贯是在做减法。**
   - 删 XML 而不是保留出口；
   - 砍掉暂停、三档权限和 Shizuku 护栏；
   - 不做自启和 PAKE。
   
   交付方的提案则一贯是全量。用户加重的地方有两处：U23 把显示 C 升级为协议必填，以及 zoom 选了 C 而不是交付方推荐的 B。这两处的选项表都没有列“不做”这一最简选项（§6）。

## 5. 优先级：报告排序 vs 候选 40 项

### 5.1 两份报告各自的优先级

- **B “只做三件”**：(1) 三处缺陷（covered 提示、配对码、跳转 unknown）；(2)+(3) 事件时钟 + `effect/windows/toast/next` 与差异输出，B 称“不破契约且砍掉一大半等待和阅读”；(5) VD **探针阶段**。

## 7. 文风：限定语渗入产品契约与公开指引

**公开指引**（`skills/androidctl/SKILL.md`，3f45af6）中的原句：
- “A path alone is not a viewed image.”
- “Partial collection can establish reliable positive facts; gaps cannot prove absence or selector uniqueness. Reading omissions and host truncation are different from collection gaps.”
- “Ref repair is a bounded aid after definitely unsent input, not proof of business identity.”
- “Local value verification does not prove persistence or a business submission.”
- “select then commit is not a transaction.”
- “Platform dispatch, App outcome and listener cleanup are separate facts.”
- “A platform receipt, changed tree or input echo alone is insufficient.”
- “complete samples or idle do not establish business readiness.”

我做了粗略的正则统计：SKILL.md 85 句中有 33 句含否定或限定（约 39%）；observations.md 297 句中 139 句（47%）；actions.md 244 句中 129 句（53%）。B 附录 A 的草稿是“状态 → 你做什么”的写法，**没有被吸收**。

**产品契约**中的例子（成对 Contacts 实跑的 fill 首行，截断）：

```
fill: done; changed; windows={"state":"changed","appeared":1,"fields":["bounds","layer"]}; selection={"state":"unchanged"}; content={"state":"changed"}; baselineSequence=6; baselineFinishedMs=12022805; baselineAgeMs=11173; baselineComputedAtMs=12033978; effect={"state":"changed","target":{…},"fields":{"text":{"before":"First name","after":"ACV-…"},"showingHintText":{…},"actions":{"before":{"jsonPreview":"[{\"id\":2,…","length":392,"omitted":136,"unit":"utf16"},…
```

同一步在基线里是：

```
fill: done; changed; focus=done, sent=false; fill=done, verification="matches", actualValue="ACV-…"
```

其它同类机制：
- settle 与 observedChange 两个变化权威并存，后者又分 windows/selection/content 三维；
- 事件头 `source{receivedClock,eventClock,types}`、`range{mode,startExclusive,endInclusive,listenedBeforeStart}`、`retained{…}`；
- 剪贴板 `read/clipboard/write/readback` 四段；
- IC 的 `attempted/callReturned`；
- 借贴收尾分列；
- 通知的“平台派发 / App 结果 / listener 清理”。

**对可用性的影响**：
1. 每一步的上下文成本被直接放大，与成对实测的 ×2–×5 一致。
2. 消费者是 LLM，它需要的是“下一步做什么”。现在它拿到的是“这些事实互相不能推出什么”，要靠它自己做反事实推理。B §8.1 已经指出这一点。
