# 专题 76：站在项目外面看整体方向

核查对象：产品 `fb75afc`（与被实测的 `a27fe5aa` 树相同），基线 `7d5be70`；独立 docs `66bb380a`。
本专题只读、无设备。自写脚本在 `S/agents9/76/`（`ctx.py`、`argv.py`、`noise.py`、`percall.py`、`opts.sh`），全部用 `python3 -I` 或 bash 运行，包内路径作参数传入。外部资料只用通用词检索公开文档，没有发送任何项目内容。

用词：**基线**是主分支 `7d5be70`；**候选**是 `fb75afc`；**调用者**是按 `skills/androidctl/*.md` 操作的 LLM agent；**回合**是执行模型发出的一次请求；**总输入**是一次任务各回合读入 token 之和（含缓存），约等于回合数乘以平均上下文；**后台屏**是候选在会话里创建的虚拟显示屏；**外来任务**是从别的屏被搬到后台屏上的 App 任务；**REF** 是观察里打印给调用者的节点引用（形如 `e784476209`）；**四道固定任务**指 Chrome 里的 GitHub 查询任务、Feeder 阅读器长列表任务、后台屏上的 Contacts 任务、Google Maps 步行路线任务；**22 案**指 11 月 10 日用基线跑的 22 个真实 App 回归案例；**报告 A／B** 指当时据同类项目写的两份改进报告。

## 1. 结论摘要

**一句话：方向没有走偏，但重心偏了——产品的骨架（语义树加结构化引用、动作前现场身份检查、如实报告"不知道是否执行"、不依赖 ADB 的 Shizuku 通道、后台屏）是对的，而且比同类工具更适合"远程操作用户真机"；偏的是最后三轮的投入方向：从"让调用者把更多真实任务做成、做便宜"，滑向"把每一个边角事实做对并证明做对"，同时证据面从 22 个真实 App 收窄到 4 道固定任务、全部在模拟器上。这个偏离是可逆的，不构成合入障碍。**

最重要的发现：

1. **原始问题与候选的对应关系松散。** 22 案报告本身的结论是"当前没有证据支持一揽子产品修复"，建议先改执行编排和证据选择（`T/../2026-11-10-current-22case-regression/deliverables/report.md` 末节）【原件】。大改的真正动机是报告 A／B 的同类项目对照，且实施方早期就定下"不以原 22 案未故障排除能力价值"（`T/decisions.md` J4）、"不机械重跑 22 案"（`T/plan.md:264`）【原件】。结果是候选从未在当初那批 22 个真实 App 上复测过；"大改解决了当初的问题"这句话目前没有直接证据，只有四道新任务的证据。
2. **测得最硬的收益，大半来自最便宜的改动。** GitHub 任务总输入 0.48 倍，其中按"指引正文字节乘以其后回合数"折算，基线每次任务被反复携带的指引约 39–65 万 token、候选约 2–3 万 token；扣掉这一项后比值约在 0.70–1.0 之间（取决于分词，4 字节一 token 时约 0.79）【重算】。网页任务另一大收益来自一个 10 行的浏览器无障碍服务（让 Chrome 交出网页树），基线读不到网页只能截图点坐标【源码】【原件】。Maps 扣除指引后仍约 0.80 倍，是产品本身的真实收益；Feeder 基本持平且端到端更慢。
3. **默认输出里仍有大块噪声，而且是调用体验上最便宜的改进。** 候选在 GitHub 任务的 CLI 标准输出里，`action-name="action-40"`／`"action-400"`／`"action-800"` 这类未命名的标准无障碍动作（无障碍焦点、HTML 元素跳转、按粒度移动）占全部字节的 30–36%，Maps 约 18%【重算 `noise.py`】。它们由 `androidctl/src/androidctl/node_facts.py:80` 对未映射动作统一打印十六进制名产生【源码】，调用者从不需要。前几轮在默认输出上花了很多精力（第四轮第 8 项、第五轮第 13 题），却没量到这一项。
4. **一项为省字节定下的规则让调用者在最常见的过期场景多付一个回合。** 第四轮第 11 项"被拒绝的动作不再重印整页"使候选在 REF 过期被拒时不附新观察；同一场景基线一次拒绝就附带了同期新树，调用者直接点新 REF【原件：`u35-c1-candidate-01` 与 `u35-c1-baseline-02` 的拒绝回执】。这是候选在调用体验上相对基线的明确退步。
5. **概念与维护面成倍增长。** 叶命令 47 到 61，选项行约 306 到 695（含 `--help` 与换行，口径粗）【实跑 `opts.sh`】；Kotlin 主源码约 9.4k 到 19.2k 行，测试约 21k 到 42k 行，跨端契约样本 175 KB 到 363 KB，反射成员名约 38 到 57 个（朴素计数）【源码】。内部设计文档的密度已接近只有作者能读。多出的部分里，有效能力（后台屏、网页内容、`find` 搜屏外、`scroll-until`、手势、预览图与标注、剪贴板）值得这个价；边角保护与事实字段（外来任务四分类与送回／丢弃、借用粘贴的恢复比对、各种 partial 原因与已执行前缀在默认文本中的展开、原因码合并）占了不成比例的认知与验证成本。
6. **前五轮评审（含评审方自己）把大量精力引向了证明体系和验收门槛。** 能力验收的三类门槛（第五轮评审已承认量错）、采集路线的四门对照实验、逐题 5 对 5 交替与 1.25 倍重跑线、每项"必须修／可选为 0"的内部评审，消耗了绝大部分时间，而上面第 3、4 条这类直接的调用体验问题一直没进入议程。真机检查又被取消，导致"远程控制用户真机"这一产品前提在两周里没有任何证据。

**是否构成合入障碍：不构成。** 候选作为产品明确优于基线（能力大幅增加、网页任务更便宜、原生任务略便宜），对外契约在 alpha 阶段可以继续调整。建议的下一步是：合入主线；合入前或合入后立刻做两处很小的调用体验修正（第 2 节缺陷 1、2）；**发布 alpha 前**补一次真机冒烟；然后停止"按决定清单逐条做到底再验收"的工作方式，改为用一批更宽、更便宜的普通任务驱动迭代（见 3.6、第 5 节）。

## 2. 确定缺陷

按对调用者的影响排序。都不是正确性缺陷，而是调用体验缺陷；所以都标"可选"，但第 1、2 条性价比极高，建议合入前做。

### 缺陷 1（可选，强烈建议）：默认观察打印未命名的标准无障碍动作，网页上约占三成字节

- 触发：任何把节点动作打印出来的默认文本观察（`snapshot`、动作后观察、`find` 祖先链）。网页节点几乎每个都带 `ACCESSIBILITY_FOCUS`(0x40)、`NEXT_HTML_ELEMENT`(0x400)、`PREVIOUS_HTML_ELEMENT`(0x800)，文本节点常带 0x100／0x200（按粒度移动）。
- 位置：`androidctl/src/androidctl/node_facts.py:80` 把不在 `ACTION_NAMES` 里的动作打印为 `action-{十六进制}`；`androidctl/src/androidctl/ui_view.py:774` 逐个输出为 `action-name="…"`【源码】。原件例：`r5-c2-final-candidate-02/evidence/cli/1795491995685053000-…/child.stdout` 首屏几乎每行都带三到五个 `action-name="action-…"`【原件】。
- 影响：GitHub 五次候选运行的 CLI 标准输出里占 30.2%–35.7%，Maps 两次抽样约 18%，Feeder 约 9%，后台屏 Contacts 约 18%【重算 `S/agents9/76/noise.py`】。这些字节随上下文被后续每个回合重复读入。`find` 的祖先链里还有大量只带这些动作、没有名字的层级（同一原件 `find` 输出连续十层 `text eNNN action-name="action-40"`）。
- 最小修正：默认文本里不打印这几类调用者不会用的标准动作（无障碍焦点及其清除、HTML 元素跳转、按粒度移动、选择清除等），`--raw`／`--json` 保留；或者给它们映射成名字后统一归入"隐藏的标准动作"。祖先链里只剩这些动作、无名字的节点可以压缩为一行省略。改动只在主机投影，契约不变。
- 把握：高（源码加原件，比例是离线重算；token 换算未做）。

### 缺陷 2（可选，建议）：REF 过期被拒时不附新观察，迫使调用者多发一次 `snapshot`

- 触发：动作参数是 REF，现场身份检查判过期而拒绝（`code=stale subject=ref`）。最常见的成因是标签随页面变化，例如 Maps 的"Walking mode:"变成"Walking mode: 18 minutes"。
- 位置：候选拒绝回执只有一行，没有观察（`u35-c1-candidate-01/evidence/cli/1795520494773501400-…/child.stdout`）；基线同一场景回执附带了动作前采到的新树，调用者在下一条命令就点了新 REF（`u35-c1-baseline-02/evidence/cli/1795521153311788600-…/child.stdout`）【原件】。来源是第四轮第 11 项第 1 条"被拒绝的动作不再重印整页"（`/home/user/androidctl/review/androidctl-r4-decisions.md` 第二节第 11 项）。
- 影响：Maps 的十次正式运行里有三次这样的拒绝，候选两次都另发了 `snapshot`（`core-results.md` 末节表）【原件，经实施方表格定位后我读了其中两条原始回执】。每多一个回合，按当时上下文约 3–5 万 token。
- 最小修正：把"不重印整页"限定在参数错误和状态错误；对"过期／已变化"这一类拒绝，附带拒绝前已采到的新观察（默认文本形状）。这是"拒绝"里唯一一类调用者下一步一定需要新树的情形。
- 把握：高。

### 缺陷 3（可选）：REF 仍是十位数字，没有做到报告 B 建议的短引用

- 现状：观察里 REF 形如 `e784476209`；指引示例写 `e15`。长 REF 在输出里约占 2–6% 字节【重算】，更主要的问题是调用者抄写长数字更易错（第四轮之前出现过把 `@` 带进参数的误用，这一点已由第五轮第 4 题宽容处理）。
- 处置：不建议现在改。短引用需要会话内编号表和"同一编号指向新节点"的防误用设计，正是候选已经有的"最近三份样本身份映射"要承担的事；在 alpha 里不值得再动一次契约。列出只是为了说明报告 B 的这一项没有落实。

除以上三条外，本专题没有发现新的确定缺陷；正确性层面的缺陷由其它专题负责。

| 会话与多设备 | 命名会话租约（同名共享、忙、到期、接管）、每次调用选一台设备 | 同左（无显示目标） | 命名会话 `-s`，空闲一小时自动关 | 选设备 | 单设备 | 单设备 |
| 后台屏／不打扰 | **有**：虚拟屏会话，主屏用户继续用 | 无 | 无头浏览器天然不打扰 | 无 | 无 | 无 |
| 文字输入 | SET_TEXT 并读回核值；按键序列；借用剪贴板粘贴并尝试恢复；密码如实报"不可核" | SET_TEXT 并核值 | 浏览器原生输入，可靠 | ADB 输入（非 ASCII 有限） | 自带输入法或 ADB | 输入法 |
| 网页内容 | Chrome 系（经浏览器服务）可读；应用内 WebView 未证实 | 读不到 | 原生 | 依 UIAutomator | 依无障碍 | 依层级 |
| 每步 token | 网页每条命令标准输出中位约 9.7 KB（其中三成是缺陷 1 的噪声），原生约 2–5 KB【重算 `percall.py`】 | 网页约 2.4 KB 但靠截图（图像输入） | 快照存文件，默认输出带快照；README 自称比 MCP 省 | 元素 JSON 较大 | 元素 JSON | 不面向 LLM |
| 安装与首次使用 | 装 host 包、导出并安装匹配 APK、装 Shizuku 并以 ADB 或无线调试启动、开 Gateway、读配对码配对；读网页再开一项无障碍 | 少最后一步 | `npm install -g` 加可选 `install --skills` | Node 加 ADB | 装 Portal 加手动开无障碍 | 装 CLI |

**真正的差异化能力**（同类里基本没有，或做得不如它）：

1. **不依赖 ADB 的 Shizuku 通道**，加 TLS 配对和证书固定——这是"在用户自己手机上、隔着网络长期使用"的前提；同类大多假设一根常驻 ADB。
2. **后台屏**：主屏用户继续用手机，agent 在虚拟屏上做事。同类里只有个别研究项目有。
3. **结构化引用加动作前现场身份检查、只在确定未派发时修复一次、UNKNOWN 永不自动重发**：在"误操作代价高（发送、支付、删除）"的真实设备场景，这是 Playwright 那套"引用失效就重拍"所不需要、而手机自动化真正需要的东西。
4. **写后读回、密码不可核的如实报告、结果不确定性分级**。
5. **语义优先、坐标有映射证据**：预览图即坐标帧、REF 标注、节点触摸前核原节点。

**明显落后的地方**：

1. **首次使用门槛高**：四到六步，涉及 Shizuku 的启动方式；读网页还要手动开一项无障碍。这是平台决定的，但指引里应当有一条"最短路径"。
2. **等待体验**：Playwright 和 Maestro 都把"等到可操作"内置在动作里；候选要求调用者显式 `wait`，并在指引里解释 idle、完整样本、业务就绪三者的区别。对 LLM 来说这是额外的判断负担。候选的 `locate` 部分弥补了这一点，但首页没有推荐它。
3. **结果模型概念多**：同类多为"成功／失败加错误文本"。候选的四态是必要的（见 3.3），但"主结果与整命令退出码分责"等第二层概念同类都没有。
4. **默认输出噪声**（缺陷 1）。

**明显过度的地方**见 3.3。

### 3.3 过度设计审查

判断标准：站在 LLM 调用者（每多一个概念就多一份误用和阅读成本）和单人维护者（每多一个状态就多一份测试、契约样本和跨端对齐）两个角度。"平台必要"指 Android 或"远程控制真实用户设备"本身带来的复杂度，不做就会误操作或说谎。

| 概念／机制 | 平台必要？ | 判断 | 建议 |
| --- | --- | --- | --- |
| 结果四态（done／failed／not sent／UNKNOWN）与 UNKNOWN 不重发 | **必要** | 真实设备上"没发出去"和"不知道发没发"必须分开，这是项目最有价值的设计，报告 B 也这样评价 | 保留 |
| 主结果与整命令退出码分责（动作成功但附件交付失败时退出码非零） | 部分必要 | 对调用者是第二层概念；同类没有。可以做成"退出码只反映主结果，交付失败写在回执里的一行警告" | 合入后可简化；不阻塞 |
| 命名会话租约（同名共享、busy、connectionBusy、到期、takeover） | 必要（设备是唯一共享资源） | 合理；同类 Playwright 也有命名会话与空闲关闭 | 保留 |
| 显示目标（`--display main／virtual` 必填、同种复用、异种须 replace） | 后台屏本身有价值；"必填"不必要 | 默认 main 即可，显式 virtual 才需要参数；必填让每个任务多一处可能出错 | 合入后改为默认 main（小改） |
| 外来任务保护（四分类、按任务编号推断来源、送回／丢弃两出路、送回失败保屏、查询失败默认不销屏） | 部分必要 | "销屏会毁掉用户界面"是真风险；但四分类和逐项送回是为一个低频情形做的完整规则。更简单：关闭时若后台屏上有非本会话打开的任务就默认拒绝，提供一个 `--force`；或者一律尝试送回 | 已做完且有测试，留着无害；**冻结**，不再加规则 |
| `--move-existing` 与落点确认里的 `unexpectedTaskMove` | 必要（否则会把用户正在用的 App 静默搬走） | 合理 | 保留 |
| 已执行前缀（fill、scroll-until 的步骤事实） | 必要（复合动作失败时调用者需要知道哪步已生效） | 合理；默认文本里只需一句"已完成第几步" | 保留，默认文本再压短 |
| partial 的各种原因、截断时的唯一性例外、`windowAbsent`、两次同类截断才失败 | 部分必要 | "partial 不能证明不存在"是必要的一句话；其余是规则细节，调用者大多用不上 | 内部保留，指引只留总则 |
| REF 过期与变化、最近三份样本身份映射 | 必要（防止点错行） | 合理；但拒绝时应附新树（缺陷 2） | 保留并改拒绝输出 |
| 保存与打印规则（按每件交付物判断保存失败） | 不必要的精细 | 对调用者只需一句"正文已打印则保存失败只是警告"；当前专题与 reference 写了一整段 | 指引压短 |
| 自身管理保护（`FLAG_SECURE`、坐标派发前查可见任务） | **必要**（安全） | 合理且便宜 | 保留 |
| 借用粘贴的恢复（比对剪贴板归属、不早于观察结束、空剪贴板准入判断） | 部分必要（不还原会改掉用户剪贴板） | 机制本身合理，但"恢复时点、准入、借写后比对"在指引里展开得太细（`input.md`） | 保留实现，指引压短 |
| 原因码体系（约 130–150 个，参数类并成 `arguments` 加字段） | 不必要的规模 | 第五轮第 15 题的合并工作量大、收益小；调用者真正分支的只有十来类 | 不再投入；未来新增一律复用已有大类 |
| 手写节点采集路线（自实现无障碍查询回调，需隐藏成员） | 有争议 | 公开路线在后台屏网页暖机后完整率 0/3 对 3/3，所以保留；但这是隐藏接口里最脆弱的一块，厂商 ROM 上风险未知 | 保留单路线；真机冒烟时重点看它 |
| 通知读（以 shell 身份登记系统通知监听、每会话登记和注销） | 能力有用（读验证码） | Android 15+ 的死亡回调和本地释放未知；可以先标"实验性" | 合入后视真机结果决定 |
| 内部 docs（`architecture.md`、`reference/ui.md` 等） | — | 密度极高，几乎每句都是实现事实，读者难以从中得到"为什么" | 不阻塞；长期应重写为面向维护者的短文 |

**如果今天从基线重新出发、只做最有价值的 30%：**

会包含（按价值排序）：

1. 首页指引压到约 6 KB，只写基本循环，专题按需读（报告 B 第 0 阶段就提过"只改 skill、零代码"）。
2. 浏览器无障碍服务（约 10 行 Kotlin 加一个 XML）和对应一句指引。
3. 默认行格式输出，过滤缺陷 1 的噪声，`find` 搜全部已采节点含屏外并给祖先。
4. 节点上限提高到 8192 并按字节预算。
5. JPEG 预览即坐标帧、REF 标注、节点触摸。
6. `scroll-until --contains`、`page-*` 方向、`reveal`。
7. 参数宽容与可照抄的报错（键名大小写、`@REF`、`open --package`）。
8. Android 14+ 下限（删旧分支，降低维护）。
9. 自身管理窗 `FLAG_SECURE`。
10. 事件唤醒的 settle；unsettled 首行提示；过期拒绝附新树。
11. 带标签的自定义动作、组合键。
12. 最小后台屏：建屏、在屏上启动、目标 App 已有任务就拒绝、关闭时有非本会话任务就默认拒绝加 `--force`。

不包含：外来任务四分类与送回、借用粘贴（先只做按键序列）、剪贴板结构化读写、多指时间线与 pinch（drag 可以留）、区域截图、通知读、原因码合并、主结果与退出码分责、手写采集路线以外的采集对照实验、每项内部评审和交替记账。

大小估计（推断，粗略）：产品源码净增约 4–6 千行（候选累计约 +16k／−3k 行源码），测试约同量；指引约 40 KB。按上一节的成本拆分，这 30% 大概能拿到现有测得收益的八成以上：GitHub 的收益主要来自第 1、2、3 项，Maps 的收益主要来自第 3、5、6 项。

**与现在的候选比较，多出的 70% 分三类：**

- **已做完、稳定、留着无害**：剪贴板、drag／pinch／时间线、区域截图、带标签动作、range、select、`--move-existing` 与落点确认、事件唤醒、自身保护。它们各自有测试，与主循环耦合低，调用者不用就不付成本（只付指引里一行索引）。
- **会持续产生维护和认知成本，但删掉要再走一轮评审，不值得在合入前删**：外来任务四分类与送回／丢弃、借用粘贴恢复规则、主结果与退出码分责、按件保存规则、截断唯一性例外、原因码字段。建议**冻结**：不再加规则；指引压到一句总则；以后只在真实任务里出问题时才动。
- **值得在合入前处理的**：只有缺陷 1、2 两处，都是删减或放宽，不增加概念。

我不建议在合入前删除任何一整块。理由：删一整块要重做跨端契约样本、测试和指引，再走一轮评审，按这个项目的节奏是一到两周；而这些块不在主循环上，对调用者的直接成本很小。

### 3.5 四道固定任务之外：我们不知道的边界

| --- | --- | --- | --- |

### 3.6 三个问题

**问题一：整体方案走偏了吗？**
结论：**骨架没有偏，重心偏了，而且可逆。**
理由：候选保留并加强了这个项目在同类里最有价值的部分（不依赖 ADB、语义优先、结构化引用与身份检查、如实的不确定性），并补上了同类里罕见的后台屏和网页内容。偏的是投入：后三轮的绝大部分时间花在为已选能力配齐边角规则、证明它们满足门槛、以及成本记账上；调用体验上最直接的问题（缺陷 1、2）和最大的证据空白（真机、更广的 App）没有被当作优先事项。可逆是因为多出来的部分大多在主循环之外，可以冻结、压缩指引而不必拆代码。
把握：中高（来自源码、原件和重算；对"偏离的代价"的量化是推断）。

**问题二：候选相对基线，是一个更好的产品吗？**
结论：**是，但更好的主要是能力和网页成本，维护成本明显变差。**

- **能力**：明显更好。后台屏、网页内容、屏外搜索、滚动查找、多种手势、预览图与标注、剪贴板、组合键、带标签动作；删掉的 editor 通道、通知写、batch、差异输出都是用户裁决过的取舍。把握高。
- **调用成本**：网页任务明显更好（0.48 倍，其中大半来自指引精简，另一大块来自网页可读）；原生任务小幅更好（Maps 约 0.75，扣指引后约 0.80；Feeder 约 0.96 且端到端时间更长）。样本是每边 5 次、四道任务、单一模型。把握中。
- **可预期性**：持平偏好。更多事实被如实写出（unsettled 首行、读回不同时报 UNKNOWN 附实际值、落点确认），但调用者要掌握的拒绝类型也更多（显示目标、外来任务拦截、截断例外、REF 过期不附树）。没有直接测量误操作率；实施方的 35 次计分记录里没有报告误操作（我没有逐条核对），而且这个样本太小，不能当证据。把握低到中。
- **维护成本**：明显更差。主源码约翻倍、测试翻倍、契约样本翻倍、反射成员增加约一半，内部文档难读。对一个人维护的 alpha，这是最大的长期负担。把握高（静态计数），影响程度是推断。

**问题三：用户接下来最该做的一件事是什么？**
结论：**合入主线，但换一种工作方式——停止按清单逐条打磨和验收，改为用更宽、更便宜的真实使用驱动。**
具体：

1. 合入前（或合入后第一件事）做缺陷 1、2，都是半天量级的主机侧改动加测试；不再要求 5 对 5 复测，跑一次 GitHub 和一次 Maps 看输出形状即可。
2. 发布 alpha 前，在一台真机（最好一台国产 ROM）上跑一遍基本循环、后台屏和网页读取的冒烟。这是第一个真正可能改变"能不能发"的事实（见第 6 节）。
3. 之后的迭代：从 22 案里挑 8–10 个不同形态的任务（中文 App、表单、聊天草稿不发送、设置开关、长任务），只跑候选、每题 1–2 次，看失败形态而不是算中位数比值；只修真实暴露的问题。
4. 冻结 3.3 表里"冻结"一栏的机制，不再为它们新增规则或门槛。

不建议"合入但先删掉某几块"：删块的收益不足以抵消再一轮契约和评审的代价（3.3 末段）。也不建议继续在隔离分支上打磨：分支与主线的长期分叉本身就是维护成本，而且现在的打磨方式边际收益已经很低。
把握：中。

### 3.7 前五轮评审（含用户裁决）在方向上带偏的地方

如实列出，按影响排序。"源头"指提出该做法的一方。

1. **能力验收三门槛（第四轮第 6 项：回合数少三成、非它不可、至少一题只有用了才答对）。** 源头：评审方作为候选项提出，用户选定。第五轮评审自己承认"有两条按算术或按构造就不可能通过"，消耗 34 次正式模型运行、约 1,500 条设备命令、18 份专门文档（`androidctl-r5-candidate-review-cab84b8.md` §1.1 第 4 条）。第五轮第 3 题改成冒烟，是正确的纠偏，但两周里最贵的一段已经花掉了。
2. **采集路线的四门对照（第四轮第 7 项、第五轮第 8 题）。** 源头：评审方提出把公开路线作为删除隐藏接口的条件，用户定门槛。结果是做了一次完整移植、Studio 暖机实验和数据整理，最终保留原路线。对"是否保留隐藏接口"这个问题，一次真机冒烟（看手写路线在厂商 ROM 上是否还能用）比模拟器上的四门对照更有判别力，但真机检查随后被取消。
3. **逐题 5 对 5 交替、1.25 倍重跑线、环境失败只重试一次（第四轮第 18、19 项，第五轮第 9–11 题）。** 源头：评审方提出、用户选定。它把成本问题变成了统计记账问题：Maps 一题为了凑齐 5 对 5，又引出 System UI 无响应诊断、新建模拟器、调内存和关虚拟机（U35 及其后的环境消息）。而按 3.1 的拆分，最大的成本因素（指引携带）用一次离线计算就能看清，不需要这么多次运行。
4. **第五轮第 1 题的搬屏检测方案 D。** 源头：评审方在决定文件里写到了按任务编号分四类、两条出路、送回失败保屏、查询失败默认拦截的完整规则。这是为一个低频情形写的完整规格；实施方按字面落实，产生了 `DisplayTasks`／`TargetManagement` 一整块。更简单的"默认拒绝加强制"就能覆盖主要风险。
5. **第五轮第 15 题原因码合并、第 13 题自定义动作标签边界、第 17 题截断唯一性例外、第 6 题换行装饰与占位提示规则。** 源头：评审方。各自都对，但都是边角；同期，同一份默认输出里占三成字节的噪声（缺陷 1）没有被任何一轮量到。这说明前几轮看输出时是按"字段是否完整、是否矛盾"看的，而不是按"调用者实际读了什么"看的。
6. **第四轮第 11 项"被拒绝的动作不再重印整页"。** 源头：评审方。直接导致缺陷 2。
7. **第四轮第 22 项及第五轮第 16 题的过程规格（每项完整行为由新上下文独立评审、必须修／可选计数）。** 源头：评审方与用户共同。结果是大量"必须修 0／可选 0"的内部评审文档和 286 KB 的决策流水。它保证了不说谎，但也把实施方锁在"每一项都要闭环"的节奏里——这正是用户说的"钻牛角尖"的制度来源之一。
8. **用户 U35 取消真机检查。** 方向上恰好相反：这是最该保留的一项检查。它的代价是一次真机冒烟，收益是对产品前提的第一份证据。建议在发布（不是合入）前恢复。
9. **早期定下"不以原 22 案未故障排除能力价值"、"不机械重跑 22 案"（实施方决策 J4、计划第 264 行）。** 源头：实施方，评审方前几轮没有质疑。它让大改脱离了最初的问题锚，后来所有验收都在新选的四道任务上进行。

反过来，前几轮里**把方向拉回来的**决定也应记下：第三轮评审指出"最该优先的事（紧凑正文、`find`、首页指引）被排在最后"并要求先做，这几项正是后来测得收益的主要来源；第五轮删除 batch、删除坐标 UID 预测与 `--expect`、参数宽容、取消三门槛，都是减法和纠偏。

## 5. 需要用户裁决的新取舍

### 5.1 下一步工作方式

- A：合入主线，修缺陷 1、2，发布前补一次真机冒烟；之后用更宽的真实任务（每题 1–2 次，只跑候选）驱动迭代，不再设比值门槛。**推荐。**得：尽快结束分叉，把精力转到调用体验和覆盖面。失：失去统计意义上的成本对照，改为看失败形态。
- B：合入前先删外来任务四分类、借用粘贴恢复、退出码分责等块。得：维护面变小。失：再一轮契约、测试、评审，一到两周；收益主要是长期的。
- C：继续在分支上按现有方式打磨，下一轮再评。不推荐：边际收益已很低。
- D：先只做真机冒烟，再决定是否合入。可以接受，但真机结果大概率只影响"能否发布"而不影响"是否合入"。

剩余未知：真机结果；更宽任务上的失败形态。

### 5.2 拒绝时是否附新观察（缺陷 2 涉及改第四轮第 11 项）

- A：过期／已变化类拒绝附新观察，其余拒绝不附。**推荐。**
- B：维持现状。
这是对外行为变化，需要用户点头；实现由实施方定。

### 5.3 真机检查是否恢复为发布前条件

- A：恢复为**发布 alpha 前**的一次冒烟（不是合入条件）。**推荐。**
- B：维持 U35 的取消。代价：alpha 用户成为第一批真机测试者，后台屏和隐藏接口在厂商 ROM 上的失败会直接暴露给他们。

缺陷 1 的输出过滤不改对外契约（`--raw`／`--json` 不变），可以作为实施细节，由实施方直接做。

## 6. 有判别价值的补验

1. **一台真机（最好国产 ROM）冒烟**：基本循环、网页读取、后台屏建屏与关闭、一次坐标点击、通知读。若后台屏或手写采集回调在真机上不可用，"后台屏作为正式能力"和"保留手写采集路线"两个取舍都要重议；若全部可用，产品前提第一次有了证据。
2. **缺陷 1 修正后的离线重放**：用现有 GitHub 原件重算默认输出字节。若减少接近三成，就说明默认输出上还有比前几轮已做的更大的空间，值得再看一遍"调用者实际读了什么"。
3. **从 22 案挑 8–10 题只跑候选**：若出现与 22 案相同的失败形态（语义点击不导航、滚动不推进、fill 读回不同），说明原始问题没有真正解决，下一轮应围绕它们而不是新能力；若大多通过，"大改解决了原始问题"才有直接证据。

不建议补更多 5 对 5 的成本对照：它不会改变合入判断。

## 7. 没能核实的内容

- 外部工具的维度对照只来自公开文档与目录站点，没有运行；命令数、等待语义可能随版本变化。来源：[Playwright CLI 简介](https://playwright.dev/agent-cli/introduction)、[Playwright CLI README](https://raw.githubusercontent.com/microsoft/playwright-cli/main/README.md)、[Playwright MCP](https://playwright.dev/mcp/introduction)、[mobile-mcp](https://github.com/mobile-next/mobile-mcp)、[DroidRun Portal 文档](https://docs.droidrun.ai/v1/concepts/portal-app)、[Maestro 等待命令](https://docs.maestro.dev/maestro-flows/flow-control-and-logic/wait-commands)。uiautomator2、Appium、scrcpy 没有单独查，按一般知识只作背景，未写入表格。
- 指引携带的 token 折算用了"约 4 字节一 token"的假设；实际分词器未知（实施方也因此把比例报为 N/A）。我给了 3–5 字节的区间。GitHub 扣除后的比值对这个假设敏感（0.70–1.0），Maps 不敏感（约 0.80）。Feeder 未做扣除。
- "30% 方案"的规模和收益占比是推断，没有实现或测量。
- 选项计数是对 `--help` 文本的粗略行计数，包含 `--help` 和换行，只用于看量级；原因码与反射成员是朴素 grep 计数，与第五轮评审的口径不同。
- `covered` 提示把点击引到弹窗下面的旧缺陷是否在候选中彻底消除，我没有逐行复核。
- 应用内 WebView 在浏览器服务开启后是否交出树、后台屏上系统弹窗和输入法的行为，均【需设备】。
- 所有设备结论只来自实施方在模拟器上的原件；真机与厂商 ROM 没有任何证据。
