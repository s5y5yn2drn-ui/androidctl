## 结论（先读这里）

1. **确定缺陷：滚动查找第一步就"没有可用方向"时，回执说"容器已到末端"，还把正确方向的建议删掉了。** 位置在 `K/ScrollProgress.kt:138-150`（`routeEnded`）。条件只看原因码，不看已经滚了几步。于是在横向容器上写 `down`、容器只公布另一轴的方向、或者"一行多列"被排除了形状映射时，0 步就停，并报 `After scrolling 0 steps, the container is at its end`。原来那句"当前可用方向……用 forward"连同 `error.message` 一起被覆盖。测试 `UiScrollUntilTest.aMissingRouteStops…` 在 `completed=0` 的情形下断言的正是这个错误文案，契约样本只有已滚 1 步的样例。修法：只在 `completedSteps > 0` 时用"到末端"的说法，约 1 行，再改一条断言。
2. **确定的误拒（实测）：名字随时间变化的节点，按引用永远操作不了。** 新十题第 1 题第 15 条：`click e241549385`，目标是计时器项，名字 `"29:23"`，带 `+click="Pause"`。被拒为 `stale`，原因是 `No current target matches the original ref signature`。附上的新树里它已经叫 `"29:17"`，引用也换成了 `e241549386`；下一份样本里又换成 `e241549387`。原因有两条：身份里含名字（`K/UiSemantics.kt:321-335`），修复规定"两个名字都非空而且不同就排除"（`K/UiRefRepair.kt:94`）。模型最后改点页面上的 `Stop` 才完成。任何读数、倒计时、"N 分钟前"之类的节点都是同样的情形。这需要用户取舍，见第 3.2 节。
3. **潜在误操作（源码推断，没有实例）：修复在名字相同的多个控件之间，只凭"位置靠近旧位置"就选定一个。** 打分里不比较行列位置链，也不比较来源节点编号。两个以上候选同分时，"边界相差不超过 8 像素"的那 +2 分正好达到最小领先分 2。所以，如果几张卡片里同名同 ID 的"Edit"按钮被重建，同时上方插进一张卡片，修复会选中现在占着旧位置的另一张卡片的按钮，并且派发出去。`repair_port.py` 推演的得分是 `[23, 21, 21, 21]`，选中的是 card A，不是原来的 card B。建议：领先只来自位置分时，按"有歧义"拒绝。代价很低，因为本轮被拒时已经附上新树。
4. **确定缺陷（小）：`wait` 在采样已于截止前到手、条件也已命中的情况下，仍可能报失败。** 位置在 `K/UiCondition.kt:452-455`。评估结束时如果预算刚好归零，回执写 `cutoffStage=evaluation` 和 "Condition was not observed within the request budget"，而 `predicate` 里同时带着 `matchedText`、`refs` 和 `matchedIndex`，前后矛盾。这和"截止后才完成的采样不评估"那条决定不是一回事：这份采样是在截止前完成的。建议：已经命中就报完成。
5. **改名提示删干净了。** `nameChange` 在产品仓库的源码、测试、契约样本、码表和指引里都没有剩余；独立 docs 仓库里只剩开发记录 `development.md:66` 一句历史说明。`freshRepair` 的设备端、主机端和指引三处一致。正式尝试里共有 3 次旧引用被拒并附新树，其中 2 次模型直接用了新树里的引用，省掉了一次 `snapshot`。

## 二、身份规则一共几层，职责是否单一

| 层 | 位置 | 职责 |
|---|---|---|
| 1 编号沿用 | `UiRefs.replace` | 身份键相同就沿用旧编号，否则新发；同时判定"引用是否可用" |
| 2 交付裁剪 | `UiTreeBudget.fit`、`UiSnapshot.assemble:39-43` | 被 8 MiB 上限裁掉的节点不进目标表 |
| 3 当前样本查找 | `UiSnapshot.target` | 只认最新一份样本 |
| 4 现场复核 | `FreshNodes` 加 `requireOriginalIdentity` | 窗口、根地址（区间设置、滚动查找、坐标输入才检查）、刷新、身份六项相等；写值之后允许名字变化 |
| 5 修复 | `UiRefRepair.select` | 按名字、ID、类名、行标签、动作、位置打分 |
| 6 交付标记 | `freshRepair` | 只决定交付方式，不参与判断 |

- 第 1 到 4 层用的是同一个身份键（`UiSemantics.identity`），没有互相打架。`ScrollContainer.kt:17` 在已经检查"引用可用"之后，又判断一次 `identity == null`。前者已经蕴含后者，这是一处多余的判断，可删可不删。
- **第 5 层与其他层用的证据不同。** 它不看来源节点编号和行列链，看的是名字、ID、行标签和位置。这本来就是它的用途：原节点被重建以后，编号和链已经不可信。问题出在：链明明可以区分"同名不同行"，打分却把位置当成了决定性证据（见第 3.3 节）。
- **"名称变化"那一层已经删干净。** `git diff f401deb HEAD` 显示删掉了 `UiRefRepair.nameChange`、它的测试和执行测试里的断言（执行测试改成断言 `freshRepair`）。全仓库搜 `nameChange`、`oldName`、`newName`，产品仓库零处；docs 仓库只剩 `development.md:66` 的变更记录。第一次尝试留下的 `resolved`/`selected` 在修复选人失败时仍然保留，表示第一次尝试的目标，含义正确。

## 三、发现

### 3.1 确定缺陷：滚动查找第 0 步没有方向时误报"到末端"，并删掉了方向建议

- **位置**：`K/ScrollProgress.kt:138-150`；测试 `android/app/src/test/.../UiScrollUntilTest.kt` 新增的 `aMissingRouteStops…`，循环里 `completed` 取 0 和 1。
- **触发条件**：`scroll-until REF DIR` 的第一步在 `awaitAction` 里抛出 `routeUnavailable`（`K/UiActions.kt:1047-1049`），即目标可见、可用，但没有这个方向。典型情形有三种：横向容器上写了 `down`；"一行多列"的容器被排除了形状映射（第七轮第 10 项落实时要求"回执建议 forward"）；容器已经在这一方向的尽头。
- **可观察的错误**：首行写 `After scrolling 0 steps, the container is at its end; no target matched`。前两种情形下这句话是假的。原来的 `error.message`，也就是 `directionAdvice` 给出的"当前可用方向：……；用 androidctl scroll … forward"，被 `put("message", reason)` 覆盖了。普通的 `scroll` 仍然给出方向，所以同一件事在两个命令里说法不同。指引 `actions.md:65-66` 写着"没有当前路线时立即拒绝，并给出可用方向"，`scroll-until` 不符合。
- **实测**：正式尝试里只出现过已滚 30 步的那一次（`EV/efficiency/r7-c2-candidate-02` 第 7 条），那次文案是对的。第 0 步的情形没有出现过。
- **建议**：把判断改成 `routeEnded = !pending && code == "routeUnavailable" && completedSteps > 0`，测试里 `completed=0` 的那一分支改成断言保留方向建议。代价约 3 行。需设备：横向列表上跑一次 `scroll-until … down`。

### 3.2 设计取舍（有实测）：名字会变的节点按引用永远操作不了

- **证据**：新十题第 1 题第 14、15、16 条的首行和正文（`EV/efficiency/r7-new-01/evidence/cli/…`）。三份样本里，同一个计时器项的引用依次是 `e241549385`、`e241549386`、`e241549387`，名字分别是 `29:23`、`29:17`、`29:15`。模型的最终答复写的是"首次点击动态读数的 Pause 因 REF 已变化被拒绝……随后使用页面 Stop 按钮成功暂停"。
- **机制**：
  - 编号层：名字变了，就是新身份，发新编号。
  - 复核层：名字不等，报"选择已变化"。
  - 修复层：两个名字都非空而且不同，直接排除这个候选（`K/UiRefRepair.kt:94`）。
  - 附新树也救不了：调用者拿到新引用、再发命令，这中间名字又变了。
  - 按名字选择（`click --name`）同样要求名字相同。
  - 唯一的出路是改点别的控件，或者用坐标触摸。
- **以往决定的关系**：第七轮第 11 项删除改名提示时，依据的是步行标签页这个场景；那里名字只变一次，附新树就够了。名字持续变化的情形当时没有讨论。
- **可选做法**：
  - A. 保持现状，在指引里补一句："名字是计时读数一类的节点，按引用会过期，改用它的父节点或同行的按钮。" 零代码，每次多 1 次调用；没有替代控件时做不了。
  - B. 修复时允许名字变化，条件是：窗口、来源节点编号、角色、行列链全部相同，而且候选唯一。好处是计时器、步行标签页这类节点都能直接修复。代价约 10 行，另加测试。风险是列表复用视图时内容会换掉，但那种情况下行列链也会跟着变，所以有保护；不在列表里的节点没有这层保护，复用的情形较少。
  - C. 身份里不比较"名字"，只比较其余五项，名字只作为修复的打分证据。改动大，会改变全部引用的沿用行为，不推荐。
- **推荐**：B，并在设备上验证一次计时器和步行标签页。证据有限（48 次尝试里明确出现 1 次），用户也可以选 A。

### 3.3 潜在误操作（源码推断）：修复靠位置分在同名控件之间选边

- **位置**：`K/UiRefRepair.kt:73-114`。
- **触发条件**，四条同时成立：
  1. 原节点被重建，刷新失败，或者复核报身份无法确认；
  2. 新树完整；
  3. 新树里有两个以上同名、同 ID、同类名的控件，而且行标签都为空：控件不在列表里，或者在列表里但这一行没有可读的文字；
  4. 版面发生了平移。
- **可观察的错误**：这些候选的分数相同，只有落在旧位置的那一个多 2 分，正好达到最小领先分 2，于是被选中并派发。`repair_port.py` 用逐行移植的打分推演：原目标是 card B 的 Edit，在顶部插入一张卡片之后，选中的是 card A 的 Edit，得分 `[23, 21, 21, 21]`。
- **测试为什么没发现**：保存的 21 个候选池（`ref-repair-pools.json`）里，同名的只有两组，都是"有行标签、可以区分"的情形，没有"同名而且无行标签"的情形。
- **建议**：最佳候选的领先如果只来自位置分，就报"有歧义"（按 `UiSelector.ambiguity` 列出候选）。代价约 5 行，加 1 个池样例。本轮被拒时已经附上新树，所以多拒一次只多花 1 次调用，而误操作是不可撤回的。
- **真实频率**：48 次尝试里，修复成功只有 1 次，所以把这条判据收紧，代价很小。

### 3.4 确定缺陷（小）：条件已命中却报失败

- **位置**：`K/UiCondition.kt:443-455`。采样到达时预算还没用完（`:419` 的检查通过了），评估之后、`:452` 再检查时预算归零：`predicate` 设成命中者的谓词，带 `matchedIndex`、`matchedText` 和 `refs`，而结果是失败，原因写"在时限内没有观察到"，`cutoffStage` 是 `evaluation`。
- **影响**：回执自相矛盾；调用者可能拉长时限重试，或者误以为页面上没有。出现的时间窗口只有一次评估的耗时（大树上是几十毫秒级），所以很少见。设备端的平台截止比回复截止提前最多 0.5 秒（`K/UiBudget.kt:24`），这时直接报完成，时间是够的。
- **建议**：`winner >= 0` 时直接返回完成，`:452` 只保留给没有命中的情形。代价约 2 行。这不违反"截止后才完成的采样不评估"那条决定：这份采样是在截止前完成的。

### 3.5 "连续两次截断就提前失败"的计数

- **已核实正确的部分**：
  - 计数只对"等待消失"和"等待空闲"生效。
  - 采集失败、窗口缺席、范围不明都会清零（`observationFailed` 里的 `:510`；窗口缺席的样本 `limits` 为空，`:465` 会覆盖成空）。所以中间夹着别的失败时，不会把不相邻的两次截断凑成"连续"。
  - 只有采集截在 3 秒上限上时才算采集时限截断（`collectionCutoff=sampleLimit`，`K/UiBudget.kt:73-80`、`K/UiBackend.kt:411-414`、`K/UiCondition.kt:474-478`）；截在命令时限上的不算。这与第七轮第 16 项一致。
  - 默认 5 秒时：第一份采样截在 3 秒上限上；第二份截在 4.5 秒的平台截止上，到手时预算已经为零，走"未观察到"那一路，原因末尾补上"树按单次采集时限截断；证明不了不存在或空闲；请改用正向条件"（`:528-534`）。`sampleLimitObserved` 不会被清零，所以这句原因留得到最后一份回执。这与第七轮第 10 问选 A 的要求一致。
- **小问题（可选）**：判断"连续"要求两次截断的原因集合完全相同（`:464`）。接近 8192 个节点的页面上，一次截在节点数上、一次截在时间上，两者都是截断，却永远凑不成"连续"。指引写的也是"same … limit"，与代码一致，所以只算设计取舍。可以改成"两次都非空"，1 行。证据：没有实例。

### 3.6 方向词映射："一行多列只否决按形状判断的那一路"

- `K/UiScroll.kt:62-68` 按第七轮第 6 节第 1 处的要求实现：
  - 列数等于 1、`ScrollView`、`GridView` 这三种情形先返回，"一行多列"不影响它们；
  - 行数或列数为负数（未知）、为 0、没有列表信息时，仍按形状判断；
  - 平台明确公布的方向动作和 `ViewPager` 的左右映射不受影响。
  - 测试覆盖了这几种情形。
- **反例检查**：
  1. 只有一项的横向 RecyclerView，报 `rows=1, columns=1`，会被当成竖向。但它不能滚动，不会公布"向前"，所以无害。
  2. Compose 的 `LazyRow` 报列数 `-1`，按规则仍按形状判断。它一般宽大于高，不会被映射。全屏高、只公布前后方向的横向翻页仍有风险，这是第七轮已经登记的已知风险，没有新证据。
  3. 正式尝试里，Maps 的标签栏是 `rows=1 columns=5` 并公布 `right`，直接走明确公布的方向，不需要这条否决（路线题第 3 次第 4 条的正文）。
- **结论**：没有找到新的反例。剩下的风险就是第七轮登记的那两类：没有列表信息的横向容器、多行多列的横向网格。

### 3.7 修复时新采失败，原来的拒绝原因被覆盖（可选）

`perform` 里新采一次（`capture`）如果抛出异常（例如时限用完），外层 `run.failure(error)` 会把第一次"未发出"回执里的原因和错误码换成采集失败的原因（`K/UiRun.kt:145-153`）。调用者看到的是 `snapshotBudget`，看不到"引用已变化"。影响是多一次重试。可以在原因里把两者都保留。代价约 3 行。

## 五、重复机制与可删、可合并之处

- `ScrollContainer.kt:17` 的 `identity == null` 判断多余。
- 修复的打分（第 3.3 节）是这条链上唯一需要维护"权重"的地方。正式尝试里成功 1 次、失败 3 次；本轮又有了"拒绝时附新树"。如果用户愿意，可以讨论把修复收窄成"唯一同名、同 ID"的精确匹配，删掉位置分和动作分。能力代价是：同名控件被重建时，从自动修复退回成拒绝加新树，多花 1 次调用。属于设计意见。

## 六、本轮差量：链变简单了还是变复杂了

- **变简单的**：删掉改名提示（约 30 行设备端代码、一个字段、一条主机端渲染分支）；主机端 `--all` 的参数从投影函数里移除（`compact_actions` 和 `attributes` 都不再接 `all_nodes`）。
