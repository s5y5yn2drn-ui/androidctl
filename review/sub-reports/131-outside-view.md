# 任务 131：局外人看方向（第八轮，候选 `409e853`）

## 结论（先读这十行）

1. 产品的核心循环（snapshot → 引用 → click/fill → 带回新界面树）是成立的，而且对模型好用：8 次原始会话里模型几乎从不迷路，读完首页就能动手。908 条候选命令里 click、snapshot、fill、back、scroll 五个命令占 86%；find 和 wait 各只用了 2 次，locate、action、range、select、reveal、tap、shell、push、pull、clipboard 都是 0 次。
2. 新十题 18 次尝试只成功 3 次，但多数失败**不是工具造成的**：两题是网站挡住了（TfL 验证页、Gutenberg 维护），两题是 App 没有题面要求的界面（Files 的分享直接跳进 Messaging，Collabora 没有 Share），一题是 Collabora 自己写回了源文件，一题是空的联系人列表没有搜索入口，一题是模型没读页尾的"最后编辑"日期。题面本身每题有八到十二个检查点，很多是在考 App 的怪癖。
3. 真正归因于工具、并且反复出现的问题只有三个，**都不在这两轮打磨的清单里**：(a) Chrome 地址栏 `fill --submit` 在新十题的 7 次 Chrome 尝试里 7 次返回 UNKNOWN（退出码 3），每次多花两三轮；(b) 系统设置开关 `check/uncheck` 因为窗口重建而 3/3 返回 UNKNOWN，加上首页那句"Stop after another UNKNOWN"，导致 07 题两次都没做完；(c) 33% 的动作回执是"页面可能还在变化"，其后跟了 101 次补救的 `snapshot`。
4. 成本主要由回合数乘以累积的上下文决定。长网页的每个动作都把整棵树（31 到 35 KB）打印进上下文，新 04 题仅 CLI 输出就有 223 KB。降成本最有效的几件事是：动作回执少打印、等页面稳定、少一轮补救。继续抠首行字段已经省不出多少。
5. 复杂度与能力不相称：主机端加设备端约 3.2 万行，测试约 4.66 万行，共享契约 371 KB，原因码 150 个，指引约 1.1 万词。支撑的却主要是五个命令。大部分复杂度花在区分"失败到底是哪一种"上，而真实会话里模型在这些区分上的决策几乎都是"再 snapshot 一次"。
6. 过程上：七轮下来，评审方和用户裁决都在越来越细的局部（回执字段、原因码、读法编号）上加码，而决定能否完成任务的三件事（上面第 3 条）没有被测到、也没有被列项。固定四题已经连续多轮 20/20，分不出好坏；新题题面又过严，失败信号大多是噪声。
7. 我的建议：**现在就合入主线**，先补做那一次一直没做的真机冒烟（它是发布条件，真机证据至今为零），然后以 0.4.0 预览版发布，让真实使用来驱动后续改进。接下来两周只修第 3 条的三件事，加上减小动作回执，不再做同样形式的第九轮。

## 1. 第一印象（像一个新用户那样读）

**依据**：读了 `S/r8/prod/README.md`、`skills/androidctl/SKILL.md`、`observations.md`、`actions.md`；运行了 `S/r8/venv8/bin/androidctl --help` 以及 `snapshot`、`find`、`click`、`fill`、`wait`、`scroll-until`、`open`、`screenshot` 的 `--help`（主机端实际运行）。

- **心智模型清楚的部分**：命令面很像 Playwright CLI，`--help` 的命令列表整洁，每个动作命令的参数一致（REF 或 `--role/--name/--text/--id`，加 `--timeout/--settle/--screenshot`）。SKILL 第 46 到 54 行那段"常用循环"九条命令，加上一行节点格式的说明（`button e15 "Pay & finish" clickable`），足够让一个模型完成"打开某 App，找到某内容，点进去，读出来"这类任务。原始会话也证实了这一点：模型读完首页后，第一条设备命令就是正确的 snapshot 或 open（例如 `EV/efficiency/r7-new-01/native.rollout.jsonl` 第 22 号以后的调用）。
- **让人费解或显得过度的部分**：
  - README 的"Setup"一节里夹着与安装无关的段落，例如 UTF-16 选区、借用剪贴板、管理界面对截图隐藏、`--windows ID` 的采集预算（README 第 103 到 119 行）。新用户读到这里会以为这些是必须理解的概念。
  - SKILL 的"Start A Task"一节有 8 条后台屏和任务保护的规则（第 26 到 33 行），而绝大多数任务用主屏。这些规则应该放进 displays 专题，首页留一行指针即可。
  - `observations.md` 和 `actions.md` 读起来像法律条文：几乎每句话都在说"什么不能证明什么"（例如"Unchanged observations do not prove nothing happened between them; changes do not prove causality or business readiness"）。这对模型的决策几乎没有增量，却每读一次花两到四千 token。原始会话里有好几次模型在出问题后去读这些专题（r7-new-04 第 51、158 号；r7-new-10 第 42、79 号），读完之后的下一步仍然是 snapshot 或截图，读专题没有改变它的决策。
  - 首行字段密度过高。一个 `check: UNKNOWN` 的首行有约 1,300 个字符（`EV/efficiency/r7-new-07`，第 79 号输出），里面同时有 `change=…`、`selection unknown`、`content unknown`、`original target unknown`、`rootUnavailableObserved`、`rootRecoveredWithinRequest`、`verificationError`、`snapshotProblem={…}`。模型实际只用了最后一句"Do not repeat automatically; first check the effect"。
  - 每个回执都有 `androidctl capture=…` 和 `edge-windows count=2 content="notRead" windows=[…]` 两行，内容在一次任务里基本不变（实测，所有 8 次会话都是这样）。

### 2.2 横向统计（实测，全部候选与新题尝试共 908 条命令）

- **命令分布**：click 346、snapshot 209、fill 92、back 71、scroll 63、scroll-until 27、open 17、recents 15，其余合计不到 80。
- **补救 snapshot**：625 个动作里 206 个（33%）的回执是 unsettled 或 loading；紧跟其后的非缓存 snapshot 有 101 次，是所有 snapshot 里最大的一类。只有 46 次 snapshot 跟在"已稳定"的动作之后。`wait` 只被用了 2 次，说明模型宁可直接再 snapshot 也不去等。
- **非"完成"结果**：新十题里 7 次 Chrome 尝试（04、04 重试、08、08 重试、09、09 重试、10）全部在地址栏 `fill --submit` 上得到 UNKNOWN；07 的三次 `check/uncheck` 全是 UNKNOWN；其余拒绝基本是旧引用（`stale`），都在一条命令内恢复。
- **成本结构**：每次尝试的缓存命中约 95%；未缓存输入加输出每次只有 1 到 8 万 token。总输入约等于回合数乘以累积上下文，所以多一轮的代价随任务进展越来越大，大页面打印进上下文的代价会在之后的每一轮重复付。

### 2.3 与同类工具相比

这是设计意见，依据是我对这些工具的一般了解，这次没有运行它们。

- **强项**：
  - 不需要 root，日常使用不需要 ADB，走 Shizuku 加网络。在面向 agent 的工具里少见，部署门槛低。
  - 引用加界面树的格式与 Playwright MCP 的 aria snapshot 同一路数，比 uiautomator2 和 Appium 的 XML dump 紧凑得多，也比 mobile-mcp 那种坐标加元素列表更适合直接点。
  - 动作前的身份核对、"未发出"与"结果未知"的区分、旧引用被干净地拒绝，比 Appium 和 uiautomator2 更安全，实测没有误点。
  - Chrome 网页内容可读，这是 mobile-mcp 和多数 uiautomator 系工具做不好的。
  - 后台虚拟屏、`scroll-until`、`find` 搜索屏外内容，都是 Maestro 和 mobile-mcp 没有的。
- **短板**：
  - **动作后的等待**。Playwright 的动作自带"等到可操作和导航完成"，Maestro 每步自动等稳定；这里三分之一的动作把"还在变"交回给模型，由它自己补一轮。
  - **复合状态变化被报成 UNKNOWN**。地址栏换节点、开关触发窗口重建，这些在 Android 上很常见；Maestro 和 uiautomator2 会简单地报完成或重找，这里报 UNKNOWN、退出码 3，再加上指引里的"停手"规则，代价比误报还大。
  - **网页大树的输出量**。Playwright MCP 也有大页面的问题，但它常见的用法是只打印增量或可交互节点；这里默认打印完整树，阈值是 64 KiB。
  - **规则文字量**：Playwright CLI 和 Maestro 的指引都以示例为主，这里约 1.1 万词，大半是限定语。

## 4. 五个问题

### 4.1 最影响"agent 能不能完成任务"的三件事

1. **动作把常见的状态变化报成 UNKNOWN**（确定缺陷，实测）。Chrome 地址栏 `fill --submit` 7/7；设置开关 `check/uncheck` 3/3（r7-new-07 第 75、150 号；07 重试一次）。原因看起来是：被填的节点或开关所在的窗口在动作期间被替换或重建，原对象就读不回来了（源码推断，需设备确认具体机制）。业务上这些动作大多已经成功，后来的 snapshot 都读到了预期值。它会直接导致任务失败，是因为下面第 2 条。
2. **指引里的"安全优先"规则压过了完成任务**（确定缺陷，实测）。正式实测用的首页写的是"Stop after another UNKNOWN"，07 两次都因此停手。`409e853` 把它改成"If a retry is also UNKNOWN, stop retrying that action"，方向对，但**没有重新实测**，不能说已经有效。同一节里"Continue on reliable business success"和停手规则的先后关系，模型读不出来。
3. **没有看到题目给的检查点**。模型读页面会漏掉页尾或屏外的内容（04 的"最后编辑"日期），这其实是 `find` 和 `scroll-until` 的适用场景，但首页没有把"在长页面里找某个字段，先用 find"讲成一条常规做法（设计意见）。`find` 在 908 条命令里只用了 2 次。

它们是不是正在被打磨的东西？**不是。** 上一轮的 23 条"下一轮"（编号见第七轮报告 §1.4 表）里，没有一条针对地址栏 UNKNOWN 或开关 UNKNOWN。下-11 涉及 `open` 后的 UNKNOWN，但只来自源码推断，出现次数为 0。原因是固定四题不覆盖这两种场景：网页题的 GitHub 搜索框在页面里，不是地址栏；也没有设置开关题。新十题这次才把它们暴露出来，但实施方的记录把这些失败都归为"业务未完整"，没有当作工具问题提出来（`r7-runtime-preparation.md` 第 256 到 281 行）。

### 4.2 最影响"agent 完成任务要花多少"的三件事

1. **回合数**。一半以上的补救回合来自动作后页面还没稳定（101 次补救 snapshot），以及 UNKNOWN 之后的只读核查（每次 2 到 3 轮，外加读一篇专题）。动作内置更好的等待，或者提供"动作加等待条件"的组合，收益最大。
2. **大页面的默认打印量**（实测）。Wikipedia 每个动作 31 到 35 KB 进上下文（新 04 两次尝试合计各约 223 KB 输出，输入 171 万和 183 万，是新十题里最贵的之一）。64 KiB 的打印阈值对动作回执来说太高；动作回执只需要首行加变化部分或可交互部分，完整树在文件里。
3. **出问题时去读专题**。专题每篇 3 到 5 千 token，读一次之后会在后续每一轮的上下文里重复计费。原始会话里这类读取至少出现在 r7-new-02、04、07、10。它们没有改变下一步决策，说明专题写的是"能证明什么、不能证明什么"，而不是"遇到 X 就做 Y"（设计意见）。

固定前缀（系统提示、工具定义、首页）每回合约 1.85 万 token，这部分产品控制不了。继续压缩首行字段，按上一轮报告 §4.3 的估计只能省几个百分点，我同意。

### 4.3 我认为是过度设计、删掉后多数调用者不会察觉的东西（设计意见）

依据是 908 条真实命令的使用分布，以及模型在原始会话里对这些字段和文字的实际反应。

- **默认输出里**：每个回执都有的 `androidctl capture=…` 行和 `edge-windows …` 行；首行的 `baselineAgeMs`、`rootUnavailableObserved`、`rootRecoveredWithinRequest`；"Estimated next sample exceeds the observation deadline"；UNKNOWN 首行里的三四个 "… unknown:" 子句。这些内容放进 `--json` 就够了。
- **指引里**：`observations.md` 中关于 `cutoffStage`、`collectionCutoff`、`missingRecords` 计数含义、`findRefreshed`、any-of 分支完备性、"Unchanged observations do not prove…"一类的段落；`actions.md` 中关于 scroll 几何路由例外（"unless collection facts report exactly one row with multiple columns"）、`--action-id` 有符号 Int32、借用粘贴恢复细节的段落；README 的 Setup 里与安装无关的段落；SKILL 首页 8 条后台屏规则（挪进专题）。
- **能力里**（只冻结，不必拆）：`select`（UTF-16 选区）、`range`、`timeline`、`pinch`、`wait --any-of / --screen-change`、多窗口集合作用域、借用粘贴的恢复规则、150 个原因码里从未出现过的绝大多数。这与上一轮报告 §2.3 的判断一致；用户上一轮没有采纳"只删不补"，我认为证据仍然支持采纳。
- **必须保留**：动作前身份核对、`not sent` 与 `UNKNOWN` 的区分（但要少报 UNKNOWN，见 4.1）、旧引用拒绝后附新树（r7-c1 候选 03、05 里模型都直接用了新树里的引用，省了一轮）、`partial` 标记、`find`、`scroll-until`、网页可读、后台屏。

### 4.4 明显该有、现在没有的能力或便利

1. **动作后等条件**：例如 `click REF --until-contains TEXT` 或 `--wait-app PKG`，一条命令完成"点击并等到目标出现"。有直接证据：101 次补救 snapshot，`wait` 只用了 2 次。
2. **地址栏和网址的捷径**：`open --url` 已经有，但首页没有说"打开网址或搜索时用 `open --url`，不要去填地址栏"，模型 7/7 都去填了地址栏。这只需改一句指引；同时应修好地址栏 fill 的核对（改为核对替换后的那个输入框，或者在原对象消失但新焦点输入框的值相同时报 done）。
3. **只读正文的视图**：例如 `snapshot --text` 只输出可见文字、不带引用和属性，给阅读长文章用。04 题的页面大部分是嵌套的 `text unreadable` 和链接，模型只是想读字。这也是 WebView 读不出来时的退路之一：配合截图加 `--marks`，或者经 shell 的 `uiautomator dump`（需设备验证 shell 身份下能否用）。
4. **开关和设置类动作在窗口重建后的重新定位**：`check/uncheck` 之后若原窗口被重建，按 role、name 或 resource id 在新窗口里找同一控件读回，而不是直接 UNKNOWN（需设备）。
5. **回执的增量打印**：动作回执默认只打印变化的子树，或者只打印 `--interactive` 视图，完整树留在文件里。
6. 截图辅助（`--marks`）和坐标手势已经有，而且在 OSM 地图题里实际好用，不需要再加。一次调用完成多步，模型自己的执行框架已经会循环调用（r7-new-02 第 146 号一次调用串了 7 条命令），不必在产品里做。

### 4.5 如果是我的产品，接下来两周

**做**：

1. 在一台真机上跑一次冒烟。上一轮报告 §1.2 写明真机证据至今为零，而真机是发布条件。这是合入前唯一的硬门槛。

3. 修 4.1 的三件事：地址栏 fill 和 `open --url` 指引；开关在窗口重建后重新定位；把首页 UNKNOWN 一节改成"先读回业务状态，读到就继续"，并删掉"停手"之类的硬规则，或者只在支付、发送、删除这类不可逆动作上保留。
4. 减小动作回执：去掉每次都有的两行；动作默认改为打印变化部分或可交互部分；阈值从 64 KiB 降到约 8 KB。

## 5. 评审过程是不是在把产品往对的方向带

依据是第七轮决定文件前 190 行和第七轮评审报告 §1、§2。以下是我的直接看法。

**总体判断：过程在正确性和诚实性上是成功的，但在"能否完成任务"和"花多少"这两个产品目标上已经失焦，最近两轮明显在局部细节上越走越深。**

迹象（都有依据）：

- **同一张清单反复翻新**。第七轮报告 §2.4 自己写了：每轮关掉二三十条，又带出二三十条；决定文件从 21 KB 涨到 35 KB、66 KB，本轮的决定文件有 1,230 行，带 47 条"读法"和 6 个"新问题"。决定文件已经比给模型的指引还长。
- **测量已经分辨不出好坏，却仍然按它来决定"再做一轮"**。固定四题连续多轮全部成功；同题 5 次之间相差 1.1 到 2.2 倍（第七轮报告 §2.4）。本轮的新十题本来是补这个缺口的，但题面延续了同一种过度规定（每题八到十二个检查点，"分享预览以两对象和数量交叉核对""Share 盘点后取消回同 PDF 及位置"），失败多半记的是 App 和网站的问题。真正属于工具的三个问题（地址栏 UNKNOWN、开关 UNKNOWN、动作后不稳定）就混在"业务未完整"里，没有被单独提出来。
- **规则在加，代价没人算**。本轮测试又净增约 2,500 行；首页 UNKNOWN 一节的硬规则直接让 07 题失败了两次。"安全优先"的文字一旦被模型照字面执行，就会以"停手"的形式付出代价，这正是 agent 产品最常见的失败方式之一。
