## 1. 方法与等价性验证

### 1.1 有什么可以重渲染【实测】
- 四个成对臂的 `evidence/cli/*/artifacts/` 只保存已渲染的正文：候选是 `.txt` 行文件，基线是 `.xml`。没有 `--raw` 调用，没有 `.json` 观察，包内也没有 workspace 目录（`find … -path '*workspace*'` 为空）。各臂 `preparation/*.json` 都是准备与绑定元数据，不含观察树。
- 因此采用"解析行→变换→用候选自己的序列化函数重写"：
  1. 解析候选 stdout：结果首行块、`androidctl {…}` 头行，以及 `role {JSON}` 正文行。缩进为 min(depth×2,16)，超过 8 层时读 `depth` 属性。
  2. 按缩进重建 `ProjectionNode` 树，变换属性。
  3. 用 `ui_view.node_line / render / reading_view / header` 原函数重新输出。
- 恒等往返：34 条候选 stdout 不做任何变换时，重写结果与原件逐字节一致（`roundtrip.py`）。

### 1.2 等价性验证【精算】
- raw 来源：`stages/final-verification/runtime-release-api34/{release-chrome-empty,comparison-chrome-start}.json`、`28-current-editor/*/oracles/*.raw.json`（6 份）、`36-native-zoom/runtime-u25-followup-api34/ic-wiki-*.json`（2 份）、`36-native-zoom/runtime-software-api34/chrome-{current-visible,addis-detail}-raw.json`（568 与 768 节点的真实 Wikipedia 页）、`27-typed-intents/runtime-mumu/oracles/{vlc-read-effect,contacts-insert}.raw.json`，共 14 份，均为 3f45af6 的对象形 actions。
- 对每份 raw，分别做 (i) `cand_patched` 渲染器直接渲染，(ii) 未改渲染器渲染后做行变换，再比较两者：
  - 12 种模式：B、C1、C1+C2、C1+C2(摘要)、C1–C3、C1–C4、F11、C1–C4+F11、C6@8k/12k/2k、A+C6@2k；
  - 3 种视图：默认、`--depth 1`、`--all`。
  - 结果：504/504 逐字节一致。覆盖情况：带文字事件的路径（raw 中有 210 条带 text 的 event）已覆盖；C6 截断实际触发 64 次。
- 多窗口验证：15/16 阶段的 12 份旧 raw 中 actions 是字符串。我把它们适配成 `{id,name,label:null}` 后再比（适配仅为覆盖多窗口 `content` 分节，属合成输入），8 种模式×3 视图，288/288 一致。首轮发现一个差异：行变换把 `content` 分节行也计入了 max-chars 预算，而真实渲染器在 `reading_view` 之后才插入分节行。修正后（先摘出分节行，按窗口标记，再重插）全部一致。
- 未被样本覆盖的路径：F11 导致的空行折叠在这些 raw 中没有发生（0 行）；折叠逻辑按候选 `project()` 的规则实现，但没有被样本验证。
- 结果首行（`ui_client.result_line`）不是树投影，只能在文本上变换。`result_line` 用 "; " 拼接各段，变换按 `; key=` 定位，再用 `json.JSONDecoder.raw_decode` 精确删除整段 JSON，等价于在 `result_line` 里不追加该段。唯一的非等价处：C5 改写后的 `effect=` 被放到 `snapshotPath=` 之前，与原顺序不同。这只影响顺序，token 差 ≤1。Requested/Resolved/Selected 三行由 `selection_lines` 整行输出，按整行删除，精确。
- 宿主包装：模型实际看到的是 exec 工具包装后的文本，有 JSON 转义加 `\r\n`，或原文两种形式。携带量计算（§4）在实际形式上替换 stdout 后再计 token。宿主截断规则从原件反推为 `ceil(bytes/4) > 10000`（例：Contacts #9 41,888B → original_token_count 10,472）。

## 8. 局限
- 成对任务没有 raw，候选两臂的数字来自行文件逆解析。在 14+12 份 raw 上，等价性 792/792 逐字节一致，覆盖了默认、`--depth`、`--all`、多窗口、max-chars 截断与带文字事件；F11 的折叠路径与 `--interactive` 下的 C7 omission 计数（54/56 一致，2 处仅 `nodes` 数字差 1）仍有小缺口。
- 结果首行的 C5 是文本层变换；effect 的位置与真实实现可能不同（token 差 ≤1）。
- C7 只在 host 侧实现；设备端的 `nameConsumed` 也会改变，所以 C7 节省为下界。C7 与 B/C1 的组合规则需要两端同时改。
- 携带量反事实假设 agent 行为与缓存命中模式不变。真实瘦身后，agent 可能少读或多读（例如看不到 show-on-screen 后是否仍用 reveal）。二阶情景只模型化 Chrome 首个快照引发的两次重读；Contacts `--all` 一条在 C6 下被截短后，agent 是否需要续读（`snapshot --cached`）未建模，若续读一次约增加 1–3k×携带次数。
