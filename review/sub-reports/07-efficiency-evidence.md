## 1. 结论摘要

1. **交付方的表格数字全部属实**【实测】。另外查出两点：候选的 *uncached* input 只多约 1.6×（Contacts 52,155→83,210，Chrome 74,980→122,853），没有 total 的 1.8–2.35× 那么多。两组里候选的 CLI 子进程时间与基线相近，Contacts 还更短（24.2s→19.0s）。wall 时间多出来的部分 **全部在模型侧**：响应次数更多、每次上下文更大、推理更长。
2. **多出来的 input 可以拆到具体来源，结论很明确**：“路径不同所以不能归因”的说法不成立。每次响应的 input 增量与新增工具文本的 o200k 计数相差在几个百分点以内，所以每段工具文本被后续携带了多少次，都能精确算出来。
   - Contacts 多 648k：CLI/快照正文 +327k（50%），公开指引 +199k（31%），多出 4 次响应带来的固定前缀、模型输出和杂项 +114k（18%）。
   - Chrome 多 1.41M：CLI/快照正文 +937k（67%），指引 +415k（29%）；图片少用 3 张，省了 −56k。
3. **单一最大来源是默认目标行的完整 `actions` 对象数组**（第 24 项 af36a32 引入）【精算】。每个目标节点都打印 `{"id":…,"name":…,"label":null}` 全表，其中 76–86% 是 focus/select/clear-selection/action-40/100/200/set-selection/show-on-screen 这类噪声项。
   - 它占候选动作结果正文的 52%（Contacts）和 55%（Chrome），占 Chrome Wikipedia 快照正文的 74–75%。
   - 按携带量计，它单独解释了 **Contacts 差额约 35%、Chrome 差额约 50%**。
4. **其次是近期事件明细（第 15 项）和变化摘要/effect（第 19 项）**。二者合计约占差额的 9%（Contacts）和 8.5%（Chrome）。effect 里还会对 `actions` 字段生成 before/after 的 `jsonPreview`，这纯粹是噪声。
5. **8192 节点不是正文变大的原因；行格式对 token 基本是中性的**。
   - Contacts 两版动作结果中“去掉 actions/事件/变化摘要后的节点正文”平均 280 vs 260 tok/次，几乎相同。
   - 交付方报告的“行格式省 11.5%/15%”是在**不含 actions 数组**的离线样本上测的，在实际默认输出里被 actions 数组完全吃掉。
   - Chrome 正文变大，是第 12 项浏览器无障碍支持把网页内容暴露成节点所致：基线下网页几乎不可见，只有工具栏约 500 tok。这是真实的能力增量，不是 8192 造成的。
6. **“默认打印”本身不是成本来源**：两组基线 agent 每个动作都自己加了 `--print`（22 案中 1,080/1,212 次也是如此）。成本来自**每份打印正文变大 3.4–4.2×**。
7. **新契约直接造成了多余的往返**【实测】：
   - 候选 Chrome 快照因 actions 数组超过宿主 10k-token 输出上限而被截断，agent 随后两次重读快照文件（+2 次往返，按携带量计约 0.32M）。
   - SKILL 示例推荐的 `--interactive` 在网页上产生 12k token 的截断输出。
   - 主题拆分的指引在“一次读多份”时被截断，于是重读（Contacts 多出 3 次文档往返）。
   - `scroll-until --name 'Job title'` 用了猜测的名字而失败（实际字段名为 Title），引出 `--all` 快照（10k tok，75% 是 actions）和读文件，共 +2 次往返。
   - 新能力省掉的往返很少：Chrome 省了 2 次 `--help` 和 3 张图片，语义点击替代了一次坐标点击。batch/diff/wait/IC/touch/zoom/通知等在四次任务中**都没有被自然使用**。
8. **候选会加重原 22 案已确认的主成本机制，即“多响应重复携带增长中的上下文”**。每次响应的平均上下文增量从 1,734→3,445（Contacts）、1,450→3,738（Chrome）tok。长任务的成本大致随“增量×步数²”增长；按原 22 案 55 CLI 的 17 号案量级估算，候选默认值会让该类案例 input 增加约 2× 以上【估算】。
9. **其它“收益”数字都是组件级的，推不出端到端收益**：
   - JPEG 省 70.2% 只是字节。同尺寸图片的模型输入在 PNG/JPEG 下都约 1,128 tok【实测】，token 上没有收益。
   - batch −72% 附件这一项未被使用，交付方自己也承认没有稳定加速。
   - 8192 完成段 3.3s 对 1024 的 3.1–3.2s 其实是变慢。
   - 传输省 140ms，不到一次模型响应时间（约 7–9s）的 2%。
10. **对处置的影响**：第 24 项的默认 actions 投影与第 15 项的默认事件明细应当**改默认值**，这件事不需要再做真实任务实验就能决定（§5 的离线重渲染已足够）。交付方推荐的 actions 选项 A 只能收回约 1/4–1/5 的差额，太保守，更合适的是接近基线的“只列非普通动作名”。指引需要按“10k 输出上限下一次读完”的约束重排。

- 校准【精算】：每段工具文本的 o200k 计数，加上上一响应的 output tokens，与相邻两次 input 之差相差约 100–400 tok。差值来自工具调用文本和包装。例如 contacts-1 第 2 段文档 9,072 tok 对增量 9,161；chrome-1c 的 11,266 tok 快照对增量 11,354。所以用“工具文本 token × 之后的响应数”来分摊总 input 是可靠的。用这种方法分摊，四臂都能精确闭合到原生总数（`attr2.py` 校验 Σ=total）。
- 关于图像 token【实测】：单张图片前后的 input 增量 − 模型输出，在 chrome-2 的 PNG（113KB base64）和 chrome-1c 的 JPEG（89KB）下都约为 **1,128 tok**（四个样本 1,225–1,228 减去约 100 输出）。JPEG 不省模型输入。

### F4【估算】反事实：改默认值能收回多少

把实际候选输出按不同规则重渲染（`sim.py`），并假设 agent 行为不变，这是保守估计：

| 方案 | contacts-2 携带量节省 | 占差额 | chrome-1c 携带量节省 | 占差额 |
|---|---|---|---|---|
| A：交付方推荐，仅删 7 个普通动作（label=null） | −147,863 | 23% | −254,999 | 18% |
| B：标准动作改短名，custom/label 保留 | −218,588 | 34% | −588,672 | 42% |
| C：接近基线，只列非普通、非参数化、非 action-* 的动作名（带 label 的保留） | −227,072 | 35% | −673,583 | 48% |
| D：默认不显示 actions | −229,450 | 35% | −669,800 | 48% |
| E：只删 event 明细，保留 events 摘要行 | −23,719 | 3.7% | −72,134 | 5.1% |
| H：删除结果首行的变化摘要/effect | −24,872 | 3.8% | −27,563 | 2.0% |

- C+E+H 合计约为 Contacts −276k（差额的 43%）、Chrome −773k（55%）。
- 二阶效应：如果 Chrome 快照不被截断，就省掉两次读快照文件（携带量约 0.32M）。加上这部分，Chrome 差额可收回约 3/4。
- 剩下的差额主要是指引读取（F2）和 Contacts 那次 `scroll-until` 失败绕路。
- 选项 A 太保守：它不删 action-100/200（移动粒度）、set-selection、action-1020044 等参数化或私有 id 项，而这些在实际输出里占比很高。

### F8【设计建议】最小判别实验：默认打印、事件、actions、8192

第一步：**离线重渲染，零设备成本，已足以决定 actions 和事件的默认值**。
1. 用候选已保存的 raw 观察（evidence 中的 snapshots/raw JSON）以及 22 案的 1,166 份样本，分别按 D（现状）、A、C、E、H 规则渲染，计算每次输出的 token 和超过 8k 的比例。
2. 再按本报告的“携带量”公式，把 22 案的原生步序代入，得到总 input 的变化。
3. 决策规则：只要 C+E 能把超过 8k 的输出比例降到接近 0，并把每步增量降到基线的 ±20% 以内，就改默认值。这一步不需要模型实验。

第二步：**只验证信息损失**，即删掉内容后 agent 是否会因此失败或多查。
- 同一候选 APK，只在 host 侧切换渲染（环境变量或隐藏参数），设备、App、起点都相同。
- 任务选 6 个，必须包括需要非普通动作的场景：自定义 accessibility action（如列表项“Delete/Archive”）、带 label 的动作、expand/dismiss、range，再加上一两个依赖事件提示的场景（toast、窗口弹出）。另外配 Contacts 表单和 Chrome 长页。
- 两臂（现状 D+全事件 vs C+摘要事件），每任务 ABBA 各 2 次，共 24 次运行。
- 指标：业务通过率；`--all`/raw/`--help` 补查次数；total 与 uncached input；wall；截断次数。
- 结果如何改变选择：
  - 补查只是偶尔一次，通过率不降：采用 C+E 为默认值，`--all` 保留全表。
  - 自定义动作类任务在 C 下失败或多出 2 次以上往返：改用 B（保留 custom/带 label 的对象，标准动作用短名），并继续删普通项。
  - 事件类任务在 E 下漏判：保留“有 text/description 的事件”（即交付方事件选项 A），删除纯元数据事件。

关于“默认打印”：基线 agent 已经 89% 自发打印，本轮四臂是 100%，默认值改与不改对行为几乎没有影响，**不需要实验**。保留默认打印，同时把正文变小。

关于 8192：它不影响默认正文的 token，效率实验对它没有判别力，应由采集耗时、内存和 partial 率的组件测量决定，交给其它评审。效率上唯一需要守住的是：保证 `--all`/raw 不会被默认流程或指引推荐（目前 SKILL 推荐的是 `--interactive`，在网页上同样很大，建议改掉）。

指引：做一个“SKILL 内含 UI 最小闭环，主题小于 8k tok、按需读取”的版本，在同一组任务上看指引往返次数和携带量。这一项也可以先离线判断：只要拆分后每份文件都能在一次 10k 上限内读完，截断重读就会消失。

## 4. 建议重新裁决的事项

**R1 默认 actions 投影**（交付方列为“未批准可选改进 3”，推荐 A）
- A：只删 7 个普通动作。安全，但只收回差额的约 18–23%。
- B：标准动作用短名，custom/带 label 的保留对象。收回约 34–42%，但会出现混合形状。
- **C（推荐）**：默认只列非普通、非参数化的动作名，带 label 的写成 `name:label`，`--all`/raw 保留完整对象数组。收回约 35–48%。这与基线的设计意图一致，基线就是这样做的且没有暴露问题。剩余未知：自定义动作在第二步实验中的可发现性。
- D：默认不显示。省得与 C 一样多，但 agent 会看不到 expand/dismiss 这类真实入口，不推荐。

**R2 默认事件明细**：同意交付方事件选项 A（默认只给摘要和有文字的事件）。实测数据支持这一选择，而交付方没有用实测来论证。

**R3 effect/变化摘要**：
- 删去 effect 中对 `actions` 字段的 before/after `jsonPreview`。
- 默认只保留 `changed/unchanged/unknown` 一词，加目标值变化。
- `baselineSequence/baselineFinishedMs/baselineAgeMs/baselineComputedAtMs` 等四个时间字段改为只在 `--json` 中出现。

**R4 公开指引结构**：保持主题拆分，但约束每个文件小于 8k tok；SKILL 内置 UI 最小闭环，让大多数 UI 任务不需要在开头读三个主题；SKILL 示例去掉 `--interactive`。

## 5. 对交付方声明与内部 review 的对照

- **成立的部分**：
  - 数字准确，原件完整，含失败尝试。
  - “不能称普遍提速”，以及“未使用的 IC/batch/diff 不能计为收益”，都对。
  - review 对 scroll-until 失败的原因描述准确：已执行 2 步、第 3 步因路由未广告而未发送。
  - 对 Chrome 状态差异（继承查找词、捐款横幅）的记录也准确。
- **回避的部分**：
  1. “bytes 不换算 token”“不能把成本差归于单一机制”：rollout 里每次响应都有原生 usage，相邻差值可以精确给出每段工具文本的 token。这种分解交付方的工具链完全能做，却没有做。做了之后结论很清楚：单一机制（默认 actions 数组）解释了 35–50%。路径差异的量级（每项约一个动作输出）比它小一个数量级。
  2. review 写的是“未发现需产品改动…才能解释的验收矛盾”。作为业务验收这句话成立，但它把效率问题排除在了关闭范围之外，而效率正是用户目标之一（“实质提升…使用效率”）。
  3. 交付方把 actions 和事件精简列为“未批准可选”，理由是“真实任务需要查询普通广告的频率…未知”。但手头唯一的端到端证据恰好表明，这两项是候选效率退化的主要原因，结论应该反过来：它们是阻碍效率目标的默认值，需要用户裁决，而不是可选优化。
  4. 继续援引 11.5%/15% 行格式收益、70% JPEG、−72% 附件、140ms 等数字，却没有说明在实际任务里它们被抵消或者与 token 无关。交付方报告中的“8192 完成段 3.3s vs 3.1–3.2s”应明确写成开销。
  5. chrome-1 的 Bad Request 紧跟在第一份 10k 截断的大快照之后出现。交付方和 review 都只写了“根因无证据”，没有指出这个时间上的巧合。它可能与内容有关，也可能是巧合，【证据缺口】。
- 原 22 案报告的判断“成本主要来自多响应携带增长中的上下文；没有证据支持一揽子产品修复”，**被本次成对运行强化而不是削弱**：候选是一揽子产品改动，它没有改善 22 案已证的失败根因，反而把每步上下文增量翻倍。
