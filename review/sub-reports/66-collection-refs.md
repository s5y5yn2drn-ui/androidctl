# 第六轮专题 66：节点采集、预算、出版、引用身份与公开采集路线实验

核查对象：产品 `fb75afc`（`SRC` = `S/r6/prod`），实施方材料包 `PKG`（`ST` = `PKG/ultragoal/2026-11-11-next-improve/stages/42-r4-decisions`）。全部只读；没有设备，没有跑 Gradle。我写的脚本在 `S/agents9/66/scripts/`（`samples.py`、`treesize.py`、`rejects.py`、`nonzero.py`、`project.py`），都用 `python3 -I`（`project.py` 用 `S/r6/venv6/bin/python -I`，即 `fb75afc` 的主机代码）运行，包内路径作参数传入。从 googlesource 下载的 Android 16 源码在 `S/agents9/66/aosp16/`（标签 `android-16.0.0_r1`）；Android 14/15/17 源码用的是以前已下载的目录。

本文用词：
- **手写采集路线**：worker 自己向系统发"按编号查节点"的请求，并自己实现接收结果的 Binder 回调（`CollectionNodes.kt`、`CollectionReplies.kt`），同时关闭系统节点缓存。这是候选新增的做法；主分支基线 `7d5be70` 在 Android 13 以上用的是公开 `getChild` 且关掉缓存（因此没有预取），采集时限 1.5 秒。
- **公开采集路线**：用公开 `AccessibilityNodeInfo.getChild(index, 预取标志)`，保持系统缓存开启，每次采集前调用公开的 `UiAutomation.clearCache()` 的对照实现。
- **后台虚拟屏**：App 的任务被放到一块后台虚拟显示上运行。
- **REF**：打印给调用者的节点引用，如 `e15`。**partial**：一次采样不完整。

## 1. 结论摘要

整体状态：采集、预算、出版和引用这一块行为正确、形态基本相称，**不构成合入障碍**。公开路线实验的结论"保留手写路线"有原件支撑，而且我认为这一次的数据已经足够让用户把采集路线问题彻底关掉。

最重要的发现：

1. **第 3 条验收失败是真实的性能差距，不是 3 秒时限造成的假象。** 3 秒采集时限是实施方在第四轮候选里从基线的 1.5 秒调高的（提交 `ab7ff63`，`UiBudget.kt:111`），用户的四条验收没有改它。两条路线用同一个采集器、同一个预取标志（深度优先、可中断）、同一个时限。按原件外推，公开路线把这页 4976 个节点采全需要约 3.5–4.7 秒，手写路线中位数 1.49 秒，差 2.3–3.1 倍；连两边的暖机样本（都采全）也差 1.8–2.0 倍。所以即使不看第 3 条，按第 1 条的耗时比口径，这一页也过不了 1.5 倍。【重算】
2. **差距的机制在源码里能找到，但没有被测量。** 两条路线发出的请求相同，差别在接收端：系统客户端只接收"最近一次请求"的那批预取结果（`AccessibilityInteractionClient.java` 在 Android 14/15/16/17 都是同一条判断），手写路线则每个请求各有一个回调对象，所有预取结果都收。另外公开路线开着缓存，每次采集从空缓存开始。实验没有记录请求次数和预取被丢的次数，所以这只是有源码依据的推断。【源码】【推断】
3. **换成公开路线能省下的东西比想象的少。** 公开路线的补丁实际净删约 250 行产品 Kotlin，加约 60 行主机代码（公开路线需要"App 卡住时主机多等约 5 秒"的宽限）。只为采集服务的隐藏成员是 7 个，加上关闭缓存用的 2–3 个；`HiddenApi.kt` 一共 62 个隐藏成员，执行动作仍然依赖同一个隐藏的服务连接、回调桩和 `getSourceNodeId`。我核了 Android 14、15、16、17 的 AOSP，这些采集专用成员的签名完全一致。【源码】
4. **引用被拒的反例：Maps 里一共 7 次，不是实施方说的 3 次。** 候选 3 次（第 1、2、3 次运行），基线 4 次（第 2、3、4、5 次运行），全是同一个步骤：步行模式标签页的名字从 "Walking mode: " 变成 "Walking mode: 18 minutes"，行列位置和角色都没变。候选每次之后多一次 `snapshot` 调用（共多 3 次模型回合）；基线的拒绝回执自带新树，下一条命令直接点新引用，没有多花调用。GitHub、Feeder、后台屏 Contacts 三道任务的候选和基线都没有出现引用被拒。【原件】【重算】
5. **把名字放进身份是对的，问题在拒绝时不给信息。** 名字能挡住"同一个控件换了含义"的误操作，例如 "Follow" 变成 "Following" 后再点一次就是取消关注；所以我不建议放松名字比较，也不建议"旧名字是新名字的前缀就放行"。候选在拒绝前已经为修复重采过一次新树，最小改法是拒绝时附上"同一来源节点现在的一行"。这样不会替调用者做决定，又能省掉一次调用。【源码】【原件】
6. **另一个风险：在后台虚拟屏上，Chrome 几乎把所有节点都报成"可见"。** 采全的那份树里 4976 个节点有 4972 个可见，但只有 546 个落在屏幕范围内。用 `fb75afc` 的主机投影代码重算，这页默认 `snapshot` 会打印约 4,000 行、43 万字符。另外"可见优先"的采集顺序和"可见部分读全就放行选择"的规则在这种页面上不起作用。【重算】【需设备】

是否构成合入障碍：**不构成。** 采集路线维持现状；第 4、5 条建议是小改，可以在合入前做，也可以合入后做。

## 2. 确定缺陷

### 2.1（可选，中）引用修复失败后，拒绝回执不给出已经采到的新目标

- **触发条件**：调用者拿着一个刚打印的 REF 去点。在这之间，同一个控件的可观察名字变了（加载完成、计时、计数）。
- **位置**：动作时先现场重读节点，名字参与身份比较，不一致就拒绝（`UiVerification.kt:22-33`）。接着修复逻辑会重新采一次树（`UiRefRepair.kt:35-41`），但候选匹配要求两边名字都非空时必须相同（`UiRefRepair.kt:96-98`），所以修复失败，报 `stale`："No current target matches the original ref signature"。这次修复采到的新树已经装成当前样本（新 REF 也已经发号），但回执只有一行错误（候选回执 141 字节）。
- **原件**：`ST/efficiency/u35-c1-candidate-01/evidence/cli/1795520494773501400-738e03ed71ba40ad8666e27d74c0fb46/child.stdout`（C02、C03 同样），下一条都是 fresh `snapshot`，再下一条点新 REF 成功。C03 拒绝前后的打印：`e563611054 "Walking mode: "` 变成 `e563611186 "Walking mode: 18 minutes"`，`rowIndex=0 columnIndex=2`、`roleDescription="Tab"` 都不变。
- **实际影响**：每次多一个模型回合。按这组成功样本的中位数（约 67 万总输入、22 回合），一个回合约 3 万输入 token（大部分命中缓存），再加十几秒。5 次候选运行里有 3 次遇到。候选这道题整体仍比基线便宜（总输入中位数比 0.749），所以这不是合入障碍。
- **最小修正方向**：在 `UiRefRepair.select` 找不到匹配时，从这棵新树里找与原目标窗口和来源编号相同、角色相同的节点，把它的一行放进拒绝信息，例如"同一来源现为 e563611186 "Walking mode: 18 minutes"；未派发"。不自动派发。Kotlin 约 15–25 行，主机不用改（信息走现有 message 字段），再加 1–2 个测试。另一种做法是对这一类拒绝恢复打印新树（基线就是这样做的，每次约 4.5 KB），但要改第四轮"被拒不重印整页"的决定。
- **确定程度**：源码路径确定，原件 3 次全部吻合。拒绝那一刻候选的来源编号是否真的没变，文本回执里看不到，所以"是同一个底层对象"只能从行列、角色、类型一致来推断。

### 2.2（可选，中，需设备）后台虚拟屏上的 Chrome 页面：可见性几乎全为真，默认打印会非常大

- **触发条件**：在后台虚拟屏上用 Chrome 读一个长网页。
- **原件与重算**：`ST/collection/r5-samples/r5-C-studio-capitals-01/artifacts.0001.tree.json` 有 4976 个节点，其中 4972 个 `visible`（稀疏编码里缺省即为可见），而 bounds 与 720×1280 屏幕相交的可见节点只有 546 个。同一页面在主屏模拟器上的旧样本是 4977 个节点、526 个可见（`r5-collection-preparation.md` 引用的旧数据）。用 `fb75afc` 的 `ui_view.observation_nodes` 加 `render` 投影这份树，结果是 4,029 行、434,652 字符；没有默认的 `--max-chars` 上限（`ui_view.py:363` 只隐藏 `visible=false` 的节点）。【重算】`scripts/project.py`
- **实际影响**：调用者对这类页面做一次默认 `snapshot`，可能收到十万 token 量级的输出。另外，采集的"可见优先"顺序（`TreeCollector.kt:62`）和选择命令的"可见部分读全即可"放宽（`UiSelector.kt:88-104`）都靠这个可见位，在这里都失效。公开路线第 1 份样本截断时，屏幕上的 546 个节点只采到 487 个，正是这个原因。
- **最小修正方向**：先在设备上确认（主屏和后台屏各取一次同一页面的可见计数）。如果确认，最简单的做法是在采集优先级里把"bounds 不与显示区域相交"也当作不可见（几行），并让默认打印按同一标准隐藏这些节点。是否改投影规则涉及"可见性以无障碍报告为准"的现有指引（`skills/androidctl/observations.md:25`），需要实施方权衡。
- **确定程度**：两份原件确凿，原因（Chrome 在虚拟屏上怎么算视口）未知。真实任务里没有后台屏上的 Chrome 任务，影响面没有实测。

### 2.3（可选，低）App 卡住时，较长的 `wait` 不交付任何部分树

- **触发条件**：手写路线，App 主线程在非根节点处卡住，调用者执行 15 秒的 `wait`。
- **原件**：`ST/collection/r5-samples/r5-C-block-wait/rpc.json`：14.7 秒后 failed，`predicate.code=rootUnavailable`，`snapshotError="Request budget exhausted before snapshot delivery"`，没有 capture。第一份样本本来能交出部分树（同条件下 5 秒 `snapshot` 能交出 4 个节点），后续样本卡在根节点读取上（公开 `window.root` 最多阻塞约 5 秒），最后什么都没交付。这份原件早于 C9 诊断提交 `cf5f6707`；之后的回执至少会说明"根读取仍在等待"（`UiBudget.kt:54-57`）。
- **影响**：命令本身按时返回（15.4 秒），不违反时限；只是调用者看不到任何树，诊断也只有一句话。
- **方向**：可以保留，或者在最终没有可交付样本时交付本命令最后一份已组装的部分样本。我不认为值得专门做。

没有发现必须修的缺陷。

### 3.2 公开路线实验：3 秒是谁定的、为什么慢、是否公平

**3 秒时限。** `UiBudget.beginSample` 返回 `min(until, deadline, started + 3000)`（`UiBudget.kt:68,111`）。基线是 1.5 秒（`7d5be70:TreeCollector.kt:258`），第四轮候选提交 `ab7ff63` 改成 3 秒。用户的决定没有涉及这个数，实施方的准备文档也说明了"现存 3 秒采集窗是源码预算事实，不是新增验收门"（`ST/r5-collection-preparation.md:146`）。两条路线共用这个时限。【源码】

**重算的原件事实（`ST/collection/r5-samples/`，`scripts/samples.py`）。**

| 样本 | 节点数 | partial | 采集耗时 ms |
| --- | ---: | --- | ---: |
| 手写暖机 0 / 1 | 4976 / 4976 | 否 / 否 | 995 / 951 |
| 手写正式 01 / 02 / 03 | 4976 ×3 | 否 ×3 | 1490 / 770 / 1998 |
| 公开暖机 0 / 1 | 4976 / 4976 | 否 / 否 | 2038 / 1725 |
| 公开正式 01 / 02 / 03 | 3236 / 3850 / 4321 | 是 ×3（`collectionLimit`） | 3042 / 3009 / 3014 |

按节点速率线性外推，公开正式三份采全分别需约 4.68、3.89、3.47 秒，对手写中位数 1.49 秒是 2.3–3.1 倍。暖机配对是 1.8–2.0 倍。上一轮评审子报告 49 说第四轮那批后台屏数据"有混杂"（手写暖机也被截断），这一轮正规暖机后手写 5/5 采全、公开仍然慢约 2 倍，所以**那条"混杂"的说法现在站不住**：后台屏上的差距已经在两轮独立实验里重复出现。【重算】

**为什么慢：逐条核对用户列的几个猜测。**
- *逐节点跨进程调用？* 两条路线都是按需对每个缓存未命中的子节点发一次请求（手写 `CollectionNodes.kt:39-50`，公开走 `getChild`），这一点相同。
- *没有用预取标志？* 两边用的是同一个标志 `FLAG_PREFETCH_DESCENDANTS_DEPTH_FIRST`，都没有加"不可中断"（手写 `CollectionNodes.kt:47`；公开补丁 `TreeCollector` 的 child 读取）。
- *在 worker 里同步等待？* 两边都在采集线程上同步等主结果，相同。
- *真正的差别在接收端。* 系统客户端收到主结果后，才登记"正在等哪个请求的预取"；预取回调只有在请求编号等于这个登记值时才入缓存（Android 14 `AccessibilityInteractionClient.java:1260`，16 同一判断）。采集器是"可见优先、按深度"的广度遍历，而预取是深度优先，所以下一个兄弟节点很快就会未命中、发出新请求，前一批迟到的预取就被丢掉。手写路线每个请求都有自己的回调对象，`awaitPrimary` 返回后仍然接收迟到的预取（`CollectionReplies.kt:232-260`，`accepting` 不会因主结果到达而关闭），采集前先把它们全部收进本地表（`CollectionNodes.kt:69-79`）。此外，公开路线开着缓存，界面事件可能使缓存里的节点失效，每次采集也从清空的缓存开始。【源码】
- *后台屏上 Chrome 的无障碍树是惰性生成的？* 不能解释：公开路线的暖机 1 份在同一页面上 1.7 秒就采全了。但手写和公开两组不是交替做的：手写在前；约 20 分钟后公开组开始，Chrome 的渲染进程也已重建（`r5-results.md` 说明了这一点）。公开正式三份的节点数逐次上升（3236→3850→4321），说明存在一种"越采越快"的状态因素，原件解释不了。

**还有一处没解释的现象。** 主屏模拟器（MuMu，Android 15，`ro.build.version.sdk=35`，见旧包 `runtime/mumu/commands` 下的设备信息原件）上的旧对照里，公开路线在同一页反而更快（0.70 倍），另一页 1.20 倍。同样是带异步预取的系统版本，结果方向却相反，现有材料解释不了。只有"按请求计数、记录预取被丢次数"的观测才能分辨原因。

**是否公平。** 作为"按现在的写法替换公开接口"的对照，它是公平的：同一个共同父提交、同一个采集器、相同的标志和时限、相同页面，暖机也到位。不公平的地方有两点：样本量是 3 对 3，而且两组没有交替；公开路线也没有针对平台限制做调优（例如换成广度优先或兄弟节点预取，让预取方向与遍历方向一致；或者对小请求用"不可中断"预取）。实施方在第四轮已经查过"不可中断"预取：它把主结果和预取打成一个包，有过 1.2 MB 事务发送失败、只采到根节点的反例（旧包 `collection/normal-analysis.md`"UNINTERRUPTIBLE 的窄补查"一节，引用 App 端 `FAILED BINDER TRANSACTION` 日志）。我同意不把它当默认做法。

**有没有不靠两条路线并存、又能过四条的中间方案。**
- *公开路线加调优预取策略*：改一行标志，或者改遍历顺序（约 30 行，而且会改变"可见优先"这一现有行为）。收益未知，需要再开一轮设备实验。
- *放宽单次采集时限*：改一行。但默认 `snapshot` 的工作截止约为 4.5 秒（`UiBudget.kt:19`，5000 减 500），公开路线采全就要 3.5–4.7 秒，再加组装和交付就会超时；要过，必须同时调大默认超时，所有大页命令都会变慢 2–3 秒。
- *按节点数自适应、或超大树降级为 partial 并如实报告*：后者按定义就过不了第 3 条（完整率相同）。
- 结论：**没有能在不增加调用者等待的前提下过第 3 条的现成方案。**唯一可能的是"调优预取"，但它的收益要靠新实验才知道。

### 3.3 调用者真的需要 5000 节点的完整树吗

- 真实任务里没有一次撞到节点上限或字节上限。保存的观察文件中（候选 `.txt`，`scripts/treesize.py`），投影行数中位数分别是：Maps 51，GitHub 76（最大 691），Feeder 15，后台屏 Contacts 12。partial 的比例是 Maps 8/79、GitHub 6/63、Feeder 2/57、Contacts 0/71；原因几乎都是 `nodeUnavailable`（采集中途节点消失），少数是动作后或 `wait` 的短截止 `collectionLimit`，而且发生在很小的树上（5–75 行）。保存的文本里没有原始节点数，所以"真实树多大"只能用投影行数作代理。【原件】【重算】
- 但大树的完整性有实际用途：GitHub 任务里多次用 `find ... --all` 读出 `offscreenMatches=4` 的屏外内容（例如 `r5-c2-final-candidate-0{1,2,3,5}` 的 `find May`）。【原件】
- 依赖"完整"的规则在 partial 下的表现：`wait --gone` 要求整树完整（`UiCondition.kt:162-175`），树持续 partial 时永远不会成功，只能等到超时；按文字或角色选择目标的动作，在有上限截断、又有可见节点缺子节点时拒绝（`UiActions.kt:912-917`，`UiSelector.kt:88-104`）；按 REF 的动作不受 partial 影响；`scroll-until --contains` 在 partial 下也可以命中。所以在后台屏的大网页上，公开路线会让 `wait --gone` 和按名字选择在这一页上失效；再加上 §2.2 的"全都可见"，可见区放宽也救不回来。

### 3.4 预算与表示

- **最终定稿和交付用的是同一个算法。** `UiTreeBudget.fit` 先算"节点为空时整份载荷"的字节数，再逐个加 `NodeEncoding.node(node)` 的 UTF-8 长度和逗号（`UiTreeBudget.kt:35-47`）；交付时编码的是 `NodeEncoding.tree(treePayload(observation))`（`UiDelivery.kt:234`），用的是同一个编码函数，作用在同一个对象上。`source`、`display`、`connection`、`sequence` 这些字段都在 fit 之前写好（`UiBackend.kt:408-410`，`UiSnapshot.kt:38-40`）。fit 的循环在每次修补之后重新计数，所以最后一轮的字节数就是实际字节数。【源码】
- **采集中的早期估算是下界，不是同一个算法。** `TreeCollector` 每加一个节点用 `rawBytes`（不含 ref/parent，也还没有语义字段）累计（`TreeCollector.kt:289-295`）。最终加上 `view`、`row`、`refReason` 等字段后，fit 可能再裁一刀。两处都报 `treeByteLimit`，对调用者的呈现一致。"提前预算与最终定稿同算法"这个说法如果指的是这个早期估算，就不准确；但这不影响正确性。【源码】
- **partial 的几种原因怎么呈现给调用者。** 节点上限为 `nodeLimit`，字节上限为 `treeByteLimit`，时限为 `collectionLimit`（带 unread 计数；手写路线等不到主结果时另加"App 可能无响应"的说明，即 C9 那项），子节点读不到为 `nodeUnavailable`/`unavailableChildren`，重复来源为 `repeatedSource`。它们都进入 `missing`，在打印里汇总成 `observationWarning="partial; missing=N"` 和 `missingSummary.reasons`（真实回执里可以看到，例如 `u35-c1-candidate-02` 的 `000016` 号保存文件）。【源码】【原件】
- **"其实完整却报 partial""其实不完整却报完整"。** 我没有找到前者。后者只有一种平台固有的情形：一次采集跨越几百毫秒，期间新出现的子节点不会被发现，预取到的节点也可能比后来的主查询旧，于是得到一棵"结构完整、但时间上混合"的树。这一点任何多次查询的采集都避免不了，指引里"空的 missing 不证明页面完整"（`observations.md:99`）已经覆盖。【源码】【推断】

### 3.5 引用身份规则（讲清楚）

1. 身份由六项组成：来源编号、窗口编号、角色、名字、行标签、行位置链（`UiSemantics.kt:320-334`）。来源编号缺失，或者角色、名字、行信息不完整，就没有身份，这个节点不发可用 REF（`refReason="Selection identity is incomplete"`）。
2. 每次组装新样本时，如果节点的身份与"最近 3 份已出版样本或当前样本"中某个身份完全相同，并且来源地址在本样本里唯一，就沿用旧 REF；否则发新号（`UiRefs.kt:36-83`）。只要名字一变，就是新 REF。
3. 动作只能用"当前已装样本"里的 REF（`UiSnapshot.kt:76-83`）。派发前用公开接口现场重读这个节点和它的祖先链，重新组成身份比较；不相等就报 `changed/selection`（`UiVerification.kt:22-33`，`FreshNodes.kt`）。
4. 确定没有派发、预算也还有余时，修复只做一次：重新采一棵完整的树，按"包名和角色必须相同；名字非空时必须相同；名字或资源 ID 至少一个相同；再看类型、行、共有动作、位置"打分，取明显最高的一个；没有就报 `stale`，分不出就报 `ambiguous`（`UiRefRepair.kt:58-125`）。

**名字保护了什么。** 一类是列表复用：同一个 View（来源编号相同）被绑定到另一条内容，而 App 又没有提供行信息。另一类是名字本身表达状态的控件：例如 "Follow" 变成 "Following"，再点一次就是取消关注。所以名字进身份是必要的保护，不应因为这次 Maps 的反例就去掉。顺带说明，"旧名字是新名字的前缀就放行"这种放宽恰好会放过 "Follow" 变 "Following" 的情形，不能采用。

**"被拒不重印整页"是谁的决定。** 这是第四轮决定第 11 项"动作后的观察"第 1 条（`androidctl-r4-decisions.md:102`）："被拒绝的动作不再重印整页"。在 Maps 这一类拒绝上，它的代价可以测出来：候选每次多一个回合，基线不多。不过这条决定在其他拒绝类型上（如 `notReady`）是合理的。所以我建议只对"修复时已经采过新树"的这一类拒绝附上同来源节点的一行（§2.1），不必推翻整条决定。

### 3.6 缓存与重采

规则：`snapshot` 新采；`snapshot --cached`、`snapshot REF` 读当前样本；`find` 读当前样本，但如果上一个动作的结果是"可能还在变化"或"仍在加载"，就在同一范围内重采一次（`UiSnapshot.kt:87-113`）；动作返回自己的动作后观察；被拒的动作不打印，当前样本可能已经被修复时的重采替换掉。

- 这些规则在原件里按设计工作。Maps 候选第 5 次运行在"可能还在变化"的点击之后执行 `find Walking`，回执里没有 `cached`，说明是新采的，拿到 `Walking mode: 18 minutes` 的新 REF，直接点击成功。读旧样本的 `find` 都会印出 `cached; ... age=...ms`（例如 Contacts 的四次 `find Notes`，样本年龄约 9–11 秒），调用者看得到样本有多旧。【原件】
- 会在不知情时读到旧内容的路径，我只找到一条，而且很轻：动作被拒后，回执既不说"已经重采了新样本"，也不给出它，于是调用者不知道 `snapshot --cached` 里已经是新内容，通常会再发一次新采的 `snapshot`。这对应 §2.1。指引里"被拒后用 `snapshot --cached` 查看采集样本"的说法（`actions.md:49-50`）是对的，但回执不提示，模型在这 3 次里都用了新采的 `snapshot`。
- `refreshBeforeFind` 只由动作设置；一次本身就显示"加载中"的 `snapshot` 不会触发下一次 `find` 重采。影响很小，不必改。

### 3.7 前几轮决定的回看

### 3.8 整体判断

## 5. 需要用户裁决的新取舍

### 第一题：采集路线是否就此定案

- **A. 保留手写路线，关闭这个问题，不再做路线实验（推荐）。**
  - 得：后台屏上的长网页能采全，速度约为公开路线的 2 倍；`wait --gone` 和按名字选择在这类页面上可用；App 卡住时不需要主机侧 5 秒宽限。
  - 失：继续维护约 360 行产品代码、165 行测试和 7 个采集专用隐藏成员（外加关闭缓存用的 2–3 个）。这些成员在 Android 14–17 的签名都没有变化。
- **B. 换成公开路线，接受超大页面 partial。**
  - 得：净删约 250 行产品 Kotlin、约 150 行测试和 7–10 个隐藏成员。
  - 失：后台屏上的大网页实测 0/3 采全，这些页面上 `wait --gone` 无法成功，按名字选择会被拒绝；需要加约 60 行主机侧 5 秒宽限；隐藏接口的风险性质不变，因为执行动作仍依赖同一个服务连接和回调。
- **C. 再做一轮有判别力的实验，然后再定。** 在公开路线上加请求计数和预取丢弃计数，再试一种与遍历方向一致的预取策略，在同一后台屏页面上交替跑 3 对 3。成本是一个设备窗口和一份小补丁。只有用户确实倾向 B 时才有意义；即便结果好，省下的也只是上面 B 的那些代码。
- **D. 放宽采集时限（例如 4.5 秒）并调大默认超时，然后换公开路线。** 不推荐：所有大页命令都会变慢 2–3 秒，换来的只是删掉约 250 行代码。

推荐 A。理由：B 省下的维护量不大，而且隐藏接口风险换路线后依然存在；B 的代价已经在真实页面上量出来了。这次数据已经足够做决定，用户不需要再等第 1、2 条的数据。剩余未知：主屏模拟器和后台屏上两条路线速度比方向相反的原因。

### 第二题：动作因引用变化被拒时，回执给什么（涉及第四轮"被拒不重印整页"）

- **A. 维持现状**：只打印一行错误。调用者自己再取一次观察。
- **B. 附上同来源节点的一行（推荐）**：修复已经采到的新树里，如果有与原目标同窗口、同来源编号、同角色的节点，就在拒绝信息里给出它现在的 REF、名字和行位置；不自动派发。约 15–25 行 Kotlin 加测试，打印量增加一行。
- **C. 对这一类拒绝恢复打印新树**（基线的做法）：每次约 4.5 KB，部分推翻第四轮决定。
- **D. 名字变了但来源、类型、角色、行位置都没变时自动放行**：不推荐，会放过 "Follow" 变 "Following" 这类改变操作含义的情形。

推荐 B：保护不变，又能省掉这类情形下的一次调用（Maps 5 次运行里遇到 3 次）。

## 6. 有判别价值的补验

1. **后台屏 Chrome 的可见性**：同一长网页在主屏和后台屏各取一次快照，比较 `visible` 计数与"bounds 落在屏内"计数。如果后台屏仍然几乎全为真，§2.2 就成立，应该修改采集优先级和默认打印；如果只是那次实验环境的个例，就不用改。
2. **（只在用户倾向第一题 B 或 C 时）公开路线的请求和预取计数**：在公开路线上记录每次采集的请求次数、预取到达次数和被丢次数，与手写路线的请求次数对比。如果主要差距来自被丢的预取，调优后的预取策略才有可能把差距拉进 1.5 倍；如果差距来自缓存失效或每次调用本身的开销，就可以彻底放弃公开路线。
3. **REF 修复的成功率**：在下一次固定任务里，统计修复成功（派发了新目标）和失败的次数。如果长期只有失败，可以考虑把修复简化为"拒绝并给出同来源的一行"（第二题 B），省掉打分逻辑。
