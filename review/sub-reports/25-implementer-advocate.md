## 1. 摘要

1. **最强的一项：题 1 的设备端种类核验（不是主机偏好文件本身）。** 用户新定的规则里，纯设备命令也要先开会话。这让"同名调用者只为跑 shell 就执行 `session open --display main`"成了常规操作。这条序列会销毁原调用者的后台屏，原调用者此后不带 REF 的请求（`open`、`keys`、`editor commit`、`snapshot`）会静默落到真人正在用的主屏。D 在设备锁内核验种类，能拦住它；`--display` 必填拦不住。评审方的逐序列推演漏了这一条。【源码＋推断】
2. **D16 窗口缺席不等于消失，平台有直接依据。** AOSP 14 的无障碍窗口计算会把"被上层可触摸窗口完全遮住"的窗口从列表里剔除。屏幕被完全覆盖、且焦点窗口已经入列之后，下层窗口全部停止计算。所以权限框、全屏弹层出现时，目标窗口会暂时"缺席"。用户新定的"等消失算成功"会在这种时候给出假成功。【源码】
3. **通知注销失败要有门。** 平台按系统身份登记的 listener 不分用户接收所有回调（`isSystem → true`），登记时还会给 `com.android.shell` 授予通知 URI 读权限，要等注销才收回。如果注销持续失败（例如某个 ROM 上的隐藏接口漂移），"只记一笔、不封锁"会让一个跨用户的常驻监听和 URI 授权静默留存，而且注册不去重，条目还会累积。实施方的 C 本身（延长持有期）辩护较弱，真正站得住的是"失败要有门"。【源码】
4. **坐标退路链最后一级"不限制"与用户早先的自身保护范围冲突。** 平台没有"允许任意接收者但排除自身 UID"的注入模式；当前防止坐标点到 AndroidCtl 自身管理界面，靠的就是正向 UID 定向（`AppInput.kt:84-93`）。第一级退路（用窗口列表判断）方向安全，预测错了只会被平台拒绝。第二级退路会撤掉这道平台级保护。【源码】
5. **通知地址放宽后，有一个具体的反向误操作。** 媒体通知同一序号的按钮会在 Play 和 Pause 之间翻转。用户决定只写"比对标题、来源、按钮序号"，如果"标题"指的是通知标题，就会丢掉现有的按钮标题核验（`NotificationActions.kt:284-286`）。消息类通知有新的未读消息时，按序号执行"标记已读"或 dismiss，作用到的是调用者没看过的内容。【源码＋推断】
6. 中等：同帧 zoom、题 3 的"设备目标规则不动"（标注缺陷可以只在标注排序里修）、严格 postTime 的代价不对称、E9 两处"防护"本身的风险。较弱：持久 diff 基线、规范树不稀疏、E9 不补实验、提交策略、浮层抑制。

## 2. 逐项辩护

### 2.1 题 1：D——全显式，同时保留共享种类、每请求种类字段、display select/create、batch 冻结

**一手事实。**

- 设备端核验与取得租约在同一把锁里完成：`Sessions.acquireUi` 是 `@Synchronized`，依次执行 `admitted → requireResources → requireTarget(held, expected)`（`Sessions.kt:136-148,150-170`）。`UiBackend.execute` 对需要显示的命令先要求 `expectedDisplayKind`，再调用 `acquireUi`（`UiBackend.kt:107-108`；`DisplayTarget.kt:13-15`）。【源码】
- 同名判定只看配对身份和会话名（`SessionOwner.sessionKey = pairing to name`，`Sessions.kt:10-12`）。同名者执行 `session open` 时，`prepareChange` 会直接让旧租约失效（`Sessions.kt:99-121`，第 119 行 `invalidateLease(held)`）。失效同时清掉 REF 和图像（`clearLeaseUi`，`Sessions.kt:281-284`）。【源码】
- 公开指引示范的是固定会话名 `-s task`（`skills/androidctl/SKILL.md:22`）。照着指引做的多个 agent 实例会共用一个名字，同名并发并不是假想场景。【源码】
- `editor commit`（IC）只要求租约目标是主屏（`UiBackend.kt:239-243`），不要求 REF、不要求截图（用户 L8870 定义的"当前编辑器命令"）。`open`、`back/home/recents/key`、`wait/snapshot/screenshot` 也不依赖 REF（`RpcMethods.kt:20-21`）。【源码】
- `session open 不改偏好`是用户 U25 第 3 条原话；"显示偏好改为主机级 deviceId＋session、跨工作区共同跟随"是 U25 第 2 条；"所有依赖显示目标的 UI 请求必须携带 main/virtual 期望……batch 开始时固定目标期望"是 U23 第 1 条。D 是在这些原有决定之上只加了"全显式"。【原件：用户原话】

**偏好拦得住、必填参数拦不住的真实序列。**

| # | 序列 | 用户方案（无种类） | 实施方 D |
|---|---|---|---|
| S1 | A 用 `-s task` 在后台屏工作。B 也用 `-s task`，只想跑一条 shell。按用户新规则，B 先执行 `session open --display main`（选 main 最省：不建屏、不连 UiA）。A 的后台屏被销毁。A 下一步执行 `open --component …`、`keys back`、`editor commit TEXT` 或 `snapshot` | 全部落到主屏：在真人眼前启动 App、按返回键、往真人当前聚焦的输入框打字（IC 只认主屏，正好放行）、把真人屏幕内容读进 agent 上下文 | B 从不需要 `display select main`，共享意图仍是 virtual。A 的请求被 `displayMismatch` 拒绝，A 得知后台屏已丢失 |
| S2 | A 已发出一个不带 REF 的请求，还在路上；B 的 `session open --display main` 先拿到锁 | A 的请求按新的主屏租约执行 | 同一把锁内核验，A 的请求被拒，不存在先检查后执行的空隙 |
| S3 | batch 进行到一半时出现 S1 | 后续不带 REF 的步骤（`open`、`keys`、`wait`）跟随到主屏，前缀照常执行 | batch 冻结了种类，下一步被拒并停止，前缀如实保留（`ui_client.py:596-607`、`ui_batch.py:307-319`） |
| S4 | A 的租约过期，A 重开时 LLM 填了 `--display main`（必填只保证"填了"，不保证"填对"） | 照常执行到主屏 | 偏好仍是 virtual，A 的 UI 请求被拒 |

评审方 §4.1 推演出 D"多拦住的只有两种序列"。它漏掉了 S1、S2 和 S3。S1 的前提恰好由用户新决定"shell、文件、通知、剪贴板也要先开会话"制造出来，所以这条序列在新方案下会比在旧方案下更常见。评审方说"D 自己也只拦得住一半"，针对的是 B 也走完 `display select main` 两步的情形；可是 B 只为 shell 开会话时，根本不会走第二步。【源码＋推断】

**这几种误操作的代价不对称。** 评审方列出的 D 的四类问题（旧偏好误拒、建屏成功但保存失败、UNKNOWN、回主屏要两步）都是拒绝，代价是多一轮调用。S1 到 S4 在用户方案下是动作被执行到真人的前台屏，其中 IC 打字和启动 App 不能撤回。按用户自己定的核心场景（后台屏与真人并行，L2142、U23），后一种代价高得多。【推断】

**评审方另有一处事实偏差。** N14 说种类不符时的提示"把只想用主屏的调用者引错方向"。实际上 `Sessions.kt:160-168` 在期望 virtual、实际 main 时给出的是"run display create or display select main"，已经包含切回主屏的路径。【源码】

**`--display` 必填的伤害（较小，但真实存在）。**

- 已有脚本和指引示例中不带参数的 `session open` 全部会变成参数错误（`SKILL.md:22`、`displays.md` 示例）。这是一次性的、失败即停的破坏，不会导致误操作。
- batch 本身不含 session 命令，必填参数对 batch 没有直接影响。batch 的真正损失是失去种类冻结（S3）。
- 对 LLM 调用者来说，必填参数只把"忘了写"变成"写错"（S4）。评审方用"报错带上次目标种类"来缓解，这句提示文字不进入设备端核验，前提是调用者肯照着做。

**辩护强度：强**（只针对"设备端按请求核验种类"这一要素）。主机偏好文件、跨工作区共享、`display select` 这些部分，辩护只有**中**：用户明确要"减少状态"，这一点评审方是对的。

**如果评审方方案仍被采用，至少保留：**

1. 设备端 `expectedDisplayKind` 核验和 `requireTarget` 的锁内位置，把字段从"必填"改成"可选"。不带时按当前目标执行，带了就原子核验。
2. 在主机端给不带 REF 的目标命令和 batch 头提供无状态的 `--expect-display main|virtual` 断言。评审方 §8.2 自己列过"batch 断言"备选，实施方专题 `sessions-display.md:51` 也指出"可用显式参数/batch 一次声明，不必因此保主机永久偏好"。这样不留主机状态，S2 和 S3 照样能拦。
3. 公开指引不再示范固定会话名 `task`，改为要求每个任务用唯一名字，并写明同名就意味着共享目标、会互相跟随。

**怎样判定谁对：** 用假 daemon 或设备端 JVM 测试复现 S1（同名 B 为 shell 开 main，A 接着执行 `editor commit` 和 `open`），分别在两种方案下检查实际执行目标。再统计真实 agent 是否会复用指引里的固定会话名（例如两条并行任务都照 SKILL.md 起手）。这两项都不需要真机。

### 2.2 题 2：有限 C（用户已采用）——哪些约束必须原样保留，退路链是否妥当

**必须原样保留的约束**（来源：`inputs.md` 的"有限C规则"、整体建议题 2，并已回源码核对）：

1. **user 0 范围。** 只接受属于 user 0 的完整外部 UID。不能因为改读平台窗口的原始 ownerUid，就把支持范围扩大到 profile。当前 `AppInput.target` 遇到 userId≠0 直接拒绝（`AppInput.kt:52-61`）。【源码】
2. **显式 `--expect` 优先。** 当前 `coordinatePackage` 有 `expect` 时直接采用（`AppInput.kt:72-75`）。C 只在没有显式指定时预测。【源码】
3. **在首个 DOWN 之前选定 UID，整条手势固定使用它。** `InputSender` 构造时绑定 `targetUid`（`AppInput.kt:64-69,79-90`），整条手势和必要的 CANCEL 都用同一个 sender。不预测每个 MOVE，也不重建触摸状态。【源码】
4. **不换 UID 重发，不回退到无定向。** 平台拒绝或结果未知时如实上报，不改用别的 UID 再发一次。
5. **已派发前缀如实保留。** 只有"首次调用明确不匹配"或"确知零尝试"才能报 NOT_SENT。已成功的 DOWN、后续指针、MOVE 不匹配，以及返回 false、异常、超时，都沿用现有 UNKNOWN、possibleDown 和同 UID CANCEL（`inputs.md` 引 `PointerGesture.kt:202,246-254`）。【源码，经实施方引用；本人未逐行重读 PointerGesture】
6. **命中自身窗口时在发送前拒绝，不越过它去挑下层窗口。** `inputUid` 遇到自身 UID 抛 `protected`（`AppInput.kt:84-93`）。不能把 `INVALID_UID=-1` 当作"未知"传给 sender。【源码】
7. **坐标变换。** 选窗时在逻辑显示空间里比较"经显示变换后的可触摸区域"和点。不能把窗口自身的 transform 施加到图上的点。如果只支持恒等变换，必须明确声明其它变换会被预先拒绝。
8. **不复制 dispatcher。** 遮挡信任、连接是否存在、DROP 等交给平台判断；平台拒绝不等于该穿透到下一个窗口。
9. **元数据的取得与释放挂在本命令的生命周期上。** 独立 probe 靠 `System.exit` 释放，常驻 worker 不能照搬。R8、隐藏基类的覆写和加载路径都要按实际接线验证。

**用户决定和评审方报告中可能冲突或遗漏的地方：**

- **范围措辞。** 用户写的是"坐标**点击**的默认接收者"。实施方的 C 覆盖整个坐标族（tap、swipe、drag、pinch、timeline 共用 `PointerPlan.COMMANDS → visuals.perform`，`UiBackend.kt:223`）。如果实现时只改点击，拖动和捏合仍按"当前操作窗口 UID"，同一族里会出现两种接收者规则。【源码】
- **"做不成就退"必须是设计期的决定，不能变成运行期的级联。** 用户还写了"预测不出时拒绝并让调用者手动指定"。如果运行时"元数据取不到 → 改用窗口列表 → 再不行不限制"，就成了三层自动兜底。这与用户 L12 的"新增……重试、兜底、开关等须有具体依据"相冲突，也与第 4 条"不换接收者重发"在精神上冲突。建议在实施记录里写明：退路链只用于"内部接口在本平台上接不通时选哪一种实现"，运行时只有"预测成功"和"拒绝"两种结果。【原件：用户原话＋推断】
- **评审方 §4.4 建议在软键盘根包读不到时"用系统默认输入法包名换算"。** 这是猜测：设备上可能启用了多个输入法，"默认"不等于"当前窗口的所有者"。不过猜错只会被平台拒绝，属于安全方向。【推断】

**对退路链的评价（实施方视角）：**

- **第一级：用已采集的无障碍窗口列表判断。方向安全，误拒更多。** 平台在注入时会按目标 UID 核对，所以预测错误只会导致拒绝，不会把输入送到错误的接收者。AOSP 14 的无障碍窗口计算有以下特点（`agents5/25/a14-AccessibilityController.java:1587-1625,1660-1760`）【源码】：
  - 排除 `TYPE_INPUT_CONSUMER`、`TYPE_SECURE_SYSTEM_OVERLAY`、`TYPE_DISPLAY_OVERLAY`、`TYPE_APPLICATION_MEDIA_OVERLAY` 等类型（`isReportedWindowType`）；
  - 排除没有 IWindow token 的窗口（`addPopulatedWindowInfo`）；
  - 排除被上层可触摸窗口完全覆盖的窗口（`unaccountedSpace.quickReject`）；
  - 屏幕被完全覆盖、且焦点窗口已入列后，停止计算下层窗口（第 1624 行）；
  - 不可触摸的窗口一般不报，但焦点窗口无论是否可触摸都会报（第 1686-1696 行）。

  所以列表里的"最上层命中窗口"不一定是真正的触摸接收者。评审方说"无障碍窗口区域就是可触摸区域"，这在单个窗口的区域上成立，在"这个列表是否完整"上不成立。另外，列表来自截图那一刻的观察，和首个 DOWN 之间有时间差。这些都只会增加误拒。
- **第二级：不限制。从实施方视角看，这一级不妥。** 平台注入没有"允许任意接收者但排除自身 UID"的模式。目前坐标输入不会点到 AndroidCtl 自身管理界面，是靠正向 UID 定向保证的（`AppInput.kt:84-93`）。L2142 用户原话是"仅保护 AndroidCtl 自身管理 UI"。如果改成不定向，自身保护就只剩发送前的窗口包名预检，而预检和 DOWN 之间存在竞态。设备端管理界面上有"Force executor exit"这类确认按钮（`connection.md:162-169`）。屏幕文字可以诱导 agent 去点坐标；正好在那一刻弹出的自身确认窗，在不定向模式下会真的收到这次点击。【源码＋推断】

**辩护强度：强**（对约束清单和"不限制"一级的反对）。

**至少保留：**第 1-6 条全部保留。退路只停在第一级。如果连第一级也做不成，宁可退到 D（强制 `--expect`）或 B（当前操作窗 UID），也不要退到 A。

**怎样判定：** 在模拟器上弹出一个属于 AndroidCtl 自身的管理窗口，用 A（不定向）和 C 各点一次它所在的坐标，看平台是否拒绝（需设备）。再把只读探针的窗口元数据和同一时刻的无障碍窗口列表并排比较，统计第一级的误拒率（需设备）。

### 2.3 题 3：C——默认正文保留标准动作 ID 和短名、保留完整窗口目录、事件给摘要、只收窄 host 的 `--interactive`、设备目标规则不动、不新增按名字解析

**一手事实。**

- `UiSemantics.publicTarget` 不只决定标注，还决定**命名聚合**：`visitChild` 遇到公开目标就停止向下吸收文字（`UiSemantics.kt:158-160`），`absorbs` 遇到公开目标就不再把子节点归给父节点（`UiSemantics.kt:357-368`）。改变它，会连带改变父节点的名字、按名字的选择器匹配、`find` 的命中和默认正文的结构。【源码】
- 标注只按树的顺序取前 `MAX_TARGETS` 个公开目标（`ImageMarks.kt:145-155`）。评审方说"标注缺陷只能在设备端修，所以两端要一起改目标规则"，这个推理不成立。标注名额被纯上下文点击节点占满，完全可以只在 `ImageMarks.from` 里做优先级处理（先排有 click 或可编辑的，再排只有上下文点击的）。这仍是设备端的改动，但只改标注排序，不碰命名和选择器。【源码＋推断】
- 默认 `find` 只看可见节点是写进文档的契约："Read an offscreen REF with `snapshot --all` or cached `find NAME --all`; ordinary selector discovery stays visible-only"（`actions.md:183-185`）。也就是说，`find` 的命中范围和不带 REF 的选择器动作实际能作用的范围是一致的。【源码】
- Chrome 对照中，原版一臂自己用 `find --all` 加 `reveal` 找到了离屏目标；原型一臂没有用，结果连续滚了 4 次（`comparison-chrome.md`"实际路线"表）。这说明问题出在"能不能发现这个用法"，不是能力缺失。【原件】

**对评审方方案的具体风险：**

1. **默认隐去标准动作。** 调用者看不到节点支持 expand、collapse、dismiss、page-down 之类的动作，只能先用 `--all` 重读，或者凭猜测按名字调用、被拒后再试。评审方自己把这一点列为未验证（§9 V5）。实施方主张保留数字 ID 和短名，代价只是一个短 token。【推断】
2. **按几何规则收起"窄条窗口"是一个新的启发式分类器。** 平铺式提示、浮动气泡、悬浮通知、画中画都可能是窄条，同时又正是要操作的对象。实施方明确说过"system 类型不等于系统栏，本轮没有可靠通用分类新证据"。评审方给的补救是"走截图或坐标路径时强制全显"，但调用者正是看了默认正文才决定要不要走截图路径。【推断】
3. **无文字事件不打印。** 无文字的窗口变化或内容变化（例如只有图片的对话框弹出）本身就是"界面有动静、该再观察一次"的信号。评审方保留了"有缺口时打印"，损失有限。这一点辩护较弱。
4. **两端一起改目标规则。** 评审方对命名变化"向好"的重算只覆盖了三份 Chrome 原件，没有覆盖原生 App 的名字和选择器回归。【原件：评审方 §8.4 所述】

**按名字调用动作。** 这一项的辩护较弱：`UiSemantics.actionNames` 里已经有现成的短名映射（`UiSemantics.kt:30-48`），新增解析的成本很小。唯一的真实风险是自定义动作的 label 和标准短名重名，需要规定谁优先。

**辩护强度：中**（"设备目标规则不动、标注单独修"和"保留动作 ID"为中到强，其余为弱到中）。

**至少保留：**

1. 只在 `ImageMarks` 里做标注优先级修复，先不动 `publicTarget`。如果仍要改目标规则，要先对原生 App（Contacts、设置、WPS）做名字和选择器的前后对比。
2. 所有"隐含动作"必须能从正文已显示的状态推出来（例如 scrollable 对应 scroll）。不能由状态推出的标准动作（expand、collapse、dismiss、set-progress 等）仍要列出名字。
3. 修 `find` 时仍以可见范围为默认；离屏命中只作为"N 个离屏匹配，用 `--all` 查看"之类的提示给出，不把离屏节点混进可直接动作的结果。
4. 窄条窗口收起时保留一行窗口目录摘要（ID、包名、尺寸），不完全隐藏。

**怎样判定：** 用评审方 V5（同后端、两种呈现各跑一对任务），重点统计因看不到动作而出现的 `--all` 重读和错误调用。再对原生 App 做一次目标规则改动前后的名字和选择器差异重算（不需要设备，可用已有 raw 原件）。

### 2.4 题 4：C——listener 在每个租约首次使用时注册、随租约清理；以及"注销失败不封锁"的风险

**一手事实（AOSP 16 固定副本 `T/research/notifications/upstream/a16-*.java`，以及 `a14-NotificationManagerService.java`）：**

- `registerListener` 调用 `registerSystemService(listener, component, userid, callingUid)`（a16 NMS:5629-5633），登记为系统服务。`enabledAndUserMatches` 里有 `if (this.isSystem) return true;`（a16 ManagedServices:2129-2130）。也就是说，**这个 listener 收到的回调不限于 user 0**。【源码】
- 登记时执行 `updateUriPermissionsForActiveNotificationsLocked(info, true)`（a16 NMS:13139），给 `info.component.getPackageName()`（也就是 `com.android.shell`）授予活跃通知里 URI 的读权限。注销时 `onServiceRemovedLocked` 才收回（a16 NMS:13156-13158,13721-13748）。【源码】
- `registerServiceImpl` 直接 `mServices.add(info)`，**不去重**（a16 ManagedServices:1958-1967）。`removeServiceImpl` 会删除同一 binder 的全部条目（a16:1922-1937）。【源码】
- 当前实现：注销失败时 `access` 不清空，`cleanupFailure` 被置位（`NotificationOperations.kt:64-76`），之后所有新的执行命令都被 `uiCleanup` 拒绝（`Sessions.kt:144`，`TargetManagement.kt:46`）。公开文档写明需要走设备端的执行器重启流程（`notifications.md:35-36`，`connection.md:158-169`）。worker 进程死亡时，平台通过 `linkToDeath → binderDied → removeServiceImpl` 自动清理（a16 ManagedServices:1961,2151-2157）。【源码】

**"注销失败后不封锁"意味着什么：**

1. **一次性失败（例如 Binder 瞬时异常）：**下次使用时补注销通常会成功，风险窗口是两次命令之间的那段时间。在这段时间里，shell UID 持续收到**所有用户**的通知回调，`com.android.shell` 持有通知 URI 读权限。任何 `adb shell` 进程都能读取这些 URI，不限于 AndroidCtl worker。
2. **系统性失败（例如某个 ROM 改了隐藏接口签名，注册能用、注销不能用）：**每条通知命令都会注册一次。条目不去重，于是不断累积；注销每次都失败，用户方案又只记一笔、不封锁。结果是一个跨用户的监听加上 URI 授权一直存活，直到 worker 退出。而 worker 是常驻的，可能几天都不退出。真人看不到任何拒绝，只有 status 里的一条诊断。用户的"下次补"没有规定：如果补注销又失败，还要不要再次注册。
3. **之后不再使用通知命令（任务结束）：**用户方案里没有任何东西会触发"下次补"。这份残留会一直持续到 worker 退出。

实施方坚持"清理失败要有门"，理由是：门迫使权限残留变得**可见并被处理**，而处理方式（重启 worker，由 binderDied 兜底清理）是平台保证有效的唯一路径。评审方说远程调用者会走进死路，这一点成立。但用户定下的核心场景是后台屏与真人并行，并且通知写本身要求主屏亮且解锁（`notifications.md:59-60`）。在这个场景里，设备端的执行器重启通常有人能操作，而且与 L2142 用户选定的"Gateway 手动启动、设备端确认"的安全模型一致。【源码＋推断】

**实施方 C（延长持有期）本身的辩护较弱。** 评审方说注册和注销只需 0-3 ms（本人未核原件）。如果属实，C 省下的时间可以忽略；反过来，C 把上面第 1 点的风险窗口从"单条命令"扩大到"整个租约"（默认 10 分钟空闲期，`connection.md:132`）。从实施方自己的隐私立场看，按命令注册反而更好。C 剩下的唯一优点，是把失败处理放进已有的租约清理门里，不需要新的局部恢复逻辑。

**辩护强度：**"注销失败要有门"为**强**；"每租约持有"为**弱**。

**如果用户方案仍被采用（单一对象、每命令注册注销），至少保留：**

1. **补注销成功之前不再注册**（评审方 V3 自己列出的备选）。这样能防止条目累积和 URI 授权反复下发。
2. 至少对**通知命令**设门：补注销失败时拒绝新的通知读写，但不阻塞其它通道。这正好落在评审方抱怨"范围过宽"和实施方要求"残留可见"之间。
3. 把"listener 仍登记"写进 `status` 和设备端的控制者通知，让真人看得见。
4. 租约结束和 worker 主动停止时都要尝试补注销，并如实报告结果。

**怎样判定：** 在模拟器上用 fault-injection 让注销抛异常，然后 `dumpsys notification` 检查 listener 条目数和 `com.android.shell` 的 URI 授权（`dumpsys activity permissions`），比较两种方案在 N 次命令后的残留。这项需要设备，模拟器即可。

### 2.5 通知地址：严格比对发布时间作为默认

**一手事实。** 当前写操作要比对 key、postTime、按钮序号、**按钮标题**、PI 创建者包名和 UID（`NotificationActions.kt:236-269,275-286`；`notifications.md:62-64`）。reply 另外要求 PI 可变（第 265-267 行）。【源码】

**反向误操作（不比对 postTime 时）：**

1. **媒体通知按钮翻转。** 同一序号的按钮在 Play 和 Pause 之间切换。如果用户决定里的"标题"指的是通知标题，按钮标题核验就没了：调用者看到的是"Pause"，执行的却是"Play"。评审方说这类通知"几乎永远对不上"，而它们恰恰是按序号最容易出错的一类。【源码＋推断】
2. **消息类通知更新。** 同一 key、同一标题（对方名字）、同一来源、同一序号的"标记已读"或"归档"，会作用到调用者没读过的新消息上；dismiss 会让真人错过新消息的提醒。用户方案只对 reply 加了内容比对。【推断】
3. **严格比对的代价对称吗？**不对称。严格比对失败的结果是 `notificationChanged`，什么都没派发，补救只要一次 `notifications get` 再复制新值。放宽之后的误操作不能撤回：通知被清掉了，或者已读状态被改了。

实施方承认"平台更新会改 postTime"这一事实成立。它的立场是：放宽可以作为可选模式，默认值不该变。

**辩护强度：中到强。**

**至少保留：**

1. 无论默认值怎么定，都保留**按钮标题**比对（现有第 284-286 行）和 PI 创建者比对。
2. action 和 dismiss 也比对内容指纹，不只是 reply。或者默认严格、显式 `--loose` 放宽。
3. 用户要的"调用者只复制一个串"与严格比对并不冲突，可以把 postTime 编进这个选择串。

**怎样判定：** 在模拟器上用媒体播放器（或自建控制 App）制造按钮 Play↔Pause 翻转，用宽松地址执行旧选择串，看实际触发的是哪个动作。消息场景可以用模拟器的短信应用，不经运营商。

### 2.6 持久的 diff 阅读基线（显式 `--diff`、唯一基线、按实际交付提交）

**一手事实。** 基线只在显式 `--diff` 时生成，并在 stdout 交付成功之后才提交（`delivery-cost.md` §4.1 引 `history.py:110-182`、`ui_client.py:1022-1118`，本人未逐行重读）。L2142 用户原话是"实现差分，但显式开启"；U25 第 1 条是"保留阅读视图一致性检查"。【原件：用户原话】

**辩护论点：**

- 基线等于"调用者实际收到的那份"，这一点由交付后才提交来保证。`--diff-from PATH` 把这个保证交给了 LLM：它要记得读过哪个文件，还要确认那个文件确实被完整读过（被截断的 stdout 不算）。
- 自动保存的文件会被配额回收（`SKILL.md:50`："Automatic files are reclaimable"）。调用者指定的旧文件可能已经不存在，于是多出一类"基线文件已被回收"的失败。
- 每次调用都要多传一个路径参数（几十个 token），这一点影响很小。

**这一项辩护较弱。** `--diff-from` 同样是显式的，也同样能在比较时核对会话、worker 和视图元数据。它删掉的预留、提交和 batch 配合确实是维护负担，正好符合用户"减少状态"的原则。N15（基线推进后，续读提示只读到零变化）是持久基线自己带来的确定缺陷。

**辩护强度：弱到中。**

**至少保留：**比较前核对保存体里的设备、会话、worker、连接、目标、根和视图选项，不一致时退回完整输出（现在 `ui_diff.py` 的一致性检查）。指定文件被配额回收时，明确报告"基线不可用"，而不是当作空基线处理。

**怎样判定：** 用 V5 那类同后端对照，统计 `--diff-from` 选错文件或文件已被回收的次数。

### 2.7 同源原生帧裁剪（每租约驻留一帧原生图源，zoom 不重新采样）

**一手事实。** U23 第 3 条用户原话逐条规定了：每租约最多一帧、复用失效入口、zoom 不重采、区分图源和坐标资格、"单纯 mappingKnown=false 不妨碍只读裁图"、裁片不成为坐标帧。MuMu 原件为 1080×1920 原生源配 720×1280 JPEG（`stages/36-native-zoom`，评审方 §10 第 7 条也承认）。720×1280 下的内存峰值约 7.49 MB（`delivery-cost.md` §5.3）。【原件：用户原话；原件经实施方引用】

**辩护论点：**

1. **同一帧取证。** 瞬时内容（toast、倒计时、动画中的文字、验证码短暂显示、视频帧）重新截图就拿不到了。评审方 V8 自己也承认，这类任务一旦存在，就应保留同源裁剪。
2. **读到的细节和点击坐标出自同一帧。** 如果新的区域截图成为新的坐标帧，之前在整图上算出的坐标就失效了。如果它不成为坐标帧，调用者读细字用的是 t2 时刻的画面，点击用的却是 t1 时刻的坐标，轮播或滚动内容会让两者对不上。同源裁剪没有这个问题。
3. 评审方说"图源与坐标资格共用状态的耦合已证"。实际上 U23 已经要求把两者分开（mappingKnown=false 不影响只读裁图）。剩下的耦合只有失效规则：观察签名变化时两者一起失效。这一点实施方也承认拆开会增加责任。

**弱点：**实施方承认"细字净收益未证"，完整的预览图已经清晰可读。

**辩护强度：中。**

**至少保留：**如果改成新截图裁剪，裁片要标明自己的采样时刻，并明确不成为坐标帧；不要让它悄悄替换当前坐标帧和图像身份。

**怎样判定：** 评审方 V8。在模拟器上做一个"toast 或倒计时出现后读细字"的任务，比较两种形态能否完成。

### 2.8 独立的编辑器选区（输入法通道），不新增无障碍设置选区命令

**一手事实。**

- U18 用户原话选的是"IC：C，当前编辑器输入加独立局部选区"；U25 原话写着"同时保留独立 select"。【原件：用户原话】
- IC 的选区和 commit 走的是同一个 InputConnection，也就是同一个通道。如果用无障碍的设置选区动作（作用在节点上）先选，再用 IC commit，输入法那一侧看到的选区要等 `updateSelection` 异步同步过来。对 WebView、Compose 和自绘编辑器而言，无障碍选区和输入法选区是否同源，也没有保证。`inputs.md` §2.2 指出：WPS 实测 `setSelection` 被忽略后，如果直接 commit，会写到旧光标处。【原件经实施方引用＋推断】
- 现有无障碍动作入口 `action REF --action-id …` 已经能发出 SET_SELECTION（需要带参数，当前是否支持参数未核）。评审方要的是新增一个带参数的 `select REF START END`，需要新的动作参数、核值和回执设计。

**弱点：**评审方指出，目前没有一例"IC 选区可用而无障碍选区不可用"的证据（WPS 两者都不行，Contacts 两者都行）。实施方也没有提供这样的正例。

**辩护强度：弱到中。**

**至少保留：**如果改用无障碍选区，之后的 IC commit 前必须重新读取输入法一侧的选区并核对，选区不一致就停下来，不能直接写。现有 U25 规定的选区三态（DONE、UNKNOWN、FAILED）语义也应保留。

**怎样判定：** 在 Chrome 网页输入框（contenteditable）和一个 Compose 文本框上，分别用无障碍选区和 IC 选区选一段文字，然后用 IC commit，看写入位置是否正确（需设备，模拟器即可）。

### 2.9 规范树保持现有表示，不稀疏化，也不加传输编码

**重算。** `agents5/25/scripts/pernode.py` 对 `collector/runtime-mumu-clone/a-e9-first.raw.json` 的结果：4226 个节点，树共 6,529,144 B，每节点 1545 B，其中 actions 字段占 21.4%。按 8 MiB 计算，大约能装 5429 个节点。【重算】评审方说"8192 在网页上达不到"，这一点成立。

**辩护论点：**

- 已观察到的真实页面（4226 节点）离 8 MiB 还有约 1.6 MB 余量。超限的例子（8,377,092 B）来自自建 fixture，不是发行版 App（实施方处置表）。容量收益目前停留在假设上。【原件经实施方引用】
- 稀疏化会改变 `--raw` 的公开输出和 `contract/wire-contract.json` 的跨语言契约（按 AGENTS.md 要求导出复核）。Kotlin 端的 `getBoolean`/`has`、签名、ObservedChange，Python 端的 ui_view、diff，都要套用同一张默认值表。漏掉一处，"缺键"就会被误读成默认值。评审方自己也写了"一次性跨语言返工"。
- U25 第 7 条用户原话是"保持 8192 节点及现有字节上限"。

**弱点：**实施方自己的 schema 窄验证显示，去掉默认值可减少 49.91% 的字节；当前也已经有显式的 `unavailable` 列表来区分"未读"和"默认"，缺键语义的冲突没有那么严重。

**辩护强度：弱到中。**

**至少保留：**签名计算要基于展开后的语义值，不能基于稀疏字节，否则表示上的差异会被当成内容变化。默认值表放在唯一的共享位置，并纳入 wire-contract 测试。

**怎样判定：** 找一个真实发行版 App 页面，确认是否真的超过 8 MiB 但不到 8192 节点（需设备）。找不到就说明收益仍是假设。

### 2.10 显式窗口缺席时继续等到截止（D16 不是缺陷）

**一手事实。**

- AOSP 14 计算无障碍窗口时，被上层可触摸窗口完全覆盖的窗口会因为 `unaccountedSpace.quickReject(regionInScreen)` 被排除。屏幕被完全覆盖、且焦点窗口已入列后，循环直接 `break`，下层窗口全部不报（`agents5/25/a14-AccessibilityController.java:1599-1626,1680-1709`）。不可触摸的非焦点窗口也不报（第 1690-1696 行）。【源码】
- U25 用户原话写着"显式窗口缺席不直接判 gone"。【原件：用户原话】
- 当前 `wait` 在条件不满足时按预算继续采样（`UiCondition.kt:387-413`）。动作后观察遇到窗口缺席，报 `settle=changed` 并附说明，然后改用默认范围（`UiPostAction.kt:43-44,97-110`）。【源码】

**论点。** 窗口缺席只说明"这一刻没被报告"，不说明窗口已经销毁。一个模态对话框（权限框、全屏弹层、半透明的全屏 Activity）盖在目标窗口上方时，目标窗口会暂时从列表里消失。按用户新规则：

- `wait --window 12 --gone "Loading"` 遇到权限框弹出，窗口 12 缺席，于是**假成功**，agent 以为加载完成；
- 等元素出现时遇到短暂的模态遮挡，会**立刻报错**，而如果继续等，本来是能成功的。

评审方说两套语义（动作后观察与 wait）不一致。这两者服务的消费者不同：动作后观察报告的是"动作之后发生了变化"，窗口缺席本身就是一种变化；wait 等的是一个未来状态，缺席不能证明这个状态。它们是两种不同的问题，不是同一个问题给出了两个答案。

**辩护强度：强。**

**如果用户方案仍被采用，至少保留：**缺席判定要求窗口**连续多次采样都缺席**，或者在截止前最后一次采样时仍缺席，才算"消失"，不能单次缺席就判定。结果里如实标明"依据为窗口缺席，不是元素消失"。等其它条件时，遇到缺席继续等到截止，不要立刻报错。

**怎样判定：** 在模拟器上，等待期间触发一次运行时权限框（或系统对话框），然后读取 `getWindows()` 的输出，看目标窗口是否从列表里暂时消失（需设备）。

### 2.11 E9 不需要再做实验即可保留；评审方的"两处防护"本身有没有风险

**"不需要再做实验"这一项辩护较弱。** 模拟器上的对比实验很便宜。评审方指出缓存路线在动作之后的路径（滚动、内容变化逐出子树）上会退化，这确实是静态页实验没有覆盖的部分。

**但评审方 V2 的判定规则有一个漏洞。** 它只比较采集时间和完整率，没有比较**新鲜度**。公开缓存靠事件来失效，而事件可能延迟或被合并。动作之后，缓存可能返回动作之前的子树，表现为"完整、很快、但是旧的"，进而造成假的"无变化"。实施方的处置表把这一点称为"cache 交换旧来源"。补实验时必须加上"动作之后的内容是否反映新状态"这一判据，否则实验会系统性地偏向缓存路线。【推断】

**两处"防护"本身的风险：**

1. **放宽回包尾部检查（`CollectionNodes.kt:130`：`data.readInt() != INTERACTION || data.dataAvail() != 0`）。**每次查询都是新的 Binder，`INTERACTION` 是常量 1（第 184 行），所以这条检查实际是在**核对手写解析的布局是否仍与隐藏 AIDL 一致**。放宽之后，如果平台在末尾追加了一个有语义的参数（例如"结果不完整"之类的标志），我们会静默忽略它，把不完整的结果当成完整的；如果参数被插入在中间，`interactionId` 读到的就是别的字段，而第一道检查也只靠这个常量。现在的行为是失败即停：只剩根节点、partial、截止。放宽之后变成静默接受。从"隐藏接口漂移应当被看见"的角度看，这是降级。【源码＋推断】
2. **回包被拒时，在本连接内降级到公开调用一次。**这是一条很少被执行的第二采集路径：它的节点来源、等待方式、身份（sourceNodeId）和 Fresh 语义都与 E9 不同。公开的逐节点调用在评审方自己的数据里需要 1.9-2.2 秒。实施方的专题还提到公开 child 有平台级的 5 秒等待。这样一来，一次降级就可能吃掉 3000 ms 的采集预算，同一条命令里还混着来源不同的树。这也正是用户 L12 要求"兜底须有具体依据"的那一类机制。【源码＋推断】

**辩护强度：**"不补实验"为**弱**；"两处防护有风险"为**中**。

**至少保留：**如果放宽尾部检查，多出的尾部数据要记一条诊断并上报 `trailingData`，不要静默忽略。降级要作为一个显式选项，或者只在明确判定布局不兼容时触发，并在结果里标明"本次采集来源为公开路径"。补实验时加上新鲜度判据。

**怎样判定：** 评审方的 V2 加上新鲜度：滚动或点击后，立即比较两条路线的树是否反映新状态（需设备，模拟器即可）。

### 2.12 暂不加复制浮层抑制；锁屏或熄屏时通知写保持现状

- **浮层。**实施方的理由是：抑制标记不控制读取和粘贴时的隐私 toast，OEM 上"每次都弹"未证（`inputs.md` §3.3）。另外，后台屏与真人并行时，浮层对真人来说也是"剪贴板被借用"的可见信号。**这一项辩护较弱**：实施方专题建议加、整体建议又写"暂不加"，前后矛盾（N16 成立）。浮层还会把剪贴板内容的预览显示在主屏上，从隐私角度看反而支持加抑制。
- **锁屏和熄屏。**通知写要求主屏可交互且已解锁（`notifications.md:59-60`）。open 带有允许后台启动 Activity 的选项（`NotificationActions.kt:207-226`）。在锁屏状态下放行，可能出现无人在场时的后台副作用或界面启动。用户已同意保持现状，这里不再展开。

**辩护强度：**浮层为**弱**，锁屏为**中**（已被采纳）。

### 2.13 提交策略：不重排旧的 40 项历史，在其上追加修正提交

**事实。** U26 用户原话"不批准……重写提交历史"是实施方当时主张"追加"的直接依据。但 U21 用户原话又说"将修正归回所属 commit；必要时调整提交边界。只重写本任务创建的提交"。所以实施方的立场主要来自授权限制，不是设计上的偏好。【原件：用户原话】

**辩护论点：**

- 重新切片之后，中间的每个切片都不是经过测试的那棵树；只有最后一片与最终树逐字节相同。评审方自己的拆分实验"六块里出了五处静默错误"，说的正是这种风险。
- 已有的设备验证和独立 review 都绑定到具体的提交和 APK/host/wire 组合。重新切片后，这些对应关系需要重建；按 U21，每个完整项都要独立 review，等于要重做一遍。

**辩护强度：弱。**

**至少保留：**每个切片都要能构建并通过受影响模块的测试，不只是末片；重切之前的分支保留成归档引用；切片和原有证据、review 之间建立映射表。

### 2.15 评审方 §5 效率预期（固定轨迹投影）的可靠性；实施方保守立场对到什么程度

**投影不可靠的地方：**

1. **假设执行路线不变。**正文变短会改变模型的读取和调用决策。评审方 §5 末尾自己承认，上一轮"Contacts 11,080 token"的投影把默认上限施加到了 `--all` 上，截掉了下一步要用的 Title 引用，根本不可执行。这说明同一种方法已经产出过一次"看似省、实际走不通"的估算。【原件：评审方 §5、§10 第 5 条】
2. **每臂只跑一次。**同一个臂重复运行的波动未知。Chrome 两臂的 response 数分别是 25 和 30，CLI 次数是 20 和 15，路线完全不同：一臂滚动 4 次，另一臂用了 `find --all` 加 `reveal`（`comparison-chrome.md`）。【原件】
3. **指标口径。**评审方用"总输入"，其中缓存输入占 91%（Chrome 原型一臂 1,661,312 / 1,821,534）。总输入衡量的是上下文累积乘以轮次，受轮次数支配。评审方批评"非缓存输入近似噪声"，但它自己用的总输入同样不是金额，也不是注意力。原件里没有价格字段。【原件】
4. **基线不同。**Chrome 旧基线读不到网页正文，设备也不同，"1.0 倍"比较的是能力不同的两样东西（评审方自己也写了"只能比量级"）。
5. **混杂因素。**四臂都整读了 `actions.md`。指引的差异（SKILL 和 observations 两个主题不同）也是干预的一部分。

**实施方立场对到什么程度。** "不能归因于**格式**"基本正确：Chrome 原型一臂多出的 4 次滚动和 12 次采样，可以追到**默认 find 只搜可见节点、零匹配提示又指错方向**这条具体链条（N2），而它属于查找语义和提示，不属于正文格式。在这一点上，评审方逐调用的归因比实施方笼统的"指标交叉"更有用。实施方应当承认这条具体链条，同时坚持"格式本身的净效果未证"。

**辩护强度：中。**

**至少保留：**V5 要按同后端、两种呈现、每臂多次运行来做，并同时报告总输入、非缓存输入、工具交付字节、CLI 次数和壁钟；不用单一比值宣布收益。
