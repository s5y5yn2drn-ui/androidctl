## 1. 结论

1. **方向对；剩余未知改用"做出来、跑真实任务"来回答。** r3 的主线（设备上的会话是唯一的目标来源；阅读、保存、对比共用一份视图；输入通道由调用者显式选；能力全部保留）成立，七个专题核下来没有发现方向性错误。但产品代码三轮没有动过。r3 主稿自己写明，剩余未知"须由所选真实实现验证，当前没有值得独立追加的设备任务"。第三轮新增的真实流程没有翻转第二轮的任何一个推荐，却又引出了两道新题。继续单开研究任务的边际价值很低。工作方式见 §2.1。

2. **13 道题的处置：** 四道已由用户决定（§2.2–§2.5）；一道先验证再定（§3.1）；其余八道按已放行的默认做法执行（§3.2），它们有的是照抄平台就能定的实现细节，有的是该直接修的缺陷，有的只因为先提出了一个可以不要的机制才成为问题。

3. **最该优先的事被排在了最后。** 这个项目的起点是候选的模型总输入达到基线的 1.7–2.2 倍。三轮下来，这件事没有任何新的实测。真实流程原件里，默认输出一半以上的字节仍是逐节点的动作数组（MuMu 上约 51%，Android 14 模拟器上合计约 59%）【重算】。r3 把紧凑正文、`find` 搜全部已采节点、首页指引排在 16 个提交的第 15、16 个，没有量化验收，还删掉了上一版定稿要求的效率对照。它们和一批无争议的缺陷修复一起放在第 0 阶段最先做，做完立刻量（§9）。

4. **真实流程里最高频的摩擦，r3 没有对应项。** 12 条真实业务流程共 199 次命令【重算】，"动作后立即观察，看到的仍是旧页、加载中或空白"约 11 次（评审方逐条判读的估计），是可归于产品的摩擦里最多的一类。r3 着墨最多的两道身份题（第 12、13 题），在同一批流程里造成的额外调用是 0 次（§4.3）。

5. **"减少状态"没有兑现。** r3 落地后，命令约 69 个（候选 71，基线 47），隐藏接口成员约 70–72 个（候选 57），独立的状态或生命周期对象约 20 个（候选约 19）。"能力都留"做到了；"合并入口"净减 2 个命令；"减少状态"是删三份、加约四份。按已定的做法加上 §7 的简化，可以到约 67 个命令、隐藏成员约 70 个；在保住全部能力的前提下，状态最多做到持平（§4.2）。这些是静态计数和按文档的投影，换一种数法绝对值会有出入，增减的方向不变。

6. **新发现 6 个确定缺陷**（§5），其中两个会把调用者带进死路：系统服务重启后 worker 还活着但已经不可用，最后只能到设备上强制结束；清理失败的封锁连正常停止 worker 都挡住。

7. **上一版定稿有 18 处要修订**（§8），多数是被第二、三轮的原件或上游源码纠正的。

### 2.1 授权范围与工作方式

**要做什么**

1. 这一阶段仍属研究。允许在隔离分支上改产品代码并反复打磨，包括删命令、合并入口、改对外行为；做出来的东西可以再推翻重做。

3. 剩余未知用"做出来、跑真实任务"来回答，不再为它们单开研究任务。确实要追加纯研究时，先说明不同的结果会改变哪个决定。
4. 第 0 阶段（§9）做完，带着效率对照的数字向用户汇报一次。之后每个阶段末用真实 App 或真实网站的任务验收。
5. 只用 MuMu 和 Android Studio 模拟器；MuMu 不能建后台屏，后台屏的验证只能在 Android Studio 模拟器上做。运行结论写明"仅模拟器验证"。原有的数据保护、设备独占、不产生业务后果等边界不变。

**依据**

- 产品代码三轮没有动过。r3 主稿自己写明，剩余未知要靠所选的真实实现验证，当前没有值得独立追加的设备任务。【原件】
- 第三轮新增的真实流程没有翻转第二轮的任何一个推荐，却又引出两道新题。【原件】
- 证据最硬的改进（紧凑正文、`find` 搜全部已采节点、首页指引）三轮都没有在真实任务上量过，只有做出来才能量（§4.3）。

**验收标准**

- 主分支和候选分支的提交历史没有变化；新的工作全部在候选之上的新分支里，没有合入、推送或发布。
- 第 0 阶段结束时交出效率对照（§9.2）。
- 每个阶段结束时有真实任务的验收记录，写明误操作、误拒、超时、部分结果和已执行的前缀。
- 向用户提出的问题只限 §3.1 所列事项的验证结果，以及带具体证据的反证。

### 2.2 结果与退出码

**要做什么**

1. 动作类命令：结果字段只反映派发和核值，不因交付失败或清理失败而改写。
2. 读类命令（`snapshot`、`find`、`screenshot`、区域截图）：交付那份观察或图片就是主操作。没交付就是失败、退出 1；已经得到的正文照常打印。
3. 退出码为 0，当且仅当主操作完成、命令行明确要求的附件全部交付、清理已确认。自动的历史保存和配额回收警告不算"要求的附件"。
4. 非 0 的取值：附件或输出没交付为 1；清理未确认为 3，3 优先于 1。通知监听器注销失败只记诊断，不改退出码。
5. `batch`：每一步按同一规则得出退出码，非 0 即停。删掉 batch 里另外那一套交付停止判断。
6. 以进程退出码为准。结果行已经打印之后才发生的失败，改写不了已打印的内容。
7. 指引里写明："退出码非 0 而结果是完成：动作已经发生，不要重做，只补缺的东西。"
8. 退出码 3 同时表示"动作结果未知"和"动作完成但清理未确认"。两种情形都不该重发，不拆码；清理未确认时，回执首行写明"清理未完成"和出路命令（§3.2 第 11 题）。
9. 删掉"完成但退出 1"的两处用法：通知清理未确认只记诊断；启动落点未确认改为"未知、退出 3"（随第 1 阶段的落点确认一起改）。
10. 在第 0 阶段落地，后面各阶段新写的结果都按这套规则。

**依据**

- 候选里同一件事有两种退出码：动作做成了、顺带要的截图没存下来，单独执行退出 0，放进 batch 停下并退出 1；输出写失败、窗口列表附件没取到也是这样。【源码 `ui_client.py:1387-1404`、`ui_batch.py:360-376`】
- 调用者最常见的两种误判是"以为没发出而重发"和"以为要的东西都拿到了"。让结果回答前一个问题、退出码回答后一个问题，两个量各管一件事，单步和 batch 含义相同。【推断】
- 不把结果字段改成整条命令的终态：动作已完成、清理未确认时顶层会显示"未知"，调用者容易去重做已完成的动作。【推断】
- batch 的本地连接关闭失败现在退出 1，后台屏建立失败后的流关闭失败不改退出码，都与"清理未确认为 3"不一致，随本项统一（§5 N6）。【源码】
- 没有任何真实调用者在这些失败分支下怎样反应的数据；这套规则是设计判断，第 0 阶段之后在真实任务里观察。

**验收标准**

- "动作完成、要求的截图没存成"：单步和 batch 里退出码相同且非 0，结果字段仍是完成。
- 读类命令没交付文件：失败、退出 1，已经得到的正文仍然打印。
- 动作完成、清理未确认：退出 3，结果字段仍是完成，首行写明清理未完成和出路命令。
- 通知监听器注销失败：主回执和退出码不变。
- 公开的退出码表与实际行为一致；指引里有上面第 7 条那句话。

### 2.3 动作后的元素采集：保留 E9

**要做什么**

1. 保留 E9（候选新增的手写无障碍回调采集）。三个限额（8,192 节点、3,000 毫秒、8 MiB）数值不变。
2. 加快速失败诊断：回调布局校验失败、解析抛错或事务常量取不到时，立刻让本次采集失败，返回一个专门的错误码，不再静默丢弃后等到截止。
3. 不做尾部兼容，不做自动降级。
4. 一并修掉：本地截止被计成"节点不可用"（上一版 F21）；撞到节点数上限时没有专门原因码（§5 N5）。
5. 研究用的事务计数、研究模式开关和研究日志不进产品。

**依据**

对比实验（MuMu，同一个约 4,200 节点的网页，每格 1 次，四次在同一个 worker 上依次运行；用的是候选加研究补丁的构建）【原件＋重算】：

| 动作后 | 路线 | 采集耗时 | 跨进程事务数 | 整条命令 |
| --- | --- | ---: | ---: | ---: |
| 滚动 | E9 | 705 ms | 361 | 2.94 s |
| 滚动 | 公开缓存 | 990 ms | 1,437 | 3.11 s |
| 展开 | E9 | 903 ms | 883 | 2.86 s |
| 展开 | 公开缓存 | 884 ms | 980 | 2.89 s |

四次采到的树都完整，并且反映了动作后的新状态。四次的整份样本都超出了采集截止 75–323 毫秒，公开缓存在滚动后超得最多。

- 动作后的采集窗口只有约 1.39 秒。滚动后公开缓存用掉其中 71%，E9 用掉 51%。【原件】
- 滚动后事务数相差四倍有平台机制可以解释：滚动事件后约 150 毫秒内，公开路径不做批量预取。耗时差只有一次样本，在这条路线自身的波动范围内；事务数差不是时间噪声。【上游，AOSP 15 `AccessibilityInteractionClient`】
- 单次公开查询的阻塞上限固定为 5 秒，调用方不能缩短；E9 的子节点查询只等剩余预算。根节点和单节点重取在两条路线上都走公开接口，这项优势只覆盖子节点查询。【上游＋源码】
- 换成公开缓存也摆脱不了隐藏接口：候选为了关闭公开缓存已经在用隐藏接口。【源码 `AccessibilityConnection.kt:41`、`HiddenApi.kt:83,90`】
- E9 的接口风险与基线已有的手写动作回调是同一类；它依赖的方法签名和它们在接口里的顺序在 AOSP 14 到 17 没有变（接口文件本身有别的改动）。E9 解析节点用的是系统自己的解析器，手写的只是回调的外层布局。【上游＋源码】
- 逐节点的公开调用在这个页面上静态就要 1.9–2.2 秒，放进 1.39 秒的窗口会变成不完整，所以不考虑。【原件】
- 现在回调布局校验失败时是静默丢弃：等待线程一直等到截止，整个预算耗光后只剩根节点，没有任何指向"协议不兼容"的诊断。【源码 `CollectionNodes.kt:125-130`】
- 按上一版定稿事先写的判据（两者差距小于一次树组装、完整率相同、新鲜度没问题，就换公开缓存），这次结果落在"换"的一侧。保留 E9 的理由是上面第一、二、四条，那条判据没有考虑它们。

没有验证的：真机和厂商 ROM 上这两个接口是否被改过；更大页面、更慢 App 上的分布；公开查询卡满 5 秒在现实里多常见。**构成反证的结果**：任何一台设备报出回调布局不兼容的错误码；或者真机上两条路线在滚动后的事务数也接近。

**验收标准**

- 单元测试里构造布局不符的回调：采集立刻失败并返回专门的错误码，不等到截止。
- 本地截止、应用返回空、撞到节点数上限，三种情形在回执里是三个不同的原因。
- 真实长网页上滚动后和展开后观察：树完整，反映动作后的状态。
- 产品代码里没有研究用的计数和日志。

### 2.4 通知监听器：每个会话登记一次

**要做什么**

1. 整个 worker 只用一个监听对象，只保留一个"可能已登记"的标志。
2. 会话里第一条通知命令注册；之后的通知命令直接用。
3. 会话结束时调一次注销：成功就清标志，失败只记一笔诊断、标志留着。会话在进程内的结束路径（关闭、替换、接管、到期、撤销）汇到同一个接点，注销挂在那里。worker 停止不经过这个接点，也不需要注销，进程死亡后平台自己清理。
4. 通知命令看到标志仍在时，先直接读；只有被系统以"未知监听器"拒绝时才重新注册。别的原因被拒不重新注册（平台不对重复注册去重）。
5. 注销失败不改主回执的退出码，不封锁任何命令，不占用界面资源。`status` 里有一行"监听器可能仍登记"。
6. 不做跨会话的责任转交、来源记录和分列状态。

**依据**

- Android 14 模拟器上，同一个监听对象注册 2 次到 6 次，系统进程里对应的强引用也从 2 条到 6 条，worker 进程退出后归零。评审方用自己写的解析器复算了实施方导出的堆摘录（不是完整的堆）。【原件＋重算】
- 平台注册时挂上死亡通知，注销时不解除。【上游，AOSP 14/15/16 `ManagedServices`】
- 系统进程的这类引用上限是 51,200 条，满了整机软重启。普通用量几年也到不了；每两三秒轮询一次通知的脚本一两天能到。【上游，ART 14 `java_vm_ext.cc`；用量为推断；设备上实际运行的运行时模块版本可能不同】
- 每会话一次时，累积数等于用过通知的会话数。
- 没有会话时不挂监听。worker 常驻监听的做法状态更少，但空闲时系统里也一直有一个 shell 身份的通知监听器。
- Android 15 及以上是否还累积没有测到（堆导出被系统拒绝）。

**验收标准**

- 同一会话里连续执行通知命令：系统里本组件的登记数不超过 1；会话结束后为 0。
- 人为让注销抛错：主回执和退出码不变；随后的观察、shell、会话到期全部正常；`status` 显示可能仍登记；下一个会话的通知命令先读、不重复注册。
- 人为让读取被"未知监听器"拒绝：重新注册一次后读取成功，登记数仍不超过 1。

### 2.5 选区：删除输入法通道的独立选区命令

**要做什么**

1. 删除 `editor select`。选区只有 `select REF START END`，用无障碍的设置选区动作，主屏和后台屏都能用。
2. `editor commit` 并入 `type [REF] TEXT --via editor`；`editor` 命令组不再存在。
3. 偏移以调用者在快照里看到的节点文本为准，单位是 UTF-16；文本可能带标签或装饰字符，指引写明。
4. 选区发出后的读回放在动作后观察之后（§3.2 第 4 题）。
5. 可以让 `select` 不带 REF 时以当前输入焦点所在的节点为目标，补上"不需要 REF"这一用法；做不做由实施者定。

**依据**

- 标准 Compose 文本框上，输入法通道的选区命令一律不会发出：它要求知道文本的绝对偏移，而平台的默认实现返回"未知"，Compose 的输入连接没有覆写。【上游，核对了 androidx 主干和当前的 Compose 发布分支，更早的版本没有逐一核对；源码 `CurrentEditorInput.kt:99-100`】同一个 Compose 应用里无障碍选区成功。【原件，1 个应用 2 次】
- 输入法通道的选区只能落在光标前后 128 个字符内。【源码 `CurrentEditorInput.kt:169`】
- "无障碍选区没通过、输入法通道选区通过"的样本只有一组：Wikipedia 的搜索框上，无障碍选区发出后立刻读回 3 次都不匹配，输入法通道选区对同样的区间 2 次通过。差别来自读回的时机：把读回挪到动作后观察之后，无障碍选区 3 次全对（Wikipedia 2 次、另一个网页编辑器 1 次；前后两组不是同一个构建）。修正读回时机之后仍然只有输入法通道选区能完成的样本，一例也没有。【原件】
- r3 主稿用来支持保留的"多行编辑器 49 字写入成功"是输入法通道写入的成绩，不是选区的。【原件】
- 两种选区的偏移以不同的文本为准：无障碍选区用快照里看得到的文本；输入法通道用编辑器内部文本，调用者事先看不到。带装饰字符的编辑器里两者不同（一个网页编辑器实测是 51 对 49 个字符）。【原件】
- 这个命令不在任何已发布版本里，删除没有兼容成本。【源码，`git tag --contains d5ae012` 为空】
- 失去的：不需要 REF、不需要快照的选区（每次约省 0.4 秒）；理论上存在"有输入法连接、没有无障碍选区动作"的自绘编辑器，目前没有样本。真遇到时再以 `select START END --via editor` 加回来。

**验收标准**

- 命令面和帮助里没有 `editor` 命令组。
- 普通输入框、网页输入框、Compose 输入框上，"先 `select`、再 `type --via editor`"的 batch 走通，写入位置正确。
- 带装饰字符的网页编辑器上，按快照文本算出的偏移选中了预期的片段。
- 后台屏上 `select` 测一次（至今没有测过）。
- 指引写明偏移以快照里的节点文本为准。

## 3. 先验证再定的事项与已放行的默认做法

### 3.1 先验证再定

下面四项现在不作最终决定。每项写明验证之前怎么做、验证什么；结果都报给用户，由用户定。

**第 1 项：后台屏会话里，通知打开界面后的落点核对（第 7 题）**

- 验证之前怎么做：发送前和发送后都用"通知创建者的包和 UID"这一把钥匙。
  - 只对后台屏会话里会打开界面的通知操作（open，以及 Activity 类型的 action）适用。
  - 带目标屏发送；创建者的包在别的屏已有任务时，发送前拒绝。
  - 通知写操作补上动作后观察。观察结束时核对：目标屏上有创建者的包和 UID 的可见任务就是完成；没有就是"未知"、退出 3、停 batch，并列出目标屏上实际可见的包。
  - 不新增读取通知意图的内部接口；不解析意图。
- 核对放在观察结束时的原因：原件显示发送返回后约 16 毫秒任务还不可见，约 0.6 秒后才可见。【原件，Android 14 模拟器，1 次】
- 已知的缺口：通知打开的是别的 App 时（浏览器打开网址、系统通知打开设置），每次都会报"未知"；发送前的拒绝也拦不住接收方 App 在主屏的任务被搬到后台屏。后者只有源码依据（平台会把别屏上已有的接收方任务移到目标屏【上游，AOSP 14 `ActivityStarter`】），没有原件。
- 验证什么：在 Android Studio 模拟器上开后台屏会话，主屏上先留一个浏览器任务，执行一条"打开网址"的通知（创建者不是浏览器）。记录：是否发出、回执内容、界面落在哪块屏、主屏上的浏览器任务是否被搬到后台屏、会话结束后这个任务是否还在。
- 用户届时在两种做法里定：维持现在的做法；或只加一个接口 `PendingIntent.queryIntentComponents`，用查到的预期接收方做发送前拒绝和发送后核对。后者是第二处内部接口例外（它面向系统模块，不在公开 SDK 里，需要的权限 shell 有【上游】）。r3 主稿的方案（两个接口，只用于发送后核对）付了接口的代价却没有补上搬迁这个缺口，不在候选之列。

**第 2 项：动作后立即观察，看到的仍是旧页**

- 验证之前怎么做：只改指引，产品的稳定检查不动。指引写明：会导致页面跳转的动作之后，用等待条件确认预期内容出现；等待范围限定在页面正文内，避免命中地址栏之类的界面文字。
- 背景：这是真实流程里可归于产品的摩擦中最多的一类（§4.3）。其中两次是假的就绪信号：一次回执是"完成，有变化"而页面还是旧列表；一次 `wait --contains` 命中的是地址栏里的网址。【原件】
- 验证什么：第 0 阶段的效率对照里，统计动作后重新观察的次数，以及"回执显示已稳定、页面其实没变"的次数。
- 用户看到数字后定是否改产品。

**第 3 项：紧凑正文是否把"通用动作集"只打印一次**

- 验证之前怎么做：不加。紧凑正文只省可从已打印状态推出的动作，长按存在就列出。
- 背景：离线估算，把本页通用的动作集在头行打印一次、节点只列差异，网页首屏还能再减约 28% 的字节。【重算，字节估算，不是任务收益】
- 验证什么：第 0 阶段效率对照里的默认输出体量，以及动作数组在其中占的比例。
- 用户看到数字后定是否加。

**第 4 项：最终提交历史的形态**

- 验证之前怎么做：在候选之上的新分支里向前提交，不改写现有 40 个提交。
- 什么时候定：全部阶段验收之后。届时给出两种形态供用户定：保留现有 40 个提交再加新提交；或从基线重新切成干净的线性提交，末端与验收过的最终树逐字节相同。

### 3.2 已放行的默认做法

r3 主稿的另外八道题和稀疏表示一项，按下表执行，不再作为问题提出。其中三处会改变可见行为，用户已确认放行，表中已标出。"可见行为的变化"一栏标"—"的，对外行为不变。

| 题 | 做法 | 依据 | 可见行为的变化 |
| --- | --- | --- | --- |
| 第 2 题 坐标接收者的几何范围 | 照抄平台的命中判定：把各窗口的可触摸区域逐个矩形按显示变换换到逻辑坐标，再与按下点比较。支持旋转和缩放。遇到不保矩形的变换，发送前拒绝并提示 `--expect` | 平台就是这样判的，Android 14、15、16 三版相同【上游 `InputDispatcher.cpp` `windowAcceptsTouchAt`】。交给输入系统的显示变换只由平移、缩放、直角旋转组成，永远保矩形【上游，AOSP 15】，所以"只支持保矩形变换"与"完整仿射"两种写法只在走不到的输入上有差别。只支持不旋转有真实代价：横屏的网页上预测器直接拒绝【原件】 | 横屏时不带 `--expect` 的坐标点击可用 |
| 第 4 题 无障碍选区何时确认 | 同一次读回挪到已有的动作后观察之后；读到的与动作前相同则报"未知"；预算不足也报"未知"，不跳过读回 | 网页上立即读回 3 次全错，观察后读回 3 次全对【原件】。不增加任何调用 | — |
| 第 5 题 输入法通道写入的完成证明 | 偏移未知时，允许以光标为锚做精确的局部比对：光标前紧挨着的是"原前文加写入内容"，光标后紧挨着的是原后文，选区已折叠。满足即报完成，回执注明这是相对证明；其它情况报"未知" | 按现在的规则，`type --via editor` 在所有标准 Compose 文本框上永远报"未知"、永远让 batch 停下，尽管实际写入是对的【上游＋原件，1 个 App 2 次】 | Compose 应用里 `--via editor` 能报完成，回执注明是相对证明。局部内容重复时插错位置看不出来，回执不证明整个字段。**用户已确认** |
| 第 8 题 后台屏会话是否监测别屏任务被移入 | 不监测。只在入口检查。文档写明：后台屏不隔离 App 的任务、进程、播放服务和数据 | 实测里最重要的副作用根本不涉及任务移动：主屏暂停着视频，后台屏另开同一 App 点一下，主屏那边的播放被重新启动，两个任务都没有移动【原件，1 次】。任务归属检查发现不了这类事，却要每个动作多查一次 | — |
| 第 9 题 区域截图的坐标 | 用完整交付图的像素坐标，与点击同一套单位。按 REF 取区域时，用现有的单节点重取拿当前位置再裁，不做整份观察的签名比较。图的尺寸信息保留到下一张完整图或会话结束，不随点击资格一起失效 | 与已有的点击、缩放单位一致。只读截图裁错的后果只是看到一块不对的图；整份签名比较要新采一次树，还会因为时钟、动画这类无关变化误拒 | — |

第 12、13 题的优先级不高：真实流程里，滚动后新的编号就在同一份输出里，调用者直接用了，额外调用是 0 次。它的收益在 batch 里（滚动后旧编号还能用）和 `find` 的离屏命中上。实施方说"必须等稀疏表示先完成"，不成立：最终裁剪在派生之后执行，超出上限的部分会被如实裁尾并标为不完整【源码】。

## 4. 整体方向

### 4.1 组合起来是不是一个一致的产品

把十条主线沿"开会话、选屏、观察、找元素、操作、等待、读结果、保存对比、通知、关闭清理"走一遍，同一事实各只有一个来源这一点成立：

| 事实 | 唯一来源 | 候选里原有几个来源 |
| --- | --- | --- |
| 现在操作哪块屏 | 设备上的会话 | 4 个（主机偏好文件、显示命令、每请求的种类、batch 冻结） |
| 任务落点和冲突 | 一份完整的活任务列表 | 2 个互相校验 |
| 节点、签名、身份 | worker 的节点事实 | 1 个（各消费者各自解释默认值） |
| 阅读、保存、对比 | 同一份最终视图 | 2 份正文 |

接缝处有六处含糊，都应在实施前写清：

1. **退出码 3 两种含义。** "动作结果未知"和"动作完成但清理未确认"，下一步不同（前者去观察，后者去重试清理）。r3 加了重试清理入口之后，没有规定调用者凭什么区分。处理见 §2.2。
2. **同一个"打开"有三种完成含义。** 启动 App：目标包可见才算完成。后台屏的通知打开：按 §3.1 第 1 项。主屏的通知打开：只表示已发送。用户原话是主屏"原有准入保持"；r3 把回执含义也原样保留了。主屏的通知打开也可以在回执里报告实际落点（只报告，不改变结果），做不做由实施者定。
3. **交付失败在单步和 batch 里规则不同。** 见 §2.2。
4. **发送前就被拒绝的坐标命令，图像资格也作废。** 候选在发出第一个事件之前就把当前截图标为失效【源码 `VisualInput.kt:276-290`】。预测器拒绝或命中自身界面时什么都没发出，屏幕没有因这次操作改变，调用者却要先重新截图才能带 `--expect` 再试。做法：发送前拒绝不作废图像资格（列入第 0 阶段）。
5. **按 REF 取区域截图会不会让下一步的坐标点击失效**，r3 没写。按 §3.2 第 9 题的做法（不新采整树）就不会。
6. **两种选区偏移以哪份文本为准**，r3 只写"不能直接互换"。删除输入法通道选区（§2.5）后只剩一套。

另有一处小的：`wake` 在清理封锁期间是否放行，r3 没写。

### 4.2 规模总账

基线到候选的数字用第一轮的脚本复跑，结果一致；r3 落地后的数字是按主稿和底表逐项增删的投影【重算＋推断】。

| 指标 | 基线 | 候选 | r3 落地后 | 按已定做法和 §7 简化后 |
| --- | ---: | ---: | ---: | ---: |
| CLI 叶命令 | 47 | 71 | 约 69 | 约 67 |
| 长选项 | 38 | 68 | 约 65–70 | 约 65 |
| 隐藏接口成员 | 34 | 57 | 约 70–72 | 约 70 |
| 输入通道 | 4 | 10 | 10 | 10 |
| 独立的状态或生命周期对象 | 约 9 | 约 19 | 约 20–21 | 约 19 |

说明：

- 隐藏成员增加的 13 个来自坐标接收者判断要用的窗口信息监听器（用户已批准的唯一例外）。它是编译期的桩，反射计数数不到，这里按概念计入。
- r3 删掉的状态：主机显示偏好、持久的对比基线、跨请求驻留的原生图。新增的：单条坐标命令内的监听器注册、`wake` 自建的短期连接及其收尾、worker 里"上次结束的显示种类"记录、重试清理所需的待完成清理所有权。
- 最后一列按已定的做法加 §7 的简化估算：删除输入法通道选区后 `editor` 命令组整体消失；重试清理并入已有命令（例如对有待完成清理的会话再执行一次 `session close`；清理失败后会话是否还能被原调用者寻址，实施时回源码确认）；`wake` 不建连接（§7）；不做"上次结束的显示种类"记录；通知的多个身份参数换成一个选择串；暂不加通知意图的读取接口（§3.1 第 1 项）。
- 结论：r3 相对候选基本持平、略偏增，相对基线全面增加。实施方的底表承认"不是少几个命令就少几套状态机"，但没有给出总账。

### 4.3 真实流程说明了什么

第三轮用冻结的候选在模拟器上跑了 12 条真实业务流程（WPS 读 PDF、Google Maps 步行路线、MDN、GitHub、GOV.UK、OpenStreetMap、Bilibili、NIST、regex101、京东、同程、Firefox）。评审方按原件重新建账【重算】：共 199 次命令（按流程的命令区间计数），9 条完成（沿用实施方对完成的判定），3 条没完成（同程被强制升级挡住，京东进了风控页，Firefox 的画面不刷新，随后模拟器的系统进程被看门狗杀掉）。

可归于产品的摩擦，按出现次数（次数是评审方逐条判读原件的估计）：

| 类别 | 次数 | 多花的调用 | r3 里的对应项 |
| --- | ---: | ---: | --- |
| 动作后立即观察，仍是旧页、加载中或空白 | 约 11 | 约 12 | **没有** |

三点值得注意：

- **第一类里有两次是假的就绪信号。** GitHub 上点开一条 issue，回执是"完成，有变化"，没有"未稳定"标记，页面却还是旧列表：稳定检查是"两次采样相同即停"，链接获得焦点这一点微小变化之后页面静止，导航还没发生【原件＋源码】。NIST 上 `wait --contains` 命中的是地址栏里的网址，不是页面正文【原件】。这类问题工具很难替调用者判断，但指引可以做到：会导致页面跳转的动作之后，用等待条件确认预期内容出现，并把等待范围限定在页面正文内。先只改指引，是否改产品看第 0 阶段效率对照的结果（§3.1 第 2 项）。
- **13 道题里，第 1、3、4、5、6、7、8、11 题在这批流程里一次也没有成为调用者的摩擦。** 其中第 2、5、6、7、8 题在第二轮有定向实验，不是凭空推演；但就"调用者最常卡在哪"而言，r3 的大部分题量落在低频问题上。
- **这批摩擦数是下限。** 操作者是实施方的 agent，通过一个脚本调用命令行，输出小于 7,000 字节才直接看，大的去读文件（第 12、13 题涉及的那两次滚动，输出各约 35 KB，"新编号就在同一份输出里"是读文件读到的）；GitHub 那一步还借了离线保存的树来选编号【原件】。一个只能按指引操作的新手会遇到更多。

输出体量：这批流程的默认输出里，逐节点的动作数组在 MuMu 上占约 51% 的字节，在 Android 14 模拟器上各组为 43%–61%、合计约 59%；其中"点击"这个动作名只占动作字节的 5.7%【重算】。第一轮指出的问题原样存在。

### 4.4 证据的质量

- 全部运行都在两种模拟器上，没有真机。受影响最大的结论：E9 的接口兼容性；剪贴板浮层的来源判断；文件发布的那个失败（触发它的是 MuMu 的宿主共享目录）；通知引用累积在 Android 15 以上是否仍存在。
- 多数结论每格只有一次样本。r3 主稿对此基本如实，并保留了失败、部分结果和已执行前缀；评审方抽查的关键说法（WPS、MDN、Bilibili、NIST、窗口缺席）与原件一致。说得偏重的一处：Maps 上"名字真的变了所以正确拒绝"，实际是同一个"步行"标签在加载后多了"18 分钟"。说得偏轻的一处：GitHub 那次是假的就绪信号。
- 实施方称各专题的"独立 review 已关闭"。这些 review 是同一套流程里另一个新上下文的 agent 做的，对事实的核对有效，但不是外部独立评审，"已关闭"不等于结论正确。本轮发现的几处（稀疏变慢的混杂因素、E9 背离事先判据、对比功能的离线验证脚本验证的其实是已放弃的方案）都是已关闭的 review 没有指出的。
- 被省略的图片不影响关键结论的可核性。

## 6. 证据不足或说过头的断言

| r3 的说法 | 核查结果 |
| --- | --- |
| 稀疏表示"命令更慢、首份窗口附件预算耗尽"是它的剩余风险 | 主要来自研究用主机的重新展开和冷启动 worker 两个混杂因素，不是稀疏本身。去掉展开，窗口附件在约 4.1 秒就能取到【重算】 |
| "不足以判断先撞到哪个上限" | 时间和字节都可以排除，先到的是节点数上限 |
| 身份改动"必须等稀疏表示完成"，因为旧的完整表示下会超出 8 MiB 86,150 字节 | 数字正确，推论不成立：超出部分会被裁尾并如实标记。代价约是一个本来就不完整的页面再少几十个尾部节点【重算＋推断】 |
| 身份问题的"真实频率未知" | 可以部分量化（§3.2）。"隐藏字段读不到会收紧可用编号"没有任何数据：保存的 16 万多个节点里没有一个带"字段读不到"的标记，既不能说它常见，也不能说它不存在 |
| "切换规则会改旧身份"是代价 | 编号只存在于会话内存里，升级后本来就全部失效，不是真实代价 |
| 监听器按会话注销"要在关闭、替换、接管、到期、撤销、停止各处挂接" | 进程内的结束路径汇到一个接点；worker 停止不经过它，也不需要注销（进程死亡后平台自己清理） |
| 常驻监听"权限窗口最宽" | 字面成立；但 worker 本来就能随时注册，远程调用者能拿到的东西没有变 |
| 保留 E9 是因为"保已有逐请求截止" | 说宽了：根节点和单节点重取在两条路线上都走公开接口，单次同样最长可能等 5 秒 |
| 输入法通道选区"后删会改变公开命令" | 该命令不在任何发布版本里 |
| 文件发布的修订有普遍意义 | 触发它的目录的文件系统标识是宿主共享文件系统（写入端没关时重命名被拒）。真机的共享存储上是否出现未知【需设备】。修法小且无害，可以做，但重要性不宜高估 |
| WPS 的例子说明旧的同帧缩放有实际用途 | 那次缩放比原图晚 30.5 秒，内容是静态 PDF，原始截图里那句话本身就清晰可读【原件，评审方看了两张图】。三轮真实流程里没有找到依赖同帧的业务 |
| 两次窗口缺席的验证 | 与用户的要求逐项对应，如实标注了"同编号窗口回来没测"。没有专门标注的是：这次是窗口真的关了，不是被遮挡；被权限框之类盖住的情形没有样本 |

仍然只有源码依据、没有运行证据的（实施时要测）：坐标接收者预测作为默认路径、在后台屏上、用于拖动和双指手势；后台屏上的无障碍选区和粘贴；跨 App 通知的落点和任务搬迁；`wake` 改走输入注入后能否唤醒；系统进程重启后的完整路径；新的区域截图链路；紧凑正文在真实任务上的净效果。

## 9. 修订后的阶段、依赖、验收与提交拆分

### 9.1 依赖

```
第 0 阶段（无争议先行批次，含结果与退出码的合同）
      │
      ├── 第 1 阶段 会话与目标 ────────────┬── 第 3 阶段 输入与通知
      │                                    │
      └── 第 2 阶段 表示、身份、可点目标 ──┴── 第 4 阶段 交付整合
```

第 1、2 阶段互不依赖，可以并行。第 3 阶段依赖第 1 阶段（通知和坐标都要用会话与任务事实）。第 4 阶段依赖第 2 阶段（保存文件的格式随记录和名字规则定型）。

r3 的 16 个提交按职责拆得基本合理，问题在顺序和几处捆绑：截止归因被绑在采集路线上，通知的缺陷修复被绑在监听器寿命上，紧凑正文被绑在保存文件格式上。下面把它们拆开。

所有提交都做在候选之上新开的分支里，向前追加，不改写现有 40 个提交。第 0 阶段做完向用户汇报一次；之后每个阶段末用真实任务验收（§2.1）。提交的拆分是建议，做的过程中可以合并、再拆或推翻重做。
