# AndroidCtl 路线复审：对实施方 U26 研究与七题的独立评审

评审对象：调研候选产品 `3f45af6`（基线 `7d5be70`）、独立 docs `e91212e`，以及实施方本轮增量包 `androidctl-external-route-followup-review-20261118T034131Z-3f45af6.zip`（整体建议、逐项处置、五专题、新原型与模拟器实测）。候选代码本轮没有变化。

本报告取代上一份外评主报告（`androidctl-candidate-route-review-3f45af6.md`）中与本文冲突的结论，冲突之处列在 §10。本文的推荐都不是用户批准。

**方法。** 增量包先做了完整性校验（外层 20 个文件、内层 5,671 个证据成员的 SHA256 全部一致）。六个子评审各自先读源码和原始回执形成判断，再对照实施方结论；工作记录在 `sub-reports/17`–`22`。子评审之间有分歧的地方由我裁定并在文中写明。文中标"本人复核"的条目是我自己重读源码或重算原件核过的。

**证据类别。** 【原件】读了原始回执、日志、树或图；【源码】读了 `3f45af6` 或固定上游的源码，给出位置；【重算】用自写脚本对原件离线计算；【推断】；【需设备】本评审没有设备，也没有做 Android 构建，这类结论不能用推断代替。

## 1. 结论

1. **实施方本轮的研究是认真的，并且纠正了上一份外评的若干错误。** 通知写、借用剪贴板粘贴（下称借贴）、IC 的 commit 应当保留，上一份外评建议删除或缓行是错的。启动落点确认（题 6）、跨屏已有任务（题 7）、动作次序规整（题 5）三项推荐成立。
2. **但总方向仍有系统性偏差：全部保留，再加新机制。** 本轮没有合并或删除任何一个能力入口，也没有减少任何一份状态。七题中有三题（会话 D、坐标接收者 C、通知 listener C）是在可以整体消除的问题上做局部加法，都有更简单、能力不减的做法。
3. **效率回退没有解决。** 实施方的紧凑阅读原型在 Contacts 上已低于基线，但在 Chrome 网页上总输入仍约为基线的 1.75 倍，题 3 的推荐 C 不改变网页默认正文。原因可以具体指认，其中一项是实施方和内部 review 都没有发现的确定缺陷：默认 `find` 只搜当前视口。
4. **本轮新发现或重新定性的问题有 16 条**（§7.1，含一条实施方文档自相矛盾），其中影响最大的四项：动作数组次序进入设备端变化签名，会把无效动作报成"有变化"；默认 `find` 对离屏目标假阴性；后台屏会话里 `notifications open` 会把界面启动到主屏；通知注销失败一次后，远程调用者无法恢复。
5. **建议的总方向是：保能力，并入口，收状态，不新增隐藏 API。** 具体方案见 §4，需要用户裁决的事项见 §8。相对实施方方案，它少一份主机持久状态、少约 5 个命令、不新增隐藏类；相对上一份外评，它保留通知写、借贴和 IC。

## 3. 整体架构判断

**实施方。** 一是把"不是行为等价"当作保留的充分理由，而等价本来不是标准，标准是能力得失对调用者是否重要。二是每个窄区分都留一份状态，例如题 1 的 D 同时保留设备租约、主机偏好文件、每请求种类字段和 batch 冻结。三是用"已选""内部 review 已关闭"代替"现在该不该有"的论证。四是新增机制只和现状比，不和更简单的公开等价物比（题 2、题 4）。

## 4. 建议的整体方案

原则四条：保留每一项有不可替代场景的能力；同一类操作只有一个入口；同一事实只有一个来源；新增隐藏 API 或长驻注册之前，先证明公开等价物有实测缺口。

### 4.1 会话与显示目标

**做法。**

- 设备租约是唯一权威。只有 `session open --display main|virtual` 和 `session takeover --display …` 能建立或替换租约，`--display` 必填、没有缺省。
- 主机不保存任何显示状态，请求不带种类字段。删除 `display select`、`display create`、偏好文件、batch 种类冻结。
- 没有租约时，所有新的设备命令（包括 shell、文件、通知、剪贴板、应用列表、唤醒）返回"没有会话"，报错里带上本会话上一次的目标种类。已开始的后台任务和传输的后续操作不受影响。
- 回执和 `status` 显示当前目标。
- 建后台屏之前，先做静态前提检查，再让旧租约失效。现状是先失效旧租约再建屏，不支持后台屏的设备上一次失败的建屏就会结束调用者原有的主屏会话（`Sessions.kt:116-120`）。

**为什么不选实施方的 D。** 显示种类偏好是 U23 为"隐式取得主屏租约"设计的保护。全显式之后，隐式建立这条路径已经不存在。逐序列推演【源码＋推断，工作记录 17 §2.1.3】，D 比"无偏好"多拦住的只有：

- 调用者收到"没有会话"后，习惯性执行不带参数的 `session open`，然后把后续操作发到主屏。`--display` 必填在 open 这一步就挡住，比 D 在后续请求处才报种类不符更早。
- 同名的另一调用者只执行了 `session open`、没有执行 `display select main`。这时后来者自己的请求也会被拒；他按 D 的正规两步切回主屏后，先前的调用者照样跟随。D 在这里并不提供可依赖的保护。

D 自己带来的问题：上一个任务留下的 virtual 偏好会误拒只想用主屏的新任务，报错还引导去建屏；建屏成功但偏好保存失败；建屏回执为未知而设备实际已发布；回主屏需要两步。实施方自己的 Contacts 实验收尾时也走了两步【原件】。

**代价。** 现有不带参数的 `session open` 变为参数错误；同名调用者之间没有产品级保护。实施方指出上一份外评的显式会话方案下"同名者切到主屏后旧调用者会跟随"，这一点成立，上一份外评没有跨请求的代际机制。如果用户确实需要同名并发保护，应当做调用者自持的租约句柄，而不是共享的种类偏好；本评审不推荐做。

### 4.2 启动、落点与后台屏

- 落点确认采用实施方题 6 的 C。补充一点：目标屏前景可以直接取最后一次观察里目标屏的应用窗口包名，它与调用者将要操作的树同源同时点，不需要额外读取【原件：VLC 回执中 settle 内最后一次采样已是 `org.videolan.vlc` 窗口】。任务列表读取只用于启动前的冲突判定和启动后"是否有别屏任务被移入"的后验。
- 跨屏已有任务采用实施方题 7 的 C。选项建议直接叫 `--multiple-task`，避免"新实例""安全"这类暗示隔离的词；带上它时，对启动模式必然使其无效的组件在解析阶段就拒绝。
- 结果与退出码统一：落点未确认时不要再出现"done 加退出码 1"。
- 后台屏本身同意实施方：保留现有建屏参数、逐输入检查目标屏状态、主屏亮且解锁的输入门；不加隐藏输入法策略、保活、独立能力探针命令。上一份外评在这几处的建议撤回（§10）。

### 4.3 节点、等待与变化

- **动作次序按确定缺陷修**（题 5 的 B）：生成节点事实之前按动作 ID 排序。次序没有任何消费者。
- **目标判定两端共用一条规则，只把上下文点击（ID 16908348）归为普通动作。** 实施方只改 host 的 `--interactive` 筛选，会留下截图标注缺陷，并引入第二个"目标"概念。上一份外评的白名单会藏掉不带标签的自定义动作，太强，实施方的批评成立。三份 Chrome 原件重算：40 个标注名额中 25–33 个被只带上下文点击的文字节点占用，14–21 个真正可点的目标得不到标注【重算，工作记录 19】。
- **规范树改为稀疏表示**（缺键即默认值，动作只存 ID，有标签时另附）。当前 Chrome 页每节点约 1,546 字节，8 MiB 只装得下约 5,400 个节点，8,192 的节点上限在网页上达不到；稀疏后约 774 字节，才真正可达【重算】。实施方"只在传输层压缩不增加容量"的判断是对的，这正说明应该改规范树本身。
- **E9（手写的无障碍回调采集）暂时保留，但属于证据不足。** 静态页面上，公开的缓存路线与 E9 的采集时间接近（655/1,047 ms 对 606/580 ms），逐节点公开调用明显更慢（1,909/2,209 ms）【原件】。上游源码显示缓存路线在动作之后的路径上会退化：只接收最后一次交互的预取、滚动后 150 ms 内不预取、内容变化会逐出子树【源码，AOSP 15】。本轮实验只测了静态页面，没有测这条路径，而它决定取舍（§9 V2）。两个子评审在这里有分歧，一个主张保留、一个倾向换成缓存路线；我采用"保留并补一次决定性实验"，同时做两处加固：放宽回包尾部的严格检查（`CollectionNodes.kt:130`），以及回包被拒时在本连接内降级到公开调用一次。
- **窗口缺席统一语义。** 对 `--gone` 条件，窗口缺席算满足并附说明；其它条件立即以"窗口缺席"失败。动作后观察和 `wait` 用同一张解释表。
- **变化的默认呈现合并为一个结论**（有变化、无变化、仍在变、未知，加变化所在位置），各套计算和 JSON 细节保留。
- 实施方拒绝"settle 改成纯稳定判断""系统动作借旧树做基线"，成立，上一份外评这两条撤回。采样加一个固定的起点间隔下限（例如 100 ms），不按上次耗时成比例。

### 4.4 输入

- **插入式文本输入统一到 `type [REF] TEXT --via keys|paste|editor`。** `editor commit` 并入 `--via editor`，语义不变。
- **IC 的 commit 保留。** 它等同于像键盘一样打字，是主屏上覆盖面最广的 Unicode 插入方式，不碰剪贴板。WPS 正文既不暴露文本也不暴露设置文本、粘贴动作，IC 一步写入了中文【原件，旧原型】。上一份外评把 IC 去留挂在 Termux 一项测试上，而这项测试旧包里已经跑通，这个决策门设计得不对。
- **独立选区改为按节点的 `select REF START END`**（无障碍的设置选区动作），主屏和后台屏都能用。IC 的独立选区目前没有一例不可替代的证据：WPS 上被忽略，Contacts 本身也支持无障碍选区【原件】。是否同时保留 IC 选区交用户裁决。
- **借贴保留。** 它的独有价值是一次请求内完成"粘贴并尽量还原真人的剪贴板"，在后台屏与真人并行时最有用。实施方用"Termux、WPS 还需要快捷键或菜单"论证"两命令替代不等价"，这个论据不成立：借贴自己也只走无障碍粘贴动作（`UiActions.kt:257-262`），同样用不了这两个 App。保留的理由是恢复能力本身。同时应加复制浮层抑制（实施方的专题建议加，整体建议却写"暂不加"，前后矛盾），并精简默认回执。
- **坐标默认接收者用无障碍窗口目录命中。** 规则：在已与截图核对一致的窗口目录里，按层从高到低找第一个区域包含首个按下点的窗口，用它的根包换算 UID 后固定给整条手势；读不到根包、命中自身窗口时在发送前拒绝，调用者改用 `--expect`。依据：AOSP 14 的无障碍窗口填充器本身继承自窗口信息监听器，无障碍窗口区域就是可触摸区域【源码】；失败用例的工作区里，目录已含 `inputMethod` 窗口，区域 `[0,658,720,1184]` 与实测可触摸区域一致，被拒的点 (72,902) 命中的正是它【重算，本人复核目录原件】。它保留了平台的 UID 检查，不需要继承隐藏抽象类、不需要回调生命周期和坐标变换。局限是嵌入式跨 UID 内容会被如实拒绝，表现与现状相同。目录里软键盘窗口当前没有读根包（`content: notRead`），实现时要读一次，或用系统默认输入法包名换算，这一点需设备确认（§9 V1）。
- 首个按下已明确未发出时跳过后采样（`VisualInput.kt:244`），实测这一步白花约 2 秒【原件】。派发前先记未决状态的做法保留，上一份外评把它定为缺陷过强。
- 结构化启动参数保持现有窄子集。上一份外评建议改走平台迁移，会自动加读授权并扩大载体，撤回。

### 4.5 通知

- **读和写都保留。** 决定性的事实是：后台屏会话里下拉通知栏被直接拒绝（`SystemActions.kt:41`，本人复核）。上一份外评让调用者"打开通知栏加节点操作"替代通知写，在后台屏模式下根本走不通。
- **listener：每个 worker 只用一个对象，每命令注册和注销，注销失败只记诊断并在下次使用或停止时补注销。** 平台按对象身份一次删除该对象的全部登记【源码，AOSP 14/15/16 `ManagedServices.removeServiceImpl`】，所以"多个旧登记累积"在单一对象下不会发生。清理三态、退出码改写和全局封锁门可以整体删除。现状是每条命令新建对象（`NotificationAccess.kt:45`，本人复核），注销失败后置一个永不复位的标志，拒绝所有新的执行命令，而文档写明没有远程强制退出手段，对远程调用者是死路。
- 不注册 listener 直接读通知不可行：shell 没有相应权限【源码，AOSP 14/15/16 Shell manifest；实施方另有设备原件】。实施方这项排除成立。
- **后台屏会话里的 `notifications open`** 现在会把界面启动到主屏，没有拒绝也没有文档说明【源码】。应当让它落到目标后台屏，做不到就拒绝并提示。
- **自身保护扩到全部通知写命令**，按通知所属包判断。现在只有计划中的 open 检查；dismiss 可能把"有人在远程控制"的通知清掉。
- 已知不可清除的通知在派发前拒绝；控制者通知按可见内容去重、轮询成功只清轮询自身的错误。这两项同意实施方。
- **地址默认值建议改。** 现状严格比对发布时间，而平台每次更新通知都会重置它，进度、媒体类通知几乎永远对不上。建议 action、open、dismiss 默认比对键、动作序号、标题和创建者；reply 比对内容指纹；合成一个由 `get` 输出的选择串，调用者只复制一个值。交用户裁决（§8）。
- reply 保留。上一份外评把"真实聊天未验证"当作不进首版的理由过重；可以在模拟器的短信应用上做一次不经运营商的验证后发布，是否可行需确认镜像【需设备】。

### 4.6 观察交付

- 默认正文按 §5 的规格重做；打印、保存、diff 共用一份视图。
- **修默认 `find`**：在全部已采节点上搜索，离屏结果标明并给出引用，可直接 `reveal`。
- **diff 改为无状态。** `--diff-from PATH` 由调用者指定一份自己读过的保存体；删除工作区持久基线、预留与提交协议、batch 收尾配合。实施方反驳"无变化只打印一行不是等价替代"成立，上一份外评这条撤回。
- **看清细字的能力改为新截图带区域裁剪**（`screenshot --region …`，设备端按原生分辨率裁剪），不再每个租约驻留一帧原生图。上一份外评说"证据全部是 720×1280、从未缩放"是事实错误，MuMu 原件是 1080×1920 的源和 720×1280 的预览【原件】。但同一组原件里完整预览图已清楚可读，实施方也承认细字收益未证；而图源与坐标资格共用状态的耦合是已证的。用户看重同一帧取证时再保留现形态（§8）。
- batch、默认 JPEG 与交付坐标、标注、采样与发布分离、独立交付、传输块大小、帮助同源：保留。

## 5. 效率回退是否已解决

**四臂复算**【重算，工作记录 20；原生 usage，与实施方数字一致】

| 臂 | 总输入 token | 相对旧基线 | CLI 次数 |
| --- | ---: | ---: | ---: |
| Contacts 旧基线 | 812,987 | 1.00 | 16 |
| Contacts 候选原版 | 1,395,045 | 1.72 | 20 |
| Contacts 紧凑原型 | 629,770 | 0.77 | 15 |
| Chrome 旧基线 | 1,041,124 | 1.00 | 20 |
| Chrome 候选原版 | 2,326,407 | 2.23 | 15 |
| Chrome 紧凑原型 | 1,821,534 | 1.75 | 20 |

Chrome 新旧两轮设备不同，旧基线读不到网页正文，只能比量级。

**Chrome 原型为什么仍然贵**，可以逐调用指认【原件＋源码】：

1. 默认 `find` 在非 `--all` 时丢弃不可见节点，只在 84 个视口节点里搜索 4,226 节点的树，离屏目标返回零匹配；续读提示又固定指向同样看不到离屏内容的 `snapshot --cached`（`ui_view.py:236-237,269-284,533-541`，本人复核）。原型执行者因此连滚 4 屏，每屏打印 4–6 千 token 的整页正文。
2. 原型只做了浅层精简，输出里 42% 字节仍是动作数组，`{"id":64}` 出现 1,014 次。
3. 网页上每个容器都因上下文点击成为目标。
4. 四臂都整读了 `actions.md`。

实施方说"Chrome 指标交叉，不能归因"，过于保守。另外，它用"非缓存输入更高"说明原型更贵，这个指标约等于最终上下文大小加缓存未命中噪声，不能用来判断格式【重算】。

**实施方题 3 的 C 不解决网页回退。** 它只收窄显式的 `--interactive`，实施方自己也写明"普通正文不会因此自动更短"。它还坚持默认保留标准动作的数字 ID 且"不新增动作名解析"，而 `action` 已支持按标签调用，标准动作大多有专用命令，设备交付的动作本来就带名字。

**建议的默认正文规格**（细则见工作记录 20 §2.2）：

- 节点行只写偏离默认的状态；动作只列非隐含项（`click` 短名、带标签的 `名:标签`、无标签的自定义 `{id}`）；标准动作可用 `action REF --action NAME` 按已交付的名字唯一匹配。
- 头行只留序号和偏离默认的事实；贴边、窄条、未读的系统窗口按几何规则收起，走截图或坐标路径时强制全显；事件只在有文字或有缺口时打印。
- 失败、未发出、未知结果的行原样不压缩；内容未知必须写出。
- `--all` 也用紧凑动作，默认上限不作用于显式 `--all`。

**预期**【重算，固定轨迹投影，假设执行路线不变】：原生页每次动作约 250–450 token（基线约 600–750，原型约 1,000）；网页视口约 1.2–2.2 千（原型 4–8 千）；总输入约为基线的 0.67–1.08 倍（Contacts）和约 1.0 倍（Chrome）。这是投影，不是实测；隐藏隐含动作后执行者是否出错，需要一次同后端、两种呈现的模型对照（§9 V5）。

上一份外评的正式数字"Contacts 11,080 token、基线的 1.13 倍"不能再用：它把默认上限施加到了显式 `--all` 上，截掉了下一步要用的 Title 引用（位于第 19,969 字符处），实施方的这条反例成立【重算】。
