## 1. 总方向

**能力都留，合并入口，减少状态。** 原则上不新增 Android 内部接口，唯一例外是坐标输入的接收者判断（§2.5）。

候选相对基线的规模：CLI 叶命令 47 → 71，长选项 38 → 68，反射访问的隐藏 API 成员 34 → 57，公开指引的规范性句子 331 → 594，输入通道 4 → 10，独立的状态机或生命周期对象约 9 → 约 19【重算，静态计数】。同一对真实任务的模型总输入是基线的 1.7–2.2 倍（§5）。本文的各项决定针对这两件事：调用者要学的和要读的太多；同一事实有多个来源。

实施后应当达到：

- 每一项有不可替代场景的能力都还在：后台屏、通知读写、编辑器直输、借用剪贴板粘贴、区域细看、差异阅读、batch。
- 同一类操作只有一个入口，同一事实只有一个来源。
- 默认输出回到基线量级（§5 的预期）。

## 2. 已决定的事项

每项写"要做什么""依据""验收标准"；带条件的写明条件和退路。元素采集的去留等实验结果（§3）；另有两处要等验证结果后由用户决定（§4）。

### 2.1 会话与显示目标

**要做什么**

1. 设备上的会话（租约）是"现在操作哪块屏"的唯一来源。主机不记显示种类：删除偏好文件 `display.json`、每请求的种类字段 `expectedDisplayKind`、`display select`、`display create`、batch 的种类冻结。
2. 只有 `session open --display main|virtual` 和 `session takeover --display main|virtual` 建立或替换会话。`--display` 必填，没有缺省。
3. 没有会话时，所有新的设备命令都返回"没有会话"，包括 shell、文件、通知、剪贴板、应用列表这些不碰屏幕的命令。已开始的后台任务和传输的后续查询、输出、取消不受影响。`status`、`devices`、`pair` 不需要会话。
4. `wake` 不需要会话。别的会话占着设备时仍然拒绝。
5. 同一会话已经存在时再次 `session open`：
   - 请求的种类与现有会话相同：原样返回现有会话，不清空引用、图像和后台屏。
   - 请求的种类不同：拒绝，报错写明现有会话的种类，并给出两条出路：先 `session close`，或带显式的替换选项（例如 `--replace`）重开。
6. 不提供"随命令带上期望种类、由设备核对"的单次断言。
7. "没有会话"的报错带上本会话上一次的目标种类。这份记录只在 worker 内存里；worker 重建后没有记录，报错要明确写"上次目标未知"，不给缺省值。
8. 回执和 `status` 显示当前目标。公开指引的示例写 `--display KIND` 并解释怎么选，不把 `main` 写成字面示例；要求每个任务用自己的会话名，并写明同名即共用同一个会话。
9. 建后台屏时，先做能在建屏前判断的前提检查（权限、平台特性、主屏亮且解锁），全部通过后再让旧会话失效。
10. 建屏结果的"已完成"记录与会话发布放在同一个同步块里。

**依据**

- 显示种类偏好是为"没有会话时隐式取得主屏会话"设计的保护。会话全显式之后这条路径不存在，偏好剩下的作用很小，却带来四类误拒或多余步骤：上一个任务留下的 virtual 偏好误拒只想用主屏的新任务；建屏成功但偏好保存失败；建屏回执未知而设备实际已发布；回主屏要两步。【源码＋推断】
- 候选在无会话时隐式建立主屏会话：`Sessions.kt:90-97,136-149`；shell 与文件经 `ShellJobs.kt:33`、`FileJobs.kt:24`。建屏失败后续发的命令因此落到主屏，实施方的 API 37 实测发生过一次。【源码＋原件】
- 主屏的 `session open` 不连接 UiAutomation，也不要求亮屏（`TargetManagement.kt:100-105`），所以"不碰屏幕的命令先开主屏会话"几乎没有代价。【源码】
- 现状是先让旧会话失效再检查建屏前提：`Sessions.kt:98-121`，失效点在第 119 行；主屏就绪检查、权限、建屏本身都在其后（`TargetManagement.kt:46-102`、`WorkDisplay.kt:33-77`）。不支持后台屏的设备上，一次失败的建屏会结束调用者原有的主屏会话。【源码】
- 建屏的"已完成"记录在同步块之外（`TargetManagement.kt:49-59`），回复恰好落在两步之间时回执是未知而设备已发布。【源码】
- 候选里重开会话就是替换：旧会话失效，引用和图像清空，后台屏关闭（`Sessions.kt:98-121`、`UiBackend.kt:478-497`）。由此有两种误操作。一是调用者在命令超时或结果未知后习惯性再开一次后台屏会话，原会话其实还在，后台屏和屏上未保存的内容被销毁。二是同名的另一个调用者只为跑 shell 而开主屏会话，原调用者的后台屏被销毁，它之后不带引用的命令（启动、按键、编辑器直输）落到真人的主屏；`--display` 必填拦不住这一种。候选的公开指引示范的是固定会话名（`SKILL.md:22`）。【源码＋推断】
- 熄屏时要开后台屏，得先唤醒主屏。`wake` 若也要求会话，就要走"开主屏会话、唤醒、换成后台屏"三步。【源码：建后台屏要求主屏亮且解锁，`TargetManagement.kt:100-107`】

**这项决定不防什么。** 同名的两个调用者共用一个会话。其中一个显式替换成另一种屏之后，另一个的后续命令会跟随。产品不为此再加机制，靠"每个任务用自己的会话名"的约定。

**验收标准**

- 仓库里不再有偏好文件的读写、种类字段、`display select/create`。契约按 `AGENTS.md` 的流程重新导出。
- 无会话时逐一执行 `snapshot`、`shell`、`files`、`clipboard get`、`notifications list`、`apps`，全部返回"没有会话"，设备上不出现新会话。
- 不带 `--display` 的 `session open` 是参数错误，并提示两种取值。
- 已有后台屏会话时再执行 `session open --display virtual`：返回同一个会话，此前的引用仍可用，后台屏上的任务还在。再执行 `session open --display main`：被拒，报错含现有种类和两条出路；带替换选项后才替换。
- 没有会话时 `wake` 可以执行；另一个会话占着设备时 `wake` 返回占用。熄屏时"`wake`，再 `session open --display virtual`"两步可以建成后台屏。
- 在不支持后台屏的环境（MuMu）上，已有主屏会话时执行 `session open --display virtual`：返回"不支持"和具体原因，原主屏会话仍在。
- 建屏的四种结局（成功、前提不满足、建屏失败、回执未知）之后执行 `status`，结果与设备实际一致；不出现"回执未知但实际已建成且无法得知"的情形。

### 2.2 启动落点确认

**要做什么**

1. `open` 发出后，等已有的动作后观察结束再判断落点：界面稳定了，或观察窗口到期，取这时的最后一次采样。一直在动的界面（启动动画、视频）不会因为"没稳定"而被判未确认。
2. 判断对象：目标屏上是否出现目标 App，按包名和 UID 判断，不要求与解析出的组件精确相等。主屏和后台屏用同一规则。
3. 确认：继续。未确认（目标屏前台是别的包、目标屏没有可见任务、查询失败）：停止 batch，结果是"落点未确认"，退出码非零。未确认不能表达成"失败"或"未发出"。
4. 回执写明目标屏的前台包；前台包不是目标 App 但所在任务属于目标 App 时（例如首次启动弹出的权限框、跳转到浏览器的入口），把这一点写出来。
5. 任务信息只用一个来源（完整的在线任务列表）；删除两个接口的交叉校验。启动前的冲突判断（§2.3）和启动后的落点判断都用它。

**依据**

- 候选在后台屏上只在启动返回后读一次，并要求顶层 Activity 与解析出的组件相等（`ActivityLaunch.kt:254-258`、`ActivityTasks.kt:117-150`）。带入口页的 App 必然得到"落点未知、退出码 1"。【源码】
- VLC 实测：启动返回时读到的是不可见的入口页；观察窗口内最后一次采样里，后台屏的应用窗口已经是 `org.videolan.vlc`；观察结束后 1 毫秒的读取是可见的播放页，同一任务。原回执是"done、落点未知、退出码 1"。【原件，仅模拟器】
- "未确认"表达成失败会诱发重发；对分享类启动，重发意味着重复撰写甚至重复发送。【推断】

**验收标准**

- 带入口页的 App（VLC）在后台屏启动：落点确认，退出码 0。
- 目标屏前台是别的包时：未确认，batch 停止，回执给出前台包。
- 主屏与后台屏对同一 App 的同一启动给出相同的判断。
- 结果字段与退出码不再出现"done 且退出码 1"。

### 2.3 后台屏上启动主屏已有任务的 App

**要做什么**

1. 默认：目标 App 在别的屏已有任务时，发送前拒绝。报错区分"别屏有可见任务"和"别屏只有最近任务里的后台任务"，并给出下一条的显式选项。
2. 显式选项 `--multiple-task`：加上"新任务"和"多任务"两个启动标志另开一个实例。帮助文本写明：与主屏实例共享进程和数据；只保护入口，App 内部之后的跳转仍可能把主屏的任务移到后台屏；会话结束时后台屏上的任务随屏销毁。
3. 带 `--multiple-task` 时，入口组件的启动模式使它必然无效的（singleTask、singleInstance；文档模式为 never 且不是 singleInstancePerTask），在解析阶段拒绝。
4. 不做"移入后台屏""借用后归还"。

**依据**

- 平台按任务亲和性跨屏查找可复用任务，找到后把它重新挂到目标屏（AOSP 14 `ActivityStarter`）。singleTask 和 singleInstance 不论是否带多任务标志都会尝试复用。【上游】
- VLC 的入口页是标准模式，它转发到的播放页和主页是 singleTask（VLC 3.7.1 清单）。给入口加标志只能让入口落在新任务，转发的页面仍复用已有任务。【源码】
- Contacts 实测：主屏任务 176 与后台屏任务 177 同进程同 UID；只在后台屏的草稿里编辑，主屏草稿不变；关闭会话只结束后台屏任务。这两次启动是直接用 shell 的 `am start` 发出的，证明的是平台能力，没有经过候选的 `open` 命令和预检。【原件，仅模拟器】
- 候选的冲突检查把最近任务里不可见的后台任务也算在内（`ActivityTasks.kt:50,85-107`）。常用 App 大多会被默认拒绝，所以报错必须直接给出显式选项。【源码】

**验收标准**

- 主屏有任务的 App 在后台屏启动：默认被拒，报错含任务状态和 `--multiple-task`。
- 标准模式入口带 `--multiple-task`：后台屏出现新任务，主屏任务的编号和所在屏不变；会话关闭后只有后台屏任务被销毁。
- singleTask 入口带 `--multiple-task`：解析阶段被拒。

### 2.4 后台屏本体

后台屏保留。下列各项保持候选现状，不改：

- 建屏标志组合（公开、仅自有内容、支持触摸、销屏时销毁内容、可信、自有焦点、不抢顶层焦点），以及建屏后读回标志。
- 建屏时在预算内等待屏状态变为 ON。
- 每次输入前检查目标屏为 ON；"主屏亮且解锁"是建后台屏和在后台屏上输入的前提。
- 所有结束路径都销毁后台屏及屏上内容；不保留内容，不搬回主屏。

不做的：保活、锁屏豁免、独立显示组、输入法隐藏策略、独立的能力探针命令。

平台事实，写进公开指引：

- 后台屏只服务"真人正在用手机，agent 并行干活"。主屏锁定时屏上应用被停；Android 16 上后台屏的电源状态跟随主屏。【上游】
- 后台屏拿不到输入法，编辑器直输只能用于主屏（§2.6）。【上游】
- 通知、剪贴板、shell、文件、唤醒是设备级的，不因会话在后台屏而与真人隔离。
- 后台屏会话里不能用 `notifications`（下拉通知栏）、`home`、`recents`（`SystemActions.kt:41-43`）。【源码】
- MuMu 不能建后台屏（shell 没有可信屏权限）。后台屏的全部验证只能在 Android Studio 模拟器上做。【原件】

要修的两处：缺可信屏权限时回执是通用的 `workerFailure`，改为"不支持"加具体原因（§6 F14）；锁态事实的参数错误（F15）。

### 2.5 坐标输入的默认接收者

这是"不新增 Android 内部接口"的唯一例外，例外只限这一项。

**要做什么**

没有显式 `--expect` 时，在首个按下之前，用窗口元数据内部接口（`android.window.WindowInfosListener`）取得当次的输入窗口列表，预测按下点的接收窗口所属 UID，把整条手势固定发给这个 UID。适用于整个坐标命令族（tap、swipe、drag、pinch、定时手势）。

必须遵守的规则：

1. 显式 `--expect` 优先，有它就不预测。
2. 只接受用户 0 的完整外部 UID。命中 AndroidCtl 自身的窗口时在发送前拒绝，不越过它去选下层窗口。
3. 首个按下之前选定 UID，整条手势和必要的取消事件都用它。不换 UID 重发，不退到不定向重发。
4. 预测不出时在发送前拒绝，由调用者用 `--expect` 指定。拒绝的回执给出按下点所在窗口的包名（能得到时），让调用者有东西可填；回执写明这次用的是哪种判断来源。
5. 只有首次调用明确不匹配、或确知一次都没发出，才是"未发出"。已发出的前缀、后续指针不匹配、返回失败、异常、超时，沿用现有的"未知"、可能按下和取消处理。
6. "未发出"时跳过动作后观察。
7. 选窗时跳过不可见、不可触摸、只旁观的窗口；可触摸区域按显示变换换算后与按下点比较。首版只支持恒等的显示变换，其它情况发送前拒绝并写进文档。
8. 不复制平台的分发逻辑：遮挡、连接是否存在、丢弃规则交给平台；平台拒绝不等于该穿透到下一个窗口。

接入方式的硬性要求：

- **只在单条坐标命令执行期间注册，用完注销，不做常驻监听。** 回调里只做一次原子赋值，不加锁，不做分配大对象的处理。原因：SurfaceFlinger 在任一监听者没有确认收到上一条更新时，会扣住后续的非强制窗口信息更新；输入分发器也是同一组监听者之一；本进程的确认要等 Java 回调返回。worker 的回调一慢，全系统的窗口几何更新都会延迟。【上游，AOSP 14 `WindowInfosListenerInvoker.cpp:86-110`，14/15/16 一致】
- 每次注册拿到的初始数组是空的，数据经回调到达。设一个首次回调期限；超时即视为不可用。注册和注销的原生调用都不回报状态，权限被拒与"还没有数据"从 Java 一侧无法区分，只能靠这个期限。【上游＋原件】
- 注销返回后仍可能收到一次在途回调，要忽略。原生层只持有监听对象的弱引用，注销返回前 worker 必须强引用它。【上游】
- 这是隐藏的抽象类，必须子类化，不能用动态代理。候选现有的隐藏接口都走反射，这里要新增只参与编译的桩。发行构建开了代码压缩，要加保留规则；否则覆写的回调方法可能被改名或删除，表现为静默收不到数据。必须在发行构建上验证。【上游＋源码】
- `InputWindowHandle` 的 frame 字段在 Android 14 是四个整数，15 起是矩形；不要用它，用可触摸区域。【上游】

**条件与退路**

- §8.1 的 C1–C6 全部通过：按上面实施。

### 2.6 文本输入

**要做什么**

1. **统一入口。** 光标处插入文字统一为 `type [REF] TEXT --via keys|paste|editor`。`editor commit` 并入 `--via editor`，行为不变。带 REF 用 `--via editor` 时，REF 必须是当前输入焦点，否则拒绝。不新增发送后自动换通道。
2. **编辑器直输（输入法通道）保留"打字"。** 只用于主屏。
3. **选区改为通用做法。** 新增 `select REF START END`，用无障碍的设置选区动作，对任意输入框按位置选，主屏和后台屏都能用。删除输入法通道的独立选区命令。实现要点：
   - 目标不是当前输入焦点时先聚焦再选。平台的文本控件对可编辑框执行该动作时不会请求焦点。
   - 执行前先读当前选区；与请求相同时直接报完成。平台在选区未变时返回失败。
   - 执行后读回选区核对；回执给出选区和对应的文本片段。
   - 偏移以编辑器的真实文本为准，单位是 UTF-16。节点的无障碍文本可能带附加标签（Contacts 的姓名框多一个", 姓名"后缀），文档写明这一点。
   - 非空选区会弹出系统的选择工具条，它会进入之后的观察；文档写明。
4. **借用剪贴板粘贴保留。** 借写和恢复都带上系统界面的"抑制复制浮层"标记。默认回执精简为三项：插入核值、粘贴是否发出、剪贴板是已恢复、已跳过还是未知。文档写明：
   - 原剪贴板含 URI 或 Intent 时拒绝借贴，这时用 `clipboard set` 加粘贴并接受覆盖。
   - 目标 App 粘贴时系统的"已从剪贴板粘贴"提示关不掉。
   - 恢复后的剪贴板来源是 shell，描述里多一个系统键。
   - worker 被强杀时借写的内容会留在剪贴板，原内容丢失。
5. 结构剪贴板的读写与空值准入保留。对外只给三种状态并附原因：有内容、确认为空、读不到。其余采样细节只进 JSON。
6. 结构化启动参数保持现有的窄子集（标量、单个流、显式读授权），不改走平台的自动迁移。

**依据**

- 编辑器直输是主屏上覆盖面最广的任意文字插入方式，不碰剪贴板。WPS 正文的焦点节点不可编辑、没有文本、不提供设置文本和粘贴动作，直输一步写入了中文。【原件，研究探针，仅模拟器】
- 输入法通道的独立选区没有不可替代的证据：WPS 上请求选区后选区未变；Contacts 上成功，而该节点同样提供无障碍的设置选区动作。【原件】
- 平台文本控件对设置选区动作的处理：只对不可编辑文本请求焦点；选区与当前相同时返回失败；设置后启动选择工具条。【上游，AOSP 14 `TextView.java:14276-14302`】
- 借贴只走无障碍粘贴动作（`UiActions.kt:258-271`）。它的独有价值是一次请求内完成"粘贴并尽量还原真人的剪贴板"：借写后先读当前剪贴板，已不是借写内容就跳过恢复，保留真人新复制的内容（`BorrowedPaste.kt:244-290`）。后台屏与真人并行时这一点最有用。【源码】
- 写剪贴板没有带抑制标记（`ClipboardAccess.kt:79,98-104`）。系统界面只在"模拟器，或来源是 shell"且带该标记时抑制浮层。【源码＋上游，AOSP 14/15/16 `ClipboardListener`】
- Termux 上"写剪贴板后发 Ctrl+Alt+V"粘贴中文已跑通。【原件，研究探针，仅模拟器】

**验收标准**

- `type --via editor`、`--via paste`、`--via keys` 分别在主屏完成一次插入；`--via editor` 带非焦点 REF 被拒。
- `select` 在未聚焦的输入框上：选区正确，随后的插入写进该框。
- 借贴前后剪贴板内容一致；借贴期间真人另行复制时，恢复被跳过。
- 单元测试断言写剪贴板时的来源包名是 `com.android.shell` 且带抑制标记。模拟器上不论来源都会抑制浮层，所以真机上的来源条件没有验证，交付稿如实写明。

### 2.7 通知

**要做什么**

1. **读和四个写操作（action、open、dismiss、reply）都保留。**
2. **监听器。** 整个 worker 只用一个监听对象。每条通知命令注册、用完注销。注销失败只记一笔诊断，不改主回执的退出码，不封锁任何命令。补充要求：
   - 对象仍处于登记状态时，下一条通知命令直接复用，不再注册一次。平台不对重复注册去重。
   - 补注销的时机：下一条通知命令结束时、会话结束时、worker 停止时。
   - "监听器仍登记"进入 `status`。
   - 删除清理三态、退出码改写、通知命令占住 UI 资源的例外。
3. **确认"还是那条通知"。** 所有写操作都比对通知的键、来源（创建者包与 UID）、通知标题、按钮序号与按钮文字。不比对发布时间。`get` 输出一个选择串，调用者只复制这一个值，设备端重算核对。
   - 内容比对：reply 总是比对内容；消息类通知的其它写操作（action、open、dismiss）也比对内容；非消息类通知的其它写操作不比对内容。
   - 消息类的判定：通知使用消息样式（带消息列表），或通知类别是消息、邮件、社交之一。两者都没有的按非消息类处理。
   - 内容指纹由设备端计算，取通知正文和消息样式里最后一条消息；判定结果和指纹都编进选择串。
   - 文档写明退化情形：没有用消息样式、也没有设类别的聊天通知会被当作非消息类，写操作不比对内容；对这类通知，操作前重新 `get` 一次。
4. **后台屏会话里的通知写。** 会启动界面的操作（open，以及 Activity 类型的 action）带上目标后台屏发送；创建者的包在别的屏已有任务时，按 §2.3 的规则发送前拒绝并提示。不启动界面的操作照常发送。发出后界面没有落在后台屏的，如实报告。
5. **锁屏或熄屏时不允许通知写操作**，保持现状。
6. **自身保护。** 通知属于 AndroidCtl 自身包（App 的包，不是 shell）时，所有写操作都拒绝。
7. 已知不可清除的通知，dismiss 在发送前拒绝。
8. 控制者通知按可见内容去重后再发；轮询成功只清除轮询自身写入的错误。
9. 清理失败的退出码与全局规则统一为 3。

**依据**

- 后台屏会话里下拉通知栏被拒绝（`SystemActions.kt:41-43`）。产品命令面内，通知写是后台屏任务处理通知的唯一路径。【源码】
- shell 没有直接读取活动通知的权限，必须注册监听器。【上游，AOSP 14/15/16 Shell 清单】
- 候选每条命令新建监听对象（`NotificationAccess.kt:45`）。注销失败后置一个没有任何复位路径的标志（`NotificationOperations.kt:20-21,65-74`），它拒绝所有 UI 命令，包括只读的 `snapshot` 和 `notifications list`（`UiBackend.kt:46,108`、`Sessions.kt:144`）；同时不释放 UI 资源（`UiBackend.kt:139`），新的 shell 和文件任务、会话到期、远程停止因此都被挡住。恢复只能在设备本机的管理界面上强制退出 worker；`connection.md:169` 写明没有远程强制命令。仍可用的只有 `ui.read`、`status` 这类查询。【源码】
- 平台按对象身份一次删除该对象的全部登记；重复注册会产生重复登记，不抛异常；注销未登记的对象不报错；worker 死亡时登记自动清除。【上游，AOSP 14/15/16 `ManagedServices`】
- 注册实测 0–1 毫秒，注销 0–3 毫秒。【重算，101 组回执，仅模拟器】
- 平台每次更新通知都把发布时间重置为当前时间；候选严格比对它（`NotificationActions.kt:243`）。进度、媒体类通知因此几乎永远对不上。候选已有的"标题"比对针对的是按钮文字（`:278-286`），媒体通知同一序号的按钮会在播放与暂停间切换，这项比对必须保留。【上游＋源码】
- 聊天通知来了新消息，键、标题（会话名）、来源、按钮布局都不变。不比对内容的话，"标为已读"或 dismiss 会作用到调用者没看过的消息。进度类通知的正文持续变化，对它比对内容等于不能操作。按通知类别区分可以两头兼顾。【源码＋推断；聊天应用实际怎样更新通知需设备，见 §8.1 C14】
- 候选发送 PendingIntent 时没有设置目标屏（`NotificationActions.kt:187-231`），通知命令也不受显示目标约束（`RpcMethods.kt:48-56`）。平台会采纳发送方给的目标屏，但目标 App 在主屏已有任务时会把那个任务移到后台屏。【源码＋上游，AOSP 14 `SafeActivityOptions`、`ActivityStarter`；落屏行为需设备】
- 通知写没有自身包检查（`NotificationActions.kt:238-269`），而结构化启动对自身是拒绝的（`ActivityLaunch.kt:187-190`）。【源码】

**监听器登记期间的事实，写进内部文档。** 以系统身份登记的监听器接收所有用户的通知回调；登记时平台把活动通知里的 URI 读权限授给 shell，注销时收回。注销失败到补注销成功之间，这两点持续存在。【上游，AOSP 16 `ManagedServices:2129-2130`、`NotificationManagerService:13139`】

注册频度另有一处要等验证结果后由用户决定（§4 Q4）。

**验收标准**

- 人为让注销抛异常：主回执和退出码不变；随后的 `snapshot`、`shell`、会话到期全部正常；`status` 显示监听器仍登记；下一条通知命令结束后登记数回到 0。
- 同一对象登记状态下连续执行通知命令，系统里该组件的登记数始终不超过 1。
- 进度类通知在更新后仍可 dismiss；按钮文字变化后 action 被拒。
- 消息类通知收到新消息后，用旧选择串执行 reply、action、dismiss 都被拒，回执给出新的选择串。
- 后台屏会话里 open：界面落在后台屏，或发送前被拒并给出原因；主屏的前台任务不变。
- 对 AndroidCtl 自身的通知执行任一写操作：拒绝。

### 2.9 可点目标规则

**要做什么**

设备端和主机端共用一条规则：把上下文点击（动作 ID 16908348）归入普通动作，节点不再仅因它而成为目标。没有标签的自定义动作仍使节点成为目标。所有节点仍有引用，仍可用通用动作命令执行上下文点击。

**依据**

- 设备端的目标判定同时决定截图标注的 40 个名额（`ImageMarks.kt:145-155`）、命名时向下吸收文字的边界、选择器的归并（`UiSemantics.kt:55-56,158-160,357-368`）；主机端同规则（`ui_view.py:39-53,72-86`）。只改主机端会留下标注问题，并出现两个不同的"目标"概念。【源码】
- Chrome 页 4,226 个节点里 4,201 个是目标，其中 3,353 个仅因为上下文点击。13 份网页树重算：40 个标注名额里 22–31 个被这类节点占用（列表、单元格、标题、图片、区域等容器，不只是文字），9–29 个真正可点的目标得不到标注。首屏可见的 105 个节点里 84 个是目标，`--interactive` 只滤掉约两成。【重算】

**验收标准**

- 同一批网页树上，标注名额不再被仅带上下文点击的节点占用。
- 实施前先做 §8.1 的 C13：用已有的原生 App 树（Contacts、设置）和 Chrome 树，按新旧规则各算一次节点名、选择器命中和标注，逐项列出差异。名字因吸收更多文字而明显变长、或选择器命中发生非预期变化时，先报告再继续。
- 契约测试更新；设备端与主机端对同一棵树给出相同的目标集合。

### 2.10 差异阅读

**要做什么**

`--diff` 改为 `--diff-from PATH`：调用者指定和哪一份保存的观察文件比。删除工作区的持久基线、预留与提交协议、batch 收尾里的配合、基线占用的配额、`diffBaselineError`。

实现要点：

- 先定 PATH 指向的格式。自动保存的正文是按预算截断、按视图过滤后的投影；比较时不能把"旧文件里因截断没出现"的节点报成新增。可选的做法是保存时带上足够的规范记录，或在视图层比较并把截断处之后的部分按全文给出。
- 比较前核对两边的设备、会话、worker、连接、目标、根和视图选项。不一致、文件不存在、已被配额回收或格式不符时，输出全文并写明原因，不当作空基线。
- 回执写出被比较文件的采样时间和序号。
- 变化条目比全文长时退回全文。

**依据**

- 没有差异阅读不损失任何能力，只多付 token；受益的是长页上的局部改动和反复看同一页。默认正文瘦身后原生页全文只有约 300 token，受益面主要在网页上的局部切换。【重算＋推断】
- 持久基线涉及跨进程的工作区单基线、锁、配额、打印成功后才提交、batch 收尾；续读提示还有一处走不通：截断时提示再读一次，而基线已经推进，重读只得到零变化（`ui_diff.py:290-298`）。【源码】
- 自动保存的文件受 150 个、20 MiB 的配额回收（`history.py:20-21`）。【源码】

**验收标准**

- 仓库里不再有持久基线的读写。
- 指定同会话较早的保存文件：输出变化条目与基线的采样时间。
- 指定别的会话的文件、已删除的文件、被截断的文件：输出全文和原因；不出现把未读部分报成新增的情形。

### 2.11 看小字

**要做什么**

`zoom` 改为"重新截一张，只交付指定区域的原始分辨率"，例如 `screenshot --region L,T,R,B`。不再为每个会话驻留一帧原生图。

- 裁片标明自己的采样时刻；不成为坐标帧，不替换当前坐标帧和图像身份。
- 区域用 REF 指定时，重截的同时核对该 REF 当前的边界；界面已变（签名不一致）时拒绝按 REF 裁，只接受坐标区域。
- 文档写明：这是新的一帧，瞬时内容（提示条、动画中的文字）可能已经不在。

**依据**

- 原生图源与坐标输入资格共用同一份状态和同一组失效触发（`VisualInput.kt:17-44,132-148`）；只有 120 秒时效单独约束坐标输入。【源码】
- 细看的增益只在预览图被缩小的设备上存在：MuMu 的原生源是 1080×1920，预览是 720×1280；API 34 模拟器的原生源本身就是 720×1280，裁剪没有分辨率增益。现有证据里完整预览图已清楚可读，细字的净收益没有证明。【原件＋重算】
- 候选保留一帧原生图约占 7.5–8.3 MB。【原件】

**验收标准**

- 会话里不再驻留原生帧；截图、带标注的截图功能不变。
- MuMu 上区域截图得到原生分辨率的裁片。
- 界面变化后按旧 REF 裁：被拒并提示改用坐标区域。

### 2.12 界面树只存非默认值

**要做什么**

规范树改为稀疏表示：缺键即默认值；动作只存编号，有标签时另附标签表。

- "未知"只由现有的 `unavailable` 表达，保留这个数组，否则读不到的字段会被当成默认值。
- 默认值表只有一份，从共享契约生成，Kotlin 与 Python 共用；契约样本覆盖"字段等于默认值"的情形。
- 只在定稿时统一稀疏化一次，签名在这之后计算。任何产出节点的路径（包括重新取单个节点的路径）都经过同一处，否则同一界面会得到不同的签名。
- 设备端现有的严格读取（缺键即抛异常）全部改为带默认值的读取。

**依据**

- Chrome 页每节点约 1,545 字节，8 MiB 只装得下约 5,429 个节点，8,192 的节点上限在这类页面上达不到。稀疏后约 540–770 字节（取决于省略哪些字段），8,192 个节点可以装下。【重算】
- 实施方的窄验证：动作简写加默认值省略共减少 49.91% 字节。只在传输层压缩不增加容量，要增加容量就得改规范树本身。【原件】
- 采样里组装阶段约 600–785 毫秒，与采集本身同量级；稀疏后预计减少，实际能省多少没有测量。【原件＋推断，需设备】

**验收标准**

- 同一界面连续两次采样签名相同；经不同路径取得的同一节点表示相同。
- 4,226 节点的 Chrome 页编码后明显小于现状；构造的 8,192 节点网页树可完整装入。
- 契约重新导出，两端验证通过。

### 2.13 窗口缺席、变化结论、采样间隔

**要做什么**

1. **等窗口里的条件而窗口已不在。**
   - 等"消失"：连续两次采样窗口都缺席才算成功，结果注明依据是"窗口缺席"而不是"元素消失"。
   - 等其它条件：继续等到截止；超时的原因写明"窗口缺席，可能被遮挡"。
   - 动作后观察不变：请求的窗口缺席算有变化。
2. **变化只给一个结论。** 默认回执把几套变化信息合并为一行：有变化、无变化、仍在变、未知，加变化所在位置。局部核值（fill、check 的读回）与整体签名矛盾时以局部核值为准并写出。各套计算和 JSON 细节保留。
3. **采样最小间隔。** 两次采样的起点之间至少隔一个固定值（例如 100 毫秒）。不按上次采样耗时成比例放大。

不改的：动作后观察不改成"只看是否稳定"；系统动作不借旧树做基线。

**依据**

- 动作后观察遇到请求的窗口缺席时立即停止采样并报有变化（`UiPostAction.kt:43-44,97-110`）；`wait` 遇到同样的缺席每轮重新枚举窗口列表，一直重试到超时再报失败，不区分等的是"消失"还是别的条件（`UiCondition.kt:387-413`、`UiScope.kt:65-85`）。缺席期间只枚举窗口、不采节点，等待本身很便宜。【源码】
- 窗口缺席不等于窗口没了。平台会把被上层可触摸窗口完全遮住且没有焦点的窗口从无障碍窗口列表里拿掉；窗口编号不变，遮挡消失后会回来。权限框、全屏弹层、来电界面出现时，目标窗口就是这样暂时缺席的。所以单次缺席不能当作"消失"，也不能让其它条件立刻报错。【上游，AOSP 14 `AccessibilityController.java:1624,1700`】
- 候选并列五套变化信息（settle、observedChange、effect、局部核值、差异）。调用者实际只有一个决策：动作有没有效果，在哪里，页面还在不在动。【源码＋推断】
- 有相关事件时下一次采样立即开始，250 毫秒的计时只在没有事件时起作用（`UiBackend.kt:292-305`）。小页面遇到持续事件时每秒可能采样几十次。风险有源码依据，量没有测过。【源码＋推断】

**验收标准**

- 等窗口 W 里某段文字"消失"：W 被关闭后，第二次采样时返回成功并注明依据；W 只在一次采样里缺席随即回来时不提前成功。
- 等 W 里出现某段文字：W 被全屏界面暂时盖住再露出，文字出现后返回成功；W 一直缺席到截止则超时，原因写明窗口缺席。
- 默认回执里变化信息只有一行；局部核值失败时这一行不写"有变化"了事。
- 持续动画页面上，同一个点击的动作后采样次数有上限。

### 2.14 结果、退出码与清理失败的封锁

**要做什么**

1. 结果字段与退出码一一对应。消除两处不一致：落点未确认时的"done 加退出码 1"（§2.2）；通知清理未确认时的退出码 1（§2.7）。
2. 未请求图像时不打印图像占位行；正文的打印不依赖保存成功，保存失败另行报告。
3. 清理失败的封锁门保留：会话的界面资源清理失败、连接失败后断开失败时，继续拒绝新的 UI 命令和会话切换。
4. 新增一条远程可达、不需要会话的"重试清理"命令。它重新执行上次失败的清理；成功即解除封锁，失败则保持封锁并返回具体原因。封锁期间的拒绝报错里给出这条命令。不做自动重试。
5. 通知监听器的注销失败不进这道门（§2.7）。

**依据**

- 封锁标志由会话清理失败和断开失败写入（`UiBackend.kt:46-50,466-498`、`TargetManagement.kt:83-95`），没有任何复位路径。置位后所有 UI 命令和会话切换被拒；恢复只能在设备本机的管理界面上强制退出 worker，`connection.md:169` 写明没有远程强制命令。对远程调用者是死路。【源码】
- 门本身有理由：后台屏或连接没清干净时继续执行，新旧资源会混在一起。要补的只是一条出路。【推断】

**验收标准**

- 人为让会话清理失败：随后的 UI 命令被拒，报错含重试清理的命令。排除故障后执行重试清理：成功，随后的命令正常。故障未排除时执行：仍被拒，返回原因。
- 通知注销失败不触发封锁（与 §2.7 的验收一致）。

## 3. 待实验后再定：元素采集（E9）

E9 是手写的无障碍回调采集：直接向各窗口的连接请求整棵子树，绕过公开的逐节点调用。它多维护一份手写的回包解析和约 7 个只给它用的隐藏成员。

**现在做的**

- E9 暂时保留，预算（8,192 节点、3,000 毫秒、8 MiB）不变。
- 加两处防护，都要可见，不静默：
  1. 回包尾部有多余数据时不再整包拒收（`CollectionNodes.kt:125-130`），只校验已知前缀；同时记一条诊断并在结果里标出。
  2. 回包被明确判定为布局不兼容时，本连接内改用公开调用，结果里标明"本次采集来源为公开路径"。不因一次超时或偶发失败触发。
- 采集截止被计成"提供方不可用"的问题照修（§6 F21）。

**补一次对比实验**（§8.1 C7）

在约 4 千节点的网页上，分别做"滚动一屏后观察"和"点击展开后观察"，E9 与公开缓存路线交替进行。记录：

- 每次动作后采样的采集时间；
- 采到的树是否完整；
- 公开缓存臂的实际跨进程调用数或缓存命中数（现有原型没有这项计数，要补）；
- 是否超出动作后观察的截止；
- **新鲜度**：动作之后采到的树是否反映了新状态。公开缓存靠事件失效，可能返回"完整、很快、但是旧的"子树，只比时间和完整率会系统性偏向它。

**实验后怎么定**

| 结果 | 去向 |
| --- | --- |
| 公开缓存与 E9 的差距小于一次树组装，完整率相同，新鲜度没有问题 | 建议换成公开缓存，删除手写回调。报告给用户定 |
| 公开缓存明显退化、出现不完整或旧数据 | 保留 E9 |

**已有的事实**

- 静态页面上的采集时间：E9 为 1,024、399、606、580 毫秒；公开缓存为 655（同一 worker 的第二次采集）和 1,047（首次）；逐节点公开调用为 1,909 和 2,209。两组来自不同的运行，每格一次，E9 自身在 399–1,024 之间波动。【重算，仅 MuMu 模拟器，单一页面】
- 公开缓存路线在动作之后可能退化的三个机制都有源码依据：平台只接收最后一次交互的预取结果；滚动事件后 150 毫秒内不预取；内容变化和滚动事件会把子树逐出缓存。UiAutomation 确实把事件转给了这套机制。【上游，AOSP 15 `AccessibilityInteractionClient`、`AccessibilityCache`，分支副本】
- 现有实验只测了静态页面上的快照，没有测动作之后的路径，而后者决定取舍。

## 4. 待验证后由用户决定

两处已决定的做法各有一个已知风险，要先在模拟器上验证；结果报用户，由用户决定是否修改。验证之前按下面写的做。

### Q4 通知监听器的注册频度

- **现在的做法**（§2.7）：每条命令注册、用完注销。
- **风险**：平台注销监听器时不解除它在注册时挂上的死亡通知（AOSP 14/15/16 的 `ManagedServices` 全文没有解除调用）。每注册一次，system_server 里就多留一个引用，直到 worker 进程死亡。用单一对象不能避免，累积数等于本 worker 生命周期内的通知命令数。长期高频轮询通知的 agent 会让它持续增长；增长到什么程度出问题没有核实。【上游；后果为推断，需设备】
- **验证**：§8.1 C8 (b)。
- **若确认线性增长，备选做法**：每个会话首次使用通知时注册一次、会话结束时注销；监听对象仍是整个 worker 一个，注销失败仍不封锁。代价是监听和 URI 授权的持续时间从单条命令延长到会话。
- **验证之前**：按 §2.7 实施。

### Q6 后台屏会话中别屏任务被移入

- **现在的做法**（§2.3）：`--multiple-task` 只在启动时检查；帮助文本写明它只保护入口。
- **风险**：之后在 App 里点一下，App 内部启动它的单例页面，平台可能把真人主屏上的同包任务移到后台屏，并在会话结束时随屏销毁。这一步发生在后续的点击里，不在启动里。【上游＋推断，需设备】
- **验证**：§8.1 C15。
- **若确认会发生，备选做法**：后台屏会话里每次动作后的观察附带一次任务归属检查，发现别屏任务被移入时在回执首行报告。
- **验证之前**：不加这项检查。

## 5. 核心证据：效率

同一对真实任务（Contacts 新建联系人、Chrome 列表到详情再返回），同一模型，原生用量记录。【重算，两名评审各自复算一致】

| 臂 | 模型总输入 token | 相对基线 | CLI 次数 |
| --- | ---: | ---: | ---: |
| Contacts 基线 `7d5be70` | 812,987 | 1.00 | 16 |
| Contacts 候选 | 1,395,045 | 1.72 | 20 |
| Contacts 实施方紧凑原型 | 629,770 | 0.77 | 15 |
| Chrome 基线 | 1,041,124 | 1.00 | 20 |
| Chrome 候选 | 2,326,407 | 2.23 | 15 |
| Chrome 实施方紧凑原型 | 1,821,534 | 1.75 | 20 |

读这张表要注意：每臂只跑了一次；Chrome 的基线来自另一台模拟器，并且基线读不到网页正文，只能比量级；总输入里缓存命中的部分占九成左右，它反映的是"上下文累积乘以轮次"，不是金额。初始任务提示在记录里是加密的，无法核对各臂的任务文字是否逐字相同。

Chrome 原型臂仍然贵的原因可以逐调用指认：默认 `find` 的范围（§2.8），多出 4 次滚动，每次打印 4–6 千 token 的整页正文；输出里 41.4% 仍是动作数组；网页上每个容器都是目标（§2.9）；四臂都整读了 `actions.md`。

**§2.8 规格的预期。** 把同四臂的真实输出按 §2.8 的规格离线重渲染，并假设执行路线不变：总输入约为基线的 0.67–1.08 倍（Contacts）和约 1.0 倍（Chrome）。【重算，单人核对】这是投影，不是实测：正文变短会改变模型的读取和调用决策；离线变换不等于在渲染器里的实现。实际效果以 §8.2 的 A1 为准。

## 9. 给实施的约束

1. **不自行改动 §3 和 §4。** E9 的去留、§4 的两处由用户定。验证之前按各条写明的做法推进，结果报用户。
2. **新增机制先过三问。** 这项机制去掉或合并后，调用者失去了什么；有没有公开接口的等价做法；它新增了哪份状态、由谁清理。答不出第一问的不加。
3. **每个新的结果字段先回答**：调用者看到它的不同取值，会做出哪个不同的下一步。答不出来的只进 `--json`。
4. **不新增 Android 内部接口。** 例外只有 §2.5。
5. **不新增自动重试、自动兜底、自动换通道。** 未知结果如实报告，不重发。
6. **本文没有覆盖、又会改变对外行为的取舍**：列出真实选项（包含"不做"）、各自代价、推荐和未知，交用户裁决。不依赖该决定的工作继续。
7. **没跑过的不写通过。** 模拟器结果不外推到真机；研究探针的结果不等于产品代码的结果；一次成功不等于普遍成立。
8. **不要把"没有冲突"当作"合并正确"**（§2.16）。
9. **交付稿首页写明**：A1 的各项指标；host 检查在三个平台上各自的结果；Android 构建与测试结果；§8 每一条的执行情况；§3 的实验结果；§4 两处的验证结果。

## 10. 证据范围与局限

- 本评审实际做的：评审包与增量包的完整性校验；对原生用量、CLI 记录、原始树、窗口列表的离线重算；候选源码与固定上游源码（AOSP 14、15、16 的相关文件）的核对；候选与拆分分支上的 host 检查（Linux、Python 3.12）。
- 没有做的：任何设备或模拟器运行；Android 构建；候选之上的任何新实现；包内脚本的执行。
- §2 的各项方案都没有实现过。涉及平台行为的部分是源码核对，没有运行验证；标【需设备】的结论要以 §8 的结果为准。

- 上游源码多数取自各版本的首个发布标签，少数是发布分支的副本，不是运行镜像逐字的版本。
- 上下文点击归入普通动作后，原生 App 的节点名和选择器会怎样变化，还没有算过（§8.1 C13）。
