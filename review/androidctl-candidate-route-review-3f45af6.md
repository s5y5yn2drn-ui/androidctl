## 1. 结论

### 1.1 一句话

**骨架和大部分基础重构是对的，但这一轮把"每个事实都精确分列"当成了目标，把"agent 每一步要读多少、要懂多少"当成了可选项。唯一的端到端证据显示：同样的任务，候选让 agent 多读 4–5 倍输出、多花 1.8–2.35 倍模型输入、耗时更长。按现状合入，会让原 22 案已确认的头号成本（多轮携带不断增长的上下文）加重，而不是减轻。**

不建议按现状整体合入。建议按 §7 的 R0 重新切分：先把"基础重构 + 已证实的能力"连同"默认输出瘦身"作为一个可合入的核心，把证据不足、契约很重的六块能力（后台屏、IC、借贴、通知写操作、zoom、diff）留在分支上，各自凭一项低成本补证再决定去留。第二轮已在独立克隆里把这六块实际拆了一遍：全部可拆，host 侧检查通过；Android 侧需要构建环境验证。

### 1.2 站得住的部分

这些在独立复核后仍然成立，应当保留：

- **输入派发纪律**：四态结果、UNKNOWN 不重发、身份 REF、写后读回。没有任何评审者找到错误派发路径。
- **节点架构 A**（worker 内 UiAutomation 作唯一节点链）：两轮外评和本轮独立重判结论一致。普通无障碍服务对 Chrome 无论如何都要存在，所以"两者并存"不是 A 的额外成本。
- **基础重构**：Android 14 下限（净删 161 行）、sample/publish 分离、CLI 返回 Result、全局选项后置、字节预算定稿（修的是真缺陷）。
- **有自然采用证据的能力**：在成对真实任务里，全新 agent 自发用了 `scroll-until`、`reveal`、`find --context`、`--depth`、`tap --image`、JPEG 截图，以及浏览器网页语义（Chrome 少用 3 张图）。
- **交付方的原始记录是诚实的**：失败、中断、反例和未知都保留了原件，数字经复算全部属实。问题不在记录，在于如何解读和排序（见 §8）。

### 1.3 最重要的七个问题

1. **默认输出比基线大 4–5 倍，这是回退，不是"可选优化"。**〔亲核〕【实测】
   同一个 Contacts 任务、各 16 条命令：agent 收到的 CLI 输出从 34.5KB 涨到 149.3KB；Chrome 任务从 35.8KB 涨到 183.6KB。其中 51–56% 是每个可操作节点后面附带的完整动作对象数组。按 R1 的 C 方案用候选自己的渲染器离线重渲染，同一批输出降到基线的 1.13 倍（Contacts），逐条成对比较是基线的 0.74 倍〔复核〕【精算】。详见 §3。

2. **"效率"目标没有证据支持，现有证据指向相反方向。**〔亲核〕【实测】
   候选的模型输入是基线的 1.80 倍（Contacts）和 2.35 倍（Chrome），wall 时间多 21% 和 17%。多出的时间全部在模型侧，CLI 子进程耗时没有变差。交付稿的说法是"不能称普遍提速""路径不同不能归因"；实际上逐响应的原生 usage 足以把差额拆到具体机制（§3.2）。

3. **上次外评最重要的建议被降级处理，而新的成对实测恰好证实了它。**
   上次外评要求合入前做三件事：修大树交付缺陷、把默认输出做小、做一次成对 agent 复测。交付方做了第一件和第三件；第三件的结果证实了第二件的必要性，第二件却被列为"三项未批准的可选变化"，并附上保守选项。按交付方推荐的组合重渲染，CLI 输出仍是基线的 3.4–3.5 倍，只能收回差额的 16–19%〔复核〕【精算/估算】。

4. **报告 B 的核心意图"给得更少"被做反了；它排在前三的"结果直接给下一步"只零散存在。**〔复核〕【源码】
   B 设想的行是 `[e7] button "Allow"`，候选的行是 `button {"ref":"e834208075","name":"Cancel","actions":[{"id":1,"name":"focus","label":null},…]}`。没有统一的下一步字段：部分拒绝原因的末尾带一句提示（如"; run snapshot"），UNKNOWN 和 failed 没有统一指引。公开指引从 81.5KB 涨到 147.6KB。B 处置表与最终源码之间没有对账表，其中三项为 0 处（附录 A）。

5. **投入向"能力面"倾斜，其中六块的证据自带反例或自述无收益。**
   按逐提交新增的产品代码计，约 56% 投在新通道上〔单方〕。后台屏、IC、借贴、通知写操作、zoom、diff 这六块合计约 4,600 行（约 28%，见附录 B）〔亲核〕，在四次完整真实任务中没有一次被自然使用。两份报告都要求后台屏"先真机探针再定投入"，这道门被跳过；用户日常用的 MuMu 已实测不支持后台屏。

6. **同一件事有多份编码，结果行已经不适合阅读。**〔亲核〕【实测】
   一次 `fill` 的结果首行，基线是 `fill: done; changed; focus=done, sent=false; fill=done, verification="matches", actualValue="…"`；候选在这之前插入了 `windows={…}; selection={…}; content={…}; baselineSequence=6; baselineFinishedMs=12022805; baselineAgeMs=11173; baselineComputedAtMs=12033978; effect={…含两段被截断的动作数组 JSON 预览…}`。"是否变化"至少有五种编码，其中 `settle` 在系统动作和 partial 页面上是恒定值。

7. **候选在 Linux 上过不了自己的 host 测试。**〔亲核〕【实测】
   本次在 Linux / Python 3.12 上运行：基线 0 失败；候选 **23 失败**。交付稿的"1884 passed"只在 Windows 上成立，而仓库 CI 矩阵包含 ubuntu-24.04 和 macos-15。23 项中 22 项属于第 38 项（后台屏）的主机偏好测试。详见 §5.1 D1。

## 2. 整体架构判断

### 2.1 候选其实是三层东西

把 40 项按"价值是否已证、维护面多大"分开看，结论差别很大：

| 层 | 内容 | 判断 |
| --- | --- | --- |
| **一、基础与修缺陷** | 1–6、10、12、13（不含 E9 的去留）、16–18、21、23（节点 touch 与 REF 键定向）、33、40 | 方向正确，多数有真实页面证据，应合入 |
| **二、默认呈现** | 7 的投影、11 的行内新字段、15 的事件明细、19 的变化摘要、24 的动作数组与目标判定、34 的指引体量、39 的无上限默认打印 | 这是回退的来源。必须在合入前改，不是可选项 |
| **三、扩展能力面** | 8 diff、25 range、26 手势、27 keys、28 typed Intent、29 IC、30–32 通知、35–36 剪贴板与借贴、37 zoom、38 后台屏 | 分化明显：keys、手势、range、通知只读、剪贴板读写可留；IC、借贴、通知写、zoom、diff、后台屏证据不足，应拆出或删除 |

### 2.2 根本性偏差：优化对象错了

实施过程反复优化的是"每条事实的认识论精度"：某个值是即时后态还是持久状态、某次清理是确认完成还是未知、某个基线是何时计算的。这些区分在工程记录里有意义，但产品的使用者是 LLM，它每一步只需要回答三个问题：

1. 我刚才的操作发出去了吗、成功了吗？
2. 屏幕现在是什么样？
3. 下一步建议做什么？

候选把大量篇幅花在第 1 个问题的细分上，让第 2 个问题的答案变贵了四倍，第 3 个问题只零散地回答。报告 B 第 8 章对这一点有准确的诊断："对照组的否定句是'不要做什么'，androidctl 的否定句是'某个事实不意味着什么'，后者要求模型在每一步做反事实推理。"这个诊断没有被吸收，反而被放大到了结果契约里。

这种偏差有一个可观察的特征，可以用来检查后续工作：**凡是"分别报告 A、B、C"的地方，问一句"LLM 看到 A≠B 时会做出不同的下一步吗"。** 本轮多数分列通不过这个检验（§5.2 列了具体例子）。

第二轮请了一名只看源码、用户原话和成对任务原件的评审员独立提方案（看不到任何评审材料）。它独立得出了同一个诊断和同方向的方案，对照见 §11。

### 2.3 组合后的一致性

逐个接点的结论：

| 接点 | 结论 |
| --- | --- |
| 目标种类偏好 / 租约 target / 窗口 scope / REF / 坐标帧 / App UID | 设备侧一致，没有发现会导致错误操作的路径。缺口在主机侧：create 失败后偏好仍是 main，后续命令会落到主屏（§5.1 D3，包内真实发生过一次）；遗留的 virtual 偏好会让后续任务被拒且提示有误导（§5.2 T7） |
| 节点 / IC / keys / paste / Intent / 通知 各通道 | "不自动换通道"的纪律守住了。但"文本进入一个字段"有五条路，是两份报告分歧的并集而不是择一（§7 R3）；各通道的 done/failed/UNKNOWN 映射规则不一致（§5.2 T5） |
| 采样 / 事件 / 等待 / 局部核值 / settle / observedChange / 交付 | 发布阶段不再重复采样，这一点做对了。重复出在"变化"的多重编码和 settle 的恒定值（§5.2 T2）；事件唤醒去掉了原有的 250ms 节流且没有 A/B 证据（§5.3 E4） |
| partial 与局部可靠 REF | 组合正确：partial 下局部 REF 仍可用，不会因全局不完整而拒绝。真实 Chrome 页面有业务闭环证据 |
| 图源 / 派生图 / Canvas / 大树共存 | 单线程 executor 串行，没有发现泄漏或双重释放。但全部内存证据来自 720×1280 设备，JPEG 实际没有缩放，高分辨率下的峰值未知（§5.3 E5） |
| full 权限 / 自身 UI 保护 / main 解锁 / 通知准入 | 文档没有把防误操作夸大成安全隔离。新缺口一处：`notifications open` 能拉起自身管理页（§5.1 D6） |

### 2.4 长期维护责任的量

- 产品代码：Android main 10.8k → 19.7k 行（+83%），host 8.0k → 12.0k 行（+49%）；两者合计净增 14.9k / 删 2.1k 行。
- 契约：`contract/wire-contract.json` 175KB → 441KB。每个"分别报告"的字段都是一份长期公开契约加一份跨语言夹具。
- 使用面：叶命令 47 → 70；命令局部选项 233 → 611；结果首行可能出现的字段 35 → 111；`click --help` 131 → 319 词。〔单方〕
- 平台风险最集中的三处：E9 的手工 Parcel 回调链（§7 R5）；Chrome 靠普通服务保持网页树，依赖 Chrome 内部启发式；通知写路径的 postTime 守卫与平台刷新行为冲突（§5.2 T6）。

按 §7 的推荐把六块拆出后，主线净少约 2.6k 行 Kotlin 产品代码、约 1.3k 行 Python 产品代码、约 2.5k 行契约样本和约 5.8k 行测试〔亲核分支统计〕【实测】，损失的能力都属于"尚未被证明有人需要"的一类。

## 3. 核心证据：效率回退的定量归因

这一节是整份报告的事实基础，全部来自评审包内 `stages/final-verification/paired-runtime/` 的原件，没有引入任何新的设备实验。成对运行所用版本 99e31a9 与 3f45af6 的差别只有三处与渲染无关的文件，可以代表当前候选。

### 3.2 多出来的模型输入从哪来〔复核〕

把每次响应的原生 usage 增量与新增工具文本的 token 数逐段对齐，就能算出每段文本被后续响应携带了多少次。两名子评审各自独立重建了这个模型：分摊结果闭合到原生总数的误差在 −2.2% 到 +4.1% 之间（+4.1% 来自图片）；相邻响应之间，单段文本的原生增量与 o200k 计数恒差 10 token。

| 来源 | Contacts 差额 +648k 中的占比 | Chrome 差额 +1.41M 中的占比 |
| --- | ---: | ---: |
| CLI 正文与重读快照文件 | 52–55% | 67–68% |
| 公开指引（多文件、截断后重读、开头一次读完） | 30–31% | 29–32% |
| 多出的响应带来的固定前缀等 | 余下部分 | 余下部分 |

（区间来自两名子评审对"读 launcher""读快照文件"等边界项的归类略有不同。）

几个常见猜测经核实**不成立**：

- **不是默认打印造成的。** 基线 agent 每个动作都自己加了 `--print`（22 案里是 1,080/1,212 次）。成本来自每份打印变大，不是打印次数变多。
- **不是 8192 节点造成的。** 去掉动作数组、事件和变化摘要后，两版 Contacts 的节点正文是 280 对 260 token，基本相同。默认行只投影可见节点。
- **不是任务路径差异造成的。** 两臂的状态差异（继承的查找词、捐款横幅）各约等于一次动作输出，比上表的主要来源小一个数量级。

### 3.3 它还直接制造了多余的往返〔复核〕

- 候选两臂共有 3 条输出超过 8k token，其中 2 条被宿主截断（宿主的规则是按字节数除以 4 估算，超过 10k 即截断）。
- Chrome 候选的第一个 `snapshot` 有约 12.2k token，被截断；agent 去读保存的文件，又被截断；之后才改用 `--depth 1`。这一份快照里约四分之三是动作数组。按 C 方案渲染，同一个快照是 2,718 token，不会截断。
- SKILL 示例里推荐的 `click REF --interactive` 在网页上产生了约 12k token 的输出，与不加该选项几乎一样大。原因见 §5.1 D14：网页节点几乎全被判成了"可操作目标"。
- 指引拆成多文件后，agent 习惯一条命令读几份，被 10k 上限截断，再分段补读：Contacts 候选有 6 次文档往返，基线 3 次。

### 3.4 "行格式省 11.5%"是口径错配

研究阶段测的是**同一组字段**用行语法和 XML 语法各渲染一遍，行语法确实省 11–15%。用户据此选了"默认行格式、删 XML 出口"。但进入产品的"行格式"在测量之后又被加进了完整动作数组（第 24 项 `af36a32`，`androidctl/src/androidctl/ui_view.py:120-121`〔亲核〕）、近期事件（第 15 项）和新节点字段（第 11 项）。用户做选择时依据的收益没有兑现，交付稿却仍在引用这个数字。

其它几个"收益"数字的性质（〔单方〕）：JPEG 省 70% 是字节，模型图片 token 在 PNG 和 JPEG 下都约 1,128；batch 附件少 72% 但端到端无提速，且未被自然使用；8192 的 3.3 秒对 1024+ref 的 3.1–3.2 秒是开销不是收益；传输省 140ms 不到一次模型响应时间的 2%。

### 3.5 对原 22 案根因的覆盖

原 22 案报告的结论是：13 个未完成案主要出在执行编排（收尾证据晚于 close、报告写作超时）、模型服务中断、业务入口没找到；成本主要来自"多响应重复携带增长中的上下文"；"当前没有证据支持一揽子产品修复"。

候选 40 项里能直接对应这些根因的只有两项：指引里的收尾顺序文案，以及 8192 对 partial 的改善（原报告已说明该案的缺口在相关区域之外）。编排、服务、超时、入口问题都没有被触及。而成本主因被加重：每次响应的平均上下文增量从约 1.7k 涨到 3.4k（Contacts）、1.5k 涨到 3.7k（Chrome）。

（22 案的逐案归因表不在评审包内，这里只能依据总报告的摘要。）

### 3.6 离线重渲染的正式结果（第一轮补证 P1，已完成）〔复核〕

### 5.2 设计取舍（建议调整）

**T1 结果首行。** 默认文本的首行应收敛为"命令: 结果; 原因; 关键核值; 是否变化; 路径"。当前首行里的三段维度 JSON、四个基线数字、effect 的字段级前后对比、手势和按键的内部回执（一次普通 tap 约 800 字节）都应只在 `--json` 中出现。其中 `baselineFinishedMs` 和 `baselineComputedAtMs` 是设备 uptime 毫秒数，对 LLM 没有任何用处；effect 里对 `actions` 字段生成的前后 JSON 预览是纯噪声。〔亲核〕首行收敛在 Contacts 上值约 2.8k token（§3.6 的 C5 层）〔复核〕。

**T2 "是否变化"的多重编码。** 现在有 `settle`（含 changed/unchanged）、`observedChange.state`、三个维度、`effect.state`、`verification`。其中 `settle` 在两类常见场景下是恒定值〔单方〕【源码】：

- 系统动作（back、home、key、open）一律以空基线进入，必然报告 `settle=unsettled; change=unknown; changeReason="No before or final observation"`，即使最终树已经采到并交付（`SystemActions.kt:57-60`、`UiPostAction.kt:193`）。
- 基线树为 partial 时（Chrome 长页几乎总是），settle 无法提前结束，每个动作都耗满 settleMs 反复整树采样，最后仍报 unsettled。

建议 settle 只回答"是否稳定"，"是否变化"只由 observedChange 回答。交付方拒绝合并的理由是"A→B→A 有不同含义"，但那种情形下 settle 本来就归为 unsettled，用不着 changed/unchanged 来表达。

**T3 显式窗口缺席。** 动作后查不到窗口就立即切换范围并报 `settle=changed`；而 `wait --window W --gone` 在 W 已消失时却一直等到超时再报 failed（`UiCondition.kt:64-75,395-411`）。窗口 ID 不会复用，空等没有意义。建议 wait 遇到"目录完整且请求窗口缺席"时立即返回并标明 windowAbsent。这不违背"缺席不等于 gone"。〔单方〕

**T4 坐标手势默认按操作窗 UID 定向。**〔复核〕【源码+上游】；软键盘一例的最终确认需设备。

- 候选让无 `--expect` 的 tap/swipe/drag/pinch 以"当前唯一操作窗口的根包"作为注入目标 UID（`VisualInput.kt:232-240,258-269`）。"操作窗口"明确排除输入法窗口（`UiScope.kt:50-52`〔亲核〕）。基线不定向。
- AOSP 14 的 InputDispatcher 在触点落到 owner UID 不同的窗口时返回目标不匹配。输入法窗口属于输入法的 UID。所以键盘弹出时，无 `--expect` 点软键盘上的键会得到 not sent。这条推理链在源码和上游两端没有断点，但包内没有任何一次"截图后点软键盘"的真实记录。
- 包内有一条性质相同的真实拒绝：第 21 阶段清理时，按输入焦点窗口定向的 BACK 因为嵌入窗口的 owner 不同被平台拒绝，项目随后把无 REF 的按键改成了不定向（global-key-fix），坐标手势却保留了同样的定向。
- 同一函数在派发前已经比较了截图时与当前的完整窗口集合（含输入法窗口），不一致就报 staleImage。UID 条件额外防住的只是毫秒级竞态。
- 用户确认的是"节点派生触摸核实 App UID"，没有要求坐标手势默认定向。

建议坐标手势默认不定向，`--expect` 作为显式定向；节点 touch 和 REF 键维持定向。

（第一轮这里写的"photopicker 实测必须加 `--expect`"不准确：那次运行一开始就带了 `--expect`，没有做过不带的对照。已撤回。）

**T5 各通道结果映射不一致。**〔单方〕IC commit 永远不会 failed 而 select 会；IC select 有一条"未匹配且与 before 相同为 UNKNOWN、变成别的为 FAILED"的规则，包内所有真机 select 都是 matches，这两条分支从未在真实环境触发；借贴在"PASTE 根本没发、原剪贴板已恢复"时报 FAILED。对 LLM 真正改变下一步的只有三类：没发出去 / 已确认完成 / 发了但没确认。建议各通道统一到同一条映射。

**T6 通知写操作的地址守卫。**〔复核〕【上游+源码】写操作要求回传 key、postTime、action 索引、title、creator、creatorUid 六个字段，其中 postTime 要求严格相等（`NotificationActions.kt:147,245`）。AOSP 14、15、16 每次 `notify()` 都以当前时间新建通知记录，postTime 不会从旧记录继承；候选比较的正是这个值，不是 App 设置的 `Notification.when`。进度通知、媒体通知、有新消息的聊天通知，在"读取"到"操作"这段跨越 LLM 思考的时间里很可能已经换了版本。"因此反复被拒"是由此得出的推断，包内写路径只测过 Termux 自造的静态通知，真实表现需设备。研究自己也实测过共享 PendingIntent 把回复错投给另一条对话，说明这些守卫并不能绑定业务对象。

**T7 遗留的 virtual 偏好。**〔复核〕【源码】会话名默认是 `default`，偏好按主机共享，close、到期、worker 重建都不清。一个任务用过后台屏之后，同设备同会话名的后续任务每条 UI 命令都会被 `displayRequired` 拒绝，而拒绝文案只提示 `run display create`（`Sessions.kt:157`），不提 `display select main`；`status` 也不显示这个偏好。`session open` 后偏好若仍是 virtual，下一条 UI 命令报 `displayMismatch`，提示"run session open or display select virtual"，照提示再 open 会原地循环。干净上下文评审员独立指出了同一问题。若保留后台屏，至少应在显式 close 时清除主机偏好（close 已销毁后台屏，继续后台工作本来就要重新 create，不损失保护）、status 显示偏好、提示里补上 `display select main`。

**T8 SEND 的 ClipData 迁移。**〔单方〕【上游+源码】`ActivityIntent.kt:44-48` 自造了平台 `Intent.migrateExtraStreamToClipData` 的一个变体：ClipData 的 MIME 是 `text/uri-list` 而不是 Intent 的类型，不自动加读权限，不支持 SEND_MULTIPLE。接收方看到的东西与真实分享不同。建议直接调用平台实现。

**T9 公开指引。** SKILL.md 本身从 15.7KB 缩到 8.0KB，这是对的。但目录整体从 81.5KB 涨到 147.6KB；SKILL 自己不足以完成"打开 App → 找字段 → 输入 → 核验"的最小闭环，必须再读两三个主题；主题里写进了锁、配额、ACK、发布提交点、"published 不等于 delivered"等内部机制。否定和限定句式约占四到五成，例如"A path alone is not a viewed image""select then commit is not a transaction""Platform dispatch, App outcome and listener cleanup are separate facts"。成对任务里候选 agent 在第一个动作前读了约 24–25k token 文档（基线约 4–19k），并因截断重读〔复核〕【实测】；这些文档在之后每次响应里都被重新计入。建议：SKILL 控制在 3–4k token，内置一个完整的最短会话和一份带逐项释义的输出样例；每个主题文件能在一次 10k 输出上限内读完，开头用几行说明"什么时候需要读它"；删掉内部机制叙述；每节至多一句总则，其余改成"状态 → 你做什么"。并加一个字节上限的守门测试防止回胀。

**T10 内部架构文档的可读性。**〔亲核〕`docs/architecture.md` 后半部分和 `docs/reference/ui.md`（78KB）的行文高度压缩，单句内并列四五个限定条件，新维护者很难据此建立模型。这本身是长期维护成本，建议随上述精简一起重写受影响的段落，而不是继续追加。

### R5 E9 预取（第 13 项的一部分；用户在 U18 选了"A，包含 E9"）

架构 A 和 8192 不建议重开。只针对 E9。

**证据现状**〔复核〕【实测+源码】：

- "不带 E9 就拿不到完整树"的依据是 J67：3,157ms 取得 3,869 节点、partial。它跑的是基线的单节点采集链加大预算（8192 / 3000ms），并且是一个新 worker 的**第一次**采样。
- 同一批原件里，E9 自己的冷首采也比随后的热采慢 1.8–4.5 倍：J68 首采 1,378ms，同一 worker 之后各次 305–761ms；J54 首采 1,114 / 834ms，之后 600 / 352ms。
- J54 的公开单节点探针（约 0.9–1.1 秒取得 4,214 节点、完整）测的是热态。它与基线采集链每个节点做的事相同：各 1 次取子节点的往返，cache 都关，读的字段集合相同。
- 所以 J67 与 J54 之间约 3 倍的差距，最合理的解释是冷/热之差加上两组实验相隔一次重启，而不是"不带 E9 时每个节点更慢"。第一轮说这个差距"没有解释"不准确，已更正。性能报告本身没有提到冷/热。
- 把冷/热对齐后看：同处冷态时不带 E9 约为 E9 的 2.3 倍；同处热态时约 1.8–2.7 倍。E9 确实更快，但"不带 E9 在 3 秒内拿不到约 4.2k 节点的完整树"目前只在冷首采上成立过一次。

## 8. 对交付方声明与既有 review 的对照

**成立的部分。** 数字准确，原件完整，失败和中断没有被筛掉。"不能称普遍提速""未使用的能力不能计为收益""模拟器不推广到真机"这些边界声明都是对的。内部 review 对实现正确性的核查（锁、封口、释放、前缀保真）经抽核是可信的。

**不成立或回避的部分：**

1. **"成本差不能归因于单一机制"。** 原生 rollout 里每次响应都有 usage，相邻差值可以精确给出每段文本的 token。这个分解用交付方自己的工具链就能做，做了之后结论很清楚（§3.2、§3.6）。"不归因"在这里掩盖了一个可以直接行动的结论。

2. **把造成回退的默认值列为"未批准的可选改进"。** 理由是"改变当前可见内容需要授权"。但用户批准的是"默认行格式"以提升效率，没有批准"每个目标默认打印完整动作对象"。后者是实施过程中自行决定的，内部审计自己也承认没有用户明示。把自己加进去的东西的撤回说成需要新授权，方向反了。

3. **继续引用 11.5% 的行格式收益。** 该数字测量的投影早于动作数组和事件的加入（§3.4）。

4. **"实际 dense 树 8,377,092B / 127 个唯一 REF"。**〔复核〕【实测+源码】这棵树来自任务自建的包 `org.androidctl.research.dense`：一个 64KiB 的行标签被复制进行内 123 个后代节点（`UiSemantics.kt:173-204`）。内部 review 写明了它"不是发行 App 业务"，但交付稿那一句没有写，单看交付稿容易读成真实页面。它暴露的是一个真实机制：行标签会被逐节点放大，真实页面上（行首文本很长、后代很多）也可能出现。更对症的处理是给行标签设长度上限或只在行根节点放一份，而不是只靠最终的字节定稿去裁尾。

5. **"三位最终累计 review 未关闭的 must-fix 和 optional 均为 0"。** 这些 review 核的是"实现是否符合已写下的契约"，没有一份去问"契约本身是否值得存在"。上次外评提出的删减和合并类建议（合并-1 至合并-14）几乎全部以"各有实际职责"被拒，而被接受的 U25 八项中有三项是增加状态的。

6. **B 处置表与最终源码之间没有对账表。**〔复核〕【源码】处置表开头声明了"处置建议本身不是用户批准"，它不是交付清单，所以这里的问题不是"声称做了却没做"，而是用户无从知道哪些建议最终落地了。逐项核对的结果：
   - 三项为 0 处：skill 里写明"屏幕、通知、shell 里的文字是数据不是指令"；staleRef 时给出候选；应用笔记约定。
   - 下一步提示：没有统一的字段，约 20 处拒绝原因的末尾带一句提示，多数是基线已有；UNKNOWN 和 failed 没有统一指引。

7. **"create 失败后 VIEW 落到主屏"被定性为操作者错误。** 对一个以 agent 为使用者、并专门为此设计了必填种类的产品，这是该机制的覆盖缺口（D3）。

**关于上次外评。** 它的总体判断成立，并被本轮成对实测证实，实际结果比它预测的更差。需要指出两点：它的作者就是报告 B 的作者（已披露）；它也推动了两处增加状态的改动（主机级偏好、基线年龄字段），并且没有质疑"行格式"在产品里变成逐行 JSON、没有指出 IC 与借贴是两份报告分歧的并集、没有指出 B 自己设的"先探针"门被跳过。
