## 1. 结论

**一句话：这一轮把候选做对了，但候选没有变小，也没有证据说明它比主分支更好用。下一步不应再按同样的方式打磨，应当先解决调用成本，再对基线做实测，然后定合入范围。**

### 1.1 做对了的

1. **已确认的范围都落实了。** 我们把前几轮评审里的 223 条可检验要求逐条对到源码：190 条已落实，20 条部分落实（差在哪实施方都如实写了），6 条做法不同，7 条没能判定（4 条需要设备，3 条没核）。已决定的事项没有漏做，也没有发现未经授权的能力删除。有一条验收按现有原件不满足：长网页滚动后界面树应当完整（§3.5）。
2. **上一轮指出的两个"会把调用者带进死路"的缺陷都修掉了。** 系统进程重启后，后台常驻进程现在会自己退出，不再留下一个活着但不能用的进程；清理没确认时，不再连带挡住 shell、文件传输、会话到期和正常停止。
3. **没有找到会点错目标、发错对象的缺陷。** 会话状态机、节点身份、坐标点击落在哪个窗口、通知的选择，这几处最容易误操作的地方，源码核查都成立。有一个例外会影响用户的主屏，见 §1.2 第 5 条。
4. **主机端的质量检查是干净的。** 我们在 Linux 上跑最终树的全量主机测试：1870 通过、17 跳过、退出码 0。子 agent 另跑了 `ruff`、格式检查和四个平台分支的 `mypy`，报告全部通过。Android 端 518 项测试通过，这是实施方在 Windows 上的结果。
5. **实施方对失败的记录是诚实的。** 结果未知、采集不完整、超时、只执行了一部分的情形，都按发生时的原样保留，没有被后来的成功覆盖。效率表里的数字我们重算了：50 个完全一致，4 个墙钟时间因为起算点不同各差约 0.4 秒。

### 1.2 问题

1. **调用成本没有被当成目标来优化。** 三轮评审加四轮实施，一直在提高"内部一致、可以证明、如实报告"，没有盯着"调用者办成一件事要花多少"。默认输出里多数页面约八成字节是调用者用不到的；首页指引按逐段标注约四成是"不能据此断言什么"的限定句；有几条为严谨而设的规则把成本转给了调用者（§3.4、§3.5）。这不是实施方单方面的问题：其中好几条是评审方建议、你确认过的，§6 逐条列出。
2. **候选相对基线到底好不好用，一直没有测。** 唯一一次对基线的真实任务对照是上一轮做的，旧候选的输入是基线的 1.80 倍和 2.35 倍。本轮的八臂比的是"同一个后端上的新旧输出"，每臂只跑一次，设计上分不出两倍以内的差别（§3.3）。这个实验设计是评审方第三轮提的。
3. **候选没有变小。** 本轮主源码从约 3.02 万行增到约 3.23 万行，隐藏接口成员从 65 个增到 70 个，指引从 2258 行增到 2663 行，命令从 70 个减到 66 个（§3.2）。这也不是当时的要求：第三轮评审建议能力全部保留，并且预测过规模最多持平。现在看，"能力全部保留"这个前提应当重新考虑：两批真实任务几乎只用到十来个命令，而后台屏、通知读写这些从未被自然用到的部分，占了本轮新增代码和待决题的大半（§3.6）。
4. **取证的投入和它的判别力不相称。** 本轮 28 个提交配了 96 份 review 文档和 161 个绑定文件。其中约 30 份源码 review 是有产出的，至少发现并修掉了 6 项产品缺陷。产出低的是另一头：为每次运行、每份物料建立的冻结、绑定和复核。效率实验的取证材料有 61 MB，而实验本身分不出两倍以内的差别（§3.7）。
5. **有一个会影响用户主屏的缺陷。** 在后台屏会话里打开一条会跳到别的 App 的通知，会把用户主屏上正在看的那个 App 搬到后台屏；会话关闭时，它的界面被销毁。第一道待决题的四个选项都挡不住它（§5.1）。

缺陷一共 23 条，其中高 2 条、中高 3 条，清单在 §4。

### 1.3 如果今天就用这个候选

调用者最常碰到的是这几件事：

- 每次观察的输出偏大，网页上一次约 4–5 千 token。
- 带启动页的 App 冷启动，`open` 会报结果未知，其实已经启动了。
- 长网页上按名字做的动作和等待可能耗满 5 秒后失败。这时应当先 `find` 拿到引用，再用引用操作。
- `scroll` 的 `down`、`up` 在多数列表上不被接受，要用 `forward`、`backward`。
- 在网页上 `find` 一个普通的词，可能拿回整页。

### 1.4 建议怎么走

1. **做一轮只针对调用成本的修正**（清单见 §7）。大部分在主机端的输出和指引，不动设备端的协议。离线重排显示，多数页面的默认输出可以降到现在的四分之一左右，任务需要的文字都还在。
2. **对基线做一次小规模实测**，同时记成功与否。它只能判断有没有两倍左右的大幅倒退，但这正是合入前最需要知道的。
3. **定合入范围，再整理提交历史。** 范围没定就重切历史，切出来的提交大半还要再改。
4. **合入前在一台真机上跑一遍核心流程。**

第 1 步放在第 2 步前面是有意的：要测的是准备合入的那个版本。

## 2. 需要你定的事

### 2.1 第 1 项：能力范围是否继续"全部保留"

| 选项 | 内容 | 得失 |
| --- | --- | --- |
| A | 全部保留，继续同等投入 | 能力最全；规模和待决题继续涨，每次改动要顾及全部能力 |
| **B（推荐）** | 分三层，见下表 | 投入集中到真实任务用得到的部分；需要你回答几个"自己用不用"的问题 |
| C | 直接删除后台屏和通知读写这两块最重的，其余保留 | 最省事；如果你其实需要其中一块，就删错了 |

三层的含义：

- **核心**：写进首页指引，继续投入。
- **冻结**：代码保留，不写进首页指引，不再加机制、不再精修，只修会伤害用户的缺陷。是否随本次合入主分支，按能力逐项定：牵涉面小的可以合入并标为实验；牵涉面大的（后台屏牵涉约 30 个文件）如果不用，就应当从合入的树里移除，而不是留一块没人维护的代码在主分支。
- **删除**：证据显示没有产出或得不偿失的。

我们建议的初始分层：

| 层 | 能力 | 依据 |
| --- | --- | --- |
| 核心 | 观察（`snapshot`、`find`、`wait`、`screenshot`）；按引用或名字的节点动作（`click`、`fill`、`check`、`scroll`、`reveal`、`back` 等）；启动 App；按键和 `type` 的按键通道；坐标点击与滑动；shell 与文件传输；主屏会话 | 真实任务实际用到的，加上基线就有的基本能力 |
| 冻结，是否合入待你回答 | 后台屏会话；通知的读取、回复、按钮、清除 | 代价最大的两块，见 §3.6。请回答下面的问题 1、2 |
| 冻结，可合入并标为实验 | 批处理（`batch`）；多指时间线与捏合；结构化剪贴板；`type` 的另外两条通道；`scroll-until`；区域截图与图像标注 | 牵涉面小，不值得现在花时间移除 |
| 冻结，保留在主路径上 | 手写采集器 | 每次采集都走它，不能移除；不再往里加机制，理由见 §6 |
| 删除 | 保存后比较（`--diff-from`）及其文件格式解码；为读一个系统设置项而加的 7 个隐藏接口成员；图像标注为画编号而改写进程全局字体表的那段 | 比较功能在实施方自己的验证里没有产出过一次有用的差量（§3.6）；后两项各自只服务一个边角判断 |

需要你回答的问题：

1. 你自己会不会让 agent 在后台屏上干活，以便同时用手机主屏？如果不会，后台屏归入删除。
2. 你需要 agent 不展开通知栏就能读通知、回复、点通知上的按钮吗？如果不需要，这一块归入删除，只保留基线就有的"展开通知栏"。
3. "在光标处插入任意 Unicode 文字"需要保留一条不靠按键的通道。输入法通道和借用剪贴板粘贴二选一，现有证据不足以判断哪条更好。你更在意"不动用户的剪贴板"还是"不要求用户开启无障碍服务"？

如果后台屏归入删除，会连带这些变化：第一道待决题不再存在；§4 的 M1、M8 里与后台屏有关的两项和 S1 随之消失；显式 `session open --display` 可以回到"首条命令自动开主屏会话"（§6 第 10 条）；首页指引要相应改写。

按使用次数决定能力去留是有风险的，实施方在委托里也明确反对这样做。八臂是两类只读任务，本来就用不到通知、后台屏和剪贴板；核心层里的 `open`、shell、文件传输在八臂的自然调用里也是 0 次。所以上表的依据不只是使用次数，还有代价、已知的副作用，以及"有没有更简单的替代走法"。

### 2.2 第 2 项：下一步的目标和工作方式

| 选项 | 内容 | 得失 |
| --- | --- | --- |
| A | 继续现在的方式：逐项实现、逐项 review、冻结与绑定，范围整体保留 | 内部一致性继续提高；调用成本和对基线的问题继续悬着 |
| **B（推荐）** | 停止新增机制，停止精修冻结层。按 §7 做一轮调用成本修正，再实测，再定范围合入 | 直接回答"好不好用" |
| C | 现状直接合入，问题以后再修 | 最快；合入时对调用成本没有任何依据，所有零使用的机制也一起进主分支 |

选 B 同时意味着调整你在授权里对实施方式的两条要求，请一并确认：

- "每个完整改进由全新上下文的子 agent 独立 review"保留，但只对源码改动做。
- 真实流程和效率实验只留三样：执行模型的原生会话记录、CLI 的原始输出、一页结果。不再为单次运行建立冻结清单、绑定文件和多层复核。

评审方这边也相应调整：下一轮不再出长报告，只在三个时点各出一页，即成本修正后的重放数字、实测结果、合入范围对应的缺陷清单。

### 2.3 第 3 项：合入前要不要做基线实测和真机检查

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 三件都做，见下 |
| B | 只做同屏对照和真机检查 |
| C | 都不做 |

三件事：

1. **同屏对照，不花模型费用。** 取十来个有代表性的屏幕，基线和候选各取一次默认输出，比 token 数。这一步是确定性的，现在就可以做，成本修正后再做一次。
2. **真实任务对照。** 基线和候选各用自己的 APK、主机程序和指引，每次都从同一个模拟器快照起跑。4 个任务：地图查路线、长网页读评论、表单填写后放弃、一个文件或 shell 任务。每个任务两版各跑 2 次，顺序交替，共 16 次。记录成功与否、轮数、输入 token、墙钟。
3. **真机检查。** 一台 Android 14 以上的实体机，用发行包跑一遍核心流程，确认手写采集器和坐标点击能工作；顺带验证两件只有推断的事：桌面上的坐标点击是否被拒（§4 的 M6），手写采集器与公开接口在同一页上的耗时差多少。

怎么读第 2 件的结果：

- 每臂只跑两次，单次成本的波动本身就有两倍上下，所以这个实验只能发现大幅倒退，不能证明两版一样省。
- 4 个任务里有 3 个候选的中位成本达到基线的两倍以上，就认为倒退属实，合入前再修一轮。
- 候选完成了基线完不成的任务（基线基本读不到网页正文），记为能力上的进步，这一项不比成本。
- 其它情况记为"没有发现大幅倒退"，不阻止合入。

成本：按本轮八臂的平均值估，16 次约 1,400 万输入 token，可能在 600 万到 3,700 万之间，其中约九成是缓存命中；金额我们算不出来，材料里没有价格。设备时间约 1–3 小时，加上准备快照约 4–6 小时。真机检查约半天。

### 2.5 默认做法（你不反对就照做）

这些是实施方按已定原则就能做的修正，不需要逐项裁决。其中前三条调整了前几轮定过的做法，所以列出来请你过目。

| 事项 | 做法 | 对应 |
| --- | --- | --- |
| 启动确认 | 动作后观察结束时没看到目标，就在剩余的时间预算内继续查任务列表，看到了报完成，预算用完才报结果未知。"启动要确认落点"这条规则不变 | §4 U3 |

### 3.3 效率证据证明了什么

**数字属实，但实验回答不了要紧的问题。**

1. **每臂只跑一次，路径差异盖过了一切。** 同一臂在两个阶段之间的总输入差到 0.6 到 4.0 倍：Maps 的 new 臂先是 32.8 万、后是 77.3 万；GitHub 的 old 臂先是 58.5 万、后是 234 万。"谁更省"的方向在两个阶段之间翻转。实施方写"净成本因果未知"，这句话准确，但没有说明这个设计本来就测不出。
2. **"输入 token"这个数主要在量轮数。** 它是每一轮上下文的累加。执行模型自带约 1.8 万 token 的固定前缀，每轮都重发，占各臂总输入的 19%–60%；86%–94% 的输入是缓存命中。产品能影响的是三样：调用轮数、每次输出的大小、指引的大小。轮数影响最大，输出大小其次，首页长度影响很小（首页减半只省 1%–3.6%）。
3. **两臂都不是基线。** old 臂是同一阶段的后端加旧输出补丁，既不是基线，也不是旧候选本身。整轮没有任何一次"最终候选对基线"的真实任务对照。上一轮唯一一次对基线的对照如下，两边业务都完成了：

   | 任务 | 基线输入 | 旧候选输入 | 倍数 |
   | --- | ---: | ---: | ---: |
   | Contacts | 812,987 | 1,461,258 | 1.80 |
   | Chrome | 1,041,124 | 2,447,717 | 2.35 |

   对照的两端是基线 `7d5be70` 和旧候选的一个邻近版本 `99e31a9`；Chrome 一行的候选只计了完成的那次尝试。更早还有一次测量，结果是 1.7–2.2 倍。
4. **最早的 22 个回归案例没有在候选上重跑过。** 那次只跑了基线：9 个通过，13 个未完成。候选是否让其中任何一个变成通过，没有证据。
5. **有一个实施方没写出来的正向信号。** 四对里，new 臂每次调用新增进上下文的 token 都更少：Maps 约 2,800 对 4,300–4,500，GitHub 约 5,600–6,500 对 7,300–8,400，降幅 23%–37%。new 臂四次里只有一次去读了专题文档，old 臂四次都读了。所以紧凑输出和自包含首页的方向是对的。要注意一个前提：最终阶段的新首页是看过这两个任务在第 0 阶段的失败之后改写的，这两个任务参与了指引的调整。

### 3.5 几处规则把成本转给了调用者

这些规则单看都有道理。合起来的效果是：产品把自己不能证明的事交给调用者再花一轮去核实，而调用者的每一轮都很贵。

| 规则 | 实际后果 | 依据 |
| --- | --- | --- |
| 启动 App 后只查一次任务列表，没看到目标就报结果未知 | 带启动页的 App 冷启动会报结果未知。实测约 10 次启动里有 2 次（VLC、WPS），事后都证实已经启动。基线和旧候选在主屏上都按平台返回码报完成 | `sub-reports/35` §2.1 |
| 按名字的动作、等待、动作后的稳定判断，都要求整棵界面树完整 | 超过节点上限的长网页，树总是不完整。材料里 126 份 Chrome 的树有 26 份不完整（原生 App 的 61 份全部完整），其中一张维基长页的 15 份样本全部撞到 8192 节点上限。这时按名字的命令反复重采到 5 秒预算用完才失败，失败时不带已经找到的唯一候选 | `sub-reports/36` D1、D2 |
| `wait --role/--name` 要求恰好一个可见目标 | 第 0 阶段有两次这样的等待失败：一次没有可见的匹配，一次有三个同名匹配 | `sub-reports/40` D3 |
| 读命令的自动保存失败就判失败 | 正文已经打印，设备也已采样，但因为工作区目录权限偏宽，`snapshot` 报失败、退出码 1。实施方自己的运行里撞到 2 次 | `sub-reports/39` D2 |

## 5. 四道待决题

### 5.1 第一题：后台屏里打开通知

**现状。** 暂行做法是按"通知创建者的包和 UID"做事前拒绝和事后确认。实测 Feeder 的通知先打开它自己的中转页，再由中转页打开 Chrome。网页其实已经正确打开，但因为观察结束时看不到创建者的包，结果报了结果未知、退出码 3。

**我们核到的事实。** 运行之前，Chrome 是用户主屏上可见的顶部任务。发送通知之后，它被搬到了后台屏。会话关闭时，它的界面进入销毁，最后只剩最近任务列表里的一条记录。实施方在交付说明里披露了搬屏和"结束后不会自动回主屏"，但没有写被搬走的是用户正在看的前台任务，以及它的界面会被销毁。A、B、C、D 四个选项都挡不住这件事。按 D，这类回执会变成"完成"，搬屏这件事更不显眼。样本是 1 台 Android 14 模拟器，每个场景 1 次。

**补充的两个选项。**

| 选项 | 做法 | 得 | 失 |
| --- | --- | --- | --- |
| **E（推荐）** | 后台屏会话里，会启动界面的通知操作一律事前拒绝，包括打开通知、界面型的按钮、界面型的回复。广播型和服务型的按钮、回复、清除照常。主屏会话不变 | 在通知这条路径上排除了搬屏；可以删掉通知专用的事前检查、落点确认和目标屏参数，连同它们的测试和指引；这道题不再存在 | 后台屏里不能直接跳到通知指向的页面。现有证据里这个能力只成功过一次，是一个 App 打开它自己 |
| F | 在 D 的基础上加搬屏检测：对比发送前后的任务表，被搬动的任务在回执里明确列出，并报结果未知 | 保留这个能力；搬屏发生时一定会被报告。需要的数据现在已经读到了 | 不能阻止搬屏；维护量与现在相当 |

**推荐 E。** 如果你确实需要在后台屏里打开通知，选 F，不选 D。两点说明：

- D 改变了"派发完成"的含义。现在的"完成"包含"看到了落点"，D 之后的"完成"只表示平台接受了派发。D 里"派发结果和观察分开报"这条原则本身是对的。
- E 只管通知这条路径。在后台屏里用 `open` 启动一个带中转页的 App，也可能以同样的方式搬动任务，这属于后台屏本身的性质，不是这道题能解决的。

**评审方的责任。** 第三轮建议"暂按创建者的包做，看到创建者可见才算完成"。后半句现在看是错的：它在中转跳转的场景必然报出假的结果未知，而比平台返回码多给的信息很少。当时给你的选择只有"维持现状"和"加查询接口"，把问题框窄了。

【`sub-reports/38` §5】

### 5.2 第二题：动作后仍见旧页，要不要改自动观察

**事实。** 八臂里"回执说已变化、正文却仍在加载"共 9 次，每臂 1–2 次，每次多读一轮，约占该任务输入的 5%–8%。执行模型每次都正确地补了一次观察，没有误判。动作后的观察是每 250 毫秒采一次：八臂里结论为"已变化"的动作多数采了 3–4 次，中位耗时约 0.7 秒。

**意见。** 暂按 A，不改观察的算法。但 A 的成本现在被低估了，因为补的那一轮会把整页重印一遍。先做三件不改观察规则的事：

1. `wait` 成功后只打印状态行和匹配到的节点，不重印整页（U9）。
2. 等待"出现"不要求唯一（U5）。
3. 页面上有加载指示时，在状态行里如实写出来。现在只认进度条控件；Chrome 是否暴露页面加载状态，需要在设备上验证。

然后用实测看补观察的次数。如果仍然常见，再做 B，也就是让动作命令接受一个期望条件。实施方不推荐 B 的理由是没有净收益的证据，这个理由成立，但那是因为没测。另外，与 B 相近的"批处理里动作加等待"在 84 次自然调用里一次也没被用过，说明调用者不会主动把两步拼起来。

### 5.3 第三题：动作怎么表示

**这道题的选项框窄了。** 实施方的 B、C、D 都在回答"怎样更省地表示全部动作"。数据说明的是另一件事：绝大部分动作不需要出现在默认输出里。焦点、选中、清除选中、无障碍焦点、显示到屏上、按粒度前后移动、上下文点击，几乎每个节点都有。调用者在八臂里从未直接点名调用过它们；其中"显示到屏上"和"焦点"由 `reveal`、`fill` 在内部发出，不依赖输出里把它们列出来。

**推荐新选项 E：默认只打印非默认动作。**

- 默认不标"可点击"；有引用却不能点击的节点，标一个否定的记号。
- 只标长按、展开、收起、关闭、设进度、带自定义标签的动作、不认识的非标准动作。滚动方向沿用现在的 `scroll` 字段。
- 完整的动作清单仍然可以用 `snapshot --cached --raw` 在同一份采样上取回，不需要重新采集。
- 只改主机端的输出，不动设备端和跨语言契约。

要留意的风险：调用者看不到完整清单后，需要调用一个少见的标准动作时得多读一次。八臂里没有出现过这种需要。

**评审方的责任。** 第三轮把"通用动作集只打印一次"列为待验证的选项，并定下"只省可以从已打印状态推出的动作"。前者把问题框窄了，后者过于保守，动作数组就是因为它才留下来的。

### 5.4 第四题：提交历史

实施方的 A、B、C、D 都默认现有范围整体合入。推荐的 C 是从基线按最终行为全面重切，问题在于：范围还没定，重切出来的提交大半还要再改；中间的提交也没有各自的测试结果。

**建议新选项 E：**

1. 先定合入范围（§2.1）。
2. 从最终树按子系统生成 6–10 个提交：平台底座、结果与退出码、会话、采集与输出、输入、图像、指引、契约。每个提交在合入前跑一次全量质量检查。
3. 旧的 68 个提交留在归档分支上，供追溯 review 记录。

在那之前保持现状，不做历史整理。

**关于手写采集器的说明。** 两个子 agent 意见不同：一个建议实测后换成公开接口，可以删掉约 500–700 行；另一个建议保留但冻结。我们采纳后者：

- 与基线相比，节点相关的隐藏接口成员反而少了，因为最低系统版本提到 Android 14 之后删掉了旧路径。它依赖的接口在 Android 14 到 main 之间没有变。
- 性能差别对调用者不关键。长页面上设备端采集要 0.6–1.8 秒，整个设备端请求要 1.6–2.9 秒，CLI 每次另有约 1 秒的固有开销。小页面采集只要几十毫秒。
- 换路线要花设备时间，对调用者没有看得见的收益。

所以保留，但不再往里加机制。今后如果真的出现协议错误，直接改走公开的路线（从 Android 14 起 `UiAutomation.clearCache()` 是公开的），不要打补丁。真机检查时顺带做一次同页对照，为那一天留个数据。

**没有被推翻的旧结论。** "结果只说主动作，退出码汇总整条命令"这套规则落地了。八臂 84 次调用里没有出现过"完成但退出码非 0"，5 次非 0 退出执行模型都反应正确。建议保留，只把指引里讲退出码的段落收成一张表。监听器每个会话登记一次、删除输入法通道的独立选区命令、名字与行标签不随可见性变化、设备端与主机端共用一套省略默认值的编码、坐标点击按平台的规则判断接收窗口，这几条的落地都与决定一致，证据支持。

## 8. 证据范围与局限

- 没有设备。所有运行结论都来自实施方的模拟器原件，我们核对的是原件与声称是否一致。样本量普遍是每个场景 1 次。
- 八次真实任务只有两类只读任务（地图查路线、网页读评论），用的是同一台 MuMu 模拟器。
- 精简输出的字节数是离线重排的结果，token 上的收益是估算。输出变小之后执行模型的路径会不会变，离线验证不了，要靠实测。
- 执行模型的推理内容是加密的，"它为什么这么做"都是从行为推断的。
- 标"推断"的缺陷（M6、U8 的后半句、M8 的末项）没有运行证据。
- 一部分设备原件没有打进材料包（通知在主屏上那一串运行的原始输出、后台屏上 Contacts 的一组运行），相关的声称只能对着实施方的汇总来核。
- `ruff`、`mypy` 的结果和 21 个隐藏接口签名的比对来自子 agent 的报告，事实复核没有重跑，只抽查了一个签名。
- 事实复核核了初稿约 135 条可检验的陈述：约 99 条成立，26 条有偏差，5 条不成立，5 条核不到。有偏差和不成立的已全部在本文改正。
